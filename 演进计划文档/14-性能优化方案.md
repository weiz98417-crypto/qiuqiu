# 14 — 性能优化方案

> 所属阶段：Phase 3 · 依赖：所有功能模块 · 优先级：P0

---

## 1. 概述

球球的核心体验高度依赖低延迟。本方案从端到端视角拆解延迟瓶颈，逐一优化。

**总目标**：从比赛事件发生到用户听到球球说话 < 2s。

---

## 2. 延迟预算分解

### 2.1 延迟链路

```
数据源延迟(不计入) → 事件处理 → LLM生成 → TTS合成 → 网络传输 → 客户端播放
                      <100ms     <1000ms   <800ms     <200ms     <100ms

总预算： < 2200ms，实际目标 < 2000ms
```

### 2.2 各环节优化策略

| 环节 | 当前延迟 | 目标延迟 | 优化策略 |
|------|---------|---------|---------|
| 事件处理 | ~50ms | <50ms | 内存处理，无IO |
| LLM生成 | ~1500ms | <1000ms | 短Prompt + 流式 + 小模型 |
| TTS合成 | ~1200ms | <800ms | 流式首包 + GPU推理 |
| 网络 | ~300ms | <200ms | 边缘节点 + 长连接 |
| 客户端 | ~200ms | <100ms | 预加载 + 音频缓存 |

---

## 3. LLM层优化

### 3.1 Prompt压缩

```
优化前：System Prompt ~500 tokens
优化后：System Prompt ~200 tokens

压缩策略：
- 删除重复说明
- 合并相似规则
- 用更简练的表达
```

### 3.2 模型选择

| 场景 | 模型 | 延迟 |
|------|------|------|
| 赛事事件 | Deepseek-V4-Flash | ~300-500ms |
| 用户对话 | Deepseek-V4-Flash | ~300-500ms |
| 兜底 | Ollama + Qwen 3.6 35B-A3B（备选，MoE 3B active） | ~300ms |
| 极端兜底模板 | 无LLM | 0ms |

### 3.3 连接优化

- HTTP/2 长连接复用
- 连接池预热（预建立5个连接）
- Token缓存（相同的System Prompt不重复计算）

### 3.4 流式生成 + 提前TTS

```
LLM流式输出 "姆巴佩！"
    │
    ▼ 检测到感叹号，触发TTS
LLM继续输出 "第七十八分钟！"
    │
    ▼ 检测到下一个句子边界
TTS已经播完第一句，开始合成第二句
```

**效果**：用户感知延迟 ≈ TTS首包延迟，而非 LLM + TTS 之和。

---

## 4. TTS层优化

### 4.1 流式首包优化

| 策略 | 效果 |
|------|------|
| GPU推理 | 首包 ~200ms |
| 模型量化（INT8） | 推理速度 +30% |
| 文本分段发送 | 不等全部文本 |
| 音频chunk预缓冲 | 客户端收到即播 |

### 4.2 常见内容预生成

```python
# 预生成 + 缓存到CDN
pre_generated = [
    "嗨～比赛要开始了！",
    "比赛结束了！",
    "好球！",
    "哇！",
    "进了！！",
    "嗯...",
    "稍等～",
    "我在听～",
]
```

### 4.3 音频格式优化

- 采样率：24kHz（而非44.1kHz，人声足够）
- 编码：PCM 16bit（避免编解码开销）
- 分块大小：40ms/chunk（平衡延迟与传输效率）

---

## 5. 网络层优化

### 5.1 连接优化

- WebSocket 长连接（避免反复握手）
- TCP快速打开（TFO）
- TLS 1.3（0-RTT恢复连接）

### 5.2 边缘部署

```
        用户(北京)                用户(纽约)
            │                        │
            ▼                        ▼
      边缘节点(北京)            边缘节点(纽约)
            │                        │
            └────────┬───────────────┘
                     ▼
               中心服务(新加坡)
```

- LLM API调用走最近区域
- 音频推流走边缘节点

### 5.3 降级策略

| 网络状况 | 策略 |
|---------|------|
| 延迟 < 100ms | 正常 |
| 延迟 100-300ms | 降低音频码率 |
| 延迟 300-1000ms | 降低TTS质量 + 提示用户 |
| 延迟 > 1000ms | 仅文字气泡，暂停语音 |

## 6. 客户端优化

### 6.1 启动优化

```
App启动
  ├── 并行加载：
  │   ├── Live2D模型（异步预加载）
  │   ├── 首页比赛列表API
  │   └── 用户偏好（本地读取）
  │
  └── 首屏显示 < 2s
```

### 6.2 音频播放优化

- 双缓冲：播放当前chunk时预加载下一个
- 缓冲水位：200ms（太低会卡顿，太高延迟大）
- 设备音频延迟补偿

### 6.3 Live2D渲染优化

- 模型纹理压缩（ASTC/ETC2）
- 帧率自适应：
  - 高端机：60fps
  - 中端机：30fps
  - 低端机：24fps
- 后台时暂停渲染

### 6.4 内存管理

```
观赛页内存预算：
- Live2D模型：  < 30MB
- 音频缓冲：    < 10MB
- UI：          < 20MB
- Flutter引擎： < 50MB
- 其他：        < 40MB
总计：          < 150MB
```

---

## 7. 后端优化

### 7.1 Go服务优化

- goroutine池（避免无限制创建）
- 对象池（复用频繁分配的结构体）
- 零拷贝（事件处理链路上避免数据复制）

### 7.2 缓存策略

| 数据 | 缓存位置 | TTL | 命中率目标 |
|------|---------|-----|-----------|
| 比赛列表 | Redis | 30s | >95% |
| 比赛状态 | 内存 | — | 100% |
| TTS音频 | CDN | 永久 | >80% |
| LLM响应 | Redis | 30s | >30%（同事件） |

### 7.3 数据库优化

- 事件写入：批量INSERT（每100条flush一次）
- 比赛查询：覆盖索引（match_id + event_type + minute）
- 读写分离：查询走只读副本

## 9. 压测方案

```
场景1：单比赛1000并发
  - 模拟1000个用户观看同一场比赛
  - 进球事件到达 → 1000个LLM请求 → 1000个TTS请求
  - 目标：P95延迟 < 3000ms

场景2：多比赛5000并发
  - 模拟50场比赛，每场100个用户
  - 目标：无排队，延迟不劣化

场景3：长时间运行
  - 连续运行4小时（模拟完整比赛+加时）
  - 目标：无内存泄漏，延迟不随时间增长
```
