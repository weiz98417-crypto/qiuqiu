# 球球（QiuQiu）架构图调研与绘制建议

> 调研日期：2026-09-02  
> 范围：AI 足球陪看助手（Flutter/Web 客户端、Go 后端、WebSocket 音频、比赛事件管道、ASR/LLM/TTS、Live2D、Redis/PostgreSQL、外部比赛数据源）。  
> 说明：本笔记只做架构图调研与建议，不修改产品实现。

## 1. 项目画像（从仓库文档归纳）

- 系统是跨平台 Flutter 客户端配 Go 后端的实时语音陪看系统；客户端包含 Live2D、VAD、录音/播放，后端承载 ASR、LLM、TTS 与事件管道，双方通过 WebSocket 传输音频、比赛事件和表情指令（见 `README.md`、`演进计划文档/01-技术选型与架构设计.md`）。
- 关键业务流有两条：用户语音链路（VAD → ASR → 事件/上下文 → LLM → TTS → 客户端播放与 Live2D）和比赛事件链路（数据源轮询 → 解析/去重/节流 → 优先级/事件队列 → AI 生成 → WebSocket 推送）。这两条链路应在图中分别用“同步/低延迟交互”和“异步事件流”标识。
- 当前仓库的演进文档同时描述 Redis、PostgreSQL、NATS/Kafka、对象存储以及 Docker Compose 单机部署；绘图应区分“当前 MVP 实际部署”和“规模化目标”，不要把候选技术画成已部署组件。

## 2. 建议交付的图集（按阅读顺序）

### A. C4 Level 1：系统上下文图（必画）

把“球球 AI 足球陪看系统”作为中心系统，外围只放用户/观众、比赛数据供应商、ASR/LLM/TTS 提供商、导播/运营控制台等直接交互者。此层不展开协议和内部技术，面向所有读者说明系统边界和外部依赖。[C4 对 System Context 的定义与范围](https://c4model.com/diagrams/system-context)

建议关系标签：`观赛并进行语音对话`、`提供比赛事实/事件`、`提供语音识别/生成能力`、`运营人员校正或发布事实`。每条箭头保持单向并写明意图。

### B. C4 Level 2：容器图（必画）

在系统边界内画可独立运行的应用或数据存储，并在容器名中写清技术：Flutter Client（Flutter/Web）、Go API + WebSocket、Match Event Ingestor、Conversation Pipeline、NATS（或实际采用的消息总线）、Redis、PostgreSQL/Fact Ledger、对象存储、Operator Console。容器图的职责分配、技术选择和通信协议正是 C4 的目标；集群、负载均衡、故障转移等部署细节应留到部署图。[C4 Container diagram](https://c4model.com/diagrams/container)

建议把 `Go API + WebSocket` 与 `Conversation Pipeline` 是否同进程画成当前实现的事实；只有代码/部署确认后，才拆成独立容器。外部 AI 服务作为容器图边界外的软件系统，避免误解为自建 GPU 服务。

### C. 动态/时序图：两条关键场景（按需画）

1. **用户打断式语音对话**：客户端采集 PCM → Go WS 接收 → ASR 增量结果 → 上下文/事件引擎 → LLM token → TTS 首包 → WS 音频与表情指令 → 客户端播放；在箭头上标注序号、协议和延迟预算。
2. **比赛事件到陪看反应**：数据源/导播事件 → 规范化与去重 → 事实账本/事件总线 → 话痨/优先级策略 → LLM → TTS/Live2D → 订阅该场比赛的客户端。

C4 动态图用于展示某个用户故事在运行时的协作和顺序，推荐“只画复杂或反复出现的模式”，不应替代静态容器图。[C4 Dynamic diagram](https://c4model.com/diagrams/dynamic)

### D. 事件流/数据流图（必画一张）

用从左到右的泳道表达：**Sources → Ingest/Producers → Event storage/bus → Processing/Consumers → Destinations**。这与 AWS 流式参考架构的五层划分一致；事件存储应标出保留期/可回放性，处理层标出顺序、并行、重试和幂等边界。[AWS streaming reference architecture](https://docs.aws.amazon.com/wellarchitected/latest/analytics-lens/reference-architecture-2.html)

对球球的映射建议：比赛 API、导播台、用户语音是 Sources；轮询/WS 接入与规范化是 Ingest；NATS（若采用）和事实账本是 Event storage/bus；去重、延迟协调、上下文与 LLM/TTS 是 Processing；客户端 WebSocket、PostgreSQL 投影、审计/指标是 Destinations。不要假设所有流都只向右：重放、补偿、影子审计和回写应画成反向的虚线或单独回放箭头。

### E. C4 部署图：按环境各一张（必画）

至少分别画 `development`、`MVP/内测`、`production`，因为部署节点和拓扑会随环境变化。图中用嵌套节点表示云 VM/主机、Docker Compose、反向代理、Go 服务、Redis/PostgreSQL/NATS；外围标 DNS/TLS、外部 AI API、比赛数据 API、备份/监控。C4 将部署节点定义为物理机、VM、容器或执行环境，并允许加入 DNS、负载均衡、防火墙等基础设施节点。[C4 Deployment diagram](https://c4model.com/diagrams/deployment)

MVP 图应忠实反映仓库当前“单机 Docker Compose + 云 API”的决策；规模化图再表现 API 多副本、备用 VM、托管 PostgreSQL/CDN 等演进项，并在标题或图例标注 `planned`，避免把路线图当成现状。

## 3. 统一画法与审图规则

- 每张图都有标题，说明图类型和范围；右下角放图例，解释颜色、形状、边框、实线/虚线和箭头。C4 明确要求标题、图例、可理解的缩写和一致标注。[C4 Notation checklist](https://c4model.com/diagrams/notation)
- 每个元素显式写类型（Person/Software System/Container/Component），写一行职责描述；容器和组件写技术。每条关系只表达一个方向，关系线上写具体意图；跨进程关系写协议（WebSocket、HTTP、NATS 等）。[C4 Notation checklist](https://c4model.com/diagrams/notation)
- 颜色只表达一种稳定语义：建议蓝色=自有运行单元、紫色=外部供应商、绿色=数据存储、橙色=事件/队列；同时用文字/线型冗余表达，保证黑白打印和色觉差异下仍可读。[C4 Notation checklist](https://c4model.com/diagrams/notation)
- 静态图不要混入部署副本、环境节点和运行时序；容器图和部署图分工明确。C4 明确指出容器图不应承载集群、负载均衡、复制和故障转移信息。[C4 Container diagram](https://c4model.com/diagrams/container)
- 事件图中的每种事件写事件名、版本、生产者、消费者、传输协议和幂等键；CloudEvents 将事件定义为“上下文 + 数据”的事实，强调生产者和消费者可独立开发/部署，并通过协议绑定传输。[CloudEvents Primer](https://github.com/cloudevents/spec/blob/main/cloudevents/primer.md)
- 事件驱动图按 `source → router/bus → destination` 画基本骨架，同时在旁注数据契约/Schema、追踪 Trace ID、重试与死信。AWS 的事件驱动参考把三者列为核心部分，并要求生产者/消费者约定数据契约、为分布式依赖启用追踪。[AWS Serverless Applications Lens](https://docs.aws.amazon.com/wellarchitected/latest/serverless-applications-lens/event-driven-architectures.html)

## 4. 语音链路的技术标注取舍

- 如果保持当前“Go 后端统一编排 ASR/LLM/TTS”的设计，容器图把客户端到 Go 标成 WebSocket，把 Go 到各 AI 供应商标成 HTTPS/WebSocket（按实际 SDK），动态​​图重点标首包延迟、取消/打断和重连。
- 如果未来改用 OpenAI Realtime 语音代理，浏览器/移动端优先标 WebRTC；服务端已有媒体管线时才标后端到 Realtime 的 WebSocket。OpenAI 官方文档明确建议浏览器/移动端使用 WebRTC，服务端到服务端使用 WebSocket，并说明 WebSocket 由后端负责 Base64 音频块与 JSON 事件处理。[Realtime overview](https://platform.openai.com/docs/guides/realtime)、[WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc)、[WebSocket](https://developers.openai.com/api/docs/guides/realtime-websocket)
- 无论采用哪种方案，图中不要把标准 API key 放在客户端；会话初始化、短期凭据和安全标识应画在可信后端边界内。OpenAI 的 WebRTC 连接示例要求由开发者服务器使用标准 API key 创建会话，并建议安全标识由可信后端设置。[OpenAI WebRTC connection](https://developers.openai.com/api/docs/guides/realtime-webrtc)

## 5. 推荐的 Mermaid 页面组织

在 `演进计划文档` 中可维护一个“架构图索引”页面，每个图单独一个 Mermaid 代码块，顺序固定为：

1. `01-context`：系统上下文（读者：所有人）。
2. `02-containers`：当前 MVP 容器（读者：开发/运维）。
3. `03-runtime-voice`：语音对话动态时序（读者：客户端/后端）。
4. `04-runtime-match-event`：比赛事实到反应的动态时序（读者：事件/AI）。
5. `05-event-flow`：事件与数据流（读者：后端/数据/可靠性）。
6. `06-deployment-mvp`、`07-deployment-production`：每个环境一张部署图（读者：运维/安全）。

每个代码块后附“范围、假设、数据契约/协议、延迟预算、未决决策”五行说明；图只承载结构和流向，细节放说明文字，避免一张图塞入所有层次。

调研对象只取项目自己的 GitHub 仓库或官方文档；许可证和能力以 2026-09-02 查询结果为准。这里的“验证/追溯”专指工具能否检查模型一致性，或把图中节点追溯到仓库证据，不等于运行时监控。

|---|---|---|---|---|---|
| **Structurizr** | Apache-2.0；Structurizr DSL/JSON workspace | 原生 `systemLandscape`、`systemContext`、`container`、`component`、`dynamic`、`deployment`，正好覆盖 C4 静态层级、运行时动态和部署 | workspace 规则检查名称/关系唯一性，自动布局；单一模型生成多视图，能保持 C4 层级一致，但官方没有 Archify 那种提交/行号级源证据 | CLI 可导出 PlantUML、C4-PlantUML、Mermaid、D2、JSON、静态 HTML；Playground/Local/Cloud 提供可浏览视图 | **最适合做总图、C4 四层和部署图的规范源**；事件数据流和生命周期需用动态/自定义视图补充 |
| **Archify** | MIT；严格 typed JSON IR | 原生 `architecture`、`workflow`、`sequence`、`dataflow`、`lifecycle` 五类，覆盖本项目的八张图语义，但不把 C4 Level 1/2/3 作为强制模型 | schema、布局、路由、标签间距和交付检查；可选 revision-pinned Git source evidence、节点搜索、上下游/路径追踪和架构快照 diff | 生成单文件交互 HTML/SVG；内置搜索、聚焦、路线/到达追踪、演示、主题；导出 PNG/JPEG/WebP/SVG/WebM/分享卡 | **最适合最终展示、事件/数据流、生命周期和运行时序列**；作为 C4 的唯一事实源时需自己维护层级约束 |

### 6.1 八张图的推荐落点

| 图 | 首选 | 备选 | 选择理由 |
|---|---|---|---|
| 总架构图 | Structurizr `systemLandscape` + Archify `architecture` 展示版 | D2 | Structurizr 负责模型边界和层级，Archify 负责可探索交付 |
| 系统上下文 | Structurizr `systemContext` | C4-PlantUML | 直接符合 C4 Level 1，外部参与者和系统边界清晰 |
| 容器 | Structurizr `container` | C4-PlantUML | C4 Level 2 的容器/数据存储/关系已有统一模型 |
| 组件 | Structurizr `component` | C4-PlantUML | C4 Level 3 可从同一 workspace 下钻，避免重复节点 |
| 运行时语音/比赛事件时序 | Archify `sequence` | PlantUML sequence 或 Structurizr `dynamic` | 需要顺序、返回、重试、打断和低延迟标注；Archify 交互追踪更直观 |
| 事件/数据流 | Archify `dataflow` | D2、Mermaid flowchart | 需要 Source → Ingest → Bus/Ledger → Consumers → Destinations 及契约、幂等、死信旁注 |
| 生命周期/状态 | Archify `lifecycle` | PlantUML state | 需要等待、重试、取消、成功/失败终态；Archify 有专用状态语义 |
| 部署 | Structurizr `deployment` | C4-PlantUML deployment、draw.io | 需要把容器实例映射到开发/MVP/生产节点；Structurizr 原生支持 deploymentEnvironment |

### 6.2 最终取舍建议

建议采用“**Structurizr 做 C4 规范源 + Archify 做全图交互交付 + Mermaid 做文档嵌入**”的组合，而不是强行让一个工具承担所有职责：

1. 在 Structurizr DSL 中维护总图、系统上下文、容器、组件、动态和部署的核心模型；用稳定的元素 ID、关系描述和 workspace 规则做评审基线。
2. 将事件/数据流、生命周期和两条关键运行时序列用 Archify typed JSON 维护并交付单文件 HTML；在 JSON 中保留事件版本、幂等键、Trace ID、重试/死信等语义标签。
3. 需要在 README/GitHub 中快速阅读时，从 Structurizr CLI 或 Archify 导出 Mermaid；导出文件是发布物，不反向作为事实源。
4. draw.io 只用于最终人工微调或培训海报；若人工修改改变了架构事实，必须回写 DSL/JSON 并重新生成，避免图与模型分叉。
5. 若团队只想维护一种源码格式，优先选 Structurizr DSL（C4 一致性最高）；若首要目标是“八张图一次生成、交互浏览和源代码证据”，则选 Archify，但要在文档中明确 C4 层级约束由团队自检。
