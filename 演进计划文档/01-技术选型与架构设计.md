## 2. 技术选型

### 2.1 后端

| 组件 | 选型 | 理由 |
|------|------|------|
| 主语言 | **Go** | 高并发、低延迟、部署简单 |
| API 网关 | **Nginx + Lua** | 成熟稳定，支持 WebSocket |
| 消息队列 | **NATS** | 极低延迟（<1ms），适合事件驱动 |
| 数据库 | **PostgreSQL** | 关系型，成熟可靠 |
| 缓存 | **Redis** | 会话、事件去重、热数据 |
| 对象存储 | **S3/MinIO** | 音频文件存储 |

### 2.2 AI 服务

| 组件 | 选型 | 理由 |
|------|------|------|
| LLM | **Deepseek-V4-Flash**（API） | 低延迟（~300-500ms），中文顶级，成本极低 |
| LLM 备选 | **Ollama + Qwen 3.6 35B-A3B**（本地，MoE 3B active） | Deepseek API不可用时自动切换 |
| TTS | **ElevenLabs / Fish-Speech** | 情绪语音支持 |
| TTS 备选 | **CosyVoice 2**（自部署，Apache 2.0） | 免费开源，中文TTS顶级 |
| ASR | **Whisper (API) / SenseVoice** | 高精度中文识别 |
| ASR 实时 | **WebSocket 流式 ASR** | 支持打断 |

### 2.3 前端 / 客户端

| 组件 | 选型 | 理由 |
|------|------|------|
| 框架 | **Flutter** | 跨平台（iOS/Android），一套代码 |
| Live2D | **Live2D Cubism SDK** | 官方SDK，支持原生和Web |
| 音频 | **WebRTC / 原生 Audio** | 低延迟音频流 |
| 状态管理 | **Riverpod** | Flutter 推荐方案 |

### 2.4 数据源

| 来源 | 覆盖 | 延迟 |
|------|------|------|
| **api-sports.io** | 全球 150+ 联赛 | 5-10s |
| **SofaScore**（仅验证） | 全球联赛 | 5-10s |
| **football-data.org**（备选） | 欧洲联赛 | 5-10s |

## 3. 关键技术决策

### 3.1 通信协议：WebSocket

- 比赛事件 → 服务端推送到客户端
- 用户语音 → 客户端流式上传
- 球球语音 → 服务端流式下发
- 心跳保活 + 自动重连

### 3.2 语音流式处理

```
用户说话 → 客户端录音(PCM) → WebSocket流式上传 → ASR实时识别
  → LLM生成文本 → TTS流式合成 → WebSocket流式下发 → 客户端播放
```

### 3.3 事件处理架构：事件驱动

```
数据源 Poll → 事件解析 → 去重/节流 → 优先级排序 → 事件队列
  → LLM生成 → TTS合成 → 语音下发 + Live2D指令
```

### 3.4 延迟预算

| 环节 | 预算 | 备注 |
|------|------|------|
| 事件到达 | < 500ms | 数据源延迟不计入 |
| LLM 生成 | < 1000ms | 短文本场景 |
| TTS 合成 | < 800ms | 流式首包 |
| 网络传输 | < 200ms | WebSocket |
| **总延迟** | **< 2000ms** | 从事件到用户听到 |

## 4. 接口设计（概要）

### 4.1 客户端 ↔ 服务端

```
WS /ws/match/{match_id}
  → server: { type: "voice", data: <PCM bytes> }
  ← server: { type: "audio", data: <PCM bytes>, expression: "excited" }
  ← server: { type: "event", event: "goal", team: "A", minute: 78 }
  ← server: { type: "expression", state: "excited" }
```

### 4.2 内部服务间

```
NATS Topic: match.event.{match_id}
  → { event_type, team, minute, player, raw_data }

NATS Topic: ai.response.{session_id}
  → { text, audio_url, expression, duration_ms }
```

## 5. 部署方案

> 单人+CC开发，部署追求极简。MVP阶段不需要任何容器编排。

### Phase 0–3（开发/内测）

```
单机 Docker Compose：
  - API 服务 ×1
  - PostgreSQL ×1
  - Redis ×1
  - NATS ×1
  - LLM/TTS/ASR → 调用云 API
  - 一台 4C8G 云VM即可
```

### Phase 4+（世界杯规模化）

```
按需升级（不是K8s，是在单机基础上加资源）：
  - API 服务 ×2（Docker Compose scale）
  - 加一台备用VM做 failover
  - PostgreSQL 云数据库（免运维）
  - CDN 加速音频文件
  - Kubernetes 推迟到"真的有1000并发"之后
```

## 7. 可观测性（NEW — CEO审查补全）

### 7.1 服务端Metrics

| 指标 | 类型 | 告警阈值 |
|------|------|---------|
| LLM调用延迟 p50/p99 | Histogram | p99 > 1.5s |
| TTS首包延迟 p50/p99 | Histogram | p99 > 1.2s |
| LLM错误率 | Counter | > 5% |
| TTS错误率 | Counter | > 5% |
| 数据源断连时长 | Gauge | > 30s |
| WebSocket活跃连接数 | Gauge | 监控趋势 |
| 事件处理管道积压 | Gauge | > 10 |

### 7.2 告警规则

| 告警 | 条件 | 通知 |
|------|------|------|
| LLM服务不可用 | 错误率 > 10%，持续1分钟 | Pager/钉钉 |
| TTS服务不可用 | 错误率 > 10%，持续1分钟 | Pager/钉钉 |
| 数据源断连 | 连续 > 60s | Pager/钉钉 |
| 端到端延迟恶化 | p99 > 3s，持续5分钟 | 钉钉 |
| LLM安全底线触发 | 任一次 output_filter 拦截 | 钉钉（含输出原文） |

### 7.3 世界杯期间On-Call

- 至少1人待命（按比赛时间轮班）
- 凌晨关键比赛（如3:00）需安排值班
- 应急预案清单：LLM API切换备用Key、TTS降级到本地CosyVoice 2、数据源切换备用API

## 8. 架构降级设计（NEW — CEO审查补全）

### 8.1 LLM Fallback

```
LLM API (Deepseek-V4-Flash) → 超时/不可用
    │
    ▼ (自动切换，<500ms)
本地Fallback（Ollama + 小模型）
    │
    ▼ 若本地亦不可用
兜底句式模板（基于事件类型+球队+球员+比分的填充模板）
    │ 如："{球员}！第{分钟}分钟！{比分}了！"
```

### 8.2 TTS Fallback

```
TTS API (ElevenLabs/Fish-Speech) → 超时/不可用
    │
    ▼ (自动切换)
CosyVoice 2（本地自部署，免费备选）
    │
    ▼ 若备选亦不可用
仅显示文字气泡，球球静音 + 提示"嗓子不舒服～"
```

### 8.3 WebSocket通道优化

```
原设计：单通道传输事件+语音+表情

优化后：优先级分通道
├── 高优先级通道：比赛事件 + Live2D表情指令（不可被语音阻断）
├── 中优先级通道：球球TTS音频流（可被用户打断时衰减）
└── 低优先级通道：用户ASR语音上传
```
