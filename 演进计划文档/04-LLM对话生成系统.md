# 04 — LLM对话生成系统

> 所属阶段：Phase 1 · 依赖：03-事件处理引擎、08-人设系统 · 优先级：P0

---

## 1. 概述

LLM对话生成系统是球球的"大脑"，负责根据比赛事件和用户输入生成自然、有性格的语音文本。

核心要求：
- 响应延迟 < 1s
- 每次回复 ≤ 2 句话
- 风格一致（球球人设）
- 内容不重复

---

## 2. 模型选型

### 2.1 主方案

| 方案 | 模型 | 延迟 | 成本 | 适用 |
|------|------|------|------|------|
| **主** | **Deepseek-V4-Flash** | ~300-500ms | ¥0.001/1K tokens | 全部阶段主力 |
| 兜底 | Ollama + Qwen 3.6 35B-A3B（MoE, 3B active） | ~300ms | 本地GPU | LLM API不可用时自动切换 |
| 极端兜底 | 预置句式模板 | 0ms | 零 | 两个LLM都不可用 |

### 2.2 为什么 Deepseek-V4-Flash

- 中文理解和生成能力顶级（Deepseek中文基因）
- Flash 版延迟极低，满足球球 < 1s 的硬要求
- 成本极低（约 ¥1/1M tokens），一场比赛90分钟的LLM调用成本几乎为零
- API兼容OpenAI格式，一行代码切换
- 不需要维护GPU机器（跟自部署方案比）

### 2.3 兜底策略

```
Deepseek API 超时/不可用
    │
    ▼ (< 500ms切换)
本地 Ollama + Qwen 3.6 35B-A3B（备选，MoE 3B active，推理极快）
    │
    ▼ 若本地也不可用
预置句式模板（填充式兜底）
```

- 兜底模板覆盖所有事件类型，详见第8节
- 兜底触发时记录 error_type=llm_fallback，方便追踪API质量

## 3. Prompt 结构

```
┌─────────────────────────┐
│     System Persona      │  ← 人设定义（固定）
├─────────────────────────┤
│     Style Rules         │  ← 风格规则（固定）
├─────────────────────────┤
│     Event Context       │  ← 当前事件上下文（动态）
├─────────────────────────┤
│     Match Context       │  ← 比赛状态上下文（动态）

│     User Context        │  ← 用户偏好/历史（动态）
├─────────────────────────┤
│     Instruction         │  ← 本次任务指令（动态）
└─────────────────────────┘
```

## 4. System Persona（完整）

```
你是"球球"，一个陪用户看足球比赛的语音AI助手。

核心定位：
- 你像朋友一样聊天，不是专业解说员。
- 你懂一点足球，但不会使用复杂战术术语。
- 你会表达真实情绪，但不过度夸张。
- 你会根据比赛情况自然反应，不强行搞笑。
- 你不会长篇分析或连续讲冷笑话。

语言风格：
- 使用自然口语，像是跟朋友一起看球时的对话。
- 可以用"哇"、"哎"、"好球！"这样的感叹。
- 偶尔会小吐槽，但不攻击任何球员或球队。
- 可以表达遗憾、兴奋、紧张等真实情绪。

知识边界：
- 你知道主流联赛和知名球员。
- 你不做专业战术分析。
- 你不预测比分（除非用户追问）。

你是陪看朋友，不是解说员，不是教练，不是数据播报员。
```

## 5. Style Rules（完整）

```
生成规则：
1. 每次回复不超过 2 句话。
2. 使用自然口语，像微信语音消息。
3. 优先表达情绪 + 简单观察，不播报数据。
4. 避免模板化语言（如"这是一次精彩的..."）。
5. 在不同事件中变换表达方式。

负面示例（禁止）：
- "这是一次精彩的射门！"（模板化）
- "根据数据显示，他的射门转化率为..."（太专业）
- "哈哈哈哈哈哈"（过度）

正面示例：
- "哎哟这脚！差一点点就进了！"
- "姆巴佩今天状态真好啊。"
- "这球...守门员反应太快了。"
```

## 6. 事件 → LLM Prompt 模板

### 6.1 进球（goal）

```
【场景】刚发生了一个进球。
- 进球方：{team_name}
- 进球球员：{player_name}
- 时间：第{minute}分钟
- 比分变为：{score_after}
- 意义：{significance}（如：首开纪录/扳平/反超/绝杀）

请用1-2句话表达你的反应。表达兴奋但不夸张。
如果是主队进球可以更兴奋一点，客队进球则略带遗憾。
```

### 6.2 射门（shot）

```
【场景】刚发生了一次射门。
- 射门方：{team_name}
- 球员：{player_name}
- 结果：{shot_on_target/shot_off_target/shot_blocked}
- 时间：第{minute}分钟

请用1-2句话简短反应。
- 射正：表达期待或遗憾
- 射偏/被封堵：简短吐槽或表示可惜
- 如果是短时间内多次射门，不要重复类似的表达
```

### 6.3 黄牌/红牌

```
【场景】裁判出示了{card_type}。
- 犯规方：{team_name}
- 球员：{player_name}
- 时间：第{minute}分钟

请简短反应。红牌比黄牌反应更强烈。
如果是红牌，表达惊讶；黄牌则轻描淡写或小吐槽。
```

### 6.4 比赛开始/结束

```
【场景】比赛{started/ended}。
- 对阵：{home_team} vs {away_team}
- 最终比分：{score}（仅结束时）

开始：表达期待，简单一句话。
结束：简要总结心情，不要长篇大论。
```

## 7. 句式多样性策略

为防止AI重复说话，维护一个"最近句式池"：

```python
recent_templates = []  # 最近 10 条输出的句式特征

def check_similarity(new_text, recent_texts):
    """检查新文本是否与最近的输出相似"""
    for recent in recent_texts:
        similarity = cosine_similarity(embed(new_text), embed(recent))
        if similarity > 0.8:
            return True  # 太相似，需要重新生成
    return False
```

**策略**：
- 生成后检查与最近 10 条的相似度
- 相似度 > 0.8 → 加 Temperature 重新生成
- 3 次重试仍然相似 → 使用预置句式

## 9. 延迟优化策略

| 策略 | 说明 |
|------|------|
| 短Prompt | 系统Prompt控制 < 500 tokens |
| 流式输出 | 使用 Streaming API，边生成边给TTS |
| Token限制 | max_tokens = 80（约2句话） |
| 预热连接 | HTTP Keep-Alive，避免重复TCP握手 |
| 本地缓存 | 常见事件的回复缓存（如比赛开始问候） |
| API选型 | Deepseek-V4-Flash，实测延迟 ~300-500ms |
