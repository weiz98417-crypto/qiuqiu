## 1. ADR 制度

### 1.1 轻量 ADR 惯例（⚖️B6 落地的机制约定）

1. **编号**：四位零垫编号（0001 起），只增不减，顺序即立法时序；文件名 = `编号-slug.md`，slug 不改。
2. **状态字段**：每篇头部带状态字段，取值四态——`proposed`（提议）/ `accepted`（已接受）/ `superseded(by: ADR-XXXX)`（被取代，必须写取代者编号）/ `deprecated`（废弃，写原因）。现状是三制并存（见 §3 债 #1），统一到本字段是工程侧待办（⚖️B6）。
3. **修订纪律**：修订一律**立新 ADR**，新篇写明 `supersedes ADR-XXXX`；被修订的旧篇必须同步补 `superseded(by)` 反向指针——修订链必须双向可走。增量澄清（不改决定语义）允许原文增补式修订注，须带日期与依据。
4. **不可变项**：已 accepted 的 ADR 正文不改写决定与背景；纠错走修订注或新篇，不静默改史。
5. **承接锚纪律**：§2 索引「承接篇与节锚」列为记账必填项——新 ADR 落地时同步填写；纯工程内部、无规范承接面的决定写「——（工程内部，无规范承接）」，不允许留空。承接锚指认不到落点的存量 ADR 即「悬空立法」候选，全表复核时登记进 §3 债清单。
6. **修订链双验**：§2「被取代关系」列是修订链的人读视图，与 §3 债 #2 的 grep 判据互为双验——两处不一致时以 `docs/adr/` 原文为准并记债。

## 4. 维护流程

1. **何时立新 ADR**：决定跨期有效且改变以下任一项——域不变量（如账本 append-only）、红线承载方式、信任/确认模型、域边界（新事实域）、产品身份边界。单次行为变更不立 ADR（走 openspec change）；裁决点（37 篇）收口后需要立法级的，落 ADR。
2. **流转**：proposed（问题+候选+决定+后果四段齐备）→ 评审 → accepted → 落地施工开 change（proposal 引用 ADR 编号）→ 修订立新篇并双向挂链 → deprecated（放弃时写原因）。
3. **记账**：新 ADR 落地同时更新本篇 §2 索引表与 §3 债清单（本篇维护人执行）；状态列永远照 `docs/adr/` 实况登记，本篇不发明状态。
4. **修订纪律与承接回写**：ADR 裁决改变行为条款时，按 00 篇 §6.7 回写承接篇并同步 37 篇裁决状态；承接篇修订记录注明 ADR 编号。

### 4.1 新增 ADR 流程（四步）

## 5. 设计说明

1. **文体与篇幅**：本篇是 reference——索引表与债清单查表即用；ADR 制度只立机制条款（编号/状态/反向指针），不复制 v2 附录 J 的方法论叙事与模板正文（模板随各篇实际格式演进，以 `docs/adr/` 现行格式为准）。
2. **取代附录 J 的边界**：v2 档案附录 J 的五态状态机（提议/已接受/受控验证/被替代/撤回）在仓库 24 篇中零使用，v3 收并为四态轻量惯例（§1.1）；其早期条目对照表属档案口径，失真处已在 §3 债 #6 如实登记，不逐行修订。
3. **如实登记原则**：状态列写「无状态字段」而非推定 accepted——索引的职责是照实反映 `docs/adr/` 现状，统一字段属工程侧清账动作（⚖️B6），清账前本表不美化。
4. **与 37 篇分工**：ADR 债的清账跟踪在本篇 §3；其中需要产品裁决才能销账的（fulltime 信任级）挂 ⚖️B1，登记与状态流转唯一落点在 37 篇。
5. **为什么补承接锚列与销账判据**：承接锚解决「从规范找立法」的导航问题——原承接列只有篇号且沿用旧章号，编号迁移后既不可导航也不可对账；锚列写到节，规范侧反查一步到位。销账判据写成命令级断言，是因为状态类债务（字段、指针、注记）的清账验收历来靠人眼翻文件，判据不可机器复算时「清了没清」会变成口舌之争——grep 命中数就是验收，复核成本一行命令。
6. **两列并陈不是长期态**：「承接篇」（旧章号口径）与「承接篇与节锚」（文件号新编号）并陈是编号迁移期的过渡格局；工程侧完成迁移对账后两列合一或旧列改标「档案口径」，迁移对账动作本身登记进 §3 债清单，不在本篇静默消失。
