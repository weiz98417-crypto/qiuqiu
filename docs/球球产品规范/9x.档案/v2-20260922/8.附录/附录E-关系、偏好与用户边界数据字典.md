# 附录E：关系、偏好与用户边界数据字典

一个陪看球赛的数字人，如果"记得"用户的方式说不清、管不住，信任就无从谈起。所以我们把"记住用户"拆成一组看得见、说得清、删得掉的数据对象，并把它们如何产生、如何使用、如何消失写成一份对外说明。本篇就是这份说明。

我们采用一个明确的方向（ADR-0006）：**记忆由系统自动抽取，用户可以查看、修改、删除和暂停。** 我们不回避"数字人会记住你"这件事，而是把记住了什么、为什么记住、怎么让它忘掉，全部摆到桌面上。

## 1. 记忆如何产生：自动抽取，全程留痕

球球的记忆分两层。

**第一层是互动账本**：每一回合的规划、投递、播报结果、事实引用等事件，都按发生顺序追加写入。账本只增不改，是服务行为的原始事实源——发生过什么，账本说了算。

**第二层是综合记忆**：系统在回合结束后异步地从对话中抽取值得长期保留的内容（比如您支持的球队、您偏好的交流方式），形成用户画像与事件摘要。这一步不拖慢对话本身。每一条综合记忆都必须引用账本序号作为出处，接受与拒绝的抽取决策连同原因代码一并留痕在**记忆抽取审计**中——一条记忆为什么存在，查得到。

有一条纪律贯穿始终：**记忆综合产物永远不创建、更正或断言比赛事实。** 您随口说的赛况不会被当成官方比分，角色的联想也不会混进事实层（事实层的规则见附录D）。

## 2. 我们记录什么：数据对象总览

### 2.1 匿名身份

开始使用服务不需要注册。系统为设备生成一个内部用户标识，**用设备标识换取内部用户 ID**（`anonymous_device_identities` 表：设备号、用户标识、过期时间）。这个映射有有效期，过期自动失效。您可以在换设备或清除数据时中断这种关联。

### 2.2 互动账本

账本（`interaction_ledger`）按事件记录服务的每一次关键动作，共七类：

| 事件类型 | 含义 |
| --- | --- |
| `turn_planned` | 一个回合被规划（球球决定回应什么） |
| `delivery` | 一条回复被投递 |
| `signal` | 一条用户信号被接收（发言、动作等） |
| `fact_revision` | 引用了哪条比赛事实的哪个修订 |
| `media_delivery` | 一条媒体内容被投递 |
| `playback_result` | 一次播报的结果（完成、被打断等） |
| `turn_stale` | 一个回合作废（被新输入或状态变化取代） |

每条事件带用户、场次、追溯与决策标识、引用的事实编号，以及投递状态与来源。账本记录**默认保留 30 天**，到期失效。

### 2.3 关系记忆

`relationship_memories` 是长期记忆的载体：每条记忆有类型、内容、置信度、**来源追溯标识**（指回产生它的那次交互）、状态、最近使用时间与过期时间。跨场的整体关系状态（`relationship_states`）以带版本号的结构存储，旧版本不能覆盖新版本。

记忆会过期、会停用。最近是否被使用、是否临近过期，都会影响它被想起的优先级。

### 2.4 开放话题

对话里有些事情值得球球"记着下回问"：您问过但还没答的问题、答应过您的事、上一个让情绪起伏的瞬间、一次预测的后续。这些进入开放话题台账（`open_threads`），共**四类来源**：

| 类型 | 含义 |
| --- | --- |
| `unanswered_question` | 您问过、还没回答的问题 |
| `promise` | 球球答应过您的事 |
| `emotional_moment` | 值得接住的情绪时刻 |
| `prediction` | 一场比赛预测的后续 |

每个话题有 `open`（开放）、`addressed`（已回应）、`expired`（过期）三种状态。开放话题默认保留 **7 天**，到期转为过期。**过期不等于已答**——过期只是话题关闭，不会被算作"已经回应过您"。

### 2.5 画像覆盖层

综合画像由系统抽取生成，而您对画像的每一次修改和"忘掉"请求，都先写入**画像覆盖层**（`portrait_overlays`，按用户、主题、子主题定位）。这张表是**下一回合真正生效的权威**：您改了什么、删了什么，从下一个回合起立刻被遵守；随后系统再把变更尽力同步到记忆服务，使两边收敛。为什么多这一层？因为远程记忆服务的读取有缓存、被删的画像可能被旧的底层资料重新综合出来，覆盖层保证了"您说忘，下一回合就是真的忘"。

### 2.6 用户偏好

您明确设置的偏好单独存放（`user_preferences`）。当前最核心的一项是**话痨程度三档**：

- `quiet`：安静——少打扰，多说少播；
- `normal`：刚好——默认的陪伴节奏；
- `active`：热闹——主动点多、反应密。

偏好由您设置，不会因为我们"觉得您可能喜欢"而被改写。

### 2.7 隐私立碑

您提出的删除请求会生成一块**隐私立碑**（`privacy_tombstones`）：记录用户、范围、状态（待处理/已完成/失败）、原因（默认"用户请求"）与申请、完成时间。立碑竖起后，**每一次读写都会先检查它**——被删除用户的数据不再被读取，迟到的写入被拒绝。对话轮次、交互痕迹、关系记忆等对象都带独立的过期与删除标记，配合立碑逐项失效。

删除的数据默认保留 30 天（保留期可按合规要求配置），期间用于保证删除可审计、误操作可追溯；清理任务**每 6 小时**运行一次，到期数据被彻底清除。

### 2.8 运营审计

我们自己的运营人员也在被记录。运营员使用个人令牌访问控制台（令牌只存哈希，角色分"总监/审计员"两类），每一次代表用户执行的写操作——改话题、动画像、处理隐私——都会在**运营审计**（`operator_audit`）中留下"谁、做了什么、对哪个对象、何时"。运营员的操作可归因，令牌可随时吊销，审计记录不随吊销消失。

## 3. 您可以做什么

- **查看**：您能查看已保存的偏好与记忆内容，不必理解任何内部标识。
- **修改**：对画像内容的修改立即写入覆盖层，下一回合生效。
- **删除**：对某条记忆或全部资料的删除请求生成隐私立碑，30 天保留期后由定期清理彻底清除；删除不是把界面项藏起来。
- **暂停**：您可以暂停记忆的使用与抽取——暂停停止未来的读取，与删除（停止读取并拒绝写入）语义不同，两者都随时可以恢复或继续。

这些操作不需要理由，也不应该遇到挽留。这是 ADR-0006 确立的方向，也是我们对每一位用户的承诺。

## 4. 我们不做什么

以下内容是产品红线（《产品全貌》§6.2），不由增长目标或个别需求推翻：

- **不把您的脆弱表达变成商业机会。** 情绪依赖、脆弱时刻不会被转化为营销分群、付费压力或额外触达（红线第 4 条）。
- **不在您不知情时保留和扩散数据。** 对话与记忆不在您不知情的情况下被长期保留、复用或跨用途使用（红线第 7 条）。
- **不假装有真实情感。** 我们不声称数字人具有真实意识、真实情感需求或人类身份（红线第 1 条）。
- **不使用排他与依赖诱导的表达**，例如"只有我会陪你""不要离开我"（红线第 2 条）。

对应到数据层面，以下对象在我们的模型中**不存在**，也不会作为"偏好优化"被悄悄加入：

- 从沉默、语速、观看时长推断的情绪、孤独、脆弱、依恋类标签；
- 对用户的亲密度、忠诚度、留存价值、付费倾向或"唤回概率"评分；
- 任何形式的自动"关系评分"；
- 投诉、求助与高风险表达进入角色记忆或角色语气——它们只服务于处理与保护；
- 未经您确认的联系人、作息、家庭或健康信息。

## 5. 概念设计（未实现）

早期设计稿中有一些对象，经过权衡**没有进入当前实现**，如实列出以免误解：

- 命名用户主体 `subject` 及其 `subject_id` 字段——现行系统用设备换内部标识的匿名身份，不建立可命名的用户主体档案。
- 共同记录 `shared_note`（用户主动保存的比赛观察笔记）。
- 权利请求 `rights_request`（查看、导出、更正等请求的工单对象）——现行删除通过隐私立碑直接执行，其余权利入口仍在演进。
- 研究同意 `research_consent`（独立研究的单独同意对象）。
- 删除屏障版本号 `deletion_barrier_version`——现行实现以隐私立碑加每次读写检查达到同样目的，没有引入版本号字段。
- 八字段的呈现偏好对象 `presentation_preference`（文字优先、声音启动、动态强度等）——现行偏好以话痨三档为核心，其余维度规划中。
