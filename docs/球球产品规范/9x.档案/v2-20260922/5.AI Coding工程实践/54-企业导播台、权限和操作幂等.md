# 企业导播台、权限和操作幂等

> 本文是"球球"AI Coding 工程实践系列的导播台篇，写给想了解这款产品的运营侧如何面对"比赛日几秒内就要录入、更正、撤销"的读者。文中描述的能力均以仓库现网代码为准，实现位置逐处标注；尚未实现的部分，统一归入文末"边界与不做"，不以既有能力的口吻表述。
>
> 核心原则：我们把导播台做成"只产草稿的面板"和"说了就算的账本"的组合。界面上可以快，快到语音说一句话就能出一张事件卡；但任何东西在 fact ledger 裁决之前都不是事实。错误不怕发生，怕的是重复发生、无法追溯、静默覆盖。

---

## 1. 要解决的问题：比赛日的运营操作，怎么做到"快而不乱、错而可追"

一场球九十分钟，导播要在这九十分钟里完成：录入进球并指认进球者、处理 VAR 翻案、撤销误报、更正比分、应对外部数据源和人工判断打架。这些操作每一个都直接连着用户耳朵——比分错一个数，庆祝语就播错一遍；误报一个进球，取消之后还得向被吊起胃口的用户交代。

行业里的常规答案是"发布前设卡"：审批队列、双人复核、多级确认。但我们面对的是实时比赛：一次进球庆祝的窗口期只有几十秒，等一个复核人看完再批，话就迟到了，迟到的"好球"不如不说。所以我们的取舍是：**不在发布前设人工卡，而在结构上让错误进不了公开事实**。

具体拆成四个问题：

1. **谁能操作**——导播台不能是一个共享账号，每一笔写都要能归到具体的人，离开的人立刻失效；
2. **怎么防误发**——界面上的一切编辑都只是草稿，发布通道只有一条且由后端事实账本裁决；
3. **怎么防重复**——浏览器刷新、网络重试、双端并发，同一个操作不能把比分加两次；
4. **错了怎么追**——谁在什么时候改了什么、角色那句话为什么说，事后都能查到原始记录。

下面按真实实现逐一展开。

## 2. 真实设计

### 2.1 一块独立的 React 导播台：两角色、四 scope

导播台是 `console/` 下的独立 Vite + React 应用，由后端静态托管在 `/console`（用户侧 Flutter web 托管在 `/`，两边从部署上就不是一个目录）。它与用户端唯一共享的是后端 API，不共享任何会话凭证。

运营身份只有两个角色、四个 scope（`backend/internal/operatorauth/operatorauth.go`）：

| 角色 | scope | 能做什么 |
| --- | --- | --- |
| director | `match:write`、`fact:confirm`、`fact:correct`、`trace:read` | 全部写操作 + 读轨迹 |
| auditor | `trace:read` | 只读：看比赛页、审计轨迹、引用审计，所有写按钮隐藏 |

角色到 scope 的映射是纯函数，未知角色返回空 scope——每条路由都 403。前端不做第二次真相：组件按 whoami 返回的 scopes 门控 UI（`console/src/api/operator.tsx` 的 `isDirector`），auditor 看到的界面天然没有写按钮，而不是"点了再报错"。

吊销的实现是整个设计里我们最满意的一处：**删行即失效**。运营表里只存令牌的 SHA-256 哈希，每个请求都拿 presented token 重新哈希查表，没有任何缓存会话。`Operators.tsx` 页面上点"吊销"，弹窗写明"吊销后 XXX 的令牌立即失效，审计记录保留姓名"——确认后删掉那一行，此人手上的脚本下一次调用就是 401。没有"等令牌过期"，也没有"踢会话"这个概念。

空表时有个引导通道：`QIUQIU_BOOTSTRAP_OPERATOR` 环境变量在启动时播种第一个 director（`backend/cmd/server/main.go`），此后所有运营员都由已登录的 director 在 Operators 页创建。

责任链的最后一环是审计：每一笔 console 写入都追加进 `operator_audit`（运营员姓名、动作、对象、时间，`operatorauth.AuditEntry`），比赛页的"审计轨迹"按时间倒序展示。从"谁改了比分"到"角色为什么说这句话"（引用审计，见 2.10），线索是连续的。

### 2.2 双通道登录：人走密码，脚本走机令牌

导播台有两条认证通道，身份解析按优先级串联（`backend/cmd/server/operator_auth.go` 的 `claims`）：

```text
JWT（人类通道） ──▶ 个人机令牌（脚本通道） ──▶ 遗留 APP_TOKEN（仅存量兼容）
   │                    │
   │                    └─ 查 operators 表：SHA-256 哈希命中即取角色 scope
   └─ 账号密码签发（PBKDF2 存储）；"密码未设置"的 JWT scope 为空
```

人类通道是账号密码登录（`backend/internal/consoleauth/`），服务端用 HS256 签发 JWT；配置上强制要求 `QIUQIU_JWT_SECRET`（不少于 32 字符），没配就起不来。机令牌通道是每个运营员的个人 bearer token，留给自动化脚本和 curl，查表即用，不走 JWT。

人类通道上有两道约束，都是为了对付"初始口令裸奔"：

- **临时密码只显示一次**：director 创建新运营员时，后端生成 12 位临时密码（`console_auth.go` 的 `newTemporaryPassword`），明文只在创建响应里出现一次，落库的是哈希；
- **首登强制改密**：用临时密码签出的 JWT 带"密码未设置"标记，这种令牌 **scope 为空**——所有受 scope 保护的路由一律 403，唯一的例外是改密接口本身（它读 claims 但不做 scope 检查，所以改密这个动作才可能发生）。改完密码，下一个 JWT 才带上 director 的四个 scope。这套约束在服务端执行，前端 `PasswordChangeModal` 只是引导。

双通道解析产出同一种 Claims 形状，所以每条路由的 scope 检查代码只有一份，不因通道而异。

### 2.3 实战导演页：18 类行为，只写草稿

`DirectorLive.tsx` 是比赛日的驾驶舱，中间一条行为条（`BehaviorBar`）摆着 18 类比赛行为，按使用频率分四组，定义在 `console/src/director/event-model.ts` 的 `eventDefinitions` 一处：

| 分组 | 事件 | 比分增量 |
| --- | --- | --- |
| 高频 | 进球（+1）、射门、绝佳机会、扑救、错失、犯规 | 仅进球改比分 |
| 纪律 | 黄牌、红牌、点球 | 0 |
| 人员 / 战术 | 换人、战术变化、持续压迫、伤停 | 0 |
| 特殊 | VAR 检查、VAR 结果、进球取消（-1）、比分更正、备注 | 特殊规则（见 2.7） |

每类行为自带角色槽（进球/助攻/策动/防守相关……）、必填槽、推荐动作和强度。这个文件的头注释写着整篇的纪律：

> 事实纪律不变：本模块只产出事件载荷，绝不直接写事实——发布仍走 POST /api/matches/:id/events（或 correct）由后端事实账本裁决。

**draft-only 不是 UI 姿态，是模块边界**：`updateDraft` 状态机只能改动本地草稿对象。草稿卡（`DraftCard`）负责把人填进去——选队伍、从名单里选球员，然后逐槽校验（`validateDraft`），校验错误全是具体的中文规则而不是"表单无效"：

- "换上与换下球员必须属于同一球队"；
- "助攻者必须属于进攻方"（进球方角色与防守方角色按 `opponentRoles` 自动分侧）；
- "请选择要取消的原进球"、"请选择 VAR 正在审查的原事实"；
- "请填写更正或采用原因"；
- "目标比分必须与当前公开比分不同"。

必填槽没填、球员身份未确认，发布就走不下去。赛前还有一块配置面：队伍、名单、比分基线都在导演页维护，保存经后端确认，并有评测锁定这条路径（`console-director` 与 workflows 套件）。

### 2.4 语音草稿：说一句话，变成一张卡

比赛日导播两只手都腾出来打字是不现实的，所以草稿可以先用嘴说。`VoiceDraft` 走两条后端端点（`backend/cmd/server/match_operator_api.go`）：

- `POST /api/matches/:id/drafts/voice`：音频先过 ASR 转文字，再由 LLM 按事件词汇抽取结构化字段——事件类型、球队、进球者、助攻者、时间，每个抽出的字段带置信度；
- `POST /api/matches/:id/drafts/voice/publish`：冲突处理完之后的发布，同样走幂等写。

抽取结果和当前草稿合并时（`event-model.ts` 的 `applyVoiceDraft`），**字段冲突不会静默覆盖**：草稿里已填了进球者是"甲"，语音里抽出"乙"，合并函数把 `{field, current, incoming}` 推进冲突列表，界面逐项让导播裁决（`applyVoiceConflict`）——采用 incoming、保留 current，一个个来。多角色槽（助攻、防守相关允许多人）自动追加，单角色槽（进球者只能一个）才产生冲突。抽错一个同音字不至于直接写进事实。

ASR 未配置返回 503，上游 LLM/ASR 故障返回 502，界面给出明确状态而不是无限转圈；此时键盘录入草稿的路径始终可用。

### 2.5 事实时间线：确认、撤销、采用、更正

时间线（`FactTimeline`）按序展示一场比赛的全部事实事件，每条带事实状态徽标（已确认/已采用/已撤销/待确认），操作按钮按状态出现：

- **确认 / 撤销**：对候选（provisional）和已确认事实，分别走 `confirm` / `revoke` 事实转移；
- **采用到草稿 / 拉回更正**：候选或冲突事件一键预填进草稿卡——导播不用重新选人填表，改完再发；
- **开放冲突置顶**：人工与外部源打架的调和项固定在时间线最上面，单选裁决，不让它沉底。

冲突调和遵循一条保守默认：**保留兼容事实时用户端比分不抖**——裁决前公共状态维持最后确认值；要采用候选，就必须填更正原因，走的是与手动更正同一条审计通道。候选（pending）在确认前从不参与公开比分投影，这就是"快"与"不乱"能同时成立的原因：导播录入再快，公众看到的始终只有账本裁过的状态。

### 2.6 外部源与人工：谁在写事件

导播不是唯一的事件来源。`APISports` 外部源以默认 3 秒轮询自动写事件（`backend/internal/datasource/manager.go`），比赛页设置里可以启停、切换来源，或**人工接管**——接管会同时暂停自动播报，避免人和机器各说各话。没有配置 key 时就是纯人工模式。源的存活按"2×轮询间隔 + p95 延迟"判定，失联状态在设置页可见。

于是"人工与外部源冲突→球球暂停确认赛况"成为一个明确的产品行为：裁判口径出现分歧时，角色对用户说的是"等一下确认"，而不是随机挑一方。调和的落点回到 2.5 的时间线，由导播逐项裁决。

### 2.7 比分纪律：加一只加一次，静默更正，取消回退

比分是所有事实里影响面最大的一类，我们给它单独立了四条纪律：

- **goal 自动加一，只加一次**。进球事件的 `scoreDelta` 是 1，比分计算发生在载荷组装时（`toEventPayload`），而真正的入账在 fact ledger——候选确认只投影一次，重复确认、重复提交都不会把比分加成两倍（`matchstate/fact_ledger.go`）；
- **score_correction 静默**。比分更正事件强制 `deliveryMode = 'quiet'`，载荷里的主动话术写成 `__quiet__`——比分修正了，但球球不会突然冒出一句播报，用户看到的比分静静地变对了。校验还要求目标比分必须是有效整数且与当前公开比分不同；
- **goal_cancelled 回退**。进球取消的 `scoreDelta` 是 -1，并且必须引用要取消的原进球（`revisionOf`），不能凭空"取消一个不存在的进球"；
- **VAR 引用被审事实**。VAR 结果必须选择正在审查的原事实才能发布，杜绝"凭空出一个 VAR 结论"。

用一条时间线串起一次完整的翻案：

```text
63:12  导播行为条点"进球"，草稿卡选进球者，发布      ——比分 1-0，角色开始庆祝
65:40  VAR 检查（provisional，不碰公开状态）          ——用户端无感
67:05  VAR 结果引用原进球，发布"进球取消"             ——比分回退 0-0
       原进球事实转 revoked，已触发的主动回复被撤回
67:06  导播在更正框填原因（必填），随 correct 入审计   ——为什么改，留了底
```

更正必填原因是硬性的：凡是 `revisionOf` 更正或比分更正，`correctionReason` 为空直接不通过，原因作为独立审计事实随 correct 一起入账，无原因的更正在接口层就被拒绝。

### 2.8 幂等写：Idempotency-Key 是唯一通行证

运营台的全部写操作——发布、更正、事实转移、冲突裁决、语音草稿发布——都过同一个幂等执行器（`backend/internal/operatorwrite/service.go`）：

- 请求必须带 `Idempotency-Key`，缺键直接拒绝；键长上限 200；
- 同键 + 同载荷哈希：返回第一次的结果，不重复执行——前端所有非 GET 请求自动带新生成的键（`console/src/api/client.ts`），5xx 单次重试与 401 续期重放复用同一把键，响应头 `Idempotency-Replayed: true` 会回填到结果对象，界面能区分"新执行"和"重放"；
- 同键 + 不同载荷：判定为冲突，拒绝——键被复用去干别的事，比重复执行更危险；
- **busy 态**：同一键的操作还在进行中时，后来的重复请求拿到"仍在进行"而不是并发执行第二遍，执行器对进行中的操作持 2 分钟租约。

这层保护的意义在重试语义上：导播点发布超时了，前端重试带同一把键——比分加了一次；如果每次重试都生成新键，"加一只加一次"就是空话。

### 2.9 时钟治理：409 不是错误，是自愈信号

比赛时钟由后端推进，界面只能 PATCH 校准，且请求带版本号。两个端（比如网页和外部源接管）同时校准时，后到的 PATCH 拿到 409 版本冲突。`DirectorLive.tsx` 对 409 的处理写在注释里：

> 409 版本冲突 = 另一端已校准时钟（双轨并存期的常态）：自动重读恢复

也就是说前端捕获 409 后自动重读最新时钟状态，不弹错误框、不让导播手动刷新。事件永远不能把主时钟往回拨，阶段切换清零也由后端统一执行——界面只是镜子。

### 2.10 概览六格、引用审计与只读红线

导播台还有三块支撑面：

- **概览六格**（`Overview.tsx`）：活跃比赛、在线会话、话题老化、记忆健康（积压深度 + 降级徽标）、最近主动引用、词汇漏斗（24 小时 unknown 率）。六格让值班的人十秒钟判断系统是否健康，记忆积压这种内部信号直接外显，不等用户感知到卡顿才被发现；
- **引用审计**（`CitationAudit.tsx`）：按 citation 前缀深查某场比赛的轨迹，回答"球球为什么说这句话"——从一句回复追溯到它引用的事实和锚源；"为什么说话"抽屉展开单条的完整证据链。比赛 ID 没填就不发请求，防止全表扫；
- **两条只读红线**：画像页对运营**只读 + 代客删除**（删除槽位需二次确认并记入审计，不支持导出，`User.tsx`；话题页可代客标记已答/过期）；话痨档位在 console **刻意只读**——档位是用户在聊天里说"别说了"换来的，运营无写入口，这条不对称是设计而非省事。

另有一个安全阀：演示/测试比赛在白名单内可一键重置，清掉 traces、关系状态与观察（`isDemoMatchID` 校验，非演示 ID 直接拒绝）——排练不可能误伤真实比赛。

## 3. 如何验证

导播台是本仓库自动化覆盖最密的面板，验证分三层：

**界面自动化**（`tests/evals/operator-control.spec.mjs`，28 例）：这组是导播台的主回归，覆盖登录、角色 scope 门控、草稿状态机、比分纪律（goal 加一一次、更正静默、取消回退）、幂等重放、时钟 409 自愈、审计轨迹落行。28 例合起来回答一个问题：把导播台当成黑盒，一个 operator 从登录到撤销事实的每条路，走两遍结果必须一致。

**console 各页契约**（Playwright）：

- `console-pages.spec.mjs`——六个页面（概览/比赛/运营员/导演直播/引用审计/话题）的渲染契约；
- `console-auth.spec.mjs`——双通道登录、首登强制改密、临时密码一次性；
- `console-director.spec.mjs`——实战导演页专项，含时钟 409 版本冲突后的自动重读恢复；
- `console-identity.spec.mjs`、`console-threads.spec.mjs`——身份与话题页；
- 概览六格的服务端契约由金样本锁定（`console_golden_test.go`，见第 59 篇）。

**Go 单测与结构对拍**：`operatorauth_test.go` 锁角色到 scope 映射、删行即失效、审计追加；`operatorwrite/service_test.go` 锁幂等执行器的键校验、载荷冲突、busy 租约；`event-model.ts` 的移植对拍由 `scripts/check-director-event-model.mjs` 在离线评测里逐字节校验，改走样直接红。

跑法与仓库一致：Go 侧 `go test ./...`，端到端走 `tests/evals` 的 Playwright 套件（提交档 `npm run eval:pr` 一条命令全跑）。

## 4. 边界与不做

- **没有审批队列**。这是与常见后台设计最大的分歧：我们没有"提交复核—等待批准"的异步流。实时性优先——进球窗口只有几十秒，draft-only + fact ledger 裁决 + 幂等重放已经把"误发"的代价压到"一条可撤销的事实"，审批队列省下的错误抵不上它吃掉的时效；
- **没有双人复核**。director 一人即可确认和更正。可追溯性由审计轨迹兜底而不是由第二双人兜底：每一笔写都归到具体运营员，事后审计能完整重建责任链。如果未来出现高影响面扩大的场景（多场次并行、外部值班），双人复核是第一个值得重新评估的项；
- **角色只有两个**。没有更细的"编辑/复核人/安全观察员"分工——当前团队规模下，两角色四 scope 已经让"写"与"读"分离，更多角色只会制造共享账号的诱惑；
- **导播台不看用户对话**。console 的用户代客操作面只有画像只读、话题标记、交互历史摘要，没有任何私人对话原文入口；画像删除是代客动作而非运营分析。这条红线不随功能增加而松动；
- **话痨档位不可远程调**。运营不能替用户把球球调回 active——档位只能由用户在聊天里自己改变；
- **没有逐用户区分**。导播的一切决定作用于公共事实层，不针对单个用户定制呈现——谁是 director 的"目标用户"这个问题，在系统里没有表达位置。
