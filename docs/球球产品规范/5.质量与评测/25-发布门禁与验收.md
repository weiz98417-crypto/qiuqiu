## 1. 发布门禁（G1-G11）

### 1.1 门禁总则

- **RL-01 评测不过，不进用户侧**：门禁是放行的前置条件，不是质量装饰。门禁的价值不在「证明系统好」，而在「让每一类已知的错误都有自动拦截点」；评测全绿只说明已知风险有拦截点，不证明已知风险之外的问题不存在。
- **RL-02 判定以工具为准**：每道门的通过与否以工具退出码与报告为据（24 篇 EV-05），不以人工声明替代。「重跑到绿就过」不成立——外部依赖抖动导致的假红，须先说明抖的是哪个服务、为什么该档没有把它隔离，能隔离的收敛进离线档，再重跑。
- **RL-03 无豁免机制**：门禁没有「高风险用例降级容忍」与豁免登记；红就是红。认为某道门判定过时，走规范修订（改 24 篇资产定义与 PRD 7.2 判定标准），不走临场豁免。
- **RL-04 全绿＋检查单才放量**：对外放量（受控试用即算）须 G1-G11 全绿且 G10 关闭（G11 未生效期以「护栏信号监测无破线」代行并如实记录，PRD 7.3.2 L1 同源）。**当前判定：不具备对外放量条件**——PRD 7.3 检查单 23 项中 10 项 P0 未完成、8 项 P1 未完成（合规待建族是第一施工优先级，映射归 33/35 篇）。
- **RL-05 挂账面**：每道门有挂账面（角色，非人名；人员落名由值班与职责表维护，归 27 篇）。门禁红时由对应挂账面处置；跨门失败（如 G3 与 G1 同时红）按最上游先修。
- **文档门在前（2026-06-09 收口补）**：PRD 7.6 评审工作流是文档门，本篇 G 门是发布机器门，30 篇 §3 五闸是放量闸门——三层链序为「文档门→机器门→闸门」：文档未过 PRD 7.6 评审门不得进发布评审；机器门禁不全绿不得放量；放量闸门无豁免（三层关系声明见 PRD 7.6.2，本条为其规范侧回指）。

### 1.3 门禁豁免纪律（三条；本篇对豁免的立场是「不存在」，条款化如次）

1. **谁可豁免——无**：RL-03 无豁免机制对本篇全部十一道门适用，不存在任何角色（含发布批准人、值守、挂账面负责人）可对任一门临场豁免、降级或「带红放行」；认为某道门判定过时，唯一通道是规范修订（改 24 篇资产定义与 PRD 7.2 判定标准），修订通过前门保持原判。
2. **记录到哪——修订记录，不是豁免登记册**：判定标准的变更走本篇与 24 篇修订记录留痕；本篇不设「豁免登记册」，任何以豁免、例外、临时放行名义出现的放行记录，在发布记录（RL-30）核验时判不通过并按违规登记。
3. **有效期——不存在限时豁免**：门禁判定没有「有效期至」概念——判定修订生效时点即新旧判定切换点，切换前的红门不因修订在途而放行；「先放行、修订随后补」的顺序违规。与 30 篇放量闸门（DL-04 无豁免机制）同构互链。

## 2. CI 双 job 与本地预检

### 2.1 CI workflow（`.github/workflows/evals.yml`，全仓唯一 workflow）

触发：`pull_request`＋`push: branches [master]`＋`workflow_dispatch`；concurrency 按 ref 取消在途。

| job | 环境/时限 | 步骤 | 密钥 |
| --- | --- | --- | --- |
| `pr-evals` | ubuntu / timeout 20min | Go 1.22 → `go test ./...` → console 构建（TS 侧契约锁编译拦截，dist 供浏览器档 /console 使用）→ Flutter analyze/test/build web → Playwright 装 Chromium（缓存绑定版本）→ `node scripts/evals/run.mjs --tier pr` → 上传 `artifacts/evals/`（`if: always()`，失败也留证） | 无模型 key（离线确定性） |
| `promptfoo-gate` | ubuntu / timeout 15min | `node scripts/promptfoo/run-gate.mjs`（自起 eval backend），`CI=true` | **无任何模型 key**（断言全确定性，judge 不参与） |

- **RL-10 双 job 同为强制门**：任一 job 红即阻断合入；promptfoo 门禁与评测 job 分立是刻意的——judge 报告永不参与门禁（24 篇 EV-02），门禁层只锁确定性负例。
- **RL-11 nightly 无自动触发（如实注记）**：workflow 无 `schedule` 触发，nightly 档（含基准与 Postgres 测试）只能本地手跑；任何「夜档自动跑」的表述失实。补 cron 为工程侧待办（24 篇 §10）。

### 2.2 本地预检阶梯

| 场合 | 最低预检 | 命令 |
| --- | --- | --- |
| 日常开发内层循环 | 离线档 | `npm run eval:offline`（秒级反馈，纯进程内） |
| 提交/合入前 | 提交档 | `npm run eval:pr`（CI `pr-evals` 的本地等价） |
| 慢性退化排查 | 夜档 | `npm run eval:nightly`（基准＋真库） |
| 发布候选验证 | 发布档 | `npm run eval:release`（真实语音冒烟，需 `MIMO_API_KEY`） |

失败处置走法（RL-02 展开）：评测报告带失败用例 ID 与期望/实际差异 → 本地复现该用例 → 按「修一个 bug 加一条 regression」落新用例（24 篇 EV-14）→ 修复后重跑。门禁每拦一次，网就密一分。

### 3.1 六个核心环境细则

- **单测**：判定＝`go test ./...` 非零即红，无跳过名单；金样本逐字锁意味着契约变更必须显式更新金样本文件（diff 可审），「顺手改了没人知道」被结构性排除。conformance 类测试（观察协调器内存/Postgres 双实现）保证两实现共享同一套纯规则、不漂移。
- **evals**：判定＝报告 `FailedCases = 0` 且事实安全率/轨迹率/留痕完整率全为 1.0；报告必须带 gitRevision——「当时的通过是在哪个版本上取得的」可精确回答。回归用例只增不删（24 篇 EV-14），通过率不可靠删除用例提高。
- **运行时 E2E**：起真实后端进程走真实 WS 话轮，断言点不止屏幕文案——跟进只出现一次（送达去重）、观察只跟进本人（隔离）、轨迹里能找到核验记录（可审计）。后端起不来、浏览器超时都停在最前面，没有「跳过失败继续跑」的路径。
- **像素回归**：`regression.mjs` 自起静态服务按后端同款 `/live2d-assets` 契约加载 live2d.html，遍历 presentation-map 动作表逐动作 `playMotion`，捕获控制台/页面错误并逐动作截图；模型未就绪、任何控制台错误、截图塌为透明画布（模型未绘制）三者任一即失败。手动触发是现网事实（非 CI 档内），挡门地位由 G4 在发布审查执行。
- **隐私 API**：判定覆盖语义与横切两面——语义面（导出 11 类完整性、删除中 409、已删 410、jobId 可无凭证查询但响应剥离 userId）；横切面（删除期间 companion 全部用户写路径被 `ErrDeletionInProgress` 挡住、in-flight 写等待后移除、完成后读路径 `ErrDataDeleted`、tombstone 立碑下一回合生效）。无 DATABASE_URL 时降级内存 Store（进程重启即失）的边界照实登记，不得据此宣称持久合规能力。
- **隔离测试**：双设备双 WS 全链——一位用户的坚持主张与画像绝不影响另一位用户的会话；trace 按用户隔离可查。此环境是 memory `isolation-*` 用例族（离线面）的运行时对应面，两层共同锁定用户隔离承诺。

- 用户面事实错误扩散：错比分、未确认事实被当确定播报类缺陷进入生产（G1 级失败在生产复现）；

### 5.2 回滚动作（现网形态）

| 动作 | 内容 |
| --- | --- |
| 镜像回退 | 后端镜像回退到上一放行版本 |
| 数据库恢复 | `pg_restore --clean --if-exists` 恢复每日备份（`pg_dump -Fc`，每日 03:30 cron；手册见 `deploy/README.md`）；memobase 库可接受丢失，不强制定时 |
| 迁移处理 | 迁移只增不删、引用按文件名——回滚到旧镜像时**迁移不逆向**，靠应用层兼容窗口 |
| 运行中止血（先于回滚） | TTS 供给三态切换（含本地腿健康门控 409）；自动化策略 active/paused＋事件白名单＋冷却；数据源人工接管（takeover→paused）；事实撤回；运营员令牌即时吊销（行删除即刻生效） |
| 观测面 | Grafana 不在 compose 内——回滚不影响观测 |

恢复命令参照（`deploy/README.md`，数据卷完好仅回滚数据时）：

```bash
# 每日备份（crontab，03:30）
30 3 * * * cd /path/to/qiuqiu && docker compose exec -T postgres \
  pg_dump -U qiuqiu -d qiuqiu -Fc > backups/qiuqiu-$(date +\%F).dump

# 数据回滚：直接覆盖恢复
docker compose exec -T postgres pg_restore -U qiuqiu -d qiuqiu --clean --if-exists \
  < backups/qiuqiu-YYYY-MM-DD.dump
```

### 5.3 回滚后验证

回滚完成后重过 `npm run eval:offline`（至少 `-suite all` 234）＋隐私 API 冒烟；语音相关回滚加跑 MiMo 语音冒烟。回滚事件按 27 篇值守流程复盘，衍生缺陷按 24 篇 EV-14 落回归用例。

按用户比例放量机制（NFR-REL-010）**规划中（未实现，P1）**——单实例形态下无灰度面；开放受控试用前须立（最小形态：邀请码＋运营台总量开关）。现阶段的「放量刻度」即 PRD 7.3 检查单：P0 关闭前不放量；P0 全闭后按受控试用（小规模邀请）→ 公开版两档推进，两档间验收差异是埋点最小面跑通一个完整赛季周期。

## 7. 设计说明（写法依据与迁移差异，非需求条款）

1. **迁移映射**：本篇承接 v2 卷5《59-端到端验收与发布门禁》。数字与结构差异：三套件 100 条 → 12 套件 249 用例（234 离线＋15 真网显式点名）；18 spec / 5,517 行 → 20 spec / 99 tests / 5,904 行；CI 单 job（pr-evals）→ 双 job（＋promptfoo-gate）；「没有灰度发布」→ NFR-REL-010 立项（规划中（未实现），P1）；新增合规门 G9 与检查单门 G10——59 章时代门禁只覆盖技术面，v3 把 PRD 7.2 的十道门转正为规范，合规与交付放行面与技术面同权。
2. **「门禁决定什么、不决定什么」**（59 章原则平移）：门禁决定「这个版本能不能进用户侧」，不决定「这个方向值不值得继续做」。评测全绿只说明已知风险都有拦截点；产品判断仍在人手上。把两者混在一起，要么让门禁背上它证明不了的承诺，要么给「为赶进度放宽评测」开口子——RL-03 无豁免机制堵的就是后一条路。
3. **验收环境即证据分层**：§3 矩阵的行序就是 24 篇 §1 的分层序（单测 → 黄金集 → 结构校验 → E2E → 界面自动化 → 像素 → 专项），外加放行侧特有环境（真网档、真实语音冒烟、延迟闸门）。像素回归保持手动触发是如实登记（现网未入 CI 档）——写成「CI 自动像素回归」即失实；其挡门地位由 G4 保证，触发时机由挂账面在发布审查时执行。
4. **回滚判据的写法**：v2 把「数据安全全部筹码押在备份恢复上」作为边界如实陈述；v3 保留该诚实口径并补齐判据侧——什么时候必须回滚（§5.1）、回滚前后各验什么（§5.3），使回滚从手册动作升级为有判定条件的规范条款。运行中止血手段（TTS 三态/策略暂停/takeover/撤回/令牌吊销）承担同类职责但不是灰度，两者分开表述，不混写。
5. **与 24 篇的分工**：24 篇管「资产与判定」（套件定义、grader 语义、盲测判据、命令语义），本篇管「门禁与放行」（门的判定标准、编排、环境矩阵、产物与回滚）。同一资产在两篇出现时参数不复制；本篇修订只随门的增删与现状翻转（如 G9 上线、G10 关闭、灰度落地）。
6. **检查单的判定纪律**：G10 的「通过」只认 PRD 7.3 有实证的条目；「P0 未完成」是上线硬关卡，不因技术门全绿而软化。合规待建族（协议文本/AI 披露/2h 提醒/依赖弹窗/语音退出/投诉入口等 10 项）是受控试用前的第一施工优先级，映射归 33/35 篇——本篇不因写作需要对检查单状态做任何乐观改写。
