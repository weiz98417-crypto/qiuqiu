# 31 埋点与数据采集规范

> 本篇基线：2026-06-07 仓库 a7e5100。

**本篇定位**：球球全部产品埋点的事件规范与采集实现篇——事件 taxonomy 与命名规范、事件全集表 v0、公共属性 schema、采集通道选型、QA 流程、与账本派生指标的边界。本篇是 28 篇（指标体系）的采集侧：28 篇管口径与治理，本篇管采集实现。**本篇全部 40 个事件与全部采集机制均为「规划中（未实现）」**——球球现网零埋点文档、价值面零采集面；现网实有观测面（Grafana 6 面板 4 告警、运营台九格、账本四表与 /ws/ops）是工程观测，不是产品埋点，两者边界见 §6。规则引用格式「31/R-NN」，事件 ID 格式「E-NN」。

**导读**：§1 总则与采集纪律｜§2 事件 taxonomy 与命名规范｜§3 事件全集表 v0（40 事件）｜§4 公共属性 schema｜§5 采集实现选型（⚖️B22）｜§6 与账本派生指标的边界｜§7 埋点 QA 流程｜§8 验收｜§9 设计说明。

**事实依据**：本篇全部「已运行」声明仅指向 28 篇 §3 实有采集面对账（Grafana provisioning、Overview.tsx、账本四表）；§3 事件全集表全部行状态=待实施、owner=待指派，无任何一行对应现网代码——这是如实状态，不是缺口修辞。表列与 PRD 6.3.2 冲突时以 PRD 为准并修订本篇。

### 1.2 总纲纪律（六条）

| # | 规则 | 反例（违规形态） |

| R-01 | **先埋点后指标**：无采集来源的指标不得立项为正式指标，只能以「待埋点（31 篇）」登记并进本篇排期（28 篇 §4.1 同款纪律） | 先在周报立「首赛转化率」目标、再回头造采集 |

| R-03 | **最小必要**：每个事件与每个属性须对应一个已登记指标的决策用途；无消费方的属性不采（28 篇 §4.1 问题卡为消费方凭证） | 为「以后可能有用」预采字段；把整段上下文塞进属性 |
| R-04 | **隐私边界**：不传消息正文与音频内容；不传口令/凭证/联系人/精确位置等 PII；标识只用匿名伪标识（anon_id）；采集器自托管为前提约束（CR-06：交互数据不出第三方）；埋点消费面只出聚合数 | 客户端接入第三方统计/广告 SDK；上报通道指向外部 SaaS；用户级明细进增长看板 |
| R-05 | **隐私三权同步**：新增任何采集数据面，须同步纳入导出（/api/me/export）与删除（/api/me/data）承载范围；承载未接的采集面不得上线（CR-07） | 事件表建成后在导出 11 类之外裸奔 |
| R-06 | **一事件一 owner**：禁止无主事件；owner 指派矩阵（§8.2）是实施前置条件 | 表里 owner=待指派就开始施工；事件上线后无人对口径负责 |

## 2. 事件 taxonomy 与命名规范

### 2.1 命名规则（六条）

| # | 规则 | 反例（违规形态） |
| --- | --- | --- |
| N-01 | 事件名一律 `object_action`：名词单数 + 动词过去式 | `start_session`（动词开头、现在时）；`sessions`（无动作） |
| N-02 | 全小写下划线，禁驼峰、禁中划线、禁中文 | `voiceConnected`、`voice-connected` |
| N-03 | v0 之后新增事件名 = 域前缀 + `object_action`（域前缀见 §2.2） | 新增无前缀事件 `page_viewed`（应为 `ui_page_viewed`） |
| N-04 | 同族共用 object 前缀：同一对象的动作挂同一名词（`reminder_delivered`／`reminder_act_entered`） | 同一提醒对象写成 `reminder_sent`／`reminder_open_click` 两种名词 |
| N-05 | 客户端与服务端事件同一名空间，不冠 `client_`／`server_` 前缀——产生端由公共属性 `platform` 与登记表「产生端」列区分 | `client_wake_word_triggered` 与服务端同名事件双轨并存 |
| N-06 | 事件名一经采集不得改名；语义变化 = 新事件 + 旧事件走 §7.3 废弃流程 | 把 `session_exited` 的口径改掉却沿用旧名，历史读数失去可比性 |

### 2.2 域划分（七域）

| 前缀 | 域 | 覆盖面 | 对应现网系统面 |
| --- | --- | --- | --- |
| fact_ | 比赛事实与知识 | 更正/撤回送达、引用码渲染、知识作答 | 账本五态、knowledge_entries |
| voice_ | 语音与会话链路 | 会话生命周期、连接、唤醒、打断、重连补发、话轮、伴随反应、语音供给切换 | /ws/match、ClientHealthLedger、agent_traces |
| mem_ | 记忆与数据治理 | 画像查看、记忆删除、导出、全量删除、手记 | 记忆域、/api/me/* |
| rel_ | 身份与关系 | 凭证绑定、登出 | ADR-0020 身份链 |
| ui_ | 界面与设置 | 设置节变更（v0 仅此；页面级事件不在 v0 范围——最小必要） | 设置 11 节 |
| ops_ | 运营与合规 | 词汇漏斗、令牌刷新失败、合规展示类（F 组七事件） | 运营台九格、CR 待建功能 |
| growth_ | 主动触达与增长 | 三簿触达与接受、订阅变更、主动回合、进入归因 | proactive_reminders、delivery_ledger |

- **v0 不改名**：§3 全集表 40 个事件的**事件名以 PRD 6.3.2 为唯一锚**，不因域前缀改名（避免 PRD↔规范双源漂移）；「域」列是 taxonomy 归属登记。
- **v0 之后**：新增事件一律 N-03 带域前缀；新增事件先进本篇 §3 追加行（含 schema 与 owner），再进施工——不允许代码先埋、规范后补。

## 3. 事件全集表 v0（40 事件）

**全表状态=待实施、owner=待指派**。各列口径：ID／事件名／域／产生端／触发时机／专有属性 schema／owner／状态。

- **属性写法**：`名:类型∈取值`；`∈` 后为枚举或约束；未标 `∈` 的 string 为受控枚举（取值随实施登记进 schema 注册表，§7.1）。公共属性（§4）各事件必带，不在本表重复。
- **产生端**：C=客户端、S=服务端、O=运营台操作触发。
- **F 组注记**：F 组七事件依赖对应 CR 待建功能，随 CR 落地**同批实施**，不单独排期。

## 4. 公共属性 schema

### 4.1 载荷必带字段（八字段）

| 字段 | 类型 | 取值/约束 | 说明 |
| --- | --- | --- | --- |
| event | string | `^[a-z][a-z0-9_]*$` | 事件名，与 §3 登记名逐字一致 |
| ts | int64 | Unix 毫秒，UTC | 客户端产生时间；服务端接收时间另存 recv_ts 用于时钟漂移核查，不替代 ts |
| anon_id | string | `usr_` 前缀伪标识 | 匿名/登录同一 ID（ADR-0020 原地绑定）；全链路唯一用户标识，**不新增任何 PII 字段** |
| session_id | string | 陪看会话标识 | 非会话事件（如 E-31 settings_changed）可为空串 |
| match_id | string | 比赛标识 | 非比赛上下文事件可空 |
| platform | string | ∈ web\|android | 端侧区分（N-05） |
| app_version | string | semver 形态 | 客户端版本；服务端事件填后端构建版本 |
| trace_id | string（可选） | 回合链路标识 | 与 agent_traces 关联；非回合事件可缺省 |

### 4.2 派生属性（enrichment，不进载荷）

| 派生字段 | 取值 | 派生方式 | 纪律 |
| --- | --- | --- | --- |
| user_form | ∈ anonymous\|verified | 查询期由 anon_id 关联身份态派生（ADR-0020：匿名是默认形态，登录是原地绑凭证的可选升级） | 派生不落载荷——身份态变化本身由 E-29/E-30 事件承载，避免双写漂移 |
| 比赛上下文 | 联赛/轮次/主客队/是否完场 | 查询期由 match_id 关联比赛面派生 | 最小必要（R-03）：赛程属性随比赛数据更新会变，进载荷必腐化 |

### 4.3 采集红线（对一切事件生效，与 5.3/5.4 一致）

1. 不传消息正文、ASR 转写文本、音频内容；文本类长度只允许 `*_len` 计数字段（如 E-33）。
2. 不传口令/凭证/联系人/精确位置；《办法》第十六条交互数据不出第三方（CR-06）——采集器自托管为前提约束。
3. E-36 语音退出事件不存原文，`utterance_matched` 恒 false 是 schema 约束不是实施疏漏。
4. 消费面只出聚合数；用户级明细仅限 28 篇 §3 隐私三层同等权限的回放/核查通道，不进增长看板（28 篇 §3.5 第 3 行）。

### 4.4 上报语义（随 B22 选型落地，现为规范约束）

| 项 | 约束 | 说明 |
| --- | --- | --- |
| 投递语义 | at-least-once ＋ 事件级去重键（event+ts+anon_id+session_id 四元组） | 重复上报在消费端折叠；去重键是幂等口径，不依赖上报顺序 |
| 断网补发 | 客户端本地缓冲、恢复后补发；缓冲上限与老化策略随选型实施登记 | 补发事件标 recv_ts 晚于 ts，周检容忍时钟与到达差 |
| 失败处置 | 上报失败静默丢弃计数，不重试阻塞、不弹窗打扰 | 采集是旁路：丢数宁可缺口，不得伤害陪看体验（§5.3） |
| 顺序性 | 消费侧按 ts 排序，不承诺到达顺序 | 跨端时钟漂移由 recv_ts 核查，不做时钟同步工程 |
| 批量与频次 | 会话内批量聚合上报，退出时冲刷 | 上报节奏本身不得成为新的触达面或耗电面 |

## 7. 埋点 QA 流程

### 7.1 schema 注册表

- §3 全集表＋§4 公共属性是**唯一 schema 源**；实施时由本表生成机器可读 schema（JSON Schema 形态，载体随 B22 选型定），代码侧校验与 CI 断言消费同一份，禁止代码里另写一份枚举。
- 专有属性的受控枚举（如 error_code、fallback_reason）在实施时回填本篇 §3 表（修订记录留痕），回填前该属性按自由 string 只进影子期。

### 7.2 四步验收（每事件从实施到翻牌）

| 步 | 名称 | 通过标准 | 不通过的处理 |
| --- | --- | --- | --- |
| 1 | **schema 校验**（合并入 main 前） | 公共属性必带且类型合法；专有属性枚举合法；命名过 N-01~N-06（CI 确定性断言，不依赖模型） | 不予合并 |
| 2 | **影子对照**（上线初 1-2 个比赛窗口） | 新事件与运行面/账本派生口径对照：session_entered 数对会话建立数、reminder_delivered 对 proactive_reminders 表计数；偏差>5%（候选值）不翻牌 | 停留在「影子对照」状态，读数不进正式视图 |
| 3 | **量级合理性周检**（上线后常驻） | 事件间量级约束成立：reconnect_attempted ≤ session_entered × 5；reminder_act_entered ≤ reminder_delivered；replay_invite_accepted ≤ replay_invite_delivered；intent_unknown_hit ≤ turn_completed | 周检异常触发口径核查，必要时事件降回影子 |
| 4 | **翻牌登记** | 依赖该事件的指标在 28 篇从「待埋点」翻「已采集」；修订记录留痕（指标 ID／依赖事件／翻牌日期） | 未过步 1-3 的指标保持「待埋点」，不得进任何对外材料（28 篇 §1.2 纪律 3） |

### 7.3 一致性抽查与废弃流程

- **一致性抽查（月度）**：随机抽 3 个已采集事件，核对其当月聚合数与对应账本/trace 派生数的比值稳定性；漂移超阈值按口径变更处理（28 篇 §4.2 四留痕）。
- **事件废弃**：先停发两个客户端版本（停发期读数双轨并陈）→ 确认无消费方 → 再从 schema 注册表删除；删除行在本篇修订记录登记，历史数据不回填改写。
- **schema 变更**：新增属性走追加（旧读数不受影响）；改枚举取值按口径变更处理；改事件语义禁止（N-06）。

### 7.4 与 evals 的关系（显式声明）

- 埋点 QA **不是评测**：evals 体系（24 篇，12 套件 249 用例）判「球球行为对不对」；本篇 QA 判「数采得对不对」。
- 两者互不替代、互不挡门：发布门禁 G1-G11 不含埋点项（埋点的放行验收在检查单 #18 与本篇 §8，不在 25 篇门禁表内新增 G 项）；评测全绿不构成埋点翻牌依据，反之亦然。
- 唯一交点：F 组事件的**功能主体**（2h 提醒、弹窗、投诉入口等）归 CR 条款验收并挂 24 篇合规负例族（规划中）；其**埋点腿**（E-34~E-40）归本篇四步验收——同批实施、两套验收各跑各的。

### 8.2 owner 指派矩阵（实施前置）

## 9. 设计说明（写法依据，非需求条款）

1. **新立篇依据**。v3 大纲调研结论 6：tracking plan（事件 taxonomy／命名规范／属性 schema／每事件 owner／QA 流程）是成熟产品标配文档，球球此前零埋点文档，62 章指标无采集侧支撑——31 篇即为此新立，是 28 篇（指标体系）的采集侧姊妹篇。v2 档案 16/64 章只有指标口径与复盘方法、无任何采集工程规范，故本篇无可平移正文，属八篇新立之一（大纲迁移映射：16 章指标 → 62＋70 拆分）。
2. **与 PRD 第六章的分工**。PRD 6.3 自述「只立需求与口径，实施载体为本篇」：本篇把 PRD 的需求级摘要（命名口径三句、公共属性八字段清单）扩为字段级 schema 与可执行 QA 流程，40 事件逐条补齐 ID/域/产生端/触发时机/属性 schema——「转正」的含义是口径从需求稿变为可施工的规范稿，事件集合与 PRD 逐字对账为零 diff，未擅自增删事件。
3. **v0 事件不改名的理由**。域前缀（§2.2）是新增事件的命名强制项，但 v0 40 事件沿用 PRD 定名——若为对齐前缀而改名（如 session_entered→growth_session_entered），PRD↔规范↔未来代码三处立即漂移，违背「数字与口径唯一」的章程纪律。域列作为 taxonomy 归属登记已满足分组消费需求；这一取舍在 B22 裁决实施时复核一次即可。
4. **B22 为什么是新裁决点**。裁决点 B1-B13 与 PRD 收编 B14-B21 均无采集通道事项；PRD 6.3.1 只立了「自托管为前提」的约束而未选载体——这是真实的未决工程决策，不假装已定（37 篇 §3 原则）。选项 c（混合）是多数成熟产品的落点，但在单实例 compose 形态下「先立显式事件表还是先榨干账本」的顺序有真实成本差异，故显式登记、默认不动。
5. **评测挂钩=无的理由**。00 篇 §6.5 的政策↔评测互链针对**行为规则**；本篇规则是**数据工程规则**，其质量属性（schema 合法、量级合理、口径稳定）由确定性 CI 断言与周检承载，不进 evals 的用例族。把埋点 QA 塞进评测套件会造成「234 例全绿但数是错的」的假安心，故 §7.4 显式切分。
6. **「零埋点」的表述纪律**。球球现网有观测（28 篇 §3）而无产品埋点——本篇行文一律区分「观测面（已运行）」与「事件面（待实施）」，不写「球球没有数据」（运行面在出数），也不写「数据已采集」（事件面为零）；两种时态混写是 v2 病根在本领域的变形，评审按 §3 表逐行对账。
