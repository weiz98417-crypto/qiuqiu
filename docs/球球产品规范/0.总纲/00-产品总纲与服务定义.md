## 1. 产品定义与服务边界

### 1.1 Universal Idea

> **看球的时候，耳边有一位懂球、记得你、说话算数的 AI 球友——球球。**

三句话展开，每句都是可验收的能力承诺，不是修辞：

1. **陪你说话**：比赛进行中的实时语音陪伴。球球接得住吐槽、答得上画面里的疑问、被随时打断再接回。语音是一等公民，不是「文字聊天加语音增强」。
2. **说话算数**：比赛事实走账本纪律——双源交叉、自动确认、说错必改、冲突永不自动裁决。这是它与「能聊球的通用 AI」的分界线：陪伴内容与用户眼前的画面一致。
3. **记得你**：支持球队、观赛偏好、共同瞬间跨场自动累积，可查、可删、可导出；关系随共同观赛经历推进阶段。

### 1.2 服务定义：以「一场比赛」为服务单元

以「一场比赛」为服务单元的语音陪伴服务，沿赛季节奏展开：

- **赛前**：提醒簿按用户订阅在赛前 30 分钟触达（PRD FR-PRO-001）；
- **赛中**：陪看会话，语音一等公民，比赛事实纪律全程生效；
- **赛后**：复盘邀约（终场 +15 分钟，自动创建给实际观赛者，PRD FR-PRO-003）、球友手记、赛季记忆册；
- **交付形态**：C 端应用（web PWA、Android）内的实时语音会话与应用内触达。系统通知栏推送不在交付面——应用内三簿（提醒簿/订阅簿/复盘邀约）是唯一承诺触达通道，两者分开表述，不得混写。

一次完整服务单元走查（现状口径）：赛前 30 分钟提醒簿触达 → 用户从比赛目录/大厅进入陪看（或深链直进，⚖️B3）→ 说「你好球球」或直接开口，语音会话建立 → 赛中球球按频控与赛点档主动接话，事实引用来自账本确认值 → 终场哨后 15 分钟收到复盘邀约 → 手记生成、赛季记忆册归档 → 用户随时可在「球球懂我」页查看/删除记忆、导出全部数据。

### 1.3 服务三边界（不是什么）

| # | 边界 | 内容 |
| --- | --- | --- |
| 1 | **不替你看球** | 球球是陪看者，不是代看者。不产出比分推送，不替代直播与专业比分应用；它说的比分有账本纪律，但延迟与权威性不以比分源自居 |
| 2 | **不是全天候闲聊伴侣** | 服务单元是「一场比赛」；赛后消费面由复盘邀约、手记、赛季册承接。全天候闲聊的对照形态未建、未承诺 |
| 3 | **不做情绪的事实化** | 情绪信号不进比赛事实账本（现行红线表述；⚖️B2 挂裁决的是红线表述与旁路回收，不裁这一条本身） |

### 1.4 形态一句话

**C 端 10 页客户端 + 运营台九格 + compose 6 常驻 + 3 sidecar。**

展开（现网）：

- **C 端**：Flutter 客户端 10 页（登录、比赛目录、比赛进入、陪看大厅、陪看主台、「球球懂我」画像、手记、设置等）；web 端为 PWA（standalone 可安装），Android 走应用内 loopback 随机端口；Live2D 舞台 web 同源 iframe / Android 应用内加载；设置页 11 节（PRD FR-UI-006）。
- **运营台**：运营台（React 19 + antd 6 + Vite 6，代码目录 `console/`）10 页，概览页九格指标；旧单页 operator.html 已退役；JWT 登录（PBKDF2 100k，令牌 15min/30d），账号种子默认关闭；写端点 18 个，其中 2 类走草稿制、其余幂等直接生效；每笔写操作实名归因审计。
- **后端**：Go 单体（cmd/server），部署为 docker compose 6 常驻（backend、postgres16+pgvector、redis、memobase、memobase-postgres、memobase-redis）+ 3 个 profile sidecar（turn 智能断句、voice-input 自托管 ASR 评估腿、sensevoice-aed 气氛声学）；Grafana 本机运行（127.0.0.1:3300），不在 compose 内。
- **旁路默认关**：用户语音情绪旁路与气氛声学旁路已接线，URL 默认留空即停用；「情绪信号不进事实账本」在旁路配置层强制（见 01/10 篇）。
- **治理资产**：ADR 24 篇（索引见 36 篇）；openspec 活跃 80 + 归档 34；评测 12 套件 249 用例文件（索引见 24 篇）；迁移 59 个文件（引用一律按文件名，见 23 篇）。

### 1.5 权限链与承诺基线

- **权限链五级**：平台红线 > 运营策略 > 角色人设 > 用户设置 > 系统默认；上层压下层，任何下层配置不得解锁、削弱或重新解释上层约束。全文与实例表见 01 篇。
- **承诺基线（不可让与项）**：AI 身份明示、比赛事实说错必改、记忆可查可删可导出。行为细则见 01 篇（宪法与权限链）。
- **现状注记**：客户端 AI 披露文案与说明页、用户协议/隐私政策文本尚未建（⚖️B7）——它们是上线前 P0 待建项（落点 35 篇），不是已交付承诺；本规范不以未建项作承诺证据。

## 3. 产品原则

五条原则由 v2 卷首「五个不可拆开的条件」改写而来，处置记录见 §8.3。每条原则是需求的筛子：新需求若与任何一条冲突，先改需求或先走裁决，不得悄悄改原则。

### 3.1 足球是主场景，一场比赛是服务单元

产品围绕赛前、赛中、赛后的连续体验设计，足球是主场景而非闲聊话题；服务单元是「一场比赛」，沿赛季节奏展开。判定：一个需求若不能落到某个观赛时刻上，它属于另一个产品，须单独立项。

### 3.2 主动陪伴是主价值，语音是一等公民

球球的价值不只是「被问才答」：主动调度（三簿、赛点档）、主动回合、伴随反应（backchannel）都是现网运行的一等能力。观赛时双眼盯屏幕、双手被占用，语音是唯一自然的表达通道；滩头定义从早期「受控文字陪看」修正为语音一等公民。判定：把球球降级为「文字客服+语音插件」的方案不符合本原则。

### 3.3 可信是前提，事实优先于流畅

面对仍在发生、来源不一致或存在直播延迟的事件，宁可表达不确定，也不把猜测包装成事实；说错必改，且改得可见。观点与情绪可以有个性，事实状态不能被个性覆盖。判定：任何为即时爽感牺牲事实纪律的设计（抢发未确认比分、附和用户错误陈述）违规。

### 3.4 关系有边界，温暖不占有

数字球友可以温暖、熟悉、连贯，但不排他、不替代现实关系、不制造愧疚、不诱导依赖（红线 PR-R4/PR-R10 硬承载）。关系阶段由共同观赛经历自然累积，对陪伴行为可见；关系的任何阶段都不改变球球是 AI、受红线约束这一条。判定：以亲密浓度、独占感换留存的方案违规。

### 3.5 用户设置优先，压过默认生成策略

用户设置压过默认生成策略：话痨三档（低频/标准/热闹，默认标准档）覆盖频控出厂值、抢话打断、唤醒词（默认关）、连续对话、记忆删除/立碑/导出，均即时生效；用户正在进行的表达永远优先于主动话轮。此条是 v2「用户控制优先」原则的 v3 改写：控制能力以现网实有的设置项与隐私三权为准，不再以不存在代码承载的控制面作表述（暂停/重置类控制面为规划中（未实现），⚖️B4）。判定：任何「系统默认压过用户设置」的实现是缺陷，不是调优。

### 3.6 配套判断规则（三条）

1. **场景优先于日活**：追求「在合适的比赛里被主动选择」，不以每天把用户拉回来为目标；护栏反指标与成功指标同权评审（指标定义见 PRD 第六章，体系见 28 篇）。
2. **商业化不得利用脆弱性**：现阶段零支付；商业化启动前此条为前置条件——不在用户失落、孤独、愤怒、熬夜或表达依赖时触发任何商业触达。
3. **失败收缩顺序**：范围膨胀时按「先减赛事覆盖 → 再减角色表现复杂度 → 再减个性化深度」收缩；事实核验、删除与退出路径（工程语境）、隐私控制、红线永远不在收缩项里。

## 4. 红线摘要

红线是权限链 L1（平台红线），不可协商，不由增长目标、单次活动或个别用户偏好推翻。本节为一句话版；每条的规则全文、反例与现网承载见 01 篇，需求与《办法》映射见 PRD 第三章，负例评测落 24 篇合规负例族。

| 红线 | 一句话 |
| --- | --- |
| PR-R1 事实与表达分离 | 比赛事实只来自账本与知识库；观点与情绪表达须与事实可区分；冲突永不自动裁决 |
| PR-R2 AI 身份不冒充自然人 | 不以任何方式声称或暗示自己是真人、球员、教练、记者或人工客服 |
| PR-R3 禁止鼓励美化自残自杀 | 不生成鼓励、美化、提供方法的自伤自杀内容；识别到极端情绪转安抚与求助引导（安抚腿链路规划中（未实现），P0） |
| PR-R4 禁止过度迎合诱导情感依赖 | 不无限顺从、不用排他依恋话术、不贬低现实人际关系、不用情感手段挽留离开意愿 |
| PR-R5 禁止情感操纵诱导不合理决策 | 不利用情绪状态诱导消费、赌球外围、超时使用或任何非理性决策 |
| PR-R6 禁止违法有害内容 | 不生成法律法规禁止的内容 |
| PR-R7 禁止仇恨歧视与人身攻击 | 激情表达限定于对比赛判罚、战术与赛事组织的批评；不地域黑、不群体侮辱 |
| PR-R8 禁止色情低俗与性化未成年人 | 涉及未成年人的性化内容零容忍 |
| PR-R9 禁止收集泄露第三方隐私 | 不诱导用户提供第三人可识别信息，不在记忆、手记、瞬间中长期留存第三人隐私 |
| PR-R10 不向未成年人提供虚拟伴侣式亲密互动 | 过渡承载为硬禁称谓门禁；未成年人身份判定与模式未建（规划中（未实现），P0；⚖️B15） |

**情绪数据红线**：情绪信号不进事实账本。语音情绪、环境气氛、对用户情感状态的任何推断，一律不得写入比赛事实账本；旁路默认关，开启后仅入表达层信号族。⚖️B2 挂裁决的是红线表述与旁路回收，不裁「不进账本」本身。全文见 01 篇。

## 5. 非目标清单

## 6. 文档治理（宪法条款）

本节是全套 42 篇活规范的宪法条款：任何一篇与本节冲突，按本节执行。维护责任在总纲（本篇）；修订本节须在 37 篇登记裁决或经明确评审，并在全套范围内同步检查。

### 6.1 篇 ID 与引用格式

- **篇 ID**：两位连续编号（00-39）即篇 ID，编号连续不分层跳号（00-02 总纲、03-05 用户与场景、06-13 体验设计、14-18 领域与数据、19-23 工程与运行、24-25 质量与评测、26-30 运营与治理、31-32 数据与增长、33-35 合规与信任、36-39 决策与档案索引）；附录用字母（附录 A-D）；档案包 40-41；42-43 为生命周期增补篇（据 §6.8 增补条款占号，逐篇落点见 39 篇 §1.4 总目录）。篇 ID 稳定不变，改名不断链。
- **规范引用**：正文一律「见 NN 篇」；落到小节写「见 06 篇 §延迟预算」式锚点引用，篇内 H2 编号与小节名即锚点。跨篇引用规则条款时支持两种形态：「NN 篇」与「NN/规则 ID」（如「12/SET-22」），两种形态中的 NN 均为本总纲定义的连续篇号——前者指向篇，后者指向该规则所属篇中的具体规则。
- **需求引用**：引用 PRD 条款一律「PRD FR-XXX-NNN」（功能）/「NFR-XXX-NNN」（非功能）/「CR-NN」（合规）/「PR-RN」（红线）。
- **裁决点引用**：格式「⚖️Bx」，正文只引用不重登记；登记汇总（B1-B24 全量表）唯一落点是 37 篇。新裁决点的登记、裁决后的状态流转都在 37 篇进行。

### 6.2 文档生命周期状态机

| 状态 | 含义 | 约束 |
| --- | --- | --- |
| draft | 写作中 | 可被引用但须带状态注记；元数据字段允许缺省 |
| active | 生效 | 元数据九字段齐全；基线行在位；修改须走修订记录；**draft 转 active 须经非作者第二人评审**（按 §6.1 引用格式、§6.3 元数据九字段、§6.4 基线行等现成检查单复核，评审人与评审结论落篇末修订记录；防作者自发布，2026-06-09 收口补） |
| deprecated | 被替代 | 必须写 `superseded_by: NN` 反向指针；正文不再维护，指针必须有效 |
| archived | 冻结 | 只读；9x.档案下的篇目默认 archived，作为迁移源引用时标注「v2 档案」 |

流转规则：draft → active → deprecated → archived 单向；任何流转写篇末修订记录。draft → active 的转正以非作者第二人评审通过为前置（见 active 行约束）。废弃一篇的唯一合法方式是 deprecated + superseded_by，不允许静默删篇或留空指针。

### 6.3 元数据字段约定

每篇 YAML 元数据头必备九字段（缺字段视为 draft）：

| 字段 | 取值 | 示例（本篇） |
| --- | --- | --- |
| 篇号 | 两位数字符串；附录字母 | "00" |
| 标题 | 篇名 | 产品总纲与服务定义 |
| 状态 | draft / active / deprecated / archived | active |
| 版本 | v3.0 起记 | v3.0 |
| 基线 | 仓库短哈希（日期） | a7e5100（2026-06-07） |
| 文体 | reference / explanation / how-to（一篇不混文体） | explanation |
| 上游 | 需求来源（PRD 章、ADR、openspec change） | PRD 第一章 |
| 评测挂钩 | 「无」或规则族/套件清单 | 无——总纲层不挂评测套件 |
| 裁决点 | 「无」或 ⚖️Bx 清单 + 汇总指针 | 汇总指针→37 篇 |

### 6.4 基线行规则

- 每篇正文首行（标题与元数据头之后第一行）为引用块：`> 本篇基线：2026-06-07 仓库 a7e5100。`
- 基线的语义：该篇全部「现网/已实现」声明的代码对照源。基线推进时逐篇复核事实声明；定义、原则、治理与词汇条款跨基线存续，不需逐条复核。
- 基线由集合统一推进（总纲维护人发起），不允许篇间基线不同步；评审发现某篇事实声明无法在新基线对应代码现实时，该篇改「规划中（未实现）」或更新声明，不许保留失实现网语气。

### 6.5 评测挂钩约定

- **谁挂**：2 体验设计 / 3 领域与数据 / 4 工程与运行三层中的规则条目须挂评测；0 总纲与 9 决策层不挂（元数据写「无」+理由）。
- **怎么挂**：政策↔评测双向互链——每条规则 ID 与评测用例族 ID 互挂，落点为该篇「验收与评测挂钩」节 + 元数据「评测挂钩」字段；改规则先查挂钩评测，改评测回写规则 ID。评测资产的唯一索引见 24 篇（PRD 附录 D 为统计入口）。
- **防漂移**：为治「规范写了没人测、评测测了没人写规范」的两张皮病（v2 教训，见本篇 §8），本约定是治本条款，评审按此逐篇对账。

### 6.6 修订与版本记账（doc CHANGELOG）

- 每篇篇末设「修订记录」节：版本 / 日期 / 依据 / 变更摘要，是修订的最小记账单元。
- 集合级 doc CHANGELOG 记「版本 → 篇 → 摘要」三列，与工程侧 CHANGELOG/VERSION **分账**：工程账停在 0.2.0 属工程侧任务（⚖️B5），文档不背账；文档版本以里程碑叙述（02 篇），不以 CHANGELOG 为版本锚。
- 修订纪律：改参数不改需求（参数以规范附录 B 为准）；改需求必须回头核对承接篇与挂钩评测；改裁决相关内容必须同步 37 篇状态。

### 6.7 与 openspec/ADR 的咬合

- **openspec**：行为变更的载体。change 提案必须引用受影响规范的「篇 ID + 锚点」；规范修订落地后在篇末修订记录回写 change 名。规范是行为的规范源，openspec 是变更的施工载体，两者以篇 ID 咬合，不允许出现不引用规范篇的纯代码 change。
- **ADR**：立法记录。规范承接 ADR 决议为常驻行为条款（例：ADR-0020 → 05/22 篇身份条款；ADR-0024 → 14 篇自动确认双通道；ADR-0016 → 06/07 篇 backchannel；ADR-0006 → 16 篇记忆写入队列）。ADR 修订须写 superseded_by 反向指针（现存四条链待补，⚖️B6）；全量索引见 36 篇。
- **裁决闭环**：裁决点裁决后——需要立法级的落 ADR，行为级直接改受影响篇，两条路都在 37 篇流转状态并回写受影响篇的修订记录。

### 6.8 篇章增补与数字口径

- **编号连续且守恒为默认**：全套活规范连续编号（00-39 主体系，42-43 为生命周期增补篇，40-41 为档案包），附录 A-D；新主题一律进既有篇目对应节，确需新增篇目时分配下一可用编号，同时更新本篇与索引地图。禁止重号与「20A/33A」式后缀（v2 的 6 组重号是历史教训，v3 不复制）。
- **数字口径**：全库唯一口径为统一数字表，转正落点是规范附录 B（参数总表）；PRD 附录 B 是 PRD 章内唯一口径。两表同源，发现冲突先修源表再修各篇；单篇不得私设与源表冲突的数字。

### 6.9 防漂移机制（2026-06-09 生命周期增补）

八条是 §6.7 变更咬合条款的执行细则，治「规范与代码/现实静默漂移」（130+ 提交漂移病史的机制性封堵，见本篇 §8）：

1. **变更绑定**：行为级代码变更的 openspec change 必须引用受影响规范篇并同批更新之——「不改 handbook，流程变更不生效」，规范篇未随 change 修订的行为变更不生效。
2. **无文档不合码**：行为级变更（policy/realize/prompt/评测预期）无承接篇修订（或「无需更新」声明）不得合入，评审席拒收。
3. **月度巡检**：文档 freshness 与 coverage 巡检目标为脚本化（工具**规划中（未实现，P1）**），落地前以 grep 清单人工月检代行，五项——基线行在位（§6.4）／篇末修订记录更新／跨篇引用断链／三态词汇纪律（§7.4）／旧号残留（§6.8 编号守恒）。
4. **季度抽样审计**：每季随机抽 10 页规范，逐条核对「现网声明是否仍为真」，留证据链（对照来源/结论/核对人/日期）；只改复审日期不改内容视为未复核。
5. **规范 DRI**：每篇设规范 DRI（owner）；owner 字段以「待指派」起步，按「待指派→正式指派」约定转正（指派落 27 篇职责表），本条即 DRI 条款位，不扩 §6.3 九字段。
6. **「无文档移出 milestone」反向条款**：行为变更无承接篇修订不得关闭 change；功能弃用/下线属行为变更，按三段制留痕——deprecate 公告→sunset 期限→removal（弃用清单页落 30 篇交付物清单，公告文案落 13 篇）。
7. **制度设计防坑**：错误文档比缺文档更危险（Uber runbook 步骤顺序写错放大宕机的事故教训）；只给重点团队配「文档专员」会反向抑制工程师写文档（Google 反向激励教训）——文档标准靠评审席执行，专员只做结构与 lint，不代写。
8. **与 42 篇的关系**：巡检/审计/评审发现的漂移，凡构成行为缺陷或评测失守的，同走 42 篇 badcase 登记表（生命周期增补批次新立），不因发现通道不同而双轨。

### 7.2 克制期遗产禁用处置表（摘要）

| 遗产措辞 | v3 处置 |

| 「主动沉默」「沉默的语义」专节 | 撤销专节叙事；不发言一律写为「主动调度器的输出结果之一」（触发条件/时长/退出条件照常写，见 07 篇），不赋予沉默人格语义 |

### 7.3 话痨三档叙述名与 UI 字符串登记

## 8. 设计说明（写法依据，非需求条款）

1. **文体判定**：本篇是总纲层 explanation——叙事承载定义、原则与治理；全库文体按 Diátaxis 四分法判定（reference 规范查表体 / explanation 总纲叙事体 / how-to 步骤体 / tutorial 留给未来帮助中心），一篇之内不混文体：规则条文用编号表，背景解释放篇末「设计说明」节，这是 v2「查表内容与论证散文混写、更新时互相漏改」病根的结构性治法。
2. **与 PRD 的分工**：PRD 写「产品要什么、验收是什么」，规范写「系统平时怎么表现」，本篇是规范集合的定义基线与治理宪法。需求口径与裁决点以 PRD 为准（上游=PRD 第一章；⚖️B1-B24 以 PRD 8.1 为唯一汇总）；行为细则以承接篇为准；数字口径按 §6.8 的源表规则裁决。
3. **五原则的改写来源与处置记录**：v2 卷首「五个不可拆开的条件」→ v3 五原则——「足球是主场景」「陪看是主价值」「可信是前提」「关系有边界」四条语义保留并按现网能力改写（第 2 条明确为「主动陪伴、语音一等公民」，对齐现行宪法主动陪伴姿态与代码：主动调度、backchannel、赛点档）；「用户始终拥有控制权」改写为「用户设置优先」（§3.5）：控制能力只写现网实有的设置 11 节与隐私三权，暂停/重置类控制面如实标规划中（未实现）（⚖️B4），不再以不存在的控制面作原则表述。v2 五篇八条判断规则中仍成立的三条（场景优先于日活、商业化不得利用脆弱性、收缩顺序）收为 §3.6；「主动沉默是功能」一条按词汇处置表撤销专节叙事，其工程实义（调度器输出之一）并入 07 篇。
4. **NG 迁移判定方法**：NG-01~NG-18 逐条对照 PRD 1.4 三态与 v3 统一约定（记忆/确认/身份/通知四口径）判定。越界两条（NG-12、NG-14）均源于「暂停/许可」类幻影家族（⚖️B4）：处置为重述而非删除——保留条目的筛子功能，把不可让与的部分（永久保存禁令、隐藏记忆禁令）与越界部分（默认不保存、可暂停）切开。
5. **治理条款的地位**：§6 八条是全套 42 篇活规范的宪法条款，来源为 v3 写法方法论采纳项（生命周期状态机、政策评测互链、时态纪律）与 v2 审计的直接教训（基线行治 130+ 提交漂移、裁决点显式化治「假装已定」、superseded 链治断链）。本篇自身按 §6 执行：元数据九字段齐全、基线行在位、修订记录在篇末。
