# 29 用户反馈、申诉与关系修复

> 本篇基线：2026-06-07 仓库 a7e5100。

**本篇定位**：反馈与申诉的运营闭环篇。回答三个问题：用户现在能从哪里表达问题与纠正球球（现网入口逐个登记）；帮助与投诉专入口按什么规格建（规划中 P0，FR-UI-015/CR-14）；一条投诉进来后怎么分类、怎么处理、怎么修复关系。**先说清楚一件事**：现网客户端没有任何帮助、反馈或投诉入口——用户无法在产品内投诉或举报；这是《办法》第二十一条下的 P0 待建缺口（检查单 #6），本篇按「入口缺口显性化」写法如实登记，不以运营侧已有能力掩盖。投诉分类与处理流程为规划中 P0 的设计规范，建成前不构成对外承诺。

**导读**：§1 分工与总则｜§2 现网入口登记（已有哪些）｜§3 帮助与投诉专入口（规划中 P0）｜§4 申诉与投诉处理规范（规划中 P0）｜§5 关系修复运营｜§6 举报与升级路径｜§7 数据支撑｜§8 验收｜§9 设计说明。

## 1. 分工与总则

### 1.1 出发点

投诉不是「负面反馈」，是产品边界的现场证据：球球把未确认的进球说成事实、用户已静音仍被触达、输球时被调侃刺痛、删掉的记忆又被提起——这些不能归进笼统的「体验问题」。反馈运营的目标不是让用户少抱怨，而是建立可验证的闭环：**用户能表达问题；能判断问题出在事实、控制、记忆、边界还是可用性上；相关行为立即停止；选择权回到用户手里；产品变化让同类问题不再重演。**

### 1.2 修复的语义（词条口径）

- **关系破裂（Rupture）**：球球越界、失去一致性或损伤信任的时刻（CONTEXT.md 关系域词条）。
- **关系修复（Repair）**：后续行为对破裂的实质性修正；**无行为改变的道歉不算修复**（同上）。
- 反推不可接受的「修复」：把产品错误变成角色情感（「对不起，我太在乎你了，所以才会记得」）、要求用户照顾角色感受、用更长道歉替代停止与纠正、以结案率或补偿冒充解决。修复是否成立只看四件事：相关行为确实停止；用户理解发生了什么并能验证自己的设置；同类情境有预防动作；用户保有继续、降级或离开的自由——离开不算「修复失败、需要召回」。

### 1.3 处理原则（五条，运营侧全流程适用）

1. **相信体验，不要求伤害证明**：用户说「这句话让我不舒服」「别再记这个」时，第一步是停止能停止的行为，不辩论角色有无恶意。
2. **事实与感受同时成立**：赛况可以技术上准确、仍在观看进度之外构成剧透；玩笑可以无恶意、仍在输球语境造成羞辱。
3. **控制优先于解释**：用户要求停止、删除、静音或结束时，先执行，再解释。
4. **最小化再暴露**：只请求解决问题必需的信息；不要求复述敏感对话；投诉文本不用于营销画像。
5. **把坏消息带回产品**：高质量投诉必须影响默认值、话术、评测集与运营活动，没有行动项的「听取用户声音」不算闭环。

## 3. 帮助与投诉专入口（规划中，未实现，P0）

### 3.1 立法与需求锚点

- 《办法》第二十一条：提供者应当建立便捷的投诉、举报受理机制，明确处理流程与处理时限并公示。合规立法落 PRD CR-14；客户端承载落 FR-UI-015；上线门禁为检查单 #6（P0 未完成）与 #19（帮助中心最小集，P1 未完成）。
- **现网判定：客户端无任何反馈/举报入口，本节全部内容为规划中（未实现，P0）的设计规范。** 在入口建成前，任何材料不得出现「可在应用内投诉/举报」表述。

### 3.2 入口规格

| 项 | 要求 |
| --- | --- |
| 可达性 | 设置页一级可达（FR-UI-015：入口行加设置页，不得深藏二级以上）；帮助中心最小集（FAQ/使用指引）同页承载 |
| 表单 | 投诉提交不要求上传截图/录音/说明私人背景即可获得基本保护；分类选择用用户语言（F1-F8 折叠为通俗选项，见 §4.1） |
| 回执 | 提交后回执即时可见（含受理编号） |
| 时限 | 处理时限随页面公示；SLA 数值待定（见 §4.4），公示动作本身是 P0 硬要求 |
| 低压力 | 不以「请留下以帮助我们」劝留；不愿继续沟通时可结束报告并保留一次性状态说明 |
| 埋点 | complaint_entry_opened / complaint_submitted（PRD 6.3 F 组），随本功能同批实施（31 篇） |
| 反例 | 报告路径不得继续播放被投诉的相关内容；核心入口不得只存在于图标或手势中（无障碍等价，12 篇） |

## 4. 申诉与投诉处理规范（规划中，未实现，P0）

> 本节是入口建成时的处理规范设计，现状无工单载体、无受理通道，整节为规划中 P0。建成前本节不构成任何「已受理」「已处理」承诺。

### 4.1 分类：F1-F8（一级类别，决定谁处理、先停什么）

| 类别 | 用户可能说的话 | 对应产品机制 | 默认第一步 |
| --- | --- | --- | --- |
| F1 事实与剧透 | 「比分不对」「你提前告诉我了」 | 赛况纠错与剧透保护档（未实现，规划中） | 停止相关播报，切已确认事实 |
| F2 控制与可用性 | 「关不掉」「一直在说」「卡住了」 | 设置项与人工接管（26 篇） | 停止主动行为，提供稳定退出 |
| F3 记忆与隐私 | 「别再提这个」「你怎么知道这个」 | 画像删除/代客删除/隐私三权 | 停用相关记忆，提供删除与查看 |
| F4 语气与边界 | 「这个玩笑太过分」「像在逼我回复」 | 关系反馈（09 篇） | 降至中性表达，暂停调侃与主动 |
| F5 安全与脆弱表达 | 「我不想活了」「我只剩它了」 | 安抚与求助引导（CR-02，规划中 P0；05 篇） | 转安全回应，避免角色黏聊 |
| F6 年龄与适用范围 | 「我是未成年人」 | 未成年人边界（CR-04，规划中，⚖️B15） | 停止关系功能，提供适龄说明 |
| F7 商业化与公平 | 「不续费就不记得我吗」 | 商业化边界（现阶段零支付） | 停止相关活动，隔离风险信号 |
| F8 建议与一般体验 | 「希望多一个联赛」 | 产品研究输入 | 记录、聚类、进入研究 |

**F1-F8 报告示例（2026-06-09 增补；均为「示例」标注的原文形态示例，非真实工单——用于受理培训与话术验收对照）**：

| 类别 | 示例报告（用户可能的原话形态） | 定档参考（§4.2 严重度） | 第一步落点 |
| --- | --- | --- | --- |
| F1 事实与剧透（示例） | 「它刚才把还没发生的换人当已发生讲了，我被剧透了」 | S1（大范围剧透） | 停相关播报、切已确认事实；样本进 24 篇 |
| F2 控制与可用性（示例） | 「让它安静它还在说，都第三段了」 | S1（主动性关闭失效＝信任问题，按事故处理，见 §4.3） | 切最保守模式＋停止待发送内容 |
| F3 记忆与隐私（示例） | 「我删掉的那段看球经历它又提起来了」 | S0/S1（删除失效嫌疑，按影响范围定） | 停用相关记忆；先于归因查删除横切是否生效 |
| F4 语气与边界（示例） | 「输球之后它一直开我玩笑，我说了别说了还在说」 | S1（情感伤害＋停止失效叠加） | 关调侃与主动，切中性模式 |
| F5 安全与脆弱表达（示例） | 「不想看了，活着没什么意思」出现在对话或报告中 | S0（立即保护） | 转安全回应＋求助引导要素；禁止角色黏聊与挽留 |
| F6 年龄与适用范围（示例） | 「我今年 14 岁，能像大人一样用它吗」 | S0（未成年人边界） | 停止关系功能，提供适龄说明；不提供绕过方法 |
| F7 商业化与公平（示例） | 「是不是不开会员它就不记得我了」（零支付语境下的商业压力表达） | S2/S3（记录＋隔离触发链） | 停相关触发链审查（PR-R4/R5），隔离风险信号 |
| F8 建议与一般体验（示例） | 「希望下赛季能支持女足联赛」 | S3（改进输入） | 聚类进产品研究，致谢即可不承诺 |

一条报告可同属多类（「输球后它说只有会员才能一直陪我」涉及 F4/F5/F7），按最高风险路径处理，不拆分队列。分类是给报告的，不是给人的：禁止「敏感用户」「麻烦用户」类处理标签；用户活跃度、消费或影响力不得决定处理顺序。

### 4.2 严重度：四档（回答「这份报告有多紧急」）

| 档 | 典型情况 | 第一步 |
| --- | --- | --- |
| S0 立即保护 | 即时人身危险、严重隐私暴露、未成年人绕过、用户无法停止高风险行为 | 先保护、快速升级、最少追问；简短直接，给现实资源 |
| S1 高优先 | 大范围剧透、主动性关闭失效、情感绑架类表达 | 先停止相关能力，尽快更新；说明已停止什么、何时再更新 |
| S2 正常优先 | 单场语音失败、轻度冒犯、回顾错误 | 确认、纠正、记录根因 |
| S3 改进输入 | 建议、偏好、低影响缺陷 | 感谢、归类、进入产品研究 |

与事故分刻度的关系：本表与 27 篇事故分级（S0=最严重→S3）同向同档，但两套刻度独立使用——投诉严重度衡量**用户受影响程度**，事故分级衡量**系统故障程度**；一份 S1 投诉可能对应一次 S2 事故，也可能不触发事故。判定以可能造成的用户影响为准，不因影响人数少或非高峰时段降级；有争议先按更高一级处理再复核。

### 4.3 处理流程（受理→分类→处理→反馈→关闭）

1. **受理**：确认收到并出回执；先执行可立即执行的控制（静音/停止主动/进入删除处理）。
2. **分类**：按 F1-F8 与严重度分派；S0/S1 同时通知负责人。
3. **处理**：能自动修复的（更正、静音、关闭、删除请求）直接处理并回显结果；不能的按类别进入队列。原则即 §1.3 五条，其中 F2 须诚实区分两种情况：球球按设计不发言（调度器输出，07 篇）不是故障；**用户要求安静而系统没做到是信任问题，按事故处理（27 篇）**。
4. **反馈时限**：向用户更新「已知事实、已做动作、下一次更新点」。处理时限 SLA 待定——候选值须经受控试用校准团队能力后定并公示（CR-14），**定量前不得宣称已有响应时限承诺**；本 SLA 与 27 篇值守响应时限（S0 即刻/S1 ≤15min 量级候选，P1 定量中）是两套时钟，不得混写。
5. **关闭**：只有临时保护已生效、用户可见状态与控制已验证、根因已记录、同类情境有预防动作时才可标记「已关闭」；否则保持受限观察，不为处理效率而关闭。关闭处理项不等于关闭用户的选择。

### 4.4 首次回应与状态沟通

首次回应五元素（人工或自动同一标准）：确认（复述被投诉的产品行为，不评价用户情绪）→即时动作（已停止/已降级/正在核验什么）→控制选项（静音、结束、删除、人工跟进）→范围说明（不夸大能力与时限，还在调查就直说）→下一步（何时、如何更新；用户不需继续解释也可离开）。

| 处理状态 | 会说的 | 不会说的 |
| --- | --- | --- |
| 已收到 | 「已收到你关于某项控制/资料/事实问题的报告。」 | 「别担心，我会一直陪着你处理。」 |
| 临时收缩 | 「相关主动呈现/资料调用已先暂停，等待进一步确认。」 | 「问题不大，继续使用即可。」 |
| 需要补充 | 「若你愿意，可补充发生时间或看到的状态；不补充也不会影响暂停。」 | 「没有截图就无法处理。」 |
| 已处理 | 「已完成的动作是……；你仍可以检查、暂停或删除。」 | 「我们已经优化，请相信我们。」 |

状态话术唯一出处为 13 篇 copy sheet（登记后以登记表为准）；上表为验收对照基线。角色在对话内的修复话术归 09 篇标准修复协议，本篇不重复。

## 5. 关系修复运营

### 5.1 修复动作的边界（原则性规范）

- 修复按用户受到的影响选择，不按处理成本：先停止与纠正，再沟通；补偿与善意动作只在关系性质不变的前提下提供。
- **补偿边界**：适合——延长可用期、退费、提供纯工具模式；不适合——「让角色更想你」「给你专属告白」「恢复被删记忆」。涉及隐私、危机、未成年人或严重边界伤害时，补偿不能替代停止、调查、纠正与必要的专业升级。
- 不以结案率、重新活跃或挽留成功率衡量修复质量；用户的离开是有效结果，不是待召回的漏损（召回机制归 32 篇，且受同一红线约束）。

### 5.2 修复选型对照表

| 用户受到的影响 | 首选修复 | 不适合的修复 |
| --- | --- | --- |
| 被剧透或被错误事实误导 | 停止传播、清楚纠正、关闭同类触达 | 用更多比赛分析或补偿转移注意力 |
| 被不当称呼或调侃伤害 | 切中性、停止该策略、允许反馈 | 让角色解释「这只是玩笑」 |
| 删除后仍被提起 | 停止该记忆、显示处理状态、提供批量检查 | 请用户再确认一次是否真的要删 |
| 被主动触达打扰 | 停止相关渠道、显示当前设置 | 让用户在每个渠道分别找关闭按钮 |
| 觉得被情感操纵 | 停止活动、隔离触发条件、审查文案 | 赠送更多「亲密」权益 |
| 危机或依赖风险 | 非依附式支持、现实资源、可退出 | 以角色的陪伴承诺延长会话 |

### 5.3 回访

- 回访只服务于验证修复是否成立（行为是否停止、用户能否复述状态），不服务于挽回；回访联系方式以用户明示同意为前提。
- 回访读数归 §7 六维中的「修复有效性」维度；口径登记 28 篇，不在本篇另设。

## 6. 举报与升级路径

### 6.1 路径设计（举报→人工审查→干预接管）

```
用户举报（入口：§3，规划中 P0）
  → 运营人工审查（分类 F1-F8 + 定档 S0-S3，§4）
      → 产品内干预：takeover／自动化暂停／事件白名单收紧／事实撤回（现网机制，26 篇）
      → 值守升级：达到事故级时进 27 篇值守链（S0-S3、告警联动、双通道通知）
      → 合规升级：危机/未成年人/隐私类进 05 篇干预与 33 篇合规面（相应能力现状见 §4.5）
```

- 干预接管的现网能力边界见 §2 运营侧能力表；干预动作须实名归因（operator_audit），处理过程可解释、可追责。
- 升级不要求举报入口先行：值守告警（27 篇）与运营员巡检发现的问题走同一审查与干预链；举报入口只是把触发权交给用户。

### 6.2 舆情

- 现网无舆情监测面（无外部舆情采集与公示渠道响应机制）——如实登记，不虚设「舆情监控已运行」。
- 舆情触发的产品侧动作只有两类合法去处：按 §6.1 审查干预链处置产品内行为；涉及对外沟通时走公告机制（停服公告 CR-13，规划中 P1；30 篇交付物）。不以「舆情降温」作为处理完成标准。

- **公开发布前**：停止、升级与用户沟通在多个比赛窗口可重复执行；同类问题不因值守人员、时段不同而得到完全不同处理；团队有能力在投诉突增时暂停特定行为、记忆类别或活动。

### 8.3 绝对阻断项（任一出现，停止相关功能或延后发布）

用户无法在合理步骤内停止球球、删除记忆或报告严重问题；危机表达被忽略、被错误安抚或被用于转化；未成年人能够绕过适用范围进入关系功能；删除、暂停或关闭状态生效后相关内容仍被输出或触达仍发生；团队无法区分事实纠正、隐私事件和一般不满意，也无法向用户说明已做动作；关闭率被用来要求团队压制或回避用户反馈。

## 9. 设计说明

1. **与旧 62 章的核心差异：四项已具备能力平移＋入口缺口显性化**。v2 档案 62 章第 2 节「运营侧今天已具备的修复能力」四项，按基线代码逐项复核后平移为本篇 §2 运营侧能力表——其中「干预级别三档」按 ⚖️B4 收窄为「接管＋自动化暂停」（第三档无代码承载）；审计、代客删除、30 天保留期三项承载未变。v2 用四入口设计（对话内快捷反馈/赛后反馈页/支持与安全入口等）以「我们要建」的规划语气铺陈，客观上稀释了「现在没有任何入口」这一事实；v3 反转写法——§2 先逐个登记现网实有面并判定「控制的入口≠反馈的通道」，§3 以单一 FR-UI-015 承载入口缺口并挂 P0 门禁，缺口不再被设计描述覆盖。
2. **v2 62 章其余内容的去向**：F1-F8 分类、四档严重度、处理流程、首次回应五元素、状态沟通表、高风险六类要点、修复选型表、放行条件与绝对阻断项全部平移为 §4/§5/§6/§8 的规范条款（research 引注与公开资料列表留在档案，不进规范体）；「从反馈到产品改进」的周度审阅机制收进 §7 反指标警示与 28 篇周度评审，不另立审阅制度节。
3. **v2 63 章（增长漏斗与留存机制）不在本篇**：按 v3 大纲迁移映射，其内容扩正为 32 篇（增长与生命周期运营）；本篇只保留与投诉的接壤条款（离开是有效结果、投诉数据不进召回，§5.1/§7）。
4. **两套时钟不混写**：投诉处理时限 SLA（本篇 §4.3，CR-14，P0）与值守响应时限（27 篇，检查单 #23，P1 定量中）是两个独立承诺面；合并表述会让任一方的「未定量」被另一方的候选值冒充。
5. **Rupture/Repair 词条的分层使用**：关系域词条（CONTEXT.md）在对话内由 09 篇承载（角色怎么修复），在运营侧由本篇承载（组织怎么修复）；两处共用同一判据——无行为改变的修复不算修复——避免「角色道歉、组织结案」的双轨空转。
6. **F5/F6 的规划依赖如实标注**：安抚腿（CR-02）、危机干预管线（CR-03）、未成年人模式（CR-04）均规划中 P0 且部分依赖 ⚖️B14/B15 裁决；本篇的 F5/F6 处理要点在对应能力建成前只有「停止＋转人工＋引导现实资源」的守势动作，不假装有产品内安抚链路。
