## 1. 值班体系

### 1.1 两种值守

| 值守 | 触发条件 | 工具面 | 退出条件 |
| --- | --- | --- | --- |
| **赛事值守** | 一场比赛开放运行的全窗口（开球前→终场后收束） | 运营台实战导演页（26 篇 §3）+ 直播监听 + 概览九格 + 观测页 | 终场后收束完成：事实状态归位、未决项登记、本场主动性默认关闭 |
| **日常值守** | 非比赛窗口 | 概览九格 + 观测页 + 钉钉告警通道 | ——（常态在岗，告警驱动） |

- **ONC-01 值班即具名**：值守以具名运营员身份进行（26 篇 §2 账号体系），不设共享账号；每笔处置动作经 withScope 鉴权与 appendAudit 实名留痕——「谁在值班」可以从审计表还原，不靠排班表回忆。
- **ONC-02 角色分权即值守分权**：现网值守角色两类——director（全量操作）与 auditor（只读监督）（ADR-0008）。v2 61 章设计的五类值守职责（赛事/事实/运行/用户安全/用户沟通负责人）与升级联系人、备份联系人制度**规划中（未实现，P1）**——当前规模下一人可兼任多项，但「谁都以为别人会处理」不允许成为默认状态：每场开放比赛须在值守记录里写明当班人。
- **ONC-03 工具面最小集**：值守不登机器拼凑现状——概览九格（26 篇 §1.2）、观测页双 kiosk（6 面板 + 告警列表）、直播监听（/ws/ops 九类行为流）、钉钉+webhook 告警双通道构成完整值守面；任何需要 SSH 上机才能回答的「系统现在怎么样」属观测面缺口，登记待建而非默许。

### 1.2 值守节拍

| 节拍 | 动作 |
| --- | --- |
| 常态（日常） | 告警驱动：钉钉 page 级告警即查即处置（§3）；无告警时无周期性人工巡检的强制项 |
| 赛中常规节拍 | 每 15 分钟扫一遍概览九格与观测面板（延迟/打断率/投递分布/微反应），异常记录进值守记录 |
| 关键事件节拍 | 进球、点球、红牌、VAR 长判、中断、终场——短窗口内确认：事实是否已确认（14 篇双通道）、播报是否正常、是否需要接管（26 篇 §3.4） |

- **ONC-04 值守记录**：异常与处置随发生随记，最小字段五项——时间、比赛/窗口、现象、已做动作、当前判断（与复盘模板 §6 的时间线字段对齐，避免事后重建记忆）。值守记录落在值班人手边（现行例：演练实录的「时间线」表），不强制系统承载。

## 2. S0-S3 分级响应

### 2.1 统一刻度

全库统一事故分级刻度为 **S0=最严重 → S3=最轻**（2026-06 裁决 B8 收口；v2 资料中 S3=最重的反义刻度作废）。刻度定义与判级示例全表归 21 篇 §4，值守侧摘要如下：

| 刻度 | 定义 | 响应预期 | 升级路径（现网形态） |
| --- | --- | --- | --- |
| **S0** | 服务整体不可用 / 用户数据泄露 / 事实纪律系统性失效 | 即刻响应，全力量处置，事后复盘 | 当班人立即处置并同步全体；数据泄露类同时冻结相关能力（22 篇删除屏障联动）；复盘升级为全文档（§6） |
| **S1** | 核心体验严重受损（语音链路不可用、账本确认停摆） | 值班即时介入 | 当班人按 §4 runbook 处置；处置不动即升级至工程负责人并冻结非必要变更 |
| **S2** | 单能力降级（TTS 单腿故障、告警噪声、面板缺数） | 当班处理，可延至次日 | 进工单池标注 S2；连续复发两次升 S1 重判 |
| **S3** | 观感缺陷（文案旧值、非阻塞 UI 瑕疵） | 进工单池按优先级消化 | 无升级路径；重复出现（≥3 次）提级复盘结构性缺口 |

- **与 P0-P3 的映射**：工单优先级 P0-P3 与事故等级 S0-S3 是两套刻度——P0≈对应 S0/S1 级事故或合规硬项的工单。全套规范出现的「P0/P1」均指工单优先级（21 篇 §4）。
- **定级原则**：以影响面与纪律面为准，不以组件为准——一个用户的隐私泄露、危机响应错误或退出路径失败与宕机同级，不由声量、付费身份或传播度降级。

### 2.2 响应时限（如实：未制度化）

- **ONC-21 现网无定量时限**：上表「响应预期」为定性描述；定量时限（S0 即刻、S1 ≤15min 量级为候选值）**规划中（未实现，P1）**，挂 PRD 上线就绪检查单第 23 项——定量前任何材料不得宣称已有响应时限 SLA。
- **ONC-22 已验证的时延事实**（来自 2026-06-03 演练，非承诺）：告警从故障注入到 firing 实收约 20 分钟（含 15m 统计窗 + 5m 持有期 + 评估周期，机制值）；resolved 通知在数据恢复后约 6 分钟内到达（group_interval 5m 内）——这是「告警链路多快叫到人」的实测基线，不是处置时限承诺。

### 2.3 升级与恢复的两条硬规则

- **ONC-23 保守优先**：任何人可提出降级/更保守模式建议；恢复更丰富模式需要人工确认降级原因已消失；负责人意见冲突时取更保守一侧，直到事实澄清。紧急收紧可以先行，紧急放宽永远需要说明。
- **ONC-24 风险事件也是生产事件**：错误记忆被提起、用户关闭主动性后仍被触达、角色在脆弱表达中越界——按 S0/S1 处置（判级看纪律面），处置顺序固定为：先停止相关能力 → 保护证据（trace/账本）→ 评估范围 → 修复 → 复盘（§6）。风险事件的运营操作面（确认/更正/接管）归 26 篇 §3-§4。

### 2.4 对用户的沟通（最小口径）

| 情况 | 必须说明 | 不应说 |
| --- | --- | --- |
| 赛况待确认 | 当前只显示已确认事件，正在核验 | 「肯定马上恢复」；用猜测填空 |
| 语音降级 | 本场切至文字陪看（text_fallback），静音/结束仍可用 | 把语音失败说成角色不想说话 |
| 主动性暂停 | 为避免误触达，已暂停本场主动回应 | 暗示用户设置有错 |
| 错误事实已更正 | 什么状态变了、现在以什么为准 | 「系统偶尔会错」式推责 |

说明文案随发布统一（13 篇 copy sheet）；本表是值守撰写时的内容纪律，不是界面文案出处。**用户侧公告文案唯一出处＝13 篇（生命周期增补批次由 13 篇承接）**，本篇只立值守沟通纪律，不落公告模板。面向用户的状态页**规划中（未实现，P1）**。

## 3. 告警处置手册

告警组 qiuqiu-operations（评估周期 1m），4 条规则、判断值 2026-06-01 收紧后口径，通知走钉钉（contact point 类型串 `dingding`）+ 通用 webhook 双集成、恢复通知开（口径与机制归 21 篇 §3）。每条 severity=page。

### 3.1 规则①：语音延迟 P95 超阈（> 3000ms 持续 15m）

| 项 | 内容 |
| --- | --- |
| 触发含义 | `agent_traces.latency_ms` 15m 窗 P95 连续 5m 超 3000ms——ASR/LLM/TTS 全链口径，语音链路整体变慢是系统性信号而非单点抖动 |
| 首查 | ① 观测页面板②（延迟分段均值，attach 键）定位慢在哪段（ASR/LLM/TTS）；② 直播监听看 turn_planned latencyMs 分布；③ 对照供应商错误告警（规则③）是否同燃 |
| 处置 | 单段慢→按 20 篇 §6 对应节点排查（供应商尖峰/超时/熔断）；TTS 本地腿问题→运营台语音供给三态卡切 cloud（26 篇 §6，本地腿不健康会被 409 拒切——那本身就是诊断信息）；全链慢→查 PG 与主机资源（§4.1/4.2） |
| 升级 | 处置 30m 不回落（两条 firing 通知未恢复）→按 S1 升级工程负责人；已造成事实播报大面积迟滞→按影响面重判 S0/S1 |

### 3.2 规则①b：首响 P95 超阈（tts_first_audio > 1800ms 持续 15m）

| 项 | 内容 |
| --- | --- |
| 触发含义 | 句粒度路径首帧可播时延超阈——**休眠保留规则**：锚点随句粒度投递拆除（2026-06-01 韵律盲测裁决，整段投递为首响 3-7s 现役形态）不再产生新数据；规则保留供句粒度方案重开时复用 |
| 首查 | 该告警若燃，先核对是否有人在未对齐裁决的情况下重开了句粒度投递——这是口径漂移信号，不是性能告警 |
| 处置 | 确认口径漂移后回滚改动；规则本身不删（保留锚点是对裁决史的忠实） |
| 升级 | 不适用（无现网数据面）；规则激活与否的裁决走 37 篇 |

### 3.3 规则②：LLM/TTS/ASR 供应商错误率超阈（30m 错误 > 3 条）

| 项 | 内容 |
| --- | --- |
| 触发含义 | `agent_traces.error` 非空计数 30m 窗超 3 条——熔断器开合的**落库代理**（熔断阈值=四 client 各连续 3 次失败开启；熔断状态本身是进程内不可查指标），含义是供应商调用持续失败、熔断开启的前兆或伴随面 |
| 首查 | ① trace 按 error 字段筛出失败调用，归到 llm/tts/asr/ambient 哪个 client；② 分段面板确认对应段延迟是否同抬；③ 单一供应商→查其配额/密钥/区域状态 |
| 处置 | 熔断已自动回退确定性话术（L3 降级，用户收到的是已确认信息不是编造文本）——值班动作是消除根因而非重启熔断；TTS 持续失败→供给三态切腿（§3.1）；ASR 持续失败→文字路径兜底已自动，等供应商恢复；LLM 失败伴随护栏拦截→查 22 篇 trace 拒绝原因区分「供应商故障」与「护栏正常拦截误报」 |
| 升级 | 错误持续 30m+ 且降级话术已影响核心体验→S1；确认为供应商区域级故障→记录故障窗口供复盘与供应商沟通 |

### 3.4 规则④：api-sports poller 停摆（24h 窗内 10m 无 provider 事件）

| 项 | 内容 |
| --- | --- |
| 触发含义 | 近 24h 有过 api-sports 事件（=有比赛数据流）但已 600s 无新 provider 事件——freshness 超窗的**落库代理**（原生 fresh/degraded/offline 标签是内存态不可查）；noDataState=OK，无比赛时不停摆不误报 |
| 首查 | ① 比赛层设置页看数据源状态（fresh/offline 标签与存活判定）；② 确认是否真有比赛进行中（无比赛时的停摆是查询空窗，不燃）；③ 查 poller 进程与 api-sports 密钥配额 |
| 处置 | 短暂断流→依赖停摆固定话术 + `schedule_unavailable`（L5 降级，用户端已可见「等一下确认」）自动兜底；持续停摆→切换数据源或人工接管（takeover 同时暂停自动播报），赛况播报降级为运营人工侧（26 篇 §4） |
| 升级 | 停摆跨入关键事件窗口（进球/VAR 时段）且人工侧无人补位→按 S1 处置——事实链断供在比赛窗口内是核心体验受损 |

### 3.5 两条全局注记

- **不规则化**：/ws/ops 饱和丢弃有意不规则化（内存计数无落库面）——不存在第 5 条告警；宣称「丢弃率有告警」违规（21 篇 §3.1）。
- **文案残差**：rules.yml 的 title/summary 文案仍为旧值（5000/2500），判断值已是 3000/1800——读告警以判断值为准，文案修正为工程侧待办（S3 工单）。

## 4. 常见故障 runbook

逐故障「症状→检查→处置」。语音链路逐节点（VAD/ASR/断句/生成/合成/播放）的排查归 20 篇 §6；本节是服务级故障面。

### 4.1 后端起不来

| 项 | 内容 |
| --- | --- |
| 症状 | backend 容器/进程启动即退；`/health` 不通；日志见迁移报错或缺配置报错 |
| 检查 | ① 迁移链：日志若卡 `CREATE EXTENSION vector`（迁移 001）——PG 无 pgvector 扩展，**演示机 PG16 portable 已知约束**（23 篇 NFR-REL-003），compose 形态应使用 `pgvector/pgvector:pg16` 镜像，portable 场景可用 `scripts/install-pgvector-windows.ps1` 注入；② 配置：存在密码账户时 `QIUQIU_JWT_SECRET` 必配，缺配置启动即拒；③ 端口：8080 被占（23 篇 ⚖️B11：8080/18080 断裂为已知缺陷，按部署篇真实路径核对） |
| 处置 | pgvector 缺失→换镜像或注入扩展后重启；缺配置→补齐环境变量再起；起不来期间用户面自然不可用，无需降级动作（服务单元整体缺席不存在「部分降级」） |

### 4.2 PG 连接故障

| 项 | 内容 |
| --- | --- |
| 症状 | 后端已起但写路径 5xx；Grafana 面板 db query error；概览记忆健康格 degraded |
| 检查 | ① `pg_isready -U qiuqiu -d qiuqiu`（compose healthcheck 同款）；② postgres 容器状态与 `postgres_data` 卷挂载（唯一全量事实源）；③ Grafana 侧单独报错→看 §4.6 Grafana 数据源注记（可能只是 Grafana 先于 PG 起的断连持有） |
| 处置 | 短暂断连→恢复后账本 append-only 语义自动续写，无补写动作；卷损坏→走备份恢复手册（`pg_restore --clean`，cron 每日 03:30 `pg_dump -Fc`），恢复后按 21 篇 §2.9 验证账本一致性；确认数据丢失→按 S0 处置并复盘 |
| 升级 | 影响 user 数据完整性判 S0；仅观测面断连（账本写正常）判 S2 |

### 4.3 TTS 供给故障

| 项 | 内容 |
| --- | --- |
| 症状 | 供应商错误告警（§3.3）伴随 TTS 段；用户端 `voice_status` 异常通知；概览语音供给三态卡健康态翻转 |
| 检查 | ① 三态卡当前模式与健康快照（回退计数）；② local_first 下本地腿（CosyVoice3）健康门状态——`PATCH tts-supply` 若 409 带原因，即本地腿未过门；③ 分段面板确认 TTS 段延迟 |
| 处置 | 云腿故障→切 local（须健康门过）；本地腿故障→切回 cloud；两腿皆损→文字路径兜底自动生效（L2/L4 降级链，20/21 篇），值班动作转为用户沟通（§2.4）与供应商跟进；重启后供给模式持久化保持，无需每次开机重切 |
| 升级 | 双腿皆损持续→S1（核心体验受损）；单腿故障→S2 |

### 4.4 smart-turn sidecar 挂

| 项 | 内容 |
| --- | --- |
| 症状 | 断句变钝（用户说完等 1400ms 才回应、提前问变少）；sidecar 容器退出或 /healthz 不通（端口 8091，profile `turn`，默认不随 compose 起） |
| 检查 | ① `docker compose --profile turn` 服务状态与 `/healthz`；② 后端配置 `QIUQIU_TURN_SIDECAR_URL` 与 `QIUQIU_TURN_SIDECAR_TIMEOUT_MS`（默认 500ms 预算）；③ LiveKit EOU 模型载入日志（v0.4.1-intl，396MB q8） |
| 处置 | sidecar 缺席/超时不是事故——三插槽判定链自动回落 VAD 静默 1400ms / 提前问 600ms（L1 降级，用户无感中断）；处置动作是拉起 sidecar（显式 `--profile turn up -d`）或维持降级运行并登记——降级形态可接受，静默不知情不可接受（21 篇 REL-30：降级必须留痕可见） |
| 升级 | 不判级（有完整 L1 退路）；长期不拉起→登记容量/资源决策 |

### 4.5 WS 断连风暴

| 项 | 内容 |
| --- | --- |
| 症状 | 直播监听页重连计数抬升；客户端成批进入 reconnecting→failed；观测面板投递七态中 client_late/failed 占比抬升 |
| 检查 | ① 后端 ws 层日志：每 IP 连接上限（≤5 条，超出 429）触发记录——若命中，是客户端侧重试风暴或代理层行为；② 服务端心跳（30s ping）与读超时（60s）；③ 单实例承载与主机资源；④ 客户端重连上限 ≤5 次（退避 1-8s）——failed 态用户界面明示，重试权交还用户，属设计内收敛 |
| 处置 | 服务端过载→按 §4.1/4.2 排查根因；代理/负载层断连→核对 Origin 校验与子协议鉴权（`qiuqiu-auth.<base64url>`）配置；风暴平息后依赖服务端恢复机制自愈：未送达回合按 deliveryKey 重放（resolved 态才补）、观察跟进重排、断线期语音补发队列（≤4 条）串行出队——值班确认无重复呈现与旧内容补播即可，无需人工补投 |
| 升级 | 大面积无法恢复连接→S1；伴随投递纪律破口（重复呈现/旧内容补播）→按事实纪律重判 S0 并复盘（四不变量「旧内容不补播」被撞，§5.2） |

### 4.6 观测栈两则（值班环境注意，演练实录沉淀）

- **Grafana 先于 PG 启动**：Grafana 进程起于 PG 就绪之前会持有断连 datasource（评估报 db query error）——重启 Grafana 恢复，不是数据丢失。
- **Windows provisioning 路径**：git bash 下 `GRAFANA_DASHBOARDS_DIR` 传 `E:\` 反斜杠路径会被吃（dashboard provisioning 报路径错；alerting provisioning 走默认路径不受影响）——路径加引号或用正斜杠。

## 5. 值班演练制度

### 5.1 已验证基线：2026-06-03 全链演练（实录摘要）

原始档 `docs/design/oncall-drill-20261003.md`（库内 design 档）。这是告警链路首次以「真故障形态」全链闭合，作为演练制度的已验证基线：

| 时刻（本地） | 事件 |
| --- | --- |
| 03:59 | 故障注入：20 条「云尖峰形态」trace（latency_ms 4000-7300ms，散布近 10 分钟；形态取自 05-30 实测 MiMo 7.3s 尖峰），P95=6610ms，超阈（3000ms）120% |
| 04:19 | capture 实收 firing：webhook `[FIRING:1] 语音延迟 P95 超阈（> 3000ms 持续 15m）`，severity=page；钉钉通道同发（URL 占位，生产替换后同管线） |
| 04:22 | 第二次 firing 通知（group_interval 重发——持续未恢复的重复提醒符合预期） |
| 04:24 | 值班响应：清故障数据，P95 归零 |
| ~04:30 | resolved 通知实收（capture 第 3 条，status=resolved；数据清理后约 6 分钟，group_interval 5m 内） |

**验证结论**：规则评估（PG 直查 P95）✓；持有期（for 5m，注入后约 15-19 分钟燃，含评估+持有周期）✓；通知双通道 ✓；持续故障重复通知 ✓；阈值灵敏度成立——尖峰 5 分钟内必燃，正常负载（两位数 ms）零误报。
**环境约束（如实）**：演示机 PG16 portable 无 pgvector→后端全栈起不来，演练不跑后端，改走「Grafana 只读直查 PG 最小表集（agent_traces/match_events）」完成——演练路径对环境约束的绕行本身是演练产物（已沉淀进 §4.1 处置）。
**演练后动作**：故障数据清理（drill-* 20 条 DELETE，实证 P95 归零）；resolved 到达确认；本记录落档。

### 5.2 演练方法论（每次演练的强制清单）

**前置清单九件事——九项没写全不开始**：① 目标不变量（这次要证明什么不会破）；② 范围（注入哪个故障、波及哪些服务）；③ 负责人（谁按停止按钮）；④ 开始条件（基线健康、测试账号就位）；⑤ 停止条件（§5.3）；⑥ 自动收缩（预期系统自己先做什么）；⑦ 用户可见影响（测试视角下界面应变成什么样）；⑧ 观察字段（看哪些信号判定成败）；⑨ 回退步骤与结果复核。演练最贵的失败不是注入失败，而是注入成功了却没人说清「刚才到底证明了什么」。

**四条目标不变量**（演练拿真实故障去撞的底线；与现网机制的对应表归 21 篇 §3.3）：

| 不变量 | 现网上锁的机制 |
| --- | --- |
| 用户控制不失效 | 控制指令评测、设置即时生效 |
| 事实不倒退 | deliveryKey/revision 保序、账本 append-only、时钟 409 自愈 |
| 删除不复活 | privacy_tombstones 拒绝迟到写入（22 篇） |
| 旧内容不补播 | deliveryKey 三道去重、补发队列 4 条上限、过期不补 |

**停止条件**（原文沿用，一字未改）：若演练意外影响真实用户、不能确认数据隔离、发现控制失效、出现无法解释的私人内容、无法停止自动呈现或未知范围的数据暴露，应立即停止注入、进入更保守服务级别并启动事件响应。不要为了「收集完整实验数据」继续让伤害扩大。

**收尾三产物**：证据（当时的信号与用户可见状态）、缺口（哪个不变量靠运气没破）、复演条件（修完缺口拿同一故障再撞一次）——三者缺一，演练只算消耗了一次故障。

### 5.3 演练频率与范围（如实：未制度化）

- **ONC-51 常态化节奏规划中**：演练频率、覆盖矩阵（§4 各 runbook 场景的演练化）与值班轮换演练**规划中（未实现，P2）**（21 篇同源声明）——现网制度是「有演练实录可循 + 方法论在案」，不是「定期演练在跑」。
- **ONC-52 不变量的日常化**：多数不变量已不需要等演练日——它们活在测试资产里每天被撞一次（client-delivery-dedupe / connection-check / fact-lifecycle / operator-control 等，24 篇索引）；演练日留给测试难以模拟的复合故障（依赖恢复后有无旧内容复活、删除与写入并发次序、整体收缩次序）。
- **ONC-53 演练数据隔离**：演示/测试比赛白名单可一键重置（`isDemoMatchID` 校验）——演练用「可爆炸现场」与真实用户数据物理隔离；注入数据用 drill-* 命名并在收尾清除。

**演练覆盖候选矩阵**（制度化时的第一批场景，规划中 P2；每格是「拿哪个故障撞哪条不变量」的预登记，不是已排期计划）：

| 候选场景 | 对应 runbook | 主撞不变量 | 已有日常化覆盖 |
| --- | --- | --- | --- |
| 语音延迟尖峰（复刻 06-03 形态） | §3.1 | ——（值守时延基线复校） | latency-test 发布闸门 |
| PG 断连→恢复 | §4.2 | 事实不倒退 | connection-check / runtime-e2e |
| TTS 单腿故障切换 | §4.3 | 用户控制不失效 | ttssupply 包单测（门控面） |

| WS 断连风暴 | §4.5 | 旧内容不补播 | client-delivery-dedupe |
| 演练注入数据与真实数据并存 | §5.3 ONC-53 | 删除不复活 / 数据隔离 | docker-restart-e2e |

## 6. 复盘制度

- **ONC-61 触发条件**：全部 S0/S1 事故、重复出现（≥3 次）的 S2/S3、每次演练——复盘是强制的；S2 单次事件可只做值守记录附注。
- **ONC-62 复盘模板**（最小五段）：① 时间线（发现→定级→处置→恢复，对齐告警与 trace 时间戳）；② 影响面（用户可见影响、纪律面影响——事实/隐私/控制哪条被碰）；③ 根因与撞线分析（四不变量哪条被撞或靠运气没破）；④ 行动项（结构机制优先于一次性补丁——缺口要变成像 tombstone、去重键那样的常驻物）；⑤ 复演条件（修完后拿同一故障再撞一次的安排）。
- **ONC-63 语气纪律**：复盘面向学习而非归罪——只有团队能报告坏消息时，值守策略才会在真正的压力下工作。看似低严重度但重复出现的问题优先级更高：重复率暴露的是结构性缺口。
- **ONC-64 归档指针**：演练与事故复盘记录落仓库 `docs/design/`（现行例：`docs/design/oncall-drill-20261003.md`）；历史复盘、库外文档（演进计划/课程树等）的归档地图与处置状态归 39 篇；复盘产出的行为变更走 openspec change 并回写受影响篇目（00 篇 §6.7 咬合条款）。
- **ONC-65 blameless 四原则（2026-06-09 生命周期增补）**：复盘按四原则执行——①**对系统不对人**：复盘对象是机制缺口与流程，不是当班人；②**全时间线重建**：先以告警/trace/审计时间戳复原完整时间线再谈判断，不凭事后记忆定叙事（与 ONC-04 值守记录字段对齐）；③**根因与责备分离**：「为什么会发生」与「谁做的」分开回答，前者是复盘产出，后者不进复盘记录（ONC-63 语气纪律的执行面）；④**行动项追踪到关闭**：action item 逐条登记并追踪至关闭，**action 完成率 ≥80% 为 42 篇健康指标之一**；复盘发现的缺陷与结构缺口 action 产出同步进 42 篇 badcase 登记表（BC-NNN），不因来源是复盘而另立台账。

## 8. 设计说明

1. **与迁移源（v2 61 章）的差异——已建成/建设中边界整体前移**：v2 61 章「已建成」一节只有六项机制（自愈编排、备份、评测门禁、熔断、导播台概览、接管开关），值守组织/分级响应/状态页/压测/告警全部在「建设中」；至基线时点，**告警体系（4 规则+双通道）、运营台九格值守面、TTS 三态切换、值班演练全链闭环**已从「建设中」移入「已建成」，本篇如实前移。v2 章内「人工接管按干预级别分三档」的现网语气按 F1 处置废除（规划中，⚖️B4）；分级刻度由 v2 的 P0-P3 反义口径统一为 S0=最重（B8）。
2. **为什么时限不写数字**：单实例演示形态下写「S1≤15min」是把排班、升级链、复核人都不存在的前提下的一个数字当承诺——它会在第一次真实比赛日失守并连带赔上整套分级制度的信用。现网写「定性响应预期+实测时延事实（§2.2）」，定量绑在上线就绪检查单第 23 项上，是「现网为真」原则在值守篇的直接体现。
3. **告警手册为什么写「落库代理」**：四条告警中两条是代理（agent_traces.error 代熔断、provider 断流代 freshness）——手册必须把代理语义讲给值班者（「这是熔断的前兆面」），否则处置会去找不存在的熔断指标。宁告警语义粗一点，不为凑数造假表（21 篇设计说明 5 同源）。
4. **演练实录单独成节的理由**：2026-06-03 演练是本制度唯一的实证资产——它证明了链路通、量出了时延基线、暴露了两条环境注意（§4.6）并直接生成了 §4.1 的处置路径。制度篇引用实录而非转述，是为了让下一次演练有可对拍的基线：频率未制度化之前，「上次怎么跑的」就是制度本身。
5. **复盘制度为何最小化**：现网无复盘例会与归档系统，强行立法「24 小时内出复盘报告」会复刻 v2 病根（纸面制度无承载）。本篇只锁定触发条件、五段模板、语气纪律与归档指针四件可立即执行的事，例会与跨团队升级链随值守组织制度化（P1）一并立项。
6. **与 21 篇的切分**：21 篇是「系统指标与机制的可靠性立法」（SLO、阈值、机制参数、刻度定义），本篇是「人拿到信息后的动作规范」（值守、处置、升级、演练、复盘）。同一条告警在 21 篇是判断值，在本篇是处置手册——两篇共用同一组数字，任何一边改阈值必须同步另一边（修订纪律）。
