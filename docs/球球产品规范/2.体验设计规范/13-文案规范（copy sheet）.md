> 本篇基线：2026-06-07 仓库 a7e5100。

**本篇定位**：球球全部用户可见文案的唯一登记出处——客户端每一句 UI 字符串、服务端每一条确定性话术，在本篇有且只有一行登记：场景 ID、位置（页面·组件）、现网文案（逐字）、状态、语言。代码改动先改本篇登记；各篇规范引用文案一律以本篇为准。规则 ID 前缀 COPY，引用格式「13/COPY-NN」。

**迁移来源**：新立篇（v2 档案无 copy sheet，文案散落在代码与各章叙事中；00 篇 §1.4「文案唯一出处」、08 篇 MEX-21f、06 篇分工表、12 篇 SET-07 均已指向本篇）。登记内容以 2026-06-07 代码全量扫描为源，不照录旧章文案叙事。

## 1. 登记规范与语气基线

### 1.1 登记规则

**COPY-00 唯一出处**。任何用户可见文案的新增、修改，先改本篇登记再改代码；本篇登记与代码字符串不一致即为缺陷（修码或修登记，二者必居其一并留痕）。规范文档引用现网文案时须与登记逐字一致。

**COPY-01 登记字段**。每条登记含五字段：场景 ID（CPY-域-NN）／位置（页面·组件，以代码文件名指认）／现网文案（逐字，含标点、省略号、空格；`{x}` 为运行时插值占位）／状态（现行＝与代码一致在用；待改＝在用但已登记失准，挂 D-x 编号；待建＝现网无此文案）／语言（现网全部 zh-CN，语言列为 i18n 扩展位，现无多语言管线）。

**COPY-02 语气基线：像懂球的朋友**。执行口径四条：① 口语、短句、结果导向（「关闭后仍保留字幕和文字对话」，不写「该功能关闭后系统将停用语音输出通道」）；② 称呼「你」，不用服务腔与治疗腔（「需要我帮你」「你的感受很重要」类模板禁用，01/EXP-G1 第 17~20 条）；③ 不表演情绪、不加挽留与道歉包装（退出/删除/关声音的反馈只描述结果）；④ 内部机制词不出现在用户面（「导播台」「后台」「记忆库」「历史记录」类，01/EXP-G1 第 24~30 条）。生成面禁词全表见 01 篇 5.1.1，对 UI 文案同效——UI 文案不经过 guard，靠本篇审批流（§12）前置把关。

**COPY-03 时态与三态纪律**。现网文案现在时；待建文案在 §11 单独登记，不混入现行表；任何文案不得出现「即将上线」「基本支持」类自造状态词（00 篇 §7.4）。

**COPY-04 范围界定**。登记范围＝C 端用户可见字符串（client/lib 全量）+ 服务端直达用户的确定性话术（intent_handlers/proactive/agent 单源）；运营台字符串面向运营员，按另册口径登记（§9）；日志、调试串、`--dart-define` 配置键不登记；Live2D 舞台 iframe 内部文案随 11/20 篇。

## 12. 新文案审批流

**COPY-10 流程七步（新增/修订用户可见文案必经）**：

1. **提案**：登记行草案（场景 ID、位置、文案、修改理由）；涉话术族的一次提案一组变体。
2. **红线校验**：逐字过 01/EXP-G1 词表 30 条（服务腔/治疗腔/关系越界/内部机制泄漏四类）、RED-04 挽留语义（含隐含表达）、00 篇 §7.2 处置表（「安静档」「不打扰是陪伴」类遗产措辞不复活）——命中即改。
3. **双形态校对**：涉身份/账号/找回的文案按 identifier 双形态（邮箱或用户名）校对，不得写死单形态（D-2 教训条款化）。
4. **反向理解检验**：按 12/SET-22——只给名称与说明，用户说得清「会做什么/不做什么/如何关闭/拒绝是否损失」才放行。
5. **评测锁定**：控制、边界、事实类话术挂确定性断言（照 baseline.control-less-talk 模式）；纯 UI 标签随一致性抽查（§13）。
6. **登记回写**：本篇登记行更新（含修订记录），代码字符串与登记逐字一致后合入。
7. **词汇自查**：对 00 篇 §7.2 左列词 grep 全篇命中清零。

**COPY-11 紧急修订**。线上文案缺陷（失准、误导、越线）可先改代码止血，本篇登记 24 小时内回写；回写前该文案处于「登记-代码不一致」缺陷态，按缺陷跟踪。

## 13. 验收

**验收总口径**：① 一致性——登记行与代码字符串逐字一致；② 红线——UI 文案零命中 EXP-G1 词表与挽留语义；③ 锁定——CPY-CTRL-02 逐字断言常绿；④ 待改项——D-1/D-2 修复时三处（登记/代码/评测）同批更新。

**文案-代码一致性抽查法**：

1. 按页面抽样：每登记域（SET/LOGIN/DOCK/MATCH/MEM/CTRL/GRT）抽 ≥3 行，新页面/新话术族全查；
2. 比对：以登记文案（去插值占位）在对应代码文件 grep，要求逐字命中（含标点与省略号）；
3. 反向扫描：在 client/lib 扫描登记外的用户新增字符串（`Text(`、`label:`、`hintText:`、`title:`、`message:` 及服务端话术常量），出现未登记行即缺陷；
4. 双向不一致处置：代码为准则回改登记并记修订；登记为准则改代码；两者都不得静默。

## 15. 设计说明（写法依据，非需求条款）

1. **新立篇的治理动机**。审计确认的病根之一是「文案散落在代码与各章叙事里，改一处漏两处」：08 篇引用的确认框文案、12 篇引用的节副标题、旧 35 章的话术承诺各自为政。v3 以「唯一出处」治理：所有指针（01 篇 §1.4、08/MEX-21f、06 篇分工表、12/SET-07）收敛到本篇，登记-代码一致性可抽查、可断言。
2. **登记源与颗粒度**。登记以 2026-06-07 代码全量扫描为源（client/lib 的 screens/services/widgets 与 backend/internal 的确定性话术单源），颗粒度到「一处用户可见出现」；同文案多处复用（如「重试」「取消」）合并登记并在位置列注明组件。开发态配置缺失文案（CPY-MATCH-11）登记但不入验收抽查——它不面向最终用户。
3. **确定性话术与生成文案的分界**。本篇只登记确定性字符串（代码常量、映射表、模板）；LLM 生成面的语气纪律不靠登记、靠 01 篇护栏与 realize 系统提示词执法——两套机制的分界即「能 grep 的入本篇，不能 grep 的入 01 篇」。
4. **D-1 双轨的来历**。「安静/刚好/热闹」是现网 UI 事实，「低频/标准/热闹」是 v3 叙述名统一（00 篇 §7.3）；本篇把双轨落为 D-1 待改项而非立即改码——改文案涉及评测断言与三篇括号注联动，须走审批流一次改齐，避免第三次漂移。
5. **与旧 35 章的关系**。旧 35 章 §10.2「设置文案的反向理解检验」表收编为 12/SET-22 与 §12 第 4 步；旧章两句话术（「把声量交给你」等）按现网原样登记为现行；旧章无登记体例，本篇为其文案实义的唯一后继载体。
6. **语气基线的出处**。「像懂球的朋友」是宪法人格条款（口语化、短、松弛、不端着）与 00 篇词汇纪律的执行摘要；§1.2 四条口径是把人格语译成文案审校可操作的检查项，不引入新人格主张。
