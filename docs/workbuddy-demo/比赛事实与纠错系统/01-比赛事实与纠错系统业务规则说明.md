# 比赛事实与纠错系统业务规则说明

> 文档类型：产品业务规则 / Explanation Input  
> 版本：v1.0  
> 产品负责人（PM）：林若安  
> 内部编制日期：2026-04-25  
> 时间口径：所有内部项目日期均相对实际项目节点前移 3 个月；外部赛事和政策日期不平移。  
> 适用范围：球球用户端、企业导播台、比赛数据源接入、Companion Agent、事实账本与客户端投递。

## 1. 文档目的

本文定义“比赛事实与纠错系统”的业务目标、事实边界、角色权限、判断规则和验收口径。它回答的是：什么可以成为公共比赛事实，什么只能保留为用户观察，什么情况下必须停止确定性表达，以及错误事实如何被修订、撤回和调和。

本文是功能设计稿的上游输入，不描述具体页面布局和代码实现。字段与接口以《03-比赛事实领域模型数据字典与接口契约》为准，状态流转以《02-比赛事实与纠错系统场景流程与状态规范》为准。

## 2. 系统定位

### 2.1 产品问题

足球直播场景同时存在四种不稳定性：

1. 用户看到的直播画面可能比结构化数据快 5-60 秒。
2. 人工导播可能误点、重复点击或晚录事件。
3. 多个数据源可能对球队、球员、比分或 VAR 结论给出冲突信息。
4. 已经发布的事实可能在 VAR、赛后校正或人工复核后被撤回。

如果系统把第一条输入直接当成最终事实，公共比分会被污染；如果系统永远等到完全确定再回应，球球又会显得“不在现场”。因此本系统把“及时回应”和“事实确认”拆成两条链路。

### 2.2 系统目标

| 目标编号 | 目标 | 用户结果 | 验收信号 |
|---|---|---|---|
| G-01 | 公共事实唯一可信 | 所有用户看到同一份可解释比分和事件 | 公共读路径只消费有效事实投影 |
| G-02 | 用户领先现场可被自然处理 | 球球先接情绪，不武断否定也不污染比分 | 未核验观察只向原用户异步跟进 |
| G-03 | 错误事实可逆 | 纠正、撤回后比分、字幕、音频和动作同步恢复 | 被撤回事实不再参与公共投影和投递 |
| G-04 | 多源冲突可审计 | 运营能看到候选、冲突关系和最终选择 | 调和记录包含事实、原因、操作人和时间 |
| G-05 | 导播写操作可重试 | 双击或网络重试不产生重复事件 | 同一幂等键重放原结果 |
| G-06 | Agent 不越权 | 模型只能读取事实和表达，不可改写事实 | 用户 Agent 工具集中不存在事实写工具 |

### 2.3 非目标

| 编号 | 非目标 | 原因 |
|---|---|---|
| NG-01 | 让 LLM 自由判断真实比分 | 语言模型无法提供可重放、可撤销和可审计的一致性 |
| NG-02 | 用向量检索回答比分、进球和 VAR 结论 | 相似检索不是硬事实查询 |
| NG-03 | 把用户口述直接写入公共比赛 | 用户画面延迟、误听和玩笑会污染所有用户 |
| NG-04 | 发生冲突时自动选择“置信度最高”的事实 | 置信度不能代替业务证据和人工责任 |
| NG-05 | 删除历史修订以保持数据整洁 | 删除会破坏审计、回放和事故复盘 |
| NG-06 | 本文覆盖赛程搜索、提醒、关系记忆和语音模型设计 | 这些能力只作为事实系统的调用方或输入方出现 |

## 3. 核心概念与真相分层

### 3.1 三层真相模型

| 层级 | 名称 | 典型对象 | 可见范围 | 能否改变公共比分 |
|---|---|---|---|---|
| L2 | 用户观察 | `PendingObservation` | 单个用户、单场比赛 | 否 |
| L1 | 候选事实 | `provisional` / `conflict` 事实修订 | 导播审计视图 | 否 |
| L0 | 公开事实 | `confirmed` / `reconciled` 且 `active/public` 的事实 | 所有用户与 Agent | 是，通过账本重放 |

三层真相不是同一对象的不同 UI 标签，而是权限、生命周期和影响范围不同的业务实体。任何低层级内容都不能直接覆盖高层级事实。

### 3.2 事实、事件、修订和投影

| 术语 | 定义 | 业务含义 |
|---|---|---|
| 事实 Fact | 对一次比赛发生事项的稳定身份 | 同一事实在多次修订中保持 `factId` |
| 事件 Event | 某次写入后形成的事件版本 | 具有独立 `eventId`、状态和记录顺序 |
| 修订 Revision | 同一事实的第 N 个不可变版本 | 通过 `factRevision` 和 `revisionOf` 追溯 |
| 公开投影 Projection | 按记录顺序重放公开事实得到的读模型 | 产生比分、最近事件、关键事件和完整性状态 |
| 冲突 Conflict | 两条或多条事实之间存在不可同时成立的关系 | 由成员与冲突边描述，不等于简单二选一 |
| 撤回 Retraction | 声明某个事实不再有效 | 创建新修订，不物理删除历史 |

## 4. 角色与权限

| 角色 | 读取公共事实 | 读取候选/冲突 | 创建事实 | 确认/撤回/调和 | 创建用户观察 |
|---|:---:|:---:|:---:|:---:|:---:|
| 普通球迷 | 是 | 否 | 否 | 否 | 是，仅本人 |
| Companion Agent | 是 | 仅完整性结论 | 否 | 否 | 是，代表当前用户 |
| 赛事导播/运营 | 是 | 是 | 是 | 是 | 否 |
| 外部结构化数据源 | 通过接入层提交 | 仅自身状态 | 是，默认候选 | 否 | 否 |
| 质量/技术人员 | 测试环境是 | 测试环境是 | 受控 | 受控 | 受控 |

### 4.1 权限红线

- `BR-01` 用户端和 Companion Agent 不得调用创建、纠正、确认、撤回或调和事实的写接口。
- `BR-02` 所有导播写请求必须携带有效运营身份；生产环境禁止开发默认令牌。
- `BR-03` 公共用户不能看到冲突原因、候选详情、操作人或内部完整性说明；当前公共 HTTP 快照会清空 `integrity` 明细，不确定性通过受控文案或产品提示表达。
- `BR-04` 待核验观察必须以 `matchId + userId` 隔离，不能跨用户跟进。

## 5. 事实进入规则

### 5.1 来源分类

| 来源类型 | 示例 | 默认事实状态 | 默认公开性 |
|---|---|---|---|
| `operator` | 导播快捷录入、人工修正 | `confirmed`，受校验和冲突检测约束 | 校验通过后公开 |
| `provider` / `api-sports` | 外部结构化赛事数据 | `provisional` 或按接入策略处理 | 未确认不公开 |
| `director_voice` | 导播口述转结构化草稿 | 草稿阶段不是事实 | 人工确认发布后才进入事实层 |
| `system` | 账本修订、撤回或系统校正 | 由动作确定 | 按目标状态决定 |
| `user_observation` | 用户说“进了” | 不创建事实 | 永不直接公开 |

### 5.2 通用校验规则

- `BR-05` `matchId`、`eventType`、`period`、`clock`、`description` 必须满足接口合同；不支持的事件类型返回 400。
- `BR-06` 赛前阶段 `pre_match` 不接受进球事实。
- `BR-07` 发生球队相关事件时，`teamId` 必须为 `home` 或 `away`，且球员必须属于配置的对应球队。
- `BR-08` 换人事件必须能识别上场与下场球员，并满足当前阵容关系。
- `BR-09` 纠正请求必须填写 `evidence.correctionReason`，不能只覆盖原事件而不留原因。
- `BR-10` `goal_cancelled` 和 `var_result` 属于关系型事件，不允许直接纠正；应撤回并重新创建，以保持引用关系清晰。

### 5.3 事实状态与公开资格

| 事实状态 | 是否有效 | 是否可进入公开投影 | 说明 |
|---|:---:|:---:|---|
| `provisional` | 候选 | 否 | 等待确认、冲突检测或撤回 |
| `confirmed` | 是 | 是 | 同时要求事件 `status=active`、`visibility=public` |
| `conflict` | 待决 | 否 | 不能进行确定性事实表达 |
| `reconciled` | 是 | 是 | 经人工冲突调和得到的有效结果 |
| `revoked` | 否 | 否 | 历史保留，但不再参与公开结果 |

- `BR-11` 公开事实的必要条件是：事实状态为 `confirmed` 或 `reconciled`，事件业务状态为 `active`，可见性为 `public`。
- `BR-12` `provisional`、`conflict`、`revoked` 事实不得进入公共比分、公共事件列表或确定性 Agent 回答。
- `BR-13` 事实状态变化必须递增 `factRevision` 并追加修订历史；内容纠正创建新 `eventId`，确认/撤回/调和在当前实现中可沿用 `eventId`，但不得覆盖既有 `FactRevision` 记录。

## 6. 比分账本规则

### 6.1 重放原则

- `BR-14` 公共比分必须由公开事实按 `recordedSequence` 升序重放产生，不能直接取“最后一条事件携带的绝对比分”。
- `BR-15` 一旦历史中存在 `recordedSequence`，完整历史中的每条事件都必须有该字段，且不得重复。
- `BR-16` 投影失败时不得回退到猜测比分；公开快照进入 `integrity=conflict`，事件列表可以为空。
- `BR-17` 新旧投影允许通过影子审计比较，但审计差异不能直接改变用户视图。

### 6.2 计分动作

| 事件类型 | 对比分的作用 | 附加约束 |
|---|---|---|
| `goal` | 对应球队 +1 | 必须有 `home/away` 队伍；同一公开进球只能贡献一次 |
| `goal_cancelled` | 中和被引用进球 | 必须通过 `revisionOf` 引用已公开进球；不能重复取消 |
| `score_correction` | 建立绝对比分检查点 | 比分不得为负；此前活跃进球视为已被检查点吸收 |
| 其他事件 | 不改变比分 | 即使请求携带比分也不得形成额外计分贡献 |

- `BR-18` 公开进球不得出现多个同时活跃的公开修订。
- `BR-19` `goal_cancelled` 不能引用未知、从未公开、发生在其后的进球，也不能取消比分检查点之前已被吸收的进球。
- `BR-20` 任一重放步骤都不得产生负比分。
- `BR-21` 纠正早期事件若会改变其计分贡献，必须先处理所有更晚的活跃事件，避免历史链断裂。

## 7. 冲突规则

### 7.1 冲突产生

- `BR-22` 新来源事实与当前有效事实在关键匹配字段上互不兼容时，创建或扩展开放冲突集合。
- `BR-23` 新冲突不能撤销或隐藏已经公开的有效事实；用户端继续显示最后已接受结果，同时完整性标记为冲突。
- `BR-24` 冲突必须记录成员角色：现有公开事实为 `accepted`，新候选事实为 `candidate`。
- `BR-25` 冲突关系必须以边表示，边两端是确实不可同时成立的事实；没有直接冲突边的事实可以被同时保留。

### 7.2 冲突期间表达

- `BR-26` 冲突期间，Agent 对争议内容只能表达“当前数据有冲突/还没确认”，不得自动选边。
- `BR-27` 非争议的最后已接受比分仍可展示，但必须避免把冲突候选说成既定事实。
- `BR-28` 内部冲突原因和候选证据不得直接暴露给普通用户。

### 7.3 冲突调和

- `BR-29` 导播解决冲突时至少选择一条仍活跃且属于该冲突的事实。
- `BR-30` 被选择的事实之间不得存在直接冲突边。
- `BR-31` 只撤销与已选择事实存在直接冲突边的事实，不得因为同属一个冲突集合就全部撤销。
- `BR-32` 被选择的 `provisional/conflict` 事实转为 `reconciled`；未再参与冲突且无需撤销的事实释放为原本可用状态。
- `BR-33` 若仍存在有效冲突边，冲突保持 `open`；只有没有剩余冲突边时才标记 `resolved`。
- `BR-34` 调和必须记录 `selectedFactIds`、`reason`、`resolvedBy`、`resolvedAt`，并在同一事务中更新事实、冲突和公共快照。

## 8. 纠正与撤回规则

### 8.1 纠正

- `BR-35` 纠正不是修改原事件，而是将原版本设为非活跃并创建同一 `factId` 的新修订。
- `BR-36` 新修订必须记录 `revisionOf`、递增 `factRevision` 和纠正原因。
- `BR-37` 纠正后的事实可先进入 `provisional`，待确认后再公开；旧修订不能重新进入公共投影。

### 8.2 撤回

- `BR-38` 撤回事实创建 `revoked` 修订，不物理删除事实历史。
- `BR-39` 撤回已公开事实后，账本必须立即重放并恢复比分和公开事件列表。
- `BR-40` 撤回消息必须携带可识别的事实与修订信息，客户端据此清理未播放音频、未执行动作、事件轮播和当前主动反应。
- `BR-41` 撤回后如需恢复内容，应创建新的事实修订并重新确认，不能把 `revoked` 修订改回有效。

## 9. 用户观察规则

### 9.1 Claim 三态

| Claim 状态 | 判定条件 | 回复边界 | 后续动作 |
|---|---|---|---|
| `confirmed` | 用户说法与公开有效事实一致 | 可自然确认 | 不创建新公共事实 |
| `contradicted` | 内部一致的公开事实明确否定 | 温和纠正并引用可用事实 | 不创建观察 |
| `unverified` | 缺少证据、数据延迟或完整性冲突 | 保留式回应 | 创建或复用 Pending Observation |

- `BR-42` 完整性为 `conflict` 时，相关 Claim 至少降级为 `unverified`，不能强硬判定用户错误。
- `BR-43` 用户观察状态包括 `pending_sync`、`corroborating`、`conflict`、`confirmed`、`contradicted`、`expired`、`superseded`。
- `BR-44` 同一用户同一比赛最多保留 5 条活跃观察；超过上限时最旧观察进入 `superseded`。
- `BR-45` 相同 `signalId` 或等价活跃观察应幂等复用，不能重复创建。
- `BR-46` 观察确认前不能形成共同瞬间或长期事实记忆。
- `BR-47` 异步确认或纠正只投递给原用户，并受 `FollowUpDeadline` 约束。
- `BR-48` 超时观察进入 `expired`，之后到达的事实不能重新触发过期跟进。
- `BR-49` 用户新一轮发言、主动取消或上下文变化可以抑制旧跟进。

## 10. 导播写入与幂等规则

幂等指相同请求重复执行多次，业务结果仍与执行一次相同。

- `BR-50` 所有导播写操作必须提供 `Idempotency-Key`；缺失返回 400。
- `BR-51` Key 去除首尾空格后不能为空，最大 200 字符，默认保留 24 小时。
- `BR-52` 幂等作用域为 `matchId + key`，请求指纹由 HTTP 方法、路径和规范化 JSON Body 计算。
- `BR-53` 同 Key、同操作、同请求指纹返回第一次完整响应，并设置 `Idempotency-Replayed: true`。
- `BR-54` 同 Key 但不同操作或不同请求指纹返回 409，不能执行第二次业务写入。
- `BR-55` 同一幂等操作仍在处理中时返回 409，客户端应等待后重试原请求。
- `BR-56` 事实创建、纠正、确认、撤回、调和与冲突解决必须与幂等记录、Outbox 在同一事务边界内完成。
- `BR-57` 时钟使用 `expectedVersion` 做乐观并发控制；版本过期返回 409，不静默覆盖。

## 11. 客户端投递规则

- `BR-58` 事实事件投递键为 `eventId:factRevision:factStatus`。
- `BR-59` 客户端对相同投递键只展示、播音和执行动作一次，但仍要消费重复帧，避免音频元数据与二进制错位。
- `BR-60` 新修订必须因 `factRevision` 或 `factStatus` 变化形成新投递键，不能因为 `eventId/factId` 相同而被去重。
- `BR-61` 撤回事实发送 `match_fact_retracted`；当前消息包含 `data.eventId` 与 `data.factId`，客户端据此按事实链清理未完成交付。修订号、状态和 deliveryKey 属于建议增强字段，不视为当前已实现载荷。
- `BR-62` 字幕优先于或独立于 TTS；语音失败不能阻断事实更正的文字到达。
- `BR-63` 当前仍缺少持久化客户端 ACK 和断线重放游标，生产灰度前必须补齐或明确可接受窗口。

## 12. 时钟与事件发生时间规则

- `BR-64` 比赛当前时钟与事件发生时刻是两个对象；晚录事件的 `clock` 不能反向修改当前比赛时钟。
- `BR-65` 时钟动作只允许 `start`、`pause`、`set`、`adjust`。
- `BR-66` 时钟阶段只允许 `pre_match`、`first_half`、`halftime`、`second_half`、`extra_time`、`fulltime`。
- `BR-67` `elapsedSeconds` 取值 0-21600 秒，自动运行时按 `anchorAt` 计算显示值。
- `BR-68` 初次 `start` 且当前为 `pre_match` 时，默认进入 `first_half`。

## 13. 口述事件规则

- `BR-69` 导播口述首先生成结构化草稿，不直接进入事实账本。
- `BR-70` 草稿至少展示转写文本、事件类型、阶段、发生时间、球队、参与者和不确定字段。
- `BR-71` 导播确认发布时必须重新经过身份、幂等、事件校验和冲突检测。
- `BR-72` ASR 未配置、输入为空、转写无效或结构化失败时，草稿接口给出明确错误，不生成猜测事实。

## 14. 支持事件类型

当前事实层支持 23 类事件：

| 分组 | 事件类型 |
|---|---|
| 比赛阶段 | `kickoff`、`halftime`、`fulltime`、`match_end` |
| 进攻与得分 | `goal`、`shot`、`big_chance`、`miss`、`penalty`、`penalty_awarded` |
| 防守与纪律 | `save`、`foul`、`yellow_card`、`red_card` |
| VAR 与纠错 | `var_check`、`var_result`、`goal_cancelled`、`score_correction` |
| 人员与态势 | `substitution`、`injury`、`tactical_shift`、`pressure` |
| 运营记录 | `operator_note` |

`operator_note` 只用于运营记录，不允许加入自动主动播报策略。

## 16. 业务验收清单

| 验收编号 | 前置条件 | 操作 | 预期结果 |
|---|---|---|---|
| AC-BR-01 | 无公开进球 | 用户说“进了” | 公共比分不变，创建本人观察，球球保留式回应 |
| AC-BR-02 | 候选进球为 provisional | 普通用户读事件 | 候选不出现在公共事件列表 |
| AC-BR-03 | 候选已确认 | 读取公开状态 | 比分按账本 +1，事实可被 Agent 引用 |
| AC-BR-04 | 已公开进球 | 导播撤回 | 比分重放回退，客户端收到撤回并清理未播内容 |
| AC-BR-05 | 两条事实存在冲突边 | 导播同时选择两条 | 返回 400，不改变冲突状态 |
| AC-BR-06 | 三条事实中只有两条兼容 | 导播选择两条兼容事实 | 只撤销直接冲突事实，两条保留并调和 |
| AC-BR-07 | 同一创建请求已成功 | 使用同 Key 重试 | 返回原响应，不新增事件，响应标记重放 |
| AC-BR-08 | Key 已用于请求 A | 同 Key 提交请求 B | 返回 409，请求 B 不执行 |
| AC-BR-09 | 时钟版本为 3 | 用 expectedVersion=2 更新 | 返回 409，当前时钟不变 |
| AC-BR-10 | 用户 A 有待核验观察 | 用户 B 在线 | 后续确认只发给用户 A |

## 17. 设计决策记录

| 决策编号 | 选择 | 未采用方案 | 理由 |
|---|---|---|---|
| DD-01 | 用户观察与公共事实分离 | 用户口述直接写事实 | 保留现场感，同时保护公共数据 |
| DD-02 | 事件重放生成比分 | 读取最后事件的比分字段 | 支持撤回、乱序修订和审计 |
| DD-03 | 冲突使用图结构 | 整组二选一 | 允许保留多个互相兼容的事实 |
| DD-04 | 撤回创建新修订 | 原地修改或删除 | 保留完整审计链 |
| DD-05 | 所有导播写操作幂等 | 只在前端禁用按钮 | 覆盖双击、重试、并发和服务恢复 |
| DD-06 | 客户端按修订状态去重 | 只按 eventId 去重 | 允许同一事实的新修订被正确播放 |
| DD-07 | 冲突保留最后已接受公开结果 | 一冲突就清空比分 | 用户仍能看到最近可靠状态 |
| DD-08 | 口述先草稿后发布 | ASR 结果直接写事实 | 避免语音误识别形成公共事故 |
