# 比赛事实与纠错系统资料包说明与 WorkBuddy 演示脚本

> 用途：直播演示“如何用 PRD + 专项产品资料生成一份功能设计文档”  
> 演示功能：比赛事实与纠错系统  
> 产品负责人（PM）：林若安  
> 内部演示日期：2026-04-25  
> 时间口径：所有内部项目日期相对实际项目节点统一前移 3 个月。

## 1. 这套资料包解决什么问题

直播中不要把一个大型 PRD 直接扔给 WorkBuddy，然后要求“写详细设计”。这种输入通常会得到结构完整但规则松散的通用方案。正确演示方式是先把功能设计所需的上游知识拆成稳定的产品资料，再让 WorkBuddy 做结构化归纳和设计展开。

本资料包把过程分成两层：

| 层级 | 文档 | 性质 | 直播中怎么解释 |
|---|---|---|---|
| 输入 | 球球总 PRD | 产品全局背景 | 告诉 WorkBuddy 产品是谁、用户是谁、功能处在什么阶段 |
| 输入 | `01-比赛事实与纠错系统业务规则说明.md` | 业务规则与边界 | 告诉 WorkBuddy 什么绝对不能错、什么可以公开 |
| 输入 | `02-比赛事实与纠错系统场景流程与状态规范.md` | 流程与状态 | 告诉 WorkBuddy每种情况如何流转、失败时怎么办 |
| 输入 | `03-比赛事实领域模型数据字典与接口契约.md` | 数据与接口真值 | 告诉 WorkBuddy字段、枚举、接口和错误码 |
| 参考 | `25-AI出题与题库管理系统设计.md` | 格式与颗粒度样板 | 只学习章节密度、表格/流程/JSON 的表达方式，不复制业务 |
| 输出 | `25-比赛事实与纠错系统设计.md` | 最终功能设计文档 | 展示 WorkBuddy 如何把分散输入合成为可交付设计 |

## 2. 为什么选择“比赛事实与纠错系统”

这个功能适合教学演示，因为它同时包含：

1. 明确的用户价值：不胡说比分，用户领先数据时也不显得迟钝。
2. 多角色：用户、球球、导播、外部数据源、质量人员。
3. 多状态机：事实、冲突、观察、幂等、时钟、客户端交付。
4. 可见页面：直播控制、事件时间线、冲突处理、用户端比分与字幕。
5. 可验证数据：字段、API、状态码、数据库对象和自动化测试都有现成证据。
6. 真实设计取舍：及时性与准确性、公开事实与私有观察、整组二选一与冲突图。

## 5. 直播前准备

1. 将五个输入文件放在 WorkBuddy 可访问的同一工作区。
2. 打开球球 PRD 的 4.4、4.5、4.8 三节作为讲解锚点。
3. 打开参考稿的目录，让学生先观察其颗粒度：页面、请求、流程、数据、工具、决策、错误处理。
4. 不先打开最终输出文档，避免演示像“照着答案抄”。
5. 准备一个固定演示案例：西班牙 vs 德国，用户先看到佩德里进球，随后确认，再被 VAR 撤回。
6. 演示环境中的项目日期使用 2026-04-25，不说实际 2026-07-25。

## 6. 建议的直播节奏（45-60 分钟）

| 时间 | 环节 | 讲解重点 |
|---:|---|---|
| 0-5 分钟 | 讲目标 | 不是让 AI 猜设计，而是让 AI根据输入合同做设计 |
| 5-12 分钟 | 看总 PRD | 找到产品红线、角色和当前阶段 |
| 12-20 分钟 | 逆向专项资料 | 为什么需要业务规则、场景状态、数据接口三份资料 |
| 20-28 分钟 | 展示规则编号 | `BR/SM/SC/API` 如何减少歧义和方便追溯 |
| 28-35 分钟 | 提交 WorkBuddy Prompt | 明确格式、颗粒度、日期和禁止事项 |
| 35-45 分钟 | 观察生成结果 | 检查是否有字段表、状态机、异常和当前状态 |
| 45-55 分钟 | 做追溯检查 | 随机抽三条结论反查输入来源 |
| 55-60 分钟 | 总结 | AI 输出质量取决于输入资料质量和验收标准 |

## 7. WorkBuddy 主 Prompt（可直接演示）

```text
你现在是球球产品的高级产品经理和系统分析师。请基于我提供的以下资料，完成《25. 比赛事实与纠错系统设计》：

1. 球球 AI 足球数字球友 PRD；
2. 比赛事实与纠错系统业务规则说明；
3. 比赛事实与纠错系统场景流程与状态规范；
4. 比赛事实领域模型、数据字典与接口契约；
5. 《25-AI出题与题库管理系统设计》仅作为格式和颗粒度参考。

要求：
- 设计文档的颗粒度、章节密度和细节程度对齐参考稿，不写成概要；
- 结合球球当前真实项目状态，明确“已实现、已有基础但需补齐、尚未实现”；
- 完整覆盖用户观察、候选事实、公开事实三层真相；
- 完整覆盖事实创建、确认、纠正、撤回、冲突图调和、比分重放、导播幂等、Outbox、客户端去重和事实撤回；

- 每个关键设计结论引用 BR、SM、SC 或 API 编号，方便反查来源；
- 不允许把 LLM 或用户文本设计为公共事实写入方；
- 不允许把冲突解决简化为整组二选一；
- 不允许声称系统已经具备持久化客户端 ACK/断线全量重放；
- 内部项目日期统一比实际节点提前 3 个月，文档日期写 2026-04-25；
- 产品负责人写“林若安”；
- 输出为中文 Markdown，标题为“25. 比赛事实与纠错系统设计”。
```

## 8. 分步 Prompt 演示法

如果课程重点是“过程”，不要一次生成完整文档，可以分四轮：

### 第 1 轮：只做结构

```text
先不要写正文。读取输入资料和参考稿，给出最终设计文档的三级目录，并标记每一节主要使用的 BR/SM/SC/API 来源。目录必须覆盖页面、流程、数据、接口、状态机、Agent、可靠性、错误处理和当前项目状态。
```

检查点：目录是否至少与参考稿一样细；是否出现“用户观察”“冲突图”“幂等”“撤回清理”。

### 第 2 轮：写事实主链和页面

```text
按确认后的目录，先写系统定位、总体架构、导播工作台、事实创建/纠正/撤回和公共账本章节。所有请求结构必须来自 API 合同；所有业务判断必须标来源编号。
```

检查点：是否错误使用请求里的绝对比分；是否说明 `recordedSequence`；页面是否有加载、空、冲突和失败状态。

### 第 3 轮：写冲突、观察和可靠性

```text
继续写冲突图调和、用户领先现场观察、幂等与 Outbox、客户端投递去重、事实撤回、时钟与口述草稿。至少提供 4 个 Mermaid 图、3 个 JSON 示例和完整异常矩阵。
```

检查点：是否允许多个兼容事实；是否只向原用户跟进；是否把 WebSocket 写成 exactly-once。

### 第 4 轮：补项目状态和验收

```text
最后补充当前实现状态、测试证据、残余风险、设计决策、非目标和验收清单。把未实现项明确标为待补，不能包装为已上线。
```

## 9. 直播中的三个抽查问题

### 抽查 1：为什么用户说“进了”不能改比分？

期望 WorkBuddy 能反查：`BR-01`、`BR-04`、`BR-42` 至 `BR-49`，以及 `SC-09`。  
合格答案必须同时说清“私有观察”“保留式回应”“权威事实确认后才重放”。

### 抽查 2：冲突为什么不是二选一？

期望反查：`BR-25`、`BR-29` 至 `BR-34`，以及 `SM-03`、`SC-08`。  
合格答案必须提到冲突边、兼容选择、只撤销直接冲突事实。

### 抽查 3：为什么 Key 相同仍会返回 409？

期望反查：`BR-50` 至 `BR-56`、`SM-05`、`API-03/04/09/11/12/13`。  
合格答案必须区分“同 Key 同请求重放”和“同 Key 不同请求冲突”。

## 10. 质量评分表

| 维度 | 权重 | 满分标准 |
|---|---:|---|
| 业务边界正确 | 20 | 用户/LLM 无事实写权限；冲突不自动选边 |
| 颗粒度对齐 | 15 | 与参考稿相当的三级目录、表格、流程、数据和异常 |
| 当前状态真实 | 15 | 已实现、待补、风险均有证据，不虚构生产数据 |
| 数据接口准确 | 15 | 字段、枚举、端点、状态码和示例一致 |
| 状态机完整 | 15 | 事实、冲突、观察、幂等、时钟、交付均覆盖 |
| 可追溯 | 10 | 关键结论可反查 BR/SM/SC/API |
| 可验收 | 10 | 正常、边界、错误和恢复路径都有断言 |

低于 80 分不建议作为课堂“最终设计稿”。事实边界错误属于一票否决。

## 11. 常见失败与现场修正 Prompt

| 失败 | 表现 | 修正 Prompt |
|---|---|---|
| 写成概要 | 每章只有几条原则 | “按参考稿颗粒度补字段表、请求响应、状态转换、异常和验收，不减少章节。” |
| 自创接口 | 出现不存在的批量删除/自动裁决接口 | “所有端点只允许来自 API-01 至 API-13；设计建议单列为待补。” |
| 用户观察混入公共事实 | 把用户说法写入 events | “重读 BR-01、BR-04、BR-42 至 BR-49，重写为私有 Pending Observation。” |
| 冲突整组二选一 | 选择 A 后撤销整个集合 | “按 FactConflictEdge 重写，仅撤销与所选事实直接相连的事实。” |
| 时间写错 | 使用 2026-07-25 | “内部项目日期统一前移三个月，改为 2026-04-25；外部日期不动。” |
| 把风险写成能力 | 声称断线后全量 exactly-once | “按 BR-63 和 Phase 5 报告区分当前观察恢复与待补的持久化 ACK/游标。” |
