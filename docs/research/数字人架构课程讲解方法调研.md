# 数字人架构课程讲解方法调研

> 调研日期：2026-09-03  
> 目的：为“球球 AI 数字人”项目设计面向普通学员的 11 张架构图讲解方式。  
> 说明：本轮没有拿到 Exa 的有效返回（此前 MCP/研究代理出现 429/额度不足），因此不声称使用 Exa 结果；以下内容来自可直接核验的公开一手页面。

## 结论先行

适合本项目的授课方式不是逐张念架构图，而是把每张图当成一个“要解决的问题”，用同一条真实用户故事贯穿：

1. 先让学员知道这节课结束时能做什么（目标和验收）。
2. 先演示一次完整体验，再拆图解释“为什么这样设计”。
3. 每次只引入少量新概念，讲一小段就让学员预测、连线、复述或动手。
4. 从总图逐步放大到运行链路、数据/事件、部署和可靠性，最后再回到总图复盘闭环。
5. 对“近期接入”“逻辑职责”“规划态”明确贴标签，避免学员把目标架构误认为已上线事实。

## 可核验来源与可迁移做法

### 1. 课程先定终点，再选内容

Cornell Center for Teaching Innovation 的课程设计指南把顺序定义为：先定义学习结果，再决定如何评估，再选择材料、活动和作业。这被称为 backward course design（逆向课程设计）。

- 来源：[Designing Your Course](https://teaching.cornell.edu/teaching-resources/preparing-teach/designing-your-course)
- 页面明确建议：学习结果应描述学员课程结束时“知道、重视、能够做什么”；评估可以用频繁的小练习检查进度；教学活动应让学员应用和练习新知识。
- 对本项目的用法：每张图开头先说“看完这张图，你能解释/画出/定位什么”，结尾用一个可观察的验收问题收束。

### 2. 直播课要短讲、练习、反馈交替

Cornell 的 Active Learning 页面建议把短时讲授与应用练习交替，并通过课堂投票、低风险小测、聊天、屏幕共享和同伴讨论及时反馈。页面还强调活动要和学习目标明确对应。

- 来源：[Active Learning](https://teaching.cornell.edu/teaching-resources/active-collaborative-learning/active-learning)
- 在线教学页面进一步建议：短讲后立即练习并获得反馈；使用同伴学习；给出清晰指令、目的、示例、截止时间和责任要求。
- 来源：[Active Learning in Online Teaching](https://teaching.cornell.edu/resource/active-learning-online-teaching)
- 对本项目的用法：一张图不要连续讲 20 分钟。建议每 5–8 分钟插入一个动作，例如“请指出用户输入从哪条边进入”“如果 Redis 不可用，哪条链路仍成立”“两人一组用一句话解释 Outbox”。

### 3. 技术工作坊用“参与式演示”，而不是只放幻灯片

The Carpentries 的讲师培训是面向编程/数据工作坊的成熟一手教材。它明确采用“短课 + 个人/小组实践 + 练习授课”的交替结构，并把 live coding（参与式现场演示）作为核心方法。

- 来源：[Instructor Training 总览](https://carpentries.github.io/instructor-training/)
- 来源：[Live Coding is a Skill](https://carpentries.github.io/instructor-training/17-live.html)
- 页面给出的做法：讲师边做边说，学员同步跟做；每个操作都慢下来、说出意图、指出结果；错误和调试是学习机会；用大字号、最大化窗口；用插图帮助学员组织材料；不要复制粘贴掩盖过程。
- 对本项目的用法：讲图时不要只展示最终 SVG。可以先画主链 `INPUT → REALTIME → AGENT CORE → DELIVERY → EXPERIENCE`，再逐层补上 Fact、Context、Grounding、Director、Reply Realizer、Outbox 等节点，让学员看到复杂度是如何长出来的。

### 4. 初学者需要分块、渐进引导和频繁检索

Carpentries 的“Memory and Cognitive Load”章节指出工作记忆有限，大量信息连续输入而没有练习会降低保留；把信息组织成 chunk（有关系的一组）能减少有效项目数；频繁形成性评估、解释自己的思路、反思和逐步引导有助于迁移到长期记忆。它还提醒，完全不给结构的开放式任务对新手容易造成认知过载。

- 来源：[Memory and Cognitive Load](https://carpentries.github.io/instructor-training/05-memory.html)
- 页面还建议：复杂任务用 guided practice，按步骤聚焦，每一步得到反馈后再进入下一步；图、文字和讲述应尽量一致，减少分心和 split-attention（注意力在多个来源之间来回切换）。
- 对本项目的用法：不要让新手一开始就面对 16 个技术模块。先只记住五段主链，再按“请求进入 → 实时编排 → Agent 决策 → 交付 → 体验”逐段加细节；图上的词和口头说法保持一致，关键术语旁放一句白话释义。

### 5. 开场和结尾是学习结构的一部分

Carpentries 的“Launches and Landings”把开场和结尾视为工作坊的必要教学环节，而不是可有可无的主持词。开场应让学员知道将学什么、需要怎样参与、日程和求助方式，并建立“我能学会”的信心；结尾应帮助学员反思、巩固并明确下一步，而不是在最后几分钟硬塞新内容。

- 来源：[Launches and Landings](https://carpentries.github.io/instructor-training/23-introductions.html)
- 对本项目的用法：开场用一个完整用户故事和课程地图；每张图结束固定回答“这张图解决了什么问题、它和上一张图怎么接、下一张图为什么需要它”；最后让学员从输入一路复述到体验并指出一处可靠性边界。

### 6. 可视化讲解要服务于“理解”，不是堆装饰

3Blue1Brown 在其官方 About 页面把频道定位为“用视觉解释数学”，并强调目标是深度理解；网站同时提供书面和交互版本，说明同一概念可以用视觉、文字和可操作材料互相校验。

- 来源：[3Blue1Brown About](https://www.3blue1brown.com/about/)
- 对本项目的用法：架构图保留一条清晰的视觉主线，使用颜色表达语义（例如请求、事实、事件、控制面），不要让每个节点都抢主角；讲解时用“如果拿掉这个节点会怎样”的动态问题，让图成为推理工具。

### 7. 系统设计课程常用“分步视觉模块”

ByteByteGo 官方站点说明其课程是文字内容配详细插图，按步骤解释如何解决问题，并提供课程目录和预览章节。

- 来源：[ByteByteGo](https://bytebytego.com/)
- 页面可核验的做法：内容以 step-by-step（逐步）组织，插图和章节目录一起使用，而不是一张大图承载所有解释。
- 对本项目的用法：把 11 张图当成有前后依赖的章节，不把它们当成 11 张孤立海报；每张图只承担一个观察层级，跨图重复的节点保持同名、同色、同位置语义。

## 映射到 11 张图的讲解主线

建议把课程组织成“四幕”，而不是按文件名机械播放：

| 幕 | 图 | 学员要回答的问题 | 讲解动作 |
|---|---|---|---|
| 1. 先看产品 | `00-overview`、`01-context` | 用户想得到什么体验？系统边界在哪里？ | 先演示一个完整回合，再让学员从总图圈出系统内外 |
| 2. 看系统怎么跑 | `02-containers-mvp`、`03-runtime-voice`、`04-runtime-match-event`、`05-event-flow` | 一次请求怎样被接住、决策、交付并留下事实？ | 沿同一 trace 逐步追踪；每段让学员预测下一跳 |
| 3. 看核心怎么想 | `agent-core`、`technical-modules` | Agent 如何从事实和上下文得到可交付回复？模块职责如何协作？ | 先用白话角色扮演，再回填技术名词和接口边界 |
| 4. 看系统怎么活 | `06-deployment-mvp`、`07-deployment-production`、`08-control-reliability` | 部署在哪里？出故障时谁兜底？哪些是事实源？ | 做一次“Redis/模型/供应商不可用”故障推演 |

这不是要求现在改图，而是建议的授课顺序。若学员明显偏工程，可以把 `agent-core` 提前到第二幕作为“决策黑盒的展开”；若学员更偏产品，则先完整跑完一遍 `05-event-flow` 再展开核心。两种变体都应先讲完总图和用户故事。

## 每张图的固定讲解模板

每张图采用同一套 7 步，降低学员的记忆负担：

1. **场景**：今天沿哪一个用户动作走？
2. **目标**：看完后学员能说出/画出什么？
3. **主线**：只先指出 3–5 个关键节点和一条箭头。
4. **逐步展开**：每次只增加一个层级，解释“为什么需要它”。
5. **参与动作**：预测下一跳、连线、找事实源、做故障推演或复述。
6. **边界标记**：说明当前实现、近期接入、逻辑职责、规划态分别是什么。
7. **回扣闭环**：用一句话接回上一张图，并预告下一张图要解决的问题。

## 需要和用户确认的课程选择

- 学员画像：完全非技术、会一点代码、还是已有后端经验？这会决定术语出现的速度和练习难度。
- 课程形态：一次 90 分钟直播，还是拆成多次课？11 张图不建议一次讲完。
- 目标深度：学员是“能讲清系统”、 “能跟着改代码”，还是“能独立画类似架构图”？三者验收标准不同。
- 是否要配套动手环境：如果要配套，建议每幕至少安排一个可运行的小任务，而不是只做口头问答。
