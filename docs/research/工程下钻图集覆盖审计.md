# 第二层｜工程下钻图集覆盖审计（复核版）

## 结论先说

当前工程下钻图集已扩展为 01–07 加 09–11：**主运行链路和三类合同级视图已覆盖**。它适合解释“系统由哪些边界组成、两条核心运行路径如何走、MVP 如何部署、生产如何演进”，也能独立讲清消息契约、事实状态和交付保障。数据库实体、容量数字、备份演练步骤和删除竞态测试矩阵继续由工程设计文档承载，不再堆进架构图。

这不是说现有 01–07 有严重主链错误。相反，主链与当前代码基本一致：用户语音链和比赛事件链都能从接入走到 Agent、Director、Delivery 和客户端；问题在于部分关键细节只写在文档/代码里，没有在工程图集中形成可独立讲解、可排障的视图。

审计范围：`architecture/archify/01-context.json` 至 `07-deployment-production.json`、`09-realtime-contract.json` 至 `11-delivery-assurance.json`，并用 A1/A2/A3、Structurizr DSL、后端实现、`docker-compose.yml` 和技术设计文档交叉核对。

## 逐图覆盖判断

### 01｜系统上下文：覆盖边界，非工程细节

**覆盖到位：** 用户、比赛供应商、运营导播、外部 AI，以及系统内部的 `INGRESS → Agent Core → Delivery` 职责边界都与当前实现相符。它回答“谁和系统交互、系统对外提供什么”。

**有意不覆盖：** HTTP 路由、WS 帧、数据库表、事实状态和部署节点。这些不应塞进 Context 图，否则会和 02、03、05、06 重复。

**复核结果：** C4 DSL 已与 Archify 的统一接入、`Agent Runtime` 和 Redis 短期状态语义对齐；它仍只表达 C4 边界，不替代 09–11 的消息与状态合同。

### 02｜MVP 容器：覆盖容器边界，但职责仍被压缩

**覆盖到位：** Flutter、Go API/WebSocket、Agent Runtime、Redis、PostgreSQL + Outbox、Fact Ledger、外部 AI、比赛源和运营控制台齐全；`docker-compose.yml:1-45` 证实 MVP 是单 backend + PostgreSQL + Redis。

**复核结果：** 容器已统一命名为 `Agent Runtime`，并明确 Scheduler、Companion Agent、Director、Delivery 的逻辑职责；事实账本仍作为独立容器表达，不暗示必须拆成独立进程。

**边界说明：** 比赛源和运营写入先到 Go API 再进事实处理，这一点图中已表达；但 Source Manager 的轮询、游标、新鲜度和错误状态仍不可见。

### 03｜用户语音时序：主链完整，协议和异常不完整

**覆盖到位：** 图中消息顺序与 `docs/humanity-runtime-technical-design.md:27` 及 `main.go:588-607` 对齐：鉴权/WS、ASR 增量与最终转写、Scheduler 提交、Agent、Response Plan、TTS、客户端表现和打断/重连均有表达。

**复核结果：** 09 已补充 WS 消息类型、音频分块序号、播放状态、打断、重连和快照恢复；ASR/TTS 供应商超时参数仍属于实现配置，不在架构图中展开。

**不应补入本图：** 事实账本冲突和主动事件调和应留在 04/05，避免把用户语音时序变成“所有系统细节图”。

### 04｜比赛事件时序：覆盖业务闭环，缺少来源治理细节

**覆盖到位：** Ingest→Fact Ledger→Observer/Observation→Agent→Scheduler→Director→Delivery→Client 与 `main.go:534-568`、`agent.go:1115` 一致；撤销、回执、Trace 也有回路。

**复核结果：** 已拆分为 `Match Source` 与 `Operator` 两个 participant，分别表达自动来源和人工确认/更正/撤销；权限、幂等键和事务 Outbox 仍在 A3、02 和 10 中承接。

**复核结果：** 10 已补充来源健康、游标、新鲜度、重试、死信和受控重放；冲突与调和以事实账本修订轨迹表达，`goal → var_result → goal_cancelled` 的领域细节继续由事实设计文档承载。

### 05｜事件与数据流：覆盖跨域流向，未覆盖合同和可运维性

**覆盖到位：** 比赛 API、导播、用户语音、接入规范化、ASR、Fact Ledger、Outbox Fan-out、对话上下文、策略、Agent+Director、字幕/动作和 TTS 音频通道形成完整有向流；这与 `docs/humanity-runtime-technical-design.md:23-31` 和 `main.go:360,534-568` 相符。

**缺口：** 图展示“数据去哪儿”，没有展示每类数据的 schema、持久化表、租户/用户隔离、版本号、幂等键和错误重试。隐私删除、Trace、Observation 通过节点出现，但没有明确哪些数据是用户私有、哪些是公共事实、哪些会在删除时联动清理（设计依据 `security-facts-privacy-idempotency-plan.md:171-204`）。

**重复边界：** 05 与 04 都讲比赛事件，但 04 是按时间讲“先后发生什么”，05 是按数据讲“同一数据流向哪些处理和通道”；两者属于互补，不是问题。讲解时不能再次完整复述另一张图的每个节点。

### 06｜MVP 部署：当前拓扑准确，但不是运行手册

**覆盖到位：** 客户端→反向代理/TLS→Go Backend→Redis/PostgreSQL/外部 API，且标出单台 VM/Docker Compose；与 `docker-compose.yml:1-45` 一致。

**缺口：** 没有健康检查、启动迁移、备份/恢复、日志采集、密钥注入、资源边界和外部 API 失败时的降级路径。Go Backend 内部包含 Ingress/Auth/Agent/Director/Outbox（图中副标题已有），但未展示这些模块如何共享进程和故障域。

**事实提醒：** Compose 声明了 `redis_data` volume（`docker-compose.yml:47-49`），但 Redis service（`docker-compose.yml:43-45`）未挂载它；因此 Redis 不能按持久化存储讲解。当前图将 Redis 定位为短期状态是正确的。

### 07｜生产部署目标：演进方向齐全，落地依赖未闭合

**覆盖到位：** CDN/WAF/TLS、API/WS 多副本、Event Worker、多源比赛 API、托管 Redis/PostgreSQL、监控/日志/告警，以及 Sticky WS、shared scheduler、Outbox/replay/DLQ 等规划方向都在图中，`planned` 标记避免了把未来能力说成现状。

**边界说明：** 07 仍是组件拓扑和规划态，不承担完整可靠性状态机；09–11 已分别承接实时合同、事实恢复和交付保障。多副本只处理一次、持久化重放游标和客户端 ACK 仍必须按规划态讲解。

**教学边界：** 07 必须明确是目标图；否则它会与 06 的当前单体部署冲突。现有 `planned` 标识已解决大部分语义风险。

## 重复与矛盾检查

### 可以保留的重复（不同抽象层）

1. `Fact Ledger` 在 02/04/05/A3/A2-M 多次出现：分别表达容器位置、事件时序、数据流、控制可靠性和模块责任，属于正常的跨视图重复。
2. `Scheduler/Director/Delivery` 在 03/04/05/A1/A2-M 多次出现：分别表达用户回合、比赛回合、流向、决策闭环和模块地图，不构成逻辑重复。
3. 06 与 07 都画数据库、后端和外部 API：一个是当前部署事实，一个是生产目标，保留两张是必要的时间维度。

### 必须统一的矛盾/漂移

1. **C4 DSL 已对齐：** 容器、Redis 和统一接入语义与 Archify 02/06 一致；后续仍需在代码或部署边界变化时同步维护。
2. **生产能力边界：** 07 的多副本、共享调度、replay、DLQ 都是 `planned`；设计文档说明当前 Outbox 只发布进程内订阅队列、没有客户端 ACK/持久化重放游标（`security-facts-privacy-idempotency-plan.md:249-251`）。任何讲解或后续图文都不能把 07 当成已部署架构。
3. **Redis 持久化含义：** Compose 有未使用的 `redis_data` 声明，但服务未挂载；图中“短期协调状态/非事实源”与实际更一致，不应把 Redis 讲成可恢复事实库。
4. **遗留 pipeline 链：** 技术设计明确 `pipeline.Engine → session.WatchSession → AIPipeline` 没有接收实际比赛事件（`humanity-runtime-technical-design.md:54-58`）。工程图没有画这条遗留链是正确的；若未来有人根据旧 DSL 或旧文档补回它，会制造第二个主动生成落点。

## 最终判断与建议

**判断（复核后）：** 01–07 加 09–11 已覆盖工程下钻的主叙事和核心合同视图，不存在需要推翻现有 7 张图的结构性问题。它不是数据库 ER 图、容量方案或运行手册；这些内容应继续由工程文档和验收方案承载。

本轮已按建议补齐以下三类独立视图（不再新增第四类）：

1. **接口与状态合同图：** HTTP/WS 消息类型、身份 Scope、会话状态、音频/字幕/`presentation`/播放 ACK、打断和重连状态。
2. **事实与事件可靠性图：** Source Manager 新鲜度/游标、Fact Ledger 状态机、冲突集合、撤销/回滚、Observation pending→reconcile→expire、Outbox retry→DLQ→replay。
3. **客户端表现与运维闭环图：** Response Plan 到 TTS/Live2D 的执行、ACK/失败回传、Trace/metrics/alerts、评测回归和隐私删除联动。

这三类视图与现有图的关系应分别是“合同”“可靠性状态”“交付与运维”，不会重复 01–07 的边界、时间顺序、数据流或部署拓扑。若暂时不新增图，至少应在逐字稿和 README 中明确：01–07 是主链/拓扑视图，详细合同和状态机以代码、迁移和技术设计文档为准。
