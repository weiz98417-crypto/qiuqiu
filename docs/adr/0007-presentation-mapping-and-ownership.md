# 0007 · 表演映射表：单一源 JSON、全量覆盖不变式与所有权规则

## 背景

发射路径审计（2026-09-17）发现：白名单放开的 30 个表演槽位（17 动作 + 13 表情）中 9 个是死库存（后端零发射），4 种沟通动作（React/Ask/Repair/Acknowledge）对身体零影响；表情名→表情文件的映射存在三份互不一致的副本，`thinking` 指向一个空参数文件（渲染为无表情）；默认动作名 "focus" 在两个渲染面上播放不同动作；普通 session_opened 路径把 hello 表演算完即弃。

## 决定

1. **单一源**：`client/assets/live2d/models/qiuqiu/presentation-map.json` 是表演映射的唯一事实源——表情名→文件序号、动作名→组/变体、(沟通动作 × 情绪象限 × 比赛事件类) → 表演、回合相位 → 表演、投递结果 → 表演。web 页、移动内嵌页、Dart 常量全部从它读取/派生；Go 表与它的一致性由契约测试锁定（沿用 presentation_vocabulary 镜像模式）。
2. **全量覆盖不变式**：30 个槽位每一个都必须被 ≥1 条映射行引用，或显式归属客户端相位表。无路由 = 测试失败。这是用户验收线：不存在"白名单有但永远出不来"的槽位。
3. **映射表是纯函数**：`presentationFor(act, quadrant, eventClass)` 是查表，与 policy.go 的人格策略表同构、可整表测试。
4. **所有权规则**：投递保持期（HoldMS）内后端表演权威；ReturnMode 结束后客户端相位/idle 层接管身体；JS idle 调度器只在相位为 idle 且无挂起表演时补位。ReturnMode 四值各得其所（watch / decay_to_focus / decay_to_listening / decay_to_idle）。
5. **投递结果入表**：用户打断 → 一次性 confused/listening 反应。

## 被否决的替代方案

- **Go 表生成客户端资产**：引入后端→客户端的构建耦合；JSON 单源 + 契约测试同样防漂移且更简单。
- **等 7 个表情全部目验后再绑**：会卡住交付；先绑暂定值（thinking→expression3），真机目验后改一处 JSON 即可换绑。
- **嘴部 25 参数的情绪着色并入本变更**：嘴部参数是口型/情绪着色轨道，骑在表情之上，独立成篇避免一次变更横跨两层。

## 后果

- 9 个死槽位全部复活；4 个哑动作有身体；三个真 bug（空表情、focus 双义、镜像漂移）随单一源消失。
- 新表情/新动作的接入流程变为：模型加槽位 → JSON 加一行 → 表格加路由 → 契约测试把关。
- 真机目验清单（7 表情命名、17 动作观感、口型参数）独立跟踪，不阻塞映射表落地。
