[打开架构图集首页，暂时不要进入任何一张图]

> 各位，今天我们通过架构图、时序图、数据流图和部署图，来看清楚球球这个数字朋友的整体结构，以及一次陪看回应到底是怎样产生的。
>
> 这 15 张图不是 15 个互不相关的知识点，而是同一个系统的 15 个观察角度。我们会一直追踪同一个例子：比赛进行到第 24 分钟，佩德里进球，法比安助攻，亚马尔参与策动。球球播报完进球以后，用户问：“刚才是谁助攻的？”
>
> 后面无论图变成什么样，大家都只需要追踪四个问题：第一，发生了什么；第二，此刻应该怎样陪；第三，哪些边界不能越过；第四，最终怎样让用户真正收到。
>
> 第一组五张图先建立全貌：总流程是什么，Agent 怎样做决定，技术职责怎样分层，真实模块怎样配合，系统怎样防止出错。第二组十张图再下钻工程：谁在系统外面，程序怎样组成，语音和比赛事件怎样运行，数据怎样流动，现在和未来怎样部署，以及实时消息、事实状态、最终表现分别遵守什么合同。
>
> 所以我们不是逐个背盒子，而是把同一件事越看越清楚。现在先从全貌开始。

## 第一层｜产品级叙事

## 00-overview.html｜全链路总图

[打开 `00-overview.html`。先不要看外围的小盒子，只指向左侧“球迷 / 观众”，然后沿中间橙色主线移动]

> 第一张是全链路总图。它只回答一个问题：用户问出一句话以后，球球怎样把可信事实和合适的人味合成一次完整体验？
>
> 我们从左边开始。用户问：“刚才是谁助攻的？”这句话先进入 `INGRESS｜统一接入层`。`Ingress` 就是进入系统的统一入口。盒子里的 `Voice` 是用户语音，`Match API` 是比赛数据接口，`Operator` 是运营或导播人员。它们都从同一个入口登记，但是登记以后会分流：用户的话进入实时互动路径，比赛数据和人工校正进入事实验证路径。统一接入不等于混在一起处理。
>
> 用户互动接着进入 `REALTIME｜实时接入`。这里的 `Gateway` 是实时网关，像消息进出系统的门；`Scheduler` 是节奏调度器，负责排队、打断和先后顺序；`WS` 是 `WebSocket` 的缩写，表示一条持续保持的双向连接。它们共同保证用户说完以后，系统能马上接住这一轮，而不是等很久才开始处理。

[沿上方绿色事实线，从“比赛数据源”和“运营 / 导播台”指到“事实账本”，再到“事实验证”]

> 但用户问的是比赛事实，所以系统不能只凭大模型印象回答。比赛数据源会通过 `API` 接口、`Replay` 历史回放或 `Manual` 人工录入提供材料；运营或导播台可以确认、更正、撤销和发布。它们同样先经过统一接入，然后进入 `Fact Ledger｜事实账本`。
>
> 事实账本不是只保存一个最终比分，而是保留事实的版本、冲突和修订过程。它告诉系统：哪条信息只是刚收到，哪条已经确认，哪条后来被撤销。接着进入 `Grounding｜事实验证`。`Grounding` 的意思是把回答钉在可靠证据上；图上写着“只引用已确认事实”，所以本轮可以把“法比安助攻”交给决策中心，却不能把还没确认的猜测当成答案。

[沿下方关系线，从“球迷 / 观众”指向“关系记忆”和“当前场景”，再指向“人格宪法”]

> 查清事实以后，还不能直接开口。因为同一句正确答案，可以说得自然，也可以说得很冒犯。
>
> `Relationship Memory｜关系记忆` 保存用户的偏好、边界和没有聊完的话题。`Current Context｜当前场景` 保存眼下的比赛状态、用户情绪和观看模式。`Personality Constitution｜人格宪法` 则规定球球是谁、能主动到什么程度、哪些表达不能越界，以及现在使用哪一版规则。
>
> 三者的区别一定要分清：关系记忆回答“我们以前怎样相处”，当前场景回答“现在正在发生什么”，人格宪法回答“不管什么时候都不能越过什么”。这三部分合起来，才是动态人味；它不是随机换语气，也不是让大模型自由发挥。

[把手指汇到 `Director｜陪伴导演`，再沿右侧主线一直走到客户端]

> 事实线、人味线和人格边界最后在 `Director｜陪伴导演` 汇合。Director 不再重新猜比分，它要决定的是：这一轮说不说、重点说什么、语气多热烈、亲密度多高、动作多强。
>
> 它把决定写进 `Response Plan｜回应计划`。计划里已经包含内容、语气、亲密度和表现强度。随后进入 `DELIVERY｜统一表现`：`Reply` 是文字回复，`TTS` 是把文字合成声音，`Motion` 是角色动作。最后由 `EXPERIENCE｜Flutter` 把结果呈现给用户。`Flutter` 是客户端使用的跨平台界面技术，`Live2D` 是二维角色的实时表情和动作，所以用户最终会同时看到字幕、听到声音、看到球球的动作。
>
> 到这里，一次完整回应已经走完：用户发问，系统接住；事实线确认“法比安助攻”；关系、场景和人格宪法决定怎样表达；Director 形成回应计划；客户端把文字、声音和动作真正呈现出来。

[最后再指外围的身份、存储、追踪和隐私节点，不再返回主线]

> 主线走完以后，我们再看四个保障。`Auth / Session` 是身份和会话控制：`Auth` 判断身份，`Session` 记录这一段连接是否有效，`Scope` 是权限范围，`Revoke` 是撤销权限。它保护入口。
>
> `Redis` 保存会话和短期协调状态，可以把它理解成临时工作区；它不是比赛事实的最终来源。`PostgreSQL + Outbox` 是长期底座：PostgreSQL 保存事实、关系和审计信息，Outbox 把“事实已经写入”和“消息准备发布”绑定在一起，避免只完成一半。
>
> `Agent Trace` 是本轮过程记录。`Trace` 是追踪记录，`Decision` 是当时的决定，`Fact IDs` 是引用过的事实编号。`Privacy / Retention` 是隐私与保留规则，负责导出、删除和清理。它们共同保证这轮回答以后可以解释、纠错，也可以按用户要求删除。

### 本图收口

> 第一张图只记住一条总公式：可信事实，加上动态关系和当前场景，再经过人格宪法约束，由 Director 形成一份回应计划，最后变成用户真正收到的体验。
>
> 下一张图不再看整个系统。我们只把镜头推进 Director 周围，看看刚才那份回应计划究竟是怎样决定出来的。

## A1｜agent-core.html｜Agent Core 决策与表现闭环

[打开 `agent-core.html`，选择“一轮回应如何决定”。先只沿主链走，不讲上方和下方支线]

> 这一张是刚才总图中“决策中心”的放大镜。我们继续追踪同一句话：“刚才是谁助攻的？”这次只看一轮回应从进入 Agent 到成功播放的完整过程。

[从“输入信号”指向 `Companion Agent`]

> 左边的“输入信号”可能是一次用户 `Turn`，也就是一轮用户发言；也可能是比赛事件或当前模式。箭头上的 `Boundary Request / Event` 表示经过入口边界检查的请求或事件。它只是在说“有一件事需要处理”，还不是答案。
>
> 信号先交给 `Companion Agent`，也就是数字球友智能体。它的第一项工作叫 `Intent`，识别用户到底想知道什么；第二项叫 `Tool Calls`，决定要调用哪些工具。这里它识别出用户问的是助攻者，而不是比分，也不是战术分析。

[沿 Agent 向下指到 `Fact / Context Tools`，再返回 Agent，然后向右进入事实验证]

> Agent 随后调用 `Fact / Context Tools`，也就是事实与上下文工具。`Snapshot` 是某一时刻的完整比赛快照，`Events` 是发生过的比赛事件，`Turns` 是之前一轮轮对话。工具查到法比安是助攻者，再把材料送回 Agent。
>
> 材料进入 `Grounding + Policy Gate`。`Grounding` 负责确认内容有事实依据，`Policy Gate` 是规则闸门，检查权限和表达边界。图中“可靠底稿、禁止新增、权限”的意思是：后面可以换说法，但不能凭空多编一个助攻者，也不能泄露用户无权看到的内容。

[指向上方人格宪法、下方当前场景和右下关系记忆，然后把手指收回 `Companion Director`]

> 接下来才轮到人味判断。`Personality Constitution` 是人格宪法，规定身份、稳定特质、禁止越界的行为和规则版本；`Current Context` 是当前场景，包括比赛状态、用户情绪和观看模式；`Relationship State + Memory` 是关系状态和记忆，包括双方熟悉到什么程度、用户偏好什么、明确拒绝过什么、还有什么话题没有聊完。
>
> 这些材料和已经确认的事实一起进入 `Companion Director`，也就是陪伴导演。它决定“说不说、说什么、什么语气、要不要主动、表现到什么程度”。用户只是问助攻者，所以 Director 可以把答案定为简短、明确、稍微带一点庆祝，而不是突然展开一大段战术课。
>
> 这就是动态人味的准确含义：事实不因为用户不同而改变，但表达会根据关系和当下场景变化；人格宪法又确保这种变化不会变成过度亲密、强行打扰或情绪绑架。

[沿 Director 的两条输出，先指 `Reply Realizer`，再指 `Presentation Plan`，最后汇到 `Server Delivery`]

> Director 接下来输出同一份 `Response Plan`，也就是回应计划，但它分成两类执行工作。
>
> 第一类交给 `Reply Realizer`。`SpeechPlan` 是说话计划，`Final text` 是最终文字。Reply Realizer 只负责把已经决定好的重点、语气和长度写成自然台词，比如：“法比安送出了助攻，这次配合很漂亮。”它不能重新决定事实，也不能重新发明人格。
>
> 第二类交给 `Presentation Plan`，也就是表现计划。`Speech` 是声音表达，`Motion` 是动作，`Hold` 是动作保持多久；箭头上的 `Voice Style` 是声音风格。它决定说这句话时角色怎样动、声音多有力、动作何时结束。
>
> 两类结果在 `Server Delivery` 汇合。这里把字幕、TTS 合成语音和 Live2D 动作送到客户端。`Playback ACK` 是播放确认回执，告诉服务端用户端究竟有没有展示和播放。到这里，一轮回答的主链才算真正完成。

[主链结束后，再依次指上方 Scheduler、下方 Observation、右上 Trace 和数据库]

> 现在再补三条支线，它们不改变主链，只负责处理特殊情况。
>
> 第一条是 `Scheduler + Proactive Gate`。Scheduler 负责优先级、打断、去重和 `TTL`；TTL 是这条任务还能有效多久。`Proactive Gate` 是主动开口闸门。人格宪法通过图上的 `proactive limits` 限制主动性：即使系统知道发生了进球，也要先判断现在适不适合打扰用户。`Run / proactive turn` 表示获准后才执行一次主动回合。
>
> 第二条是 `Observation Coordinator`，也就是观察协调器。`pending` 是待确认，`reconcile` 是把不同来源调和，`follow-up` 是后续跟进。如果用户比公共数据源更早喊“进球了”，这里会先保存为待确认观察，而不是立刻改写公共比分。
>
> 第三条是记录与恢复。`Agent Trace` 保存本轮 Trace 和引用过的 Fact IDs；`PostgreSQL + Outbox` 做事务持久化、幂等和重试发布。`CAS state + memories` 表示保存关系记忆前先核对版本，避免两次更新互相覆盖；`Trace persistence` 是长期保存过程记录；`playback result` 是把播放结果写回。这样以后才能回答“球球为什么这样说、用户究竟有没有收到”。

### 本图收口

> A1 只记一条主链：Agent 先弄清用户要什么并找到材料，事实闸门确认能说什么，Director 再结合人格、关系和场景决定怎样说，Reply Realizer 和表现计划负责执行，Delivery 负责送达，回执和 Trace 负责闭环。

## A2-L｜technical-layers.html｜技术架构分层（逻辑职责）

[打开 `technical-layers.html`。先指图中间从上到下的四层，再指右侧横向控制面，最后指左侧外部依赖]

> 这张图不是再讲一遍刚才的运行过程，而是回答：刚才看到的工作，在技术上应该怎样分组？
>
> 先把一个容易混淆的地方说清楚：图中是四个纵向职责层，加一个横向控制面，不是五个上下堆叠的程序。所谓“逻辑职责”，就是先把工作分清楚；它们今天仍然可以一起运行在同一个 Go 后端里。

[指最上方“应用与体验层”]

> 第一层是应用与体验层。这里有 `Flutter / 运营入口`。Flutter 客户端负责用户界面、Live2D、字幕和音频；运营入口负责事实校正。刚才用户问“谁助攻”，就是从这一层发出；球球最后的字幕、声音和动作，也回到这一层被用户感受到。

[向下指“实时执行层”]

> 第二层是实时执行层，也就是“把这一轮接住并跑起来”。`API` 是普通程序接口，`WebSocket` 是持续双向连接；`Voice Session` 是一轮语音会话；`Scheduler` 处理排队、打断和节奏；`Match Clock` 统一比赛阶段和时间。刚才总图里的统一接入与实时处理，主要落在这一层。

[在 Agent 智能层中从左到右移动]

> 第三层是 Agent 智能层，也是 A1 那张图的压缩版。这里故意从左到右分成三步。
>
> “事实认知”包括 `Intent`、`Tools` 和 `Grounding`：先理解问题，再调用工具，最后把回答钉在事实上。“陪伴决策”包括人格宪法、`Relationship` 关系状态和 `Director` 陪伴导演：决定此刻应该怎样陪。“表达执行”包括 `Reply Realizer` 和 `Presentation`：把已批准的决定变成自然台词、声音和动作。
>
> 因此第三层不是一个大模型盒子，而是“先查清、再决定、后表达”三个连续责任。A1 讲的是这三个责任怎样完成一轮决定；A2-L 讲的是它们在架构中属于同一智能层。

[指最下方“事实与数据层”]

> 第四层是事实与数据层。`Fact Ledger` 是事实账本；`PostgreSQL + Outbox` 保存长期事实、关系、审计和待发布消息；`Observation` 保存待确认观察；`Redis` 只保存会话和短期协调状态。上面的 Agent 之所以不会每轮都失忆，也不会随口改比分，就是因为它必须从这一层读取事实、关系和当前场景，并把结果写回。

[指右侧“横向控制面”，手势覆盖四层]

> 右侧不是第五个业务层，而是横向控制面。它包括身份、人格规则、用户主权、隐私和审计。所谓横向，就是每一层都要受它约束：入口要检查身份，实时执行要尊重打断，Agent 要遵守人格宪法，数据层要支持删除和审计。图中的“隐私 / 审计”连线只是一个落点，不代表控制面只管数据库。

[最后指左侧两个外部节点]

> 左边两个盒子是外部依赖，不属于球球内部层。比赛数据源提供赛程、比分和事件；外部 AI 能力包括 `ASR` 语音转文字、`LLM` 大语言模型和 `TTS` 文字转语音。它们可以被替换，而“事实认知—陪伴决策—表达执行”这套产品责任仍然属于球球。

### 本图收口

> 现在把前三张图连起来：00 告诉我们一轮体验从哪里来、到哪里去；A1 放大中间的决策过程；A2-L 再把这些工作放回四层架构和一条横向控制面。三个镜头讲的是同一件事，不是三套系统。

## A2-M｜technical-modules.html｜技术模块地图

[打开 `technical-modules.html`，按图中的蛇形主链从第一行走到第四行]

> A2-L 把责任分成了层，A2-M 把每层展开成真实模块。我们仍然追踪同一个问题，不逐个背名字。
>
> 第一行是入口与控制。用户通过 `Flutter Client` 说话，客户端里的 `VAD` 判断什么时候开始说、什么时候说完；运营人员通过 `Operator Console` 处理事实、比赛时钟、冲突和 `Draft` 草稿。`Auth / Session` 负责 `Access` 访问、`Refresh` 更新凭证和 `Scope` 权限范围。`Data Source Manager` 负责 `Poll` 轮询、`Replay` 历史回放和 `Freshness` 新鲜度检查。
>
> 第二行把输入跑起来。`Match Clock` 保存带版本的比赛阶段和时间；`Voice Session` 让语音依次经过 VAD、ASR 和 TTS；`Realtime Gateway` 负责 HTTP、WebSocket 和 `Subs` 订阅；`Scheduler + Proactive Gate` 处理优先级、打断、TTL 和是否打扰。
>
> 第三行完成核心判断。`Companion Agent｜事实认知` 识别意图、调用工具并做 Grounding；`Fact Ledger` 负责 `Projection` 统一事实投影、`Revision` 修订和 `Conflict` 冲突；`Observation` 处理待确认、调和和跟进；`Companion Director｜陪伴决策` 把宪法边界、关系状态和当前场景合成最终决定。
>
> 第四行负责表达和保存。`Reply Realizer` 把 SpeechPlan 写成 Text 文字；`Presentation` 决定声音、动作和保持时间；`PostgreSQL + Outbox` 保存事实、关系、Trace 和 Audit 审计；`Privacy / Retention` 处理导出、删除和清理；Redis 只承担短期协调。
>
> 这张图的关键不是模块多，而是责任顺序没有变：接入和控制先验明身份，实时模块把事情跑起来，Agent 查清事实，Director 决定怎样陪，表现模块执行，数据与隐私模块留下可追溯结果。它们今天可以在 Go 单体内协作，不代表每个盒子都是一台服务器。

### 转场

> 到这里，我们知道“正常情况下谁负责什么”。下一张 A3 专门看异常：如果身份失效、事实冲突、消息发送失败或用户要求删除，系统怎样把风险关在边界内？

## A3｜08-control-reliability.html｜控制面与可靠性闭环

[打开 `08-control-reliability.html`，沿“身份—事实—决定—交付—删除”走一圈]

> A3 不再重复正常回答，而是给刚才的主链加上保险。我们假设比赛数据源先报了一个助攻者，运营随后发现需要更正，看看系统怎样避免错误继续扩散。
>
> 首先是身份边界。`Auth / Session` 发放或刷新访问凭证；`Gateway Boundary` 检查 `Origin` 请求来源、`Token` 身份令牌和 WS 连接；运营人员还要受到 `operator scope` 权限范围约束，不是谁都能更改比赛事实。
>
> 接着是事实边界。`Source Manager` 检查轮询、回放和新鲜度；`Fact Ledger` 保留投影、修订和冲突。只有经过规范化的事件才能进入账本。`Transactional Outbox` 是事务消息寄存处，`Atomic publish` 表示事实写入和发布记录要么一起成功，要么一起失败；发送失败可以 Retry 重试。
>
> 事实变化以后，`Agent / Director` 仍要同时遵守已确认事实、人格宪法、关系和当前场景。`Observation` 决定待确认观察是继续跟进还是抑制；`Scheduler` 决定优先级、打断和 TTL；`Delivery Tracker` 记录文字、TTS 和播放结果。
>
> 最后是用户主权。`Privacy / Retention` 处理导出、删除和清理；PostgreSQL 保存事实、会话、Trace 和 Audit。当用户选择安静、结束或删除时，这些指令优先于主动陪伴，未播放内容应该被阻断，而不是为了显得有人味继续输出。
>
> 这张图还要分清当前能力和生产补齐项：当前系统已经有事实修订、关系与过程记录等基础能力；持久化重放游标、完整客户端 ACK、多副本共享调度和广播仍是后续生产能力，不能讲成已经上线。

### 第一层总结

> 第一层五张图已经形成闭环：00 看全貌，A1 看一次决定，A2-L 看职责分层，A2-M 看真实模块，A3 看风险怎样被身份、事实、人格、交付和隐私控制住。下面进入工程下钻，但仍然追踪同一条主线。

## 02-containers-mvp.html｜MVP 容器

## 03-runtime-voice.html｜用户语音时序

[打开 `03-runtime-voice.html`，严格从上到下读消息，不横向跳节点]

> 这是一张时序图。纵向表示时间从上往下走，横向是参与者。我们只追踪用户主动问“刚才是谁助攻的”这一轮。
>
> Flutter 先向 Auth 确保匿名会话有效；`anon` 是匿名，`refresh` 是凭证更新。然后打开经过身份认证的 Go WebSocket；`identity` 是身份，`subs` 是订阅。服务端返回 `session_opened`，表示会话已打开并可以开始一轮音频。
>
> 客户端用 VAD 判断开始和结束，把声音切成 `PCM chunks` 原始音频块，并发送 `asr_start` 开始识别。ASR 先返回 `partial transcript` 临时转写，让界面可以及时显示；确认用户说完后再返回 `final transcript` 最终转写。只有最终转写才作为正式用户轮次提交。
>
> Scheduler 收到新轮次后先 `cancel old` 取消旧回答，再加载关系和当前场景，随后让 Agent Core 处理。Agent Core 根据事实和人格产生 `Response Plan`，其中包括 reply 回复、tone 语气、`PresentationPlan` 表现计划和 Trace 过程记录。
>
> TTS 把文字合成声音；如果失败，`fallback error` 表示进入回退，字幕仍然可以继续。Delivery 把 subtitle 字幕、presentation 表现参数和 `voice_audio` 语音音频发送给 Flutter。客户端渲染并播放 Live2D，再回传 `displayed / playback`，也就是已经展示和播放的结果。
>
> 如果用户中途说“停”，`interrupt` 会打断旧回答；网络断开后，`reconnect` 重新连接并恢复仍然有效的会话上下文。整条链的原则是：新用户输入优先，字幕可以先到，声音失败不应让整个回答消失。
>
> 03 讲的是用户主动发问。下一张换一个起点：用户没有提问，而是比赛自己发生了新事件。

## 04-runtime-match-event.html｜比赛事件时序

[打开 `04-runtime-match-event.html`，仍然从上到下读]

> 比赛来源通过 `match poll / replay`，也就是轮询或历史回放，向 Ingest 发送事件；Operator 通过 `confirm / correct / revoke` 进行人工确认、更正或撤销。两个入口责任不同，但都先进入 Ingest。
>
> Ingest 做 `normalize` 统一格式、`dedupe` 去重并 `append revision` 追加修订，然后写入 Fact Ledger。账本的公开投影发生变化后，`Observer` 发现变化；如果用户曾提前报告同一件事，`Observation` 会处理那条 pending 待确认观察。
>
> 只有确认事实和当时的 snapshot 快照才进入 Agent。Agent 把事实、上下文和人格约束交给 Scheduler 与 Director；`Proactive Gate` 判断是否值得主动打扰，Scheduler 决定优先级和 TTL，Director 形成“说什么、怎么陪”的 Response Plan。
>
> Delivery 把字幕、声音和动作送到 Client，客户端再回传展示、播放和重连结果，Trace 记录本轮是否真正交付。
>
> 图中 `provisional` 是暂定，`confirmed` 是已确认，`revoked` 是已撤销，`reconciled` 是冲突已调和。它们不是四套业务，而是同一事实的修订轨迹。事实被撤销时会产生 `retraction` 撤回通知，防止旧反应在重连或重试后复活；持久化 `replay cursor` 回放游标仍属于生产补齐项。
>
> 03 和 04 的终点相同，起点不同：一条由用户说话触发，一条由比赛事件触发；两条最终都必须经过事实、节奏、Director、表现和回执。

## 05-event-flow.html｜事件与数据流

[打开 `05-event-flow.html`，先说明它不讲时间，再沿事实流和语音流各走一次]

> 04 已经讲了先后顺序，05 不再重复时间。数据流图回答的是：不同类型的数据从哪里来，经过哪里，最后进入哪个通道。
>
> 先走事实流。`Sources` 来源区里的比赛 API 和导播台进入 `Ingest` 接入区，经过 normalize 统一格式和 dedupe 去重，写入 `Fact Ledger` 事实账本。账本保存 `revision history` 修订历史，消息通过 `Outbox Fan-out` 分发；Fan-out 表示一条事件通知多个订阅者，`atomic publish` 是原子发布，`retry` 是失败重试。确认事实进入事件与陪伴策略，再进入 Agent + Director。
>
> 再走语音流。用户语音以 `PCM chunks` 进入 streaming ASR 流式识别，转成 `transcript` 文字；文字和 `Conversation Context` 对话上下文汇合。这里的 `user · match · relation` 是用户、比赛和关系背景，然后同样进入 Agent + Director。
>
> 两条流在决策中心汇合以后，Response Plan 分成客户端事件通道和客户端音频通道：字幕与动作走事件通道，TTS 流式音频走音频通道。`Delivery + Trace` 记录投递和播放状态。
>
> `Session / Auth` 用 identity 身份和 scope 权限保护接入；Observation 处理 pending 和 reconcile；`Privacy / Retention` 控制 export 导出、cleanup 清理和保留规则。标签 `idempotent` 表示可防重复，`replayable` 表示可回放，`async` 表示异步，`recovery` 表示恢复，`audit` 表示审计，`governance` 表示治理。
>
> 所以 04 是“什么时候做”，05 是“数据往哪里去”。下一张不再看逻辑流向，而是看这些程序今天实际住在哪里。

## 06-deployment-mvp.html｜MVP 部署

[打开 `06-deployment-mvp.html`，从用户设备走进单台 VM]

> 这张是当前部署事实。Flutter Web 或 Mobile 运行在用户设备上，请求先经过外部的反向代理和 TLS 加密入口，再进入一台云端 `VM`；VM 是虚拟机，可以理解成云上的一台电脑。
>
> VM 中用 Docker Compose 运行 Go Backend、Redis 7 和 PostgreSQL。Go Backend 内部包含 Ingress、Auth、Agent、Director 和 Outbox 等逻辑职责。PostgreSQL 是持久化数据库；Redis 只是短期会话和协调服务，不能决定比赛真相。
>
> 外部 AI API 和比赛数据 API 位于这台 VM 之外，后端通过 HTTPS 或 WebSocket 调用它们。图里没有多副本和故障转移，因为当前 MVP 就是单台 VM；这张图的价值是如实说明今天，而不是提前画成大规模平台。

## 07-deployment-production.html｜生产部署目标

[打开 `07-deployment-production.html`，先圈出所有 `planned`]

> 先读最重要的词：`planned` 是规划态，不代表已经上线。
>
> 未来用户先经过 `CDN / WAF / TLS`。CDN 是内容分发入口，WAF 是 Web 应用防火墙，TLS 是加密连接。请求再路由到多份 `Go API / WS × N`；N 表示若干副本，`Sticky WS` 表示同一条实时连接尽量保持在同一个实例，`shared scheduler` 是多副本共享调度。
>
> 比赛事件和 Outbox 消息由多份 `Go Event Worker × N` 处理。`Worker` 是后台工作进程，`replay` 是重放，`DLQ` 是 Dead Letter Queue 死信队列，用来保存多次失败后仍处理不了的消息。
>
> 托管 Redis 保存共享短期状态，托管 PostgreSQL 保存事实和可追溯历史。监控、日志和告警收集 `trace / metrics / alerts`，也就是追踪、指标和告警。外部 AI 与多源比赛 API 仍是外部依赖。
>
> 从 06 演进到 07，不是简单多开几台机器，还要补共享调度、事件广播、客户端 ACK、持久化重放游标、备份恢复和容量成本决策。因此 07 始终只能作为生产目标讲解。

## 09-realtime-contract.html｜实时接口与投递契约

[打开 `09-realtime-contract.html`，按“建会话—传语音—回结果—断线恢复”四段读]

> 第一段建立身份。Flutter 通过 `POST /api/session` 创建匿名会话，得到 `session_id` 会话编号和 `access_token` 访问令牌，再用令牌打开 `WS /ws/match/:matchId`，进入指定比赛房间。网关返回 `connection_id`，标识这一条具体连接。
>
> 第二段传递语音。`asr_chunk` 是音频块，`utteranceId` 是这一句话的编号，`sequence` 是第几块；它们让重复音频可以被识别和丢弃。`asr_finish` 表示用户已经说完。Scheduler 取消旧回合并加载上下文，Agent / Director 生成带 `traceId` 过程编号和 `version` 版本号的 ResponsePlan。
>
> 第三段投递结果。字幕、presentation 表现参数和 voice_audio 语音被装入 `versioned event envelope`，也就是带版本的消息信封。客户端回传 `voice_playback` 播放状态，告诉服务端声音是开始、结束、被打断、被设备阻止还是失败。
>
> 第四段处理断线。`interrupt` 取消当前回合；`reconnect {lastSeenVersion}` 告诉服务端客户端最后看到哪个版本；Trace Store 读取 snapshot 快照和 cursor 游标，只重放 `replay eligible` 仍然有效的内容。已经取消、过期或撤销的旧回答不能重新播放。
>
> 当前已有会话鉴权、音频序号和播放状态回传；持久化 replay cursor、完整客户端 ACK 和多副本广播仍是生产前合同。

## 10-fact-reliability.html｜事实与可靠性状态

[打开 `10-fact-reliability.html`，从 Sources 到 Recovery 只向右走]

> 这张图追踪的不是一次请求，而是一条事实怎样取得“可以引用”的资格。
>
> `Sources` 来源区提供比赛数据和人工确认。来源健康检查先看游标、延迟和可用性；通过以后进入 `Ingest`，完成去重、校时和归一，成为“已规范化”的候选事实。
>
> 在 `Fact states` 事实状态区，证据不足或来源冲突时先进入“待确认”。复核通过以后成为“已确认事实”，只有这个版本才能进入 Agent 和用户呈现。冲突和 `reconciled` 调和不是图上额外的独立服务，而是保留在事实账本里的修订轨迹。事实后来被否定时进入“已撤销”，并通过 `retraction` 撤回通知停止旧反应。
>
> 已确认事实与 Outbox 消息在同一事务中提交。发布成功以后，图上写的是“进程内已发布”，只表示服务内部订阅队列已经收到，不等于客户端已经播放。发送失败会按退避策略进入“重试”；超过次数进入 `DLQ` 死信记录；人工批准后才允许“受控重放”，并且仍使用原来的事实版本。
>
> 右侧 Observation 的“观察待调和”保存用户提前报告但尚未被公共来源确认的内容，后来根据事实变化选择跟进或抑制。
>
> 这张图只记三句话：事实有资格，发布有恢复，撤销能阻断。当前已有账本修订、Observation 调和和进程内 Outbox；DLQ、持久化游标和多副本广播仍属于生产补齐项。

## 11-delivery-assurance.html｜表现、评测与运维闭环

[打开 `11-delivery-assurance.html`，从 Decision 向右走到 Assurance]

> 最后一张回答：Director 已经决定怎样陪以后，怎样保证文字、声音和动作没有各自发挥，并且出了问题能够收缩。
>
> `Decision` 是决定区。Response Plan 先进入“资格与降级门”，重新检查事实资格、会话是否已经结束、用户是否取消或静音，以及当前媒介能否使用。
>
> `Adapters` 是适配器区，把同一份计划翻译成不同媒介。Reply Realizer 把 SpeechPlan 变成 Text 文字；TTS Adapter 把文字变成音频；Presentation 准备动作、保持时间和静态回退。三者不能重新决定事实和人格。
>
> 文字、音频和动作装进 `Delivery Envelope` 投递信封，信封带版本和 traceId，可以识别并丢弃过期内容。Flutter Client 消费同一份信封，再产生 `Playback Receipt` 播放回执。`started` 是开始，`ended` 是结束，`interrupted` 是被打断，`blocked` 是设备阻止播放，`failed` 是播放失败。
>
> `Evidence` 是证据区。Trace + Audit 把事实编号、Director 决定和播放回执串在一起。`Assurance` 是保障区：Metrics / Alerts 是指标和告警，Release Evals 是发布评测，使用黄金样例、抽样和回归检查版本质量；门禁失败以后进入“收缩 / 回滚”，优先保留文字和事实，关闭声音、动作或主动性。
>
> 当前可以记录 Trace 和播放状态；完整指标、发布评测门、自动收缩与回滚仍是生产目标。用户取消、结束、静音和删除则始终优先，未播放内容不能继续输出。

>
> 用户问：“刚才是谁助攻的？”系统先接住用户的话，也接住比赛来源和导播校正。事实账本保存版本和冲突，事实验证确认可以引用“法比安助攻”。
>
> 接着系统读取关系记忆和当前场景：我们熟悉到什么程度，用户现在是什么情绪，正在专心看球还是随口聊天。人格宪法再划出身份、主动性和表达边界。
>
> Director 把“发生了什么”“此刻怎样陪”“哪些边界不能越过”合成一份回应计划。Reply Realizer 写出台词，TTS 合成声音，Presentation 安排动作，Delivery 把同一份计划送到 Flutter 客户端。
>
> 客户端回传展示和播放结果，Trace 把引用事实、决策和回执串起来。事实有冲突就先待确认，消息失败就重试或降级，事实撤销就阻断旧反应，用户选择安静、结束或删除时，系统立即让出控制权。
>
> 到这里，15 张图实际上只讲清了一套能力：事实决定发生了什么，动态状态决定此刻怎样陪，人格宪法决定不能越过什么，Director 决定最终怎样回应，交付与可靠性模块保证用户真正收到，而且出了问题能够解释、纠错和收缩。

## 结束语

> 一个数字人 Agent 不是一个会说话的大模型，也不是给聊天框套一个 Live2D 形象。
>
> 它必须把事实验证、关系连续性、当前场景、人格边界、陪伴决策、文字声音动作和工程可靠性连成闭环。球球真正的产品特点，正是“可信事实、动态人味和人格宪法约束下的表达”同时成立。
