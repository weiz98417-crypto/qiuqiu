# 球球实战导演重构方案

## 文档状态

- 状态：阶段 A-D 已完成；阶段 E 核心链路已完成，流式转写待后续；阶段 F 待执行
- 日期：2026-07-20
- 范围：实战导演页面、比赛主时钟、人工事件录入、外部数据源候选事实、客户端比赛状态同步
- 不在本阶段：赛前配置重做、球球人格与话术优化、外部供应商选型

当前实现已经覆盖统一事件草稿、独立比赛主时钟、候选/确认事实边界、客户端时间与事件同步、导演录音转草稿、语音冲突逐项核对、候选采用、事实调和、换人同队强校验、VAR 引用原进球、审计式事实更正和独立比分更正。导演录音目前在停止录音后提交 ASR，不提供边说边显示的流式中间结果；90 分钟整场回放压测也尚未执行，这两项不得计入当前验收通过范围。

## 1. 结论

当前页面难用，不是因为足球事件本身复杂，而是同一页同时存在三套互相独立的操作模型：左右“事实员”的快捷发布、中间“逻辑组合器”的详细草稿、顶部可直接编辑的比分与时间。它们共享球队、球员、比分和时间，却没有共享同一个事件草稿，所以操作者看到的选择和最终发送的内容可能不是一回事。

实战导演应收敛为一条主链路：

> 选择球队 -> 选择球员或球队 -> 选择行为 -> 补充该行为必需的信息 -> 核对事件 -> 确认发送给球球

页面只维护一个 `DraftEvent`。任何快捷按钮和键盘快捷键都只能帮助填写这个草稿，不能绕开草稿直接发布。所有正式写入都经过右侧唯一发布区。

比赛时间也必须从事件中拆出来：后台维护独立运行的比赛主时钟，客户端持续同步展示；创建事件时冻结一份“事件发生时间”，发布事件不能推进或回退主时钟。

## 2. 当前问题与已确认根因

### 2.1 三套状态同时存在

当前实现同时维护 `side`、`focusedRole`、`eventType`、`mainPlayer`、两边当前球员、表单 slots、比分输入框和更正状态。左右事件按钮调用 `publishPreset()` 直接发布；中间表单则通过另一条路径构造 `payloadFromPreset()`。

结果是快捷入口与详细草稿并不是同一个事件。快捷按钮即使发布了“射门”，中间仍可能继续显示上一次“进球”草稿，操作者会自然认为按钮没有生效。

### 2.2 切换球队会保留对方球员

`setSide()` 在新球队没有当前球员时，会保留旧的 `mainPlayer`。实测页面已经出现：顶部显示“当前主队”，中间草稿仍是“客队 / 哈弗茨 / 进球”。这不是偶发显示问题，而是现有状态规则的直接结果。

### 2.3 切换行为没有清理旧行为内容

`syncEventTypeUI()` 会重建参与人槽位，但不会完整重置旧事件的描述、主动话术、主参与人和动作；动作甚至只在当前值为空时才采用新行为默认值。因此从“进球”切到“射门”后，仍可能保留 `celebrate`、“进了”等进球内容。

### 2.4 行为按钮承担了错误职责

事实员区域中的“进球、射门、黄牌”等按钮视觉上像“选择行为”，实际点击立即发送网络请求。选择和发布被压成同一个动作，既无法核对，也无法组合助攻者、被犯规者、换上/换下球员等关系。

### 2.5 比分、主时钟和事件互相污染

- 快捷进球会先直接修改顶部比分输入框。
- 后端 `Snapshot.Clock` 和 `Snapshot.Period` 由最后一条有效事件覆盖。
- 没有事件时，后台不存在可独立运行并同步给客户端的比赛时钟。

因此“显示当前比赛时间”和“记录某个事件发生在何时”目前是同一个字段的两种用途，无法满足持续计时、延迟录入和事件回看。

### 2.6 响应式布局破坏操作顺序

页面在视口宽度低于 1320px 时，把中间逻辑组合器排到最前，两个事实员面板放到下方。当前常用窗口中，操作者先看到一整屏旧草稿，却看不到球队和球员选择区，核心链路被页面布局打断。

## 3. 产品原则

1. **一个页面只有一个当前事件。** 所有控件都读写同一个 `DraftEvent`。
2. **选择不等于发布。** 球员、行为、模板和快捷键只组装草稿；发布按钮是唯一正式写入口。
3. **先明确谁，再明确做了什么。** 行为决定后续需要哪些参与角色，而不是展示一张永远相同的长表单。
4. **只显示当前行为需要的字段。** 射门不展示“进球者”，换人不展示“助攻者”。
5. **主时钟、事件时间、记录时间分离。** 三者不能互相改写。
6. **候选事实不影响客户端。** 只有 `confirmed/reconciled` 的公共事实才能改比分、进入客户端事件轮播并触发球球主动互动。
7. **人工和自动化共用同一事实合同。** 来源可以不同，校验、生效、修订和审计规则必须相同。

## 4. 新页面信息架构

```text
+--------------------------------------------------------------------------------+
| 主队 0 : 0 客队       上半场 23:41  [暂停] [-10s] [+10s]     数据源：正常     |
+----------------------+---------------------------+-----------------------------+
| 1. 参与者            | 2. 行为                   | 3. 当前事件  [语音录入]     |
| [主队] [客队]        | 高频                      | 主队 · 佩德里               |
| 搜索球员             | [射门] [进球] [犯规]      | 射门 · 23:41               |
| 10 佩德里            | 纪律                      | 传球者：亚马尔（可选）      |
| 19 亚马尔            | [黄牌] [红牌]             | 描述：禁区外远射            |
| 7 莫拉塔             | 人员 / 战术               | 比分影响：无                |
|                      | [换人] [战术变化]         | 事实：已确认                |
| 快捷组合             | 特殊                      | [暂存为候选] [确认并发送]   |
| [佩德里 + 射门]      | [VAR] [伤停] [备注]       |                             |
+----------------------+---------------------------+-----------------------------+
| 已发布事实 | 待确认 | 冲突/更正                                    [展开时间线] |
+--------------------------------------------------------------------------------+
```

### 4.1 顶部比赛条

顶部只承担全场状态：球队、已生效比分、比赛阶段、后台主时钟和数据源健康度。

- 比分不再使用可随手修改的数字输入框。
- 进球、进球取消和比分更正通过事实命令改变比分。
- 人工改分放在独立“比分更正”操作中，必须填写原因并进入审计时间线。
- 主时钟操作只影响 `MatchClock`，不创建比赛事件。

### 4.2 左侧：参与者

左右两个事实员面板合并为一个参与者区域，通过主队/客队分段控件切换。

- 先选球队，再显示该队球员。
- 支持号码、姓名搜索。
- 选中球员后有唯一明确的高亮状态。
- 切换球队时，如果该队没有选中球员，当前主参与人必须清空，禁止保留对方球员。
- “战术变化、持续压迫、比赛开始、比赛结束”等球队级行为允许不选球员。
- 远端事实员的输入不再复制一整套按钮，而是进入底部“待确认”队列。

### 4.3 中间：行为

行为按比赛工作流分组，而不是把 15 个按钮无差别平铺：

- 高频：射门、进球、绝佳机会、扑救、错失、犯规。
- 纪律：黄牌、红牌、点球。
- 人员与战术：换人、战术变化、持续压迫、伤停。
- 特殊：VAR 检查、VAR 结果、进球取消、备注。

单击行为只更新草稿，并自动完成以下工作：

- 写入事件类型。
- 把当前球员分配到该行为的主角色。
- 采用该行为默认强度和 Live2D 动作。
- 清理上一种行为专属的角色、描述模板和主动话术。
- 从主时钟冻结事件发生时间。
- 展示右侧还缺哪些必填项。

### 4.4 右侧：当前事件

右侧是唯一草稿和唯一发布入口，默认只显示人能读懂的事件摘要，技术字段放入“高级设置”。

语音入口放在“当前事件”标题栏右侧，使用麦克风图标和“语音录入”文字。入口不放在全局导航、顶部比赛条或发布按钮旁边，避免操作者误解为直接播报或直接发布。录音、实时转写、结构化结果和错误都在当前事件区原位展示，不使用阻断操作的弹窗。

语音交互状态：

- 默认：显示 `语音录入`。
- 录音中：显示录音时长、实时转写和明确的停止按钮。
- 识别中：保留转写内容，显示“正在整理事件草稿”。
- 已整理：自动填充草稿，并高亮由模型推断或置信度不足的字段。
- 失败：保留原草稿和可用转写，允许重试或直接手工编辑。

主要内容：

- 谁做了什么。
- 对谁或由谁协作。
- 事件发生时间。
- 是否影响比分，以及生效后的比分预览。
- 事实级别：已确认或候选。
- 最终描述。
- 球球处理方式：自动反应、只记事实、人工话术。

发布动作：

- 主按钮：`确认并发送给球球`，创建公共事实。
- 次按钮：`暂存为候选`，只进入待确认队列，不改客户端比分、不轮播、不主动说话。
- 未满足必填条件时，发布按钮禁用，并就地指出缺失内容。

## 5. 唯一事件草稿模型

```ts
type DraftEvent = {
  matchId: string
  source: 'operator' | 'operator_voice' | 'external'
  sourceRef?: string
  transcript?: string
  inferredFields: string[]
  fieldConfidence: Record<string, number>
  teamId: 'home' | 'away' | null
  eventType: EventType | null
  occurredPeriod: MatchPeriod
  occurredSeconds: number
  capturedClockVersion: number
  primaryParticipant: Participant | null
  participants: Participant[]
  description: string
  intensity: 1 | 2 | 3 | 4 | 5
  recommendedAction: string
  factStatus: 'provisional' | 'confirmed'
  deliveryMode: 'auto' | 'quiet' | 'manual'
  proactiveText: string
  scoreEffect: ScoreEffect | null
  revisionOf: string | null
  dirtyFields: string[]
}
```

### 5.1 状态转换

```text
empty
  -> team_selected
  -> actor_selected（球队级事件可跳过）
  -> action_selected
  -> incomplete / ready
  -> publishing
  -> published | publish_failed

任意阶段切换球队或行为
  -> 清理不兼容字段
  -> 重新校验
```

### 5.2 更新规则

| 操作 | 必须更新 | 必须清理 |
|---|---|---|
| 切换球队 | `teamId`、候选球员列表 | 对方球员、对方参与角色、旧比分影响 |
| 选择球员 | 主参与人、当前行为主角色 | 同一角色旧球员 |
| 切换行为 | 类型、默认动作、强度、角色结构、事件时间 | 旧行为 slots、模板描述、人工话术、旧比分影响 |
| 选择模板 | 描述 | 不改变球队、球员、行为、时间和比分 |
| 清空草稿 | 回到 `empty` | 除比赛、主时钟和已生效比分外全部清空 |
| 发布成功 | 写入时间线并创建新空草稿 | 不改变主时钟；比分只采用服务端公共快照 |
| 发布失败 | 保留草稿供修正 | 恢复服务端比分，不丢用户输入 |

## 6. 行为与参与角色

| 行为 | 主体必填 | 补充角色 | 比分影响 | 默认事实策略 |
|---|---|---|---|---|
| 进球 | 进球者，可在紧急场景暂缺 | 助攻者、策动者 | 当前队 +1 | 人工确认后生效；候选不生效 |
| 射门 | 射门者 | 传球者、封堵者、门将 | 无 | 可直接确认 |
| 扑救 | 门将 | 射门者、二点球员 | 无 | 可直接确认 |
| 错失 | 错失者 | 传球者、门将 | 无 | 可直接确认 |
| 犯规 | 犯规者 | 被犯规者 | 无 | 可直接确认 |
| 黄牌/红牌 | 吃牌球员 | 对抗对象、关联犯规 | 无 | 红牌建议二次核对 |
| 点球判罚 | 受益球队或造点者 | 犯规者 | 无 | 确认后公开，不直接加分 |
| 换人 | 上场、下场两人 | 无 | 无 | 两人必须同队 |
| 战术变化/持续压迫 | 球队 | 关键球员可选 | 无 | 可直接确认 |
| VAR 检查 | 关联事件或球队 | 受影响球员 | 无 | 只作为候选状态 |
| VAR 结果/进球取消 | 关联原事件 | 受影响球员 | 按引用事实重算 | 必须确认并引用原事实 |

校验放在共享领域层，人工页面和外部数据源都必须经过同一套规则，不能只靠前端禁用按钮。

## 7. 快捷操作

快捷方式减少操作次数，但不建立第二条发布链路。

### 7.1 页面快捷组合

- 选择球员后展示其最近常用组合，如“佩德里 + 射门”。
- 点击组合等价于连续执行“选球队、选球员、选行为”，结果仍进入右侧草稿。
- 不记忆上一次对方球队或不兼容的参与角色。

### 7.2 键盘

- 数字键选择高频行为，只更新草稿。
- 上下键移动球员，回车选中。
- `Ctrl+Enter` 只在草稿 `ready` 时执行主发布动作。
- `Esc` 清空当前草稿，但必须保留主时钟和比赛状态。

### 7.3 不保留的旧行为

- 点击事件按钮立即发布。
- 靠左右两套相同按钮决定球队。
- 事件按钮同时偷偷切换比赛阶段。
- 通过旧草稿字段推断本次快捷事件。

## 8. 主时钟与事件时间

### 8.1 独立主时钟

新增 `MatchClock`，不再从最后一条事件推导当前时间：

```go
type MatchClock struct {
    MatchID       string
    Period        string
    ElapsedSeconds int
    Running       bool
    AnchorAt      time.Time
    Source        string
    Version       int64
    UpdatedAt     time.Time
}
```

- `ElapsedSeconds` 是最近一次落库基准。
- `Running=true` 时，客户端按 `AnchorAt` 本地平滑计时。
- 服务端定期或在重连时发送新基准，客户端校正漂移。
- 开始、暂停、校时和切换比赛阶段都增加 `Version`，防止旧请求覆盖新时钟。

### 8.2 三种时间

| 时间 | 含义 | 是否可修改主时钟 |
|---|---|---:|
| 主时钟 | 当前比赛进行到哪里 | 是，只能通过时钟命令 |
| 事件发生时间 | 该事件在比赛中何时发生 | 否 |
| 记录时间 | 后台何时收到或发布该事件 | 否，服务端生成 |

当操作者选择行为时，系统从主时钟复制 `occurredPeriod + occurredSeconds` 到草稿。即使 12 秒后才发布，事件仍显示发生在选择行为的时刻。操作者可以在发布前小幅校正事件时间，但这不会让客户端主时钟跳动。

### 8.3 API 与消息

- `GET /api/matches/{matchId}/clock`：读取主时钟。
- `PATCH /api/matches/{matchId}/clock`：开始、暂停、校时、切换阶段，要求版本匹配。
- WebSocket `match_clock`：给客户端和导播台推送主时钟基准。
- `MatchEvent.clock` 保留兼容，但语义明确为事件发生时间；后续可迁移为 `occurredPeriod/occurredSeconds`。
- `match_snapshot` 组合“独立主时钟 + 公共事实比分”，不再用最后事件覆盖当前时钟。

## 9. 比分与客户端展示规则

### 9.1 生效边界

| 输入 | 导播台时间线 | 客户端比分 | 客户端事件轮播 | 球球主动互动 |
|---|---:|---:|---:|---:|
| 草稿 | 否 | 否 | 否 | 否 |
| 候选事实 `provisional` | 待确认区 | 否 | 否 | 否 |
| 已确认事实 `confirmed` | 已发布区 | 是 | 是 | 按调度规则 |
| 冲突事实 `conflict` | 冲突区 | 否 | 否 | 否 |
| 已调和事实 `reconciled` | 已发布区 | 是 | 是 | 按调度规则 |
| 已撤销事实 `revoked` | 保留审计 | 回滚重算 | 展示更正而非原事件 | 可触发更正互动 |

### 9.2 比分计算

- 比分由有效公共事实重放得到，不相信前端提交的任意绝对比分。
- 进球草稿只显示预期变化，例如 `0-0 -> 1-0`。
- 服务端确认成功后，导播台与客户端采用服务端公共快照。
- 进球取消、事实撤销和更正通过引用原事实重算比分。
- 手工比分更正作为独立审计命令，不伪装成普通进球。

## 10. 人工导演、语音与外部数据源

人工点击、人工语音和外部数据源三种来源进入相同事实入口：

```text
人工点击 -------------------------------+
人工语音 -> ASR -> 结构化抽取 -> 名单校准 -+-> 统一校验 -> 候选/确认 -> 公共事实 -> 球球/客户端
外部数据源 -> 标准化 -> 去重 ------------+
```

- 可信且提供最终状态的数据源可以按策略直接形成确认事实。
- 低置信度、信息不完整或与现有事实冲突的数据进入待确认队列。
- 待确认项提供“采用到当前草稿”，由导演补齐球员、事件时间或关联事实后确认。
- “人工接管”只暂停自动发布，不停止数据接收；候选仍可进入队列。
- 自动化策略控制哪些事件可以自动确认、哪些必须人工确认、普通事件冷却时间和主动互动策略。

### 10.1 外部数据源注入边界

- 外部事件先标准化、去重和校验，默认形成候选事实，不直接修改客户端。
- 只有命中明确的自动确认策略，且来源可信、状态为最终态、字段完整、与现有事实不冲突时，才允许自动形成确认事实。
- 导演可以采用候选到当前草稿，修改球队、球员、事件时间、关联事实和事实状态后再确认。
- 对候选的人工修改必须保留原始数据、修改差异、操作者和确认时间，不能覆盖原始证据。
- 自动确认和人工确认最终调用同一事实发布合同；客户端不区分事实来自点击、语音还是外部源。

### 10.2 导演语音录入流程

```text
点击“语音录入”
  -> 记录录音开始时的比赛主时钟
  -> mimo-v2.5-asr 实时转写
  -> mimo-v2.5-pro 按 DraftEvent Schema 抽取字段
  -> 使用当前比赛、双方名单和已有事实校准
  -> 共享领域规则校验
  -> 填入或补全当前 DraftEvent
  -> 导演核对
  -> 暂存候选 / 确认并发送
```

语音只是一种草稿输入方式，不是第三条发布路径：

- 模型只负责抽取球队、球员、行为、参与角色、描述和事件时间候选。
- 比分影响、事实状态、是否可发布和客户端可见性由确定性规则计算，禁止交给模型推断。
- 录音开始时冻结主时钟作为默认事件发生时间；语音中明确说出时间时，将识别值作为待核对修改，不直接改写主时钟。
- 球员姓名无法匹配名单时保留原始转写并标记“待确认球员”，禁止自动选择相似姓名。
- 低置信度、球队冲突、同队关系不成立或引用事实缺失时，草稿保持 `incomplete`，发布按钮禁用。
- 空草稿直接填充；已有草稿只自动补充空字段。与已有字段冲突时显示字段差异，由导演选择是否应用，禁止静默覆盖。
- 所有模型推断字段在导演确认或手工修改前保持高亮，并提供“撤回本次语音修改”。

### 10.3 MiMo 模型与密钥边界

当前阶段允许导播台和数字人共用同一 MiMo 账号及同一个 `MIMO_API_KEY`，但共用密钥不等于共用会话、提示词或模型调用：

| 用途 | 模型 | 上下文边界 |
|---|---|---|
| 导演语音转写 | `mimo-v2.5-asr` | 只处理本次录音 |
| 导演事件结构化 | `mimo-v2.5-pro` | 比赛、名单、事件 Schema，不读取用户关系记忆 |
| 数字人对话 | `mimo-v2.5-pro` | 用户对话、比赛事实、关系状态，不读取导演草稿 |
| 数字人语音合成 | `mimo-v2.5-tts` | 只处理最终回复文本和音色参数 |

- `MIMO_API_KEY` 只保存在后端环境变量中，导播台和数字人前端都只调用球球后端。
- 导演事件结构化使用低随机性、严格 JSON Schema 和字段白名单；数字人对话使用独立的提示词、采样参数和记忆上下文。
- 两条链路分别设置超时、限流、日志和指标，禁止通过共享全局会话对象复用上下文。
- 日志不得记录密钥和完整原始音频；转写文本按运营审计策略设置保留时间。
- 生产环境可按服务或环境拆分多个 Key，以便独立限额和吊销，但不作为当前版本的上线前置条件。

## 11. 错误、空状态和恢复

| 场景 | 操作者看到什么 | 系统行为 |
|---|---|---|
| 未配置球队/名单 | 参与者区显示缺失项和“去赛前配置” | 禁止球员级事件发布 |
| 未选择必填球员 | 右侧标出具体缺失角色 | 发布按钮禁用 |
| 发布中 | 发布区锁定并显示进度 | 幂等键防止双击重复 |
| 发布失败 | 原草稿保留，显示服务端原因 | 恢复公共比分，不清空输入 |
| 时钟版本冲突 | 提示“时间已被另一端校准” | 拉取最新主时钟，事件时间不自动改写 |
| 数据源离线 | 顶部显示离线和最后更新时间 | 人工导演仍可工作 |
| 外部事实冲突 | 进入冲突区并并排展示证据 | 不影响客户端，等待调和 |
| 麦克风未授权 | 当前事件区提示开启权限 | 原草稿保持不变，允许继续手工录入 |
| ASR 或结构化失败 | 保留已获得的转写并提示具体阶段 | 不创建事实、不清空原草稿，允许重试 |
| 语音结果与草稿冲突 | 冲突字段并排显示新旧值 | 只补空字段，冲突值等待导演应用 |
| 更正/撤销 | 时间线保留原记录并串联修订 | 客户端收到明确更正事件 |

## 12. 响应式与可访问性

- `>= 1180px`：保持参与者、行为、当前事件三列，不再按整屏宽度把参与者移到页面底部。
- `900-1179px`：侧导航缩为图标栏；参与者与行为合并为左栏，当前事件固定右栏；时间线使用底部抽屉。
- `< 900px`：按“参与者 -> 行为 -> 当前事件”单列排列，当前草稿摘要和发布按钮吸底；用于应急操作，不作为主工作环境。
- 所有可点击目标至少 44px；球队和事实状态不能只靠颜色区分。
- 球员、行为和发布区支持完整键盘路径和明确焦点样式。
- 发布前焦点顺序必须遵循操作顺序，错误提示与对应字段关联。

## 13. 实施阶段

### 阶段 A：建立安全基线

- 补充当前错误复现场景测试，锁定球队、球员、行为、动作、描述和比分不串状态。
- 为公共事实、候选事实和客户端可见性建立合同测试。
- 为主时钟与事件时间分离建立后端测试。

### 阶段 B：后端主时钟与比分边界

- 在 `matchstate` 增加独立 `MatchClock` 存储和版本控制。
- 调整快照构建，不再从最后事件推导当前时间。
- 增加时钟 API 和 WebSocket 消息。
- 将比分更新限制为公共事实重放结果。

### 阶段 C：统一事件草稿

- 提取纯状态模块，使用显式 action 更新 `DraftEvent`。
- 统一人工详情、快捷组合和键盘入口。
- 删除 `setSide()` 保留旧球员、旧行为字段残留和事件按钮直接发布路径。
- 建立行为角色定义与共享校验规则。

### 阶段 D：实战导演页面重排

- 合并左右事实员为参与者区。
- 建立行为分组和唯一当前事件区。
- 将已发布、待确认、冲突/更正移到统一时间线。
- 去掉顶部可随手编辑的比分，新增审计式比分更正。

### 阶段 E：语音、多源数据流与客户端联通

- 在当前事件区增加语音录入、实时转写、字段差异和失败恢复状态。
- 增加后端导演语音草稿接口，串联 ASR、事件结构化、名单校准和共享规则校验。
- 隔离导演结构化与数字人对话的提示词、上下文、超时和限流，共用后端托管的 MiMo 密钥。
- 外部源统一进入候选/确认事实入口。
- 客户端消费独立主时钟和公共事实快照。
- 验证候选事件不改比分、不轮播、不触发球球。
- 验证确认、更正、撤销和 VAR 结果能够正确更新客户端。

### 阶段 F：实战压测与灰度

- 使用完整比赛回放连续操作 90 分钟。
- 记录每类事件平均完成时间、误发率、撤销率和时钟漂移。
- 在真实外部数据延迟下验证人工接管、候选调和和恢复流程。

## 14. 验收场景

1. 选择“主队 -> 佩德里 -> 射门”，草稿必须显示主队、佩德里、射门、`focus`，比分无变化，不能出现进球话术。
2. 从“客队 -> 哈弗茨 -> 进球”切到主队且未选人，主参与人必须为空，不能保留哈弗茨。
3. 从进球切换为黄牌，进球者、助攻者、`celebrate`、进球描述和比分影响必须全部清除。
4. 单击任何行为只更新草稿，不产生网络事件；只有唯一发布按钮可以写入。
5. 进球候选发布后，导播台待确认区可见，但客户端仍保持原比分且球球不主动说话。
6. 进球确认后，比分只增加一次，客户端事件轮播包含事件发生时间，球球按调度规则互动。
7. 主时钟持续运行 60 秒且没有任何事件，导播台和客户端时间仍同步前进。
8. 23:41 选择射门、23:53 发布，事件时间保持 23:41，主时钟保持 23:53 附近且不跳回。
9. 换人必须选择同队的上场与下场球员，否则不能发布。
10. VAR 取消进球必须引用原进球，比分重算并向客户端发送更正，而不是创建一个无关联备注。
11. 外部源与人工源在同一时间窗口给出冲突进球时，客户端不更新比分，冲突进入调和队列。
12. 1280px 宽度下，参与者、行为和当前事件必须同时可见；不允许把参与者放到逻辑组合器下方。
13. 空草稿下说“德国队换人，菲尔克鲁格换下哈弗茨”，只能生成包含球队、换人角色和录音时比赛时间的草稿，不能自动发布。
14. 语音中的球员不在当前球队名单时，保留原始姓名并标记待确认，不能用相似姓名自动替换。
15. 已有“主队、佩德里、射门”草稿时，语音识别出“客队进球”必须显示字段冲突，不能静默覆盖原草稿。
16. ASR 或事件结构化失败后，原草稿、转写和主时钟都保持可用，客户端不能收到任何新事实。
17. 导播台与数字人可以共用后端 `MIMO_API_KEY`，但自动化测试必须证明前端响应、网络载荷和日志中均不出现密钥，且两条链路的上下文不会串用。

## 16. 实施前确认点

本方案建议采用以下默认决策：

1. 行为按钮只组装草稿，永不直接发布。
2. 人工导演主发布按钮创建确认事实；不确定时使用“暂存为候选”。
3. 左右事实员合并为一个参与者区；远端输入改为待确认队列。
4. 比分不允许在顶部直接编辑，手工改分走带原因和审计的更正命令。
5. 事件选择时冻结发生时间，发布不修改主时钟。
6. 语音入口位于“当前事件”标题栏，只生成或补全草稿，永不直接发布。
7. 导播台和数字人当前共用后端托管的 `MIMO_API_KEY`，但使用独立模型调用和上下文。
8. 外部源默认形成候选；只有满足明确自动确认策略时才能直接形成公共事实。

确认这些决策后，再进入阶段 A 和阶段 B，先把状态合同与时间底座做对，再重排页面。
