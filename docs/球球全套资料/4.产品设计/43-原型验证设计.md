# 原型验证：用 Google Stitch 生成可交互陪看原型

> 文档类型：产品设计阶段的原型生产说明  
> 适用阶段：信息架构、页面规格、控制与状态规则已经形成；进入技术 POC 和正式工程开发之前  
> 本轮原型基准：移动端 390 × 844 首轮测试帧；这是测试画布，不是最终设备或品牌视觉定稿  

## 本阶段目标

本篇不再讨论“原型要研究什么”。它的工作是把已经写好的产品设计，逐页变成 Google Stitch 中可点击、可串联、可拿去走查的原型。

完成后应有两组彼此隔离的页面：10 个移动端用户页面，覆盖一次完整的陪看过程；6 个桌面端导演台页面，覆盖赛前准入、候选事实、复核发布、更正、暂停、交接与审计。两端不是同一套导航换皮：用户端解决个人观看与控制，管理端解决受限运营的事实可靠和安全处置。

原型的价值不在于展示一个很会说话的角色，而在于让团队尽早看见三个问题：

- 用户能否在进入前理解“人工智能陪看”和“本场控制”；
- 比赛事实、角色表达、用户观点和系统状态能否被清楚分开；
- 用户是否能在任何页面安静、改成文字、暂停自动表达或结束本场。

本篇的直接产物是两个 Google Stitch 原型区、每页的可复现提示词、16 张已命名页面，以及两条各自闭合的主路径。用户走查、访谈和评测指标属于 45-产品评测体系设计；技术边界验证属于 44-产品承诺的技术边界验证设计。不要把这三个阶段重新混在一份“原型验证”里。

## 原型生产总流程

每一个 Step 都按相同顺序执行。不要先连续生成十六张好看的页面，再回头寻找设计依据。

~~~mermaid
flowchart LR
    A["读对应设计规格"] --> B["复制本页 Stitch 提示词"]
    B --> C["在 Google Stitch 生成或修改页面"]
    C --> D["按组件与状态清单核验"]
    D --> E{"缺项或误导？"}
    E -->|"是"| F["追加精确修复提示词后重生成"]
    F --> D
    E -->|"否"| G["命名、连线、归档提示词与截图"]
~~~

### Stitch 中的固定操作

1. 在 Stitch 中建立两个区或两个项目：用户端“陪看原型 v1 — 用户端”和管理端“陪看原型 v1 — 导演台”。用户端画布为 Mobile，管理端画布为 Desktop。
2. Step 1 生成后，把它当作用户端视觉基线；Step 11 生成后，把它当作管理端视觉基线。两端不能互相复制导航、资料范围或角色呈现。
3. 每次把本篇对应的英文提示词整段粘贴给 Stitch。不要自行删去限制条件，尤其是事实状态、结束入口和禁止表达。
4. 生成后，先检查结构和文字是否正确，再调间距、颜色和角色占比；不以角色插画好不好看代替页面验收。
5. 在 Stitch 的原型连接模式中，将明确写出的按钮或卡片连接到目标 Screen；记录原型链接或截图以便复现。
6. 页面验收通过后，记录页面名、生成日期、完整提示词、追加提示词、Stitch 链接或截图。这个记录用于复现，不是用户研究结论。

### 首轮测试视觉合同

以下是给 Stitch 的测试视觉合同。它不是品牌色值定稿；色值只为让首轮生成一致、可读和便于核验。

- 基础背景使用 #F7F7F5，表面层为 #FFFFFF，主文字为 #1A1D21，次文字为 #626A73；
- 主操作使用 #2047D4，已确认使用 #16794B，等待确认使用 #9A6700，冲突或失败使用 #B42318；
- 所有状态同时使用文字、图标和颜色；禁止只靠色块、角色表情、声音或动效传达关键信息；
- 以 8px 间距网格组织版面，卡片圆角 16px，触控目标最小 44px，正文不小于 14px；
- 角色只使用小型、可收起、无真人拟态的中性插画或 72px 占位头像；不得让角色占据比赛观看区；
- 非必要转场短且可收敛；低动态状态下不闪烁、不跳动、不放大角色；
- 所有界面文案为简体中文，语气直接、克制、结果导向；
- 不出现恋爱、排他、依赖、内疚、连续签到、角色等待用户、挽留用户或“更亲密”之类表达；
- 不凭空给出比分、进球、红牌或比赛结果；待确认、冲突和更正必须清楚可见。

## 两端隔离合同

用户端与导演台之间只共享已发布的赛事状态、明确的更正、全局安全限制和用户已授权可见的结果。用户端的私人对话、共同瞬间、原始语音、可识别个人观察和关系资料不是导演台的常规内容；导演台的候选、内部争论、操作人员和未发布来源也不是用户端内容。

管理端页面一律使用桌面 1440 × 960 测试帧、紧凑但不拥挤的信息密度和稳定位置的状态栏。它不使用角色插画、聊天气泡、增长指标或全局主动配置按钮。任何发布、更正、撤回、暂停或高风险支持动作，必须显示影响范围、理由、所需角色和可见的下一步；“保持等待”必须与“发布”同样清楚。

## 用户端原型：Mobile 390 × 844

## Step 1：01-identity — 身份与首启说明

### 读设计

阅读 21 的“首启激活”和 34 §5.1。此页只解决一件事：用户知道服务是人工智能陪看，知道可以安静或结束，并自主进入比赛选择。它不介绍关系等级、不让用户填资料、不用角色故事留住用户。

### 在 Stitch 中生成

新建名为 01-identity 的 Screen。将下列提示词整段粘贴到 Google Stitch：

~~~text
Create one mobile app onboarding screen, 390 by 844 pixels, for a Chinese AI football companion service. This is a first-round interaction prototype, not a marketing landing page. Use Chinese UI copy. Use a restrained visual system: page background #F7F7F5, white surfaces, primary text #1A1D21, secondary text #626A73, primary action #2047D4, 16px card radius, 8px spacing rhythm, and all touch targets at least 44px high.

The screen must make the AI identity and user control clear in the first viewport. At the top, show a quiet text brand “看球陪伴” and a small text link “无障碍、隐私与帮助”. In the upper-middle, place a small neutral non-photorealistic digital companion illustration or 72px avatar. It must look optional and must not dominate the screen. Next to or under it, show the exact headline “和一位数字球友一起看球”. Show the exact explanatory sentence “它是人工智能服务，不是真人；你随时可以安静或结束本场。”

Below that, create three concise promise rows with an icon plus text: “比赛事实会标明状态”, “你不说话也不会被追问”, and “随时可以结束本场”. Use readable text, not color alone. Then create a “这场先这样看” card with three local-only choices: “仅文字”, “安静”, and “低动态”, each with a selected or unselected state and a visible “稍后再选” link. Make clear that these choices apply only to this match unless the user later chooses to save them.

At the bottom, add one primary full-width button exactly labelled “选择一场比赛”. Add a quieter secondary text action “先看看服务说明”. The primary button should navigate to a screen named 02-match-select; the secondary action should visually point to a preferences/help screen but not block entry.

Do not add a login wall, relationship meter, streak, reward, countdown, romantic language, “I am waiting for you”, automatic voice, or large animated character. Do not use gradients, confetti, floating hearts, or a chat transcript.
~~~

### 对照核验

- [ ] 首屏直接写明“人工智能服务，不是真人”；
- [ ] “事实标明状态”“不追问”“可结束”三项承诺都存在；
- [ ] 仅文字、安静、低动态是可见的本场选择，并有“稍后再选”；
- [ ] “选择一场比赛”是清楚的唯一主动作；
- [ ] 隐私和无障碍入口可见，但不抢占进入动作；
- [ ] 没有登录、关系、奖励、角色等待或自动声音。

### 若 Stitch 生成错误，追加以下提示词

~~~text
Revise this screen. Remove all onboarding gamification, relationship language, streaks, login requests, chat bubbles, and decorative character scenes. The first sentence must explicitly say this is an AI service, not a human. Keep “选择一场比赛” as the only primary CTA. Show “仅文字”, “安静”, and “低动态” as local match choices with a visible “稍后再选” option.
~~~

### 连接与归档

将“选择一场比赛”连接到 02-match-select；将“无障碍、隐私与帮助”连接到 10-preferences-privacy。归档名为 01-identity。

## Step 2：02-match-select — 比赛选择

### 读设计

阅读 21 的“比赛发现与选择”、34 §5.2 和 22 的旅程起点。用户在这里找的是一场自己想看的比赛，不是接受系统替他安排的关系或提醒。

### 在 Stitch 中生成

新建名为 02-match-select 的 Screen，并粘贴：

~~~text
Create a 390 by 844 mobile screen named “02-match-select” for a Chinese AI football companion prototype. Use Chinese copy and the same restrained UI system: #F7F7F5 page background, #FFFFFF cards, #1A1D21 primary text, #626A73 secondary text, #2047D4 primary action, 16px card radius, readable high contrast, and 44px minimum tap targets.

Build a match discovery screen, not a social feed. At the top show a compact app bar with a back icon, title “选择一场比赛”, and a text control “筛选”. Under it, show a horizontally scrollable date selector with “今天  6月12日”, “明天  6月13日”, and “周末”. The selected date has both a text label and a visible selected shape, not color alone.

The main content is a vertical list of exactly three match cards. Each full card is tappable and contains team names, a competition label, local start time or current phase, and an availability/status label. Use these static examples: “英超 · 20:30  北城联 vs 海港队 · 未开始”, “西甲 · 进行中 62′  皇家蓝队 vs 山谷队 · 可进入”, and “杯赛 · 已结束  河畔队 vs 星环队 · 已结束”. Do not show a score for a match unless its label is “已确认”; for this screen, omit scores entirely. Place a small neutral availability message on each card such as “可选择本场陪看方式”.

Below the first card, show a compact, collapsible companion preview with a small neutral avatar and the text “数字球友会按你的本场设置陪看”. It must not speak, animate, flirt, or solicit interaction. At the bottom, provide a clear empty-state style text link “没有想看的比赛？查看稍后赛程”.

Tapping any available or not-started card should navigate to “03-match-mode”. Tapping an ended card should go to “09-end-recap” only as a static completed-match example. Do not include algorithmic recommendations, urgency labels, streaks, automatic reminders, rankings, betting, or a prominent character panel.
~~~

### 对照核验

- [ ] 赛事卡同时显示双方、时间或阶段、可用性；
- [ ] 筛选可见且日期选择不制造倒计时焦虑；
- [ ] 未确认的比赛没有被填入比分或赛果；
- [ ] 角色预览小、可收起、没有自动表达；
- [ ] 可选比赛的整张卡可以进入 03-match-mode；
- [ ] 没有“为你推荐”“别错过”“立即提醒我”式召回设计。

### 若 Stitch 生成错误，追加以下提示词

~~~text
Revise the match list. Remove scorelines, predictions, betting odds, personalized recommendations, and countdown urgency. Every match card must visibly contain team names, competition, local time or phase, and an availability label. Make each full available card tappable to 03-match-mode. Keep the companion preview compact, collapsed by default, and completely silent.
~~~

### 连接与归档

将前两张可选卡连接到 03-match-mode；已结束卡连接到 09-end-recap。归档名为 02-match-select。

## Step 3：03-match-mode — 赛前本场设置

### 读设计

阅读 21 §7、34 §5.2 和 35 §3、§7。本页建立本场控制契约：用户选择本场的陪看密度、声音和低动态，不被要求把选择永久保存。

### 在 Stitch 中生成

新建名为 03-match-mode 的 Screen，并粘贴：

~~~text
Create a 390 by 844 Chinese mobile screen named “03-match-mode” for setting up one football watch-along session before entry. Keep the restrained semantic UI system: #F7F7F5 background, #FFFFFF surfaces, #1A1D21 text, #626A73 secondary text, #2047D4 primary action, confirmed #16794B, 16px radius, and no marketing visual noise.

The top app bar has a back icon and the exact title “这场怎么陪你看”. Immediately below, present a compact match summary card: “北城联 vs 海港队”, “英超 · 今天 20:30”, and status “尚未开球”. Do not show a score. The page should clearly state “以下选择只对本场有效，进入后仍可随时修改。”

Create three option groups, each using radio-card choices with a short behavioral consequence:
1. “陪看密度”: “安静（除非你主动，不会自动说话）”, “只回应（只在你点开、输入或说话时回应）”, and “有限提示（只在你允许的已确认事件中给短文字）”. Default to “安静”.
2. “声音方式”: “仅文字（不自动播放声音）”, “点按播放（由你决定每次是否听）”, and “自动声音（需你明确开启）”. Default to “仅文字”.
3. “动态”: “低动态（收敛角色和界面非必要动作）” and “标准动态”. Default to “低动态”.

At the bottom, show one primary button “进入比赛房间” that navigates to 04-match-room. Below it, show a secondary text action “返回比赛列表”. Add a small inline disclosure link “查看事实与剧透说明”, leading visually to 05-facts-timeline.

Do not include a 0-to-10 talkativeness slider, a permanent-save toggle, automatic microphone permission, notification permission, a large character performance, motivational copy, or wording that makes the user feel responsible for the character’s feelings. Do not make “有限提示” more visually dominant than “安静”.
~~~

### 对照核验

- [ ] 页面明确告诉用户选择“只对本场有效”；
- [ ] 安静、只回应、有限提示都说明可预期的行为；
- [ ] 仅文字是保守默认，自动声音不是唯一醒目的选项；
- [ ] 低动态可选，且不需要跳出页面；
- [ ] “进入比赛房间”连接到 04-match-room；
- [ ] 没有永久保存、权限索取、0–10 话痨滑杆或角色化说服。

### 若 Stitch 生成错误，追加以下提示词

~~~text
Revise the option controls. Replace generic “immersive”, “friendship”, or “personality” labels with the exact result-oriented labels and consequences. Default to “安静”, “仅文字”, and “低动态”. Remove any permanent preference saving, microphone request, notification request, or visual emphasis that makes “有限提示” the recommended choice.
~~~

### 连接与归档

将“进入比赛房间”连接到 04-match-room；“查看事实与剧透说明”连接到 05-facts-timeline。归档名为 03-match-mode。

## Step 4：04-match-room — 比赛房间最小视图

### 读设计

阅读 21 §7.3、34 §5.3、35 §2.1 和 32 的角色边界。此页是整个原型的核心：比赛事实和用户控制永远高于角色与对话。不要把它做成聊天应用或角色直播间。

### 在 Stitch 中生成

新建名为 04-match-room 的 Screen，并粘贴：

~~~text
Create the core 390 by 844 mobile screen named “04-match-room” for a Chinese AI football watch-along prototype. 连接完成后，至少用下列四条路径走一遍。这里是原型交付验收，不替代后续用户研究。
~~~

1. **最小进入路径**：01 → 02 → 03 → 04。确认用户没有登录、权限、永久保存或角色故事的阻塞，就能进入一场仅文字、安静、低动态的陪看。
2. **事实不确定路径**：04 → 05 → 04。确认“等待确认”不是比分、庆祝或剧情暗示；更正可以看见前后关系。
3. **用户主权路径**：04 → 06 或 07 → 09。确认任意时点都能改成文字、停止自动表达或结束；结束没有情绪化二次挽留。
4. **故障与资料路径**：04 → 08 → 04，以及 09 → 10。确认故障仍保留文字、事实与退出；删除、暂停、关闭提醒不被隐藏。

管理端也需要单独走查，但它不打开用户端页面、不读取私人资料，也不把候选直接变成公共事实。

## 完成标准

本阶段必须同时满足以下条件：

- [ ] 用户端 Stitch 原型区有 01 至 10 十张命名清楚的 Mobile Screen；
- [ ] 管理端 Stitch 原型区有 11 至 16 六张命名清楚的 Desktop Screen；
- [ ] 每一页都有本篇记录的完整生成提示词和必要的追加修复提示词；
- [ ] 每页已逐项对照其来源设计文档，关键组件、状态、控制和禁止表达均未遗漏；
- [ ] 用户端已连接首启、选赛、赛前设置、比赛房间、事实、对话、控制、故障、结束和资料的主路径；
- [ ] 管理端已连接准入、赛中总览、候选草稿、复核发布/更正、安全支持、交接审计的主路径；
- [ ] 两端在原型中没有互相跳转；只以“已发布事实 / 明确更正 / 全局安全限制”的最小结果形成概念对应；
- [ ] “等待确认”“已更正”“仅文字”“安静”“结束本场”“连接不稳定”“删除资料”都同时有明确文字和可达操作；
- [ ] “保持等待”“暂不开放高影响能力”“暂停相关自动呈现”“送复核”“更正说明”“受限交接摘要”在管理端都有明确文字、权限边界和下一步；
- [ ] 原型中没有把角色做成事实来源、控制入口、用户挽留机制或关系等级系统；
- [ ] 用户端走查中，用户能不解释、不授权麦克风、不保存资料、不继续互动地完成进入、安静、查看事实和退出；
- [ ] 管理端走查中，运营人员不能直接查看私人资料或发布未复核候选，且可在压力下选择等待、暂停、交接和更正。

满足这些条件后，原型可以交给 45-产品评测体系设计去组织用户任务与判断标准；技术可行性与后续方案另按相应设计文档推进。

## 生产版本设计拓展｜能力深化知识

本节描述产品成熟后的能力扩展、体验深化和治理要求，作为后续版本规划与设计决策的参考。


- **新增原型场景**：自动事实发布与更正、赛前提醒订阅、有限长期偏好、语音主出口、舞台主出口、外部动作确认、删除后防回写和人工暂停。
- **场景卡字段**：用户目标、进入条件、四维控制、事实状态、授权提示、Agent 决策、工具结果、媒介输出、失败/撤回/退出、观察指标和回滚开关。
- **生产走查**：让用户在不看说明书的情况下理解自动化范围，完成授权、暂停、取消、删除和恢复；检查语音/舞台与文字或结构化状态的任务等价。
- **管理端走查**：验证运营能按单场/单能力/单版本暂停，看到最小审计上下文并完成更正和交接，不暴露无关私人资料。
- **放行规则**：原型只证明可理解和可控制；任一剧透、越权、无法撤回或退出失败场景都阻断生产扩展，回退基础手动流程。

### 生产原型场景清单

| 场景 | 用户要完成的事 | 必须观察 |
| --- | --- | --- |
| 自动事实 | 判断事实状态并关闭自动发布 | 是否理解来源、范围和撤回 |
| 提醒订阅 | 选择范围、确认并取消 | 是否知道时间窗、媒介和到期 |
| 长期连续性 | 查看、修改、暂停和删除资料 | 删除后是否相信不会再被引用 |
| 语音/舞台主体验 | 在主媒介中观看并结束 | 静音、字幕、低动态和退出是否等价 |
| 外部动作 | 查看副作用、确认或拒绝 | 未确认是否没有发生副作用 |

每个场景都要走正常、等待、冲突、失败、撤回、结束和共享设备路径；原型通过不等于生产放行，仍需 44、45 的技术和评测证据。
