# 版本现状与演进

(原篇名:版本复盘与下一阶段提案)

> 本文是"球球"AI Coding 工程实践系列的版本篇,写给想了解我们如何回答"现在到哪了、下一步去哪"的读者。版本事实以仓库 `CHANGELOG.md` 与 `VERSION` 文件为准,本文只做核对与解读,不另立版本口径;复盘与提案方法是我们每个版本真实在用的工序,不是规划中的设想。
>
> 核心判断:版本记录的用途不是宣传进度,而是让下一次取舍有据可查。我们把"现在是什么"写进 CHANGELOG,把"为什么是现在这样"写进复盘,把"下一步只做什么"写进提案——三者都不许夸大,证据不足的部分明确标为未知。

## 1. 版本现状:从 0.1.0.0 到 0.2.0.0

### 1.1 0.1.0.0(2026-07-15):数字人完整体验

第一个发布级版本回答的问题是"数字球友能不能完整陪看一场球"。CHANGELOG 记录的能力分四块:

- **用户客户端**:Live2D 角色、连续语音对话、首见问候、比赛状态轮播、文字降级;
- **企业导播台**:人工比赛事实录入、外部数据源接管、自动化策略、实时监控与决策追踪;
- **事实与关系**:比赛事实保护、用户错误赛况核验、来源冲突处理;跨比赛关系状态、共同瞬间、未完话题、边界与修复、长期偏爱记忆;
- **评测**:发布级离线、WebSocket、浏览器与真实 MiMo 语音评测。

同一版还做了一次诚实的减法:移除未接入生产链路的旧 pipeline engine、cooldown、dedup、priority、throttle 和 watch session 实现。第一个版本同时定义了"什么算做完"和"什么不算数"——后者和前者一样重要,留着的死代码会让人误以为链路已通。

这一版上线后,系统开始随真实比赛运行,内部值守由此开始:每场比赛由项目所有者在导播台录入与调和事实、看护自动化输出。CHANGELOG 里那批 Fixed(导播鉴权、音频播放回执竞态、主动信息与用户输入的排序、关系记忆的状态残留)正是真实比赛喂回来的问题——评测抓设计错误,真实比赛抓使用错误,两类证据在版本记录里都留了痕。

### 1.2 0.2.0.0(2026-09-20):结构收敛与体验修复

第二个版本的主线不是新功能,而是把第一版长歪的地方扳正(ADR-0009 至 ADR-0013):

- **导播台退役旧页**:operator.html#live 组件化进控制台(ADR-0011),旧 operator.html 下线(ADR-0013),28 条导播评测迁至新导播页。双入口并存期间的鉴权塌缩、自动化策略状态分歧、恢复语义不对称,随旧页一起消失;导播台成为唯一实时运营写入口;
- **意图路由**:关键词未命中的对话轮改经 LLM 意图路由补齐(ADR-0009),输出意图、置信与建议回复,RouterTrace 持久化到 Postgres,统一回复护栏;路由 key 缺省回落对话 key,两者皆无则整层关闭;低置信的控制指令一律拒绝;
- **运营台鉴权**:JWT 登录与 RBAC(ADR-0010),首登强制改密,15 分钟访问令牌加单次轮换刷新令牌;个人令牌保留为机器通道,供评测与脚本使用;
- **传输统一**:五个手写 LLM 客户端收敛到同一 openaicompat 传输(ADR-0012),最大的两个服务端面从 main.go 拆出,两个纯引擎从 agent.go 释放;
- **表演链路修复**:hello 开场守卫、旧表演路径移除、进球爆屏按事件 ID 边沿触发——重建页面不再重放庆祝;
- **记忆管道修复**:写入失败即移交持久积压、ForgetPortrait 如实上抛、缓存设上限,不再静默丢失;
- **客户端韧性**:WS 半开连接自愈、断线重连后补一次比赛概览幂等再同步、音频源生命周期释放、重连语音回退不遗留队列;release 构建缺失 matchId / WS 地址配置时进入明确错误空态,不再静默连向模拟器兜底地址;
- **门禁加厚**:100 例对话评测套件、控制台真实数据页 E2E、控制台↔Go 契约 golden 测试、迁移序号 lint 与根 `.env.example`;
- **架构打磨**:契约 golden 逐字节对拍、传输缝抽取、match_screen 拆分出可测试模块、观察存储收敛到纯 reducer 并加双存储一致性测试、记忆积压优先排水;前端细节同样在册——MetalButton 弃用三段渐变,对齐 DESIGN.md 的纯色与圆角规范。

当前 `VERSION` 为 0.2.0.0。两个版本合起来,版本号回答的是同一个问题:用户可感知的完整体验是否更完整、更可信——不是功能条数。

### 1.3 与清单对账

我们的版本叙述有一个事实基准:由代码全量扫描逆推的《功能与边界清单》。每次版本收尾,把 CHANGELOG 的条目与清单逐项对一遍——清单里有而 CHANGELOG 没写的(如断线语音兜底队列上限 4 条、待机首挑永不 energetic 这类冷门行为),说明发布说明做得不够;CHANGELOG 写了而清单对不上的,说明写多了。这份对账比任何宣传口径都诚实。

## 2. 演进计划:Phase 框架

仓库的演进计划文档(`演进计划文档/00-演进计划总览.md`)把路线按五个 Phase 组织:

| Phase | 主题 | 交付重心 |
| --- | --- | --- |
| 0 | 基础搭建 | 技术选型、数据源验证、架构与脚手架 |
| 1 | MVP 核心 | 事件驱动语音、Live2D、人设、基础事件响应 |
| 2 | 交互增强 | 用户语音输入、实时打断、话痨调节、表情动作 |
| 3 | 体验打磨 | 性能优化、延迟压缩、内容与表情丰富度 |
| 4 | 扩展规模化 | 多比赛支持、多端与运营能力扩展 |

0.1 与 0.2 两个版本对应其中 MVP 核心到交互增强段的落地。在此只把框架当路标:框架说"打算做什么",CHANGELOG 说"真的做了什么"——后者说了算,节奏随复盘证据调整,不为迁就既定顺序硬赶。Phase 之后的扩展段(多比赛、运营能力)在当前受控开放完成之前不排期,避免用未来的规模承诺透支当前的收敛工作。

## 3. 复盘方法论:三道工序

我们的复盘工序压缩下来是三个提示词、三道固定动作,从版本初期沿用至今。规则的细节随事故生长,骨架没变过。

**第一道,版本开始前:生成结果合同。** 输入版本范围,输出六件事——最小范围与非范围、可反驳的核心假设、反证(什么结果说明不该继续)、最高优先级停止门(剧透、控制失效、删除回写一类)、证据计划、不可推论(此次结果不能证明什么)。硬约束直接写在提示词里:不以互动时长、留存、沉默或消费作为关系成功的证据;严格保护、静音、结束、删除与文字路径必须优先;证据不足标为未知,不可写成通过。范围过大的提案先拆分,而不是增加统计来挽救解释性。

**第二道,版本结束后:生成无责复盘。** 固定结构:版本合同与实际范围、支持/反驳/未知、负向证据、问题分类、已执行收缩、需要加入评测集的案例、维持/收缩/暂停建议。两条纪律:其一,负向证据是主要输入而不是附注——用户误解等待、找不到结束、删除后旧对象重现,这类证据决定下一阶段优先级;其二,归因系统条件而不归咎个人——问"为什么结束动作没能穿透队列",不问"谁没注意到",这是 Google SRE 无责复盘文化的直接借用。失败案例的归宿是评测集:修一个 bug 加一条 regression,复盘产出直接变成门禁资产。

**第三道,下一阶段动工前:审查提案。** 对每份提案输出三选一:准入 / 需要缩小 / 拒绝。逐项检查:有没有可反驳假设;范围是否足够小;资料与许可是否说清;对事实、控制、关系、语音、实时、无障碍各有什么影响;最高优先级停止门是什么;失败后退到文字与最后确认快照的路径是否完整。没有反证和退出条件的提案不是实验,是范围愿望,退回补充。

三道工序共享一条原则:**任何正向信号都要与至少一个用户权利信号并列解释**——使用时长上升要追问"用户是否仍能轻松静音、结束、离开";保存偏好增加要追问"拒绝保存是否同样顺畅"。证据无法支持结论时,写明未知和最小保守动作,而不是包装成成功。

这套工序不需要专门工具承载,它长在两个地方:评测集(复盘产出的每条 regression 都是可执行文件)和 CHANGELOG(复盘修正的范围决定下一版条目)。工具会腐化,工序落在资产上才不会。

## 4. 下一阶段:受控开放准备

### 4.1 当前位置

| 状态 | 内容 |
| --- | --- |
| 已上线运行 | 核心系统随真实比赛运行,内部值守自 0.1.0.0 起维持,现为 0.2.0.0 |
| 尚未开始 | 受控开放(邀请真实用户使用) |
| 未开始 | 公众试点与公开运营 |

三个状态放在一起看,结论自然浮现:工程闭环已经完整,价值与风险的问题还没有被真实用户回答过——这正是下一阶段存在的理由。

### 4.2 提案方向

下一阶段的提案方向全部服务于受控开放这一个目标,口径与全套资料其他卷一致:

- **AI 披露**:明确的 AI 身份标识是受控开放前的第一优先项——这是监管办法的要求,也是我们的第一承诺;每一次交互都应让用户清楚对面不是人;
- **用户侧事实呈现**:把"不被剧透"做成用户可感知的保护(信息保护档),覆盖多源延迟与关键信息的处理和呈现——这套能力在工程侧已就绪,用户侧还没有可感知的开关;
- **赛后收束**:终场告别回合已上线(wave 动作与告别语只用一次),完整的赛后回顾与收束体验是首批体验增量;
- **值守**:例行风险评审、暂停演练、值守编排,以及反馈与举报入口,随受控开放一并建设——发现问题的通道必须先于用户存在;
- **隐私闭环走查**:画像逐条与全部遗忘、隐私状态查看、数据导出与删除生命周期均已实现;受控开放前按用户视角完整走查一遍——工程能力存在,不等于用户能顺畅走完每一条路径。

这些方向的共同点一目了然:都不是"更强的角色表现",而是"更可托付的服务"。

### 4.3 不进下一阶段的事

同样要与全套资料口径一致地列出:全量联赛、全语种、全天候覆盖不做;更强的主动性、更亲密的关系化表达、更多跨场记忆不做——没有证据说明用户需要,却确定会增加事实、关系与隐私风险;没有隐私与合规评估的能力不随开放带出。范围愿望每个版本都会冒头,这一节就是它们的固定去处。

### 4.4 顺序纪律

方向的顺序由复盘证据决定,不由路线图的既定顺序决定;每项动工前,先过第 3 节第三道工序的审查——能被否定的才值得做,不能被否定的只是愿望。若受控开放前的准备长期无法收敛,正确的决定是把开放继续往后推,而不是带着缺口放人进来。

## 5. 结语

一个版本真正留下的资产不是功能数量,而是更清楚地知道什么可以安全继续、什么必须停下、为什么。事前写结果合同,事后回收支持、反驳和未知,把失败转换为评测集里的 regression,再用小而可否定的提案调整路线——版本就会自己讲述自己的价值,不需要任何一篇文档替它修饰。

版本事实看 CHANGELOG 与 VERSION;演进方向看本文第 4 节;两者冲突时,以 CHANGELOG 为准并回来修订本文。
