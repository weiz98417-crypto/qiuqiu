# 语音输入、VAD 与 ASR 链路

> **文档性质**：真实工程叙事。这一篇记录"球球"的语音输入链路是怎样建成的：用户在看球时怎么开口、声音怎么变成屏幕上的字、识别失败时怎么兜底，以及我们用什么测试把这些行为锁住。文中所有机制均以仓库现网实现为准，关键路径逐处标注代码位置。

---

## 1. 问题：看球时说话，手要空、眼要盯屏

陪看场景对输入方式的要求和聊天软件完全不同。用户往往一只手拿着饮料，一只手搭在沙发扶手上，眼睛不能离开画面——进球就发生在转瞬之间。让他切出全屏、唤起键盘、打一行字再切回来，等于惩罚了他想说话这件事。

所以语音输入对球球不是"锦上添花的多模态"，而是看球时最自然的输入姿势。但把麦克风交给一个网页或应用，用户的顾虑同样真实：

1. **它是不是一直在听？** 电视里的解说、身边人的闲聊，会不会被当成我说的话？
2. **我说的字可靠吗？** 球员名字大多拗口，识别错了怎么办？
3. **我不想说了怎么办？** 停止必须立刻生效，不能"先把这句说完"。

我们对这三个顾虑的工程回答：

| 用户的顾虑 | 工程回答 |
| --- | --- |
| 是不是一直在听 | 收音只发生在用户主动发起的窗口内；开口判定用双重能量阈值挡环境声 |
| 说得可靠吗 | 流式识别边说边上屏，中间结果可被最终结果修正；队名与球员名单注入识别提示 |
| 能立刻停吗 | 取消是链路一等公民，取消信号穿透上传、识别与回复；文字路径永远完整可用 |

最后一条是底线：麦克风不可用、权限被拒、识别失败的所有场景下，文字输入路径无损可用。语音是增强，不是依赖。

把这三条立场翻译成用户能看见的东西，就是比赛页上的几个状态：按住说话时悬浮 dock 显示"正在听你说"，连续对话开启时显示"连续对话已开启 · 你直接说"，识别进行中临时文字逐步上屏，失败时给出明确的原因与文字入口。语音链路的每一个工程决定，最终都要落到用户此刻看到的那一行字上。

## 2. 真实链路：从按住到上屏

一次完整的语音回合穿过这样一条链路：

```text
按住/连续开口 → 采集（PCM 16k 单声道） → VAD 双阈值分句
    → asr_start / asr_chunk 边说边传 → transcript_partial 边说边上屏
    → 松手/静音封口 asr_finish → transcript_final → 回复回合
任何时刻可取消 asr_cancel；识别失败 → 文字兜底 或 整段音频重发
```

### 2.1 声音进来的两条路

客户端按运行平台走两套采集实现，对上层暴露同一个 `VADService` 接口：

- **原生端（安卓等）**：`client/lib/services/vad_service.dart` 直接用录音插件开流，配置为 PCM 16bit、16kHz、单声道，并打开回声消除与噪声抑制。音频帧在 Dart 侧逐帧计算 RMS 能量并做语音活动判定。
- **Web 端**：Flutter web 的录音插件能力不足，我们在 `client/web/index.html` 内嵌了一个原生 JS 录音机（`__qRec*` 系列函数），由它在浏览器里完成 getUserMedia、重采样到 16kHz、能量判定与分句，再把事件和 base64 音频块通过一个 DOM 桥（`__qDiv` + `__qRecDrain()`）吐给 Dart 侧的 `client/lib/services/web_recorder.dart`，后者以 80ms 轮询消费事件队列，包装成与原生端相同的 `VADEvent` 流。

两端共用的事件词汇是六个状态：listening（已开麦）、speaking（检测到说话）、sentenceEnd（一句结束）、idle（已停止）、permissionDenied（权限被拒）、failure（采集失败）。上层不感知平台差异，两端的行为契约由同一组 Playwright 测试锁定（见第 3 节）。

### 2.2 双阈值 VAD：开口要确认，句中要宽容

语音活动判定是这条链路里最容易被低估的一环。阈值设高了，小声说话永远开不了口；设低了，电视解说会不断制造"幻影句子"。我们的做法是**开口与保持用两个不同阈值**，实现位于 `vad_service.dart` 的 `VoiceActivityGate`：

| 参数 | 值 | 为什么 |
| --- | --- | --- |
| 开口阈值 | RMS > 0.015 | 高门槛挡住环境底噪与突发尖峰 |
| 开口确认 | 连续 2 帧 | 单帧噪声过不了关；环境声要"连续像语音"才触发 |
| 保持阈值 | RMS > 0.006 | 开口确认后降阈值；句中低音节的自然起伏不切断句子 |
| 静音收句 | 1400ms | 自然停顿不截断，又不让收音拖沓 |
| 单句上限 | 15s | 忘记松手也不会无限收音 |
| 预滚缓冲 | 最近 4 帧（约 200ms） | 开口时补进句首，首音节不被判定延迟吃掉 |

两帧确认还有一个隐含收益：球场的哨声、关门声这类单事件在能量上够了，但撑不满连续两帧的"像语音"判定，不会制造空回合。

### 2.3 流式识别：边说边上屏

识别不是"说完一句、整段上传、等结果"的三步舞，而是边说边传。`client/lib/services/streaming_transcription.dart` 通过同一条 WebSocket 依次发送四类消息：

- `asr_start`：携带 `utteranceId`、`signalId`、`userId`，并声明音频契约——`pcm_s16le`、16000Hz、单声道、中文。服务端在 `backend/cmd/server/transcription.go` 的 `validateTranscriptionStart` 里硬校验这四项，不合契约的会话直接拒绝，不给"猜格式"留余地。
- `asr_chunk`：音频块 base64 后带递增序号上传。用户说到一半，屏幕上已经开始出现临时文字（`transcript_partial`）。
- `asr_finish`：松手或分句后封口，等待最终文本（`transcript_final`）。
- `asr_cancel`：取消当前话语，服务端终止会话并丢弃后续帧。

服务端为每条连接维护一个 `transcriptionSessions`，把识别事件回推为三类消息，`revision` 单调递增：

| 下行消息 | 含义 | 客户端处理 |
| --- | --- | --- |
| `transcript_partial` | 临时文本 | 只接受比已显示更大的 revision；晚到的旧版本直接丢弃 |
| `transcript_final` | 最终文本 | 替换该话语的临时文本，进入回复流程 |
| `transcript_error` | 识别错误 | 带 `recoverable` 标记；可恢复只展示原因，不可恢复走兜底 |

客户端还给每条话语记录提交顺序：前一句的迟到结果不会窜进后一句的显示位，旧话语永远追不上新话语。

真正的识别由 `backend/internal/asr/client.go` 完成：接入 MiMo 的 `mimo-v2.5-asr` 模型，HTTP 超时 30s，外挂熔断器（连续 3 次失败、10s 熔断窗口），供应商抖动不会把整条连接拖垮。还有一个对足球场景很实用的细节：`voiceRecognitionHints` 会把当前比赛的主客队名和双方球员名单作为识别提示词注入——用户喊出拗口的外援名字时，识别器知道该往哪个方向猜。

回答侧的语音合成由同族的 `backend/internal/tts/client.go` 承担（`mimo-v2.5-tts`，同一兼容协议接入），TTS 失败时回复退回纯字幕。识别与合成的工程细节分别在各自的链路里展开，这里只强调一句：语音入口和语音出口是两个独立可失败的环节，任何一侧失灵都不影响另一侧，也不影响文字路径。

### 2.4 每连接最多 8 个并发识别会话

识别是整条链路里最贵的资源调用。为了防止单条连接（无论是因为 bug 还是恶意）无限堆起并发识别，`transcription.go` 里写死了每连接同时存活的识别会话上限：

```go
const maxTranscriptionSessionsPerConnection = 8
```

配套的行为规则：

- 第 9 个 `asr_start` 收到 `errTranscriptionSessionLimit`，服务端在建立会话前就取消并拒绝，不留半开的资源；
- 同一 `utteranceId` 重复 Start 被拒绝（`errTranscriptionSessionExists`），不产生双份识别；
- 已完成的会话按话语提交顺序出队投递——识别可以乱序完成，交付必须顺序；
- Append 中途出错的会话立即终止并投递，不悬挂；
- 连接断开时 `Close` 一次性取消全部存活会话。

这个上限被 `transcription_test.go` 的 `TestTranscriptionSessionsLimitConcurrentUtterances` 锁定——写死一个数字，再让测试证明第 9 个进不来，比"到时候看负载"可靠得多。

### 2.5 取消是一等公民

用户在三种时刻会想撤回一句话：说错了、不想说了、或者刚开口就被场上进球打断。链路里取消有三层：

- **松手前反悔**：`cancelActive` 发送 `asr_cancel`，服务端终止该会话并丢弃后续帧；
- **切换麦克风**：切换设备前先取消进行中的识别，避免旧设备的尾巴录进新会话（此时保留 `signalId` 供整段音频兜底重发）；
- **断线/结束**：`cancelAll` 批量撤销全部未完成话语，客户端与服务端两侧状态同步清空。

取消之后不会有"迟到的话痨"——被取消会话的识别结果即使已经产出，也会因为会话已终止而被服务端丢弃。

### 2.6 失败的两级兜底：文字、整段音频

识别链路任何一环失败，用户都不会被打断在半句话上：

- **文字兜底**：服务端判定 ASR 不可恢复失败时，下发 `voice_status` 消息（`state: "text_fallback"`），客户端提示用户改用文字输入，本轮对话不丢；
- **整段音频重发**：流式上传失败（比如发送中途断线）时，客户端手里始终留着这句话的完整音频缓冲（`drainAudio` + 每条话语的 fallback 音频）。重连后由会话控制器把整段音频作为语音消息补发，排队上限 4 条、先进先出淘汰——我们宁可淘汰最旧的一句，也不让重连瞬间被积压音频淹没；
- **可恢复错误**：识别中途的临时故障（`transcript_error` 且 `recoverable`）只展示原因，不打断正在进行的句子。

把常见故障和用户看到的结局对照如下——每一行都对应代码里的一个显式分支，而不是异常堆栈的溢出：

| 故障 | 链路行为 | 用户看到 |
| --- | --- | --- |
| 麦克风权限被拒 | 采集不启动，`permissionDenied` 事件 | 提示 + 文字输入照常可用 |
| 识别服务不可用 / 熔断 | `transcript_error`（不可恢复） | 文字兜底提示，对话继续 |
| 流式上传中断 | 本地整段音频保留，进重连补发队列（≤4 条） | 重连后语音自动补发 |
| 识别中途临时故障 | `recoverable` 标记 | 展示原因，不打断句子 |
| 设备被拔出 | 可用列表校验失败，清空选择 | 自动回落系统默认麦克风 |

### 2.7 麦克风拔出：自动回落默认设备

外接麦克风是看球场景的常见配置（USB 电容麦），但"拔插设备"也是常见操作。Web 端录音机处理了完整的设备生命周期：

- 监听 `devicechange`，设备列表变化时重新枚举并广播给客户端；
- 已保存的设备 ID 不在当前可用列表里（被拔出）时，自动清空选择、回落系统默认麦克风；
- 打开音频流时如果浏览器报 `OverconstrainedError`（指定设备约束无法满足），同样清空选择、用默认约束重开一次，而不是让用户面对一次失败的 getUserMedia；
- 切换输入时丢弃延迟返回的旧设备流，旧设备的尾巴不会录进新会话；
- 首次使用且用户未表达过偏好时，优先自动选中标签里带"电容/condenser"字样的输入设备——看球用户插电容麦就是为了说话，这个默认值帮他们省掉一次设置；
- 用户的选择记入本地存储，下次进入不用重选。

"已保存的麦克风被拔出后自动回退系统默认输入"是 `client-microphone.spec.mjs` 里的一条正式测试，不是口头承诺。

### 2.8 连续对话：默认开启，但按住说话永远可用

语音交互有个隐含负担：每说一句话都要按一次麦克风，几轮下来比打字还累。所以我们把**连续对话**做成默认开启的开关（`preferences_service.dart` 里 `continuousConversation ?? true`）：

| 模式 | 句子如何结束 | 句子结束后 |
| --- | --- | --- |
| 连续对话开（freeTalk） | VAD 静音判定或单句上限 | 160ms 后自动重新开麦 |
| 按住说话（pushToTalk） | 用户松手 | 会话结束，等下一次按住 |

关闭连续对话回到按住说话，完全由用户手势控制窗口——悬浮 dock 的麦克风按钮用指针事件（按下开麦、抬起或取消收麦）实现，配合提示文案"连续对话已关闭，按住麦克风仍能说话"。设置页的开关、比赛页 dock 上的"连续 · 开/关"快捷态保证用户永远知道当前处于哪种模式。两种模式共享同一套 VAD 与识别链路，差别只在"谁决定句子何时结束"。

## 3. 如何验证

这条链路的测试策略是"两端夹住"：客户端行为用真实浏览器跑，服务端行为用 Go 单测跑，中间的协议由双方测试共同锁定。

### 3.1 客户端三套 Playwright 验收

| 测试文件 | 例数 | 锁定的行为 |
| --- | --- | --- |
| `tests/evals/client-vad.spec.mjs` | 3 | 自然停顿一秒仍在同一句话内（保持阈值与静音计时不误切）；持续环境噪声不产生幻影话语（双阈值+两帧确认挡稳态噪声）；小音量说话在高开口阈值下仍能保持激活（确认后降阈值真正生效） |
| `tests/evals/client-microphone.spec.mjs` | 6 | 普通说话音量触发说话与句子结束；部署版客户端从真实浏览器麦克风收到说话事件；选择外接麦克风后录音确实使用该设备；保存的设备被拔出后自动回退系统默认；切换输入时丢弃延迟返回的旧设备流；欢迎流程不阻塞部署客户端的流式转写 |
| `tests/evals/client-voice-runtime.spec.mjs` | 2 | 连续语音问答使用正确比赛事实且识别失败时文字兜底可用；浏览器拦截首屏自动播放后，首次触碰恢复播放 |

客户端测试用 Chrome 的 `--use-fake-device-for-media-stream` 注入受控音频，不依赖真人对着测试机说话，所以能在 CI 里稳定复现。第二类（voice-runtime）还顺带锁定了语音回答侧的播放回执五态入账：ok / skipped / blocked:autoplay / interrupted / failed——语音的"另一半"是回答播得出来，它同样被记账与测试覆盖。

### 3.2 服务端识别会话 Go 单测

`backend/cmd/server/transcription_test.go` 覆盖五个面：协议逐字段校验、非法音频块丢弃会话、乱序完成按话语顺序交付、启动契约强制 PCM16/16kHz/单声道/中文、8 会话并发上限。

### 3.3 本地复现

```bash
# 客户端三套（仓库根目录，需先起后端与前端，见 tests/evals/support）
npx playwright test tests/evals/client-vad.spec.mjs
npx playwright test tests/evals/client-microphone.spec.mjs
npx playwright test tests/evals/client-voice-runtime.spec.mjs

# 服务端识别会话
cd backend && go test ./cmd/server -run Transcription
```

跑客户端测试前需要本地起好后端与前端服务（连接检查由 `tests/evals/connection-check.spec.mjs` 承担）；服务端单测无外部依赖，随时可跑。改 VAD 阈值、识别契约或设备回落逻辑中的任何一处，都应先让对应测试在新值下变红、再改实现变绿——这些数字和分支是被锁定的行为，不是可随手调的旋钮。

## 4. 边界与不做

这条链路有意识地不做几件事，边界本身是设计的一部分：

- **不永久留存音频**。音频块只服务于当前识别回合，识别完成或取消后即弃。整段兜底音频仅在重连补发队列里短暂存活（上限 4 条、发完即清），没有录音存档、没有音频库、没有"历史语音"页面。识别产出的文本进入正常对话流程，受与文字输入完全相同的隐私与保留期约束。
- **不做后台常开收音**。没有唤醒词、没有"待机监听"。不主动发起就没有任何音频进入系统；权限被拒时文字路径无损可用，客户端保留明确提示而不是反复弹权限框。
- **不做说话人推断**。VAD 只回答"这段音频像不像语音"，不判断说话的是谁、带着什么情绪、是不是电视里的声音。环境声最多触发"没听清"的保守分支，不会被拆成用户命令。
- **不假装在听**。收音窗口之外，UI 不呈现任何"正在聆听"状态；失败时显示具体原因与文字替代入口，而不是一个转圈的"识别中"。

语音输入的价值密度取决于它是否让人放心。按住才收音、说话即上屏、失败有兜底、拔麦自动回落——每一个环节都指向同一个判断：用户随时可以把话收回去，也随时可以不用麦克风把话说完。
