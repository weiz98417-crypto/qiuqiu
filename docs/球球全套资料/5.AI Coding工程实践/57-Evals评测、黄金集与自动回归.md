# Evals 评测、黄金集与自动回归

> **本篇已由《球球课程》同源章节取代。**
> 课程章节按"系统实际怎么工作 + 与旧设计的差异"以 status 锚重写,是本主题的唯一事实源。本页保留原篇的定位说明与阅读指引。

**原篇定位**:工程执行方案,只负责把已获批准的风险场景转化为工程可运行的检查——给定输入、状态、时序和控制,系统必须产生什么、绝不能产生什么;原型可用性、招募访谈、主观体验研究与 POC 选型不在其列。

当时目录、阈值与命令均为候选合同,必须以隔离环境、合成数据和独立评审校准;实现后大幅简化,收敛为一条退出码门。

其核心立场保持不变:工程 Evals 判断候选构建能否进入受控发布门,让用例、运行环境、判定器和结果可追溯;产品评测(用户是否理解当前事实、是否被施压)是另一套体系,见产品设计篇 45。

## 该主题讲什么

- **黄金集与判定**:真实形态是 `evals/cases` 三套件(baseline/boundary/regression)共 100 个版本化 JSON 用例(基础 36/边界 38/回归 26)——schema 强制 `version: "2026-07"`、suite 枚举与 id 规则,断言长在 `turns[].expect` 与 `final` 里;判定全部确定性(`backend/internal/evals` 的 `gradeTextAndTrace`),LLM 离线用 scriptedRealizer 替身。
- **四档 tier**:`scripts/evals/run.mjs`(91 行)按 `--tier` 分层,offline ⊂ pr ⊂ nightly ⊂ release,非 release 档清空外部 API 密钥保证离线可跑。
- **CI 门**:`.github/workflows/evals.yml` 的单一 pr-evals job(go test → flutter → Playwright → tier pr)构成门禁,效果就是退出码:任何用例失败即红;旧稿的模型裁判双轨、四变形、P0/P1 五层门与豁免制度均未实现。
