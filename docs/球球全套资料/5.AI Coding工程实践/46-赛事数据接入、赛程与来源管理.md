# 赛事数据接入、赛程与来源管理

> 文档性质：工程叙事——赛况数据从哪里进来、怎么判活、怎么兜底，以及赛程查询的真实能力边界  
> 阅读方式：文中出现的包名、路径、接口与用例全部取自当前仓库，可边读边对照代码

## 1. 问题：赛况数据从哪来，错了怎么办

球球要陪人看球，得先知道场上发生了什么。这件事拆开是两个半问题。

**半个是"从哪来"。** 我们没有自己的转播信号，没有遍布球场的记者，赛况只能来自外部数据源（APISports）或者人工录入（导播台）。数据源有延迟、会漏事件、偶尔把比分报错；人工录入受制于值班导播的反应速度和注意力。

**另一半是"错了怎么办"。** 球球是一个会主动开口的数字人，一旦把错误数据当事实喊出来——宣布一个没发生的进球、报一个错的比分——伤害的是产品最核心的信任：用户可以容忍你慢，很难原谅你错得笃定。

**还有半个是"谁来兜底"。** 没配数据源密钥的时候、数据源挂掉的时候、导播就是不信任它的时候，系统必须有一个明确的退守位置，而不是当场现想。

我们的答案一句话说完：**单一外部源自动写候选，人工确认才成事实；源不可信时，系统宁可等待也不猜测。**

外部源写进来的每一条事件都带着"待确认"的帽子，公开播报要过事实账本的确认（47 篇）；源的健康度持续被测量，不健康时系统放宽"用户可能领先"的等待窗口、收敛自动播报，而不是换个来源继续报。

早期方案里曾设计过五级来源准入（S0 未准入到 S4 备用）、八层降级（D0 到 D4）、多来源交叉对照。真实实现收敛得多，这一篇讲收敛后留下的真实设计；事件进入账本之后的确认、冲突调和与更正，见 47 篇。

## 2. 真实设计

### 2.1 三个源，一个活跃：datasource.Manager

`backend/internal/datasource/manager.go` 是来源管理的全部。它认识三种源：

| 源 | 用途 |
| --- | --- |
| `manual` | 人工导播——导播台行为条与语音草稿产生的事件 |
| `replay` | 回放——按脚本重演比赛事件，评测与演示用 |
| `api-sports` | APISports 外部数据源——轮询拉取真实赛况 |

核心规则一条：**每场比赛同一时刻只有一个活跃源，默认 manual。**

`Start(matchID, config)` 负责切换，参数里带着源类型、fixtureId、是否回灌历史事件、以及人工源的预期延迟档位。入口校验很朴素但不含糊：源类型不在三种之内直接拒绝；选 api-sports 而没有 client（未配 key）拒绝；选 api-sports 而没带 fixtureId 拒绝。

切换本身是"停旧起新"的原子操作：先拿控制锁，停掉旧源并等它的轮询协程真正退出，再起新源。不存在两个源同时往一场比赛写事件的窗口——这是刻意的选择，双写意味着冲突处理从例外变成日常，我们不愿意付这个代价。

`Stop` 就是"停掉并回到 manual"：活跃源回到人工，球球的赛况从此只信导播。

`Status(matchID)` 把状态暴露给导播台：当前活跃源、每个源的状态机（`ready` / `standby` / `running` / `stopped` / `error` / `unconfigured`），以及下一节要讲的判活结果。

### 2.2 轮询与判活：3 秒、p95、"用户可能领先"

APISports 源的实时性来自轮询。默认间隔 3 秒（`PollInterval` 非正数时回落 3s），`poller.go` 每个周期拉一次比赛事件，投进缓冲为 32 的 channel；manager 消费事件、写库、回执。

写库与游标推进之间有一条重要因果链：

1. poller 投递事件，等待回执；
2. manager 调 `Ingest` 写入事实账本——命中 `ErrDuplicate` 或 `ErrConflict` 也算"已持久化"（重复投递是常态，不是错误）；
3. 只有持久化成功，poller 才 ack，游标才前进；
4. 游标按（matchID, source, fixtureID）存库，重启续跑、不重放旧事件。

外部事件进库时的映射在 `apiSportsMatchEvent`：`match_start` 映射为 `kickoff`，`match_end` 映射为 `fulltime`，进球事件自动把比分 +1。但关键是这一行——每条外部事件落库时 `FactStatus` 一律是 `provisional`（待确认候选）。**自动写事件不等于自动发布**：它进入候选队列，公开化要过 47 篇讲的确认流程。

判活不是"进程活着就是活的"。`deriveSourceStatus` 用两条真实信号算新鲜度：

- 阈值 = 2 × 轮询间隔 + 近 5 分钟轮询延迟的 p95，下限 6 秒、上限 20 秒；
- 距上次成功轮询的年龄：不超过阈值记 `fresh`，不超过两倍阈值记 `degraded`，再往后就是 `offline`。

阈值公式里"2 × 间隔"的意思是：连续错过两个轮询周期才开始怀疑，单次网络抖动不触发降级；p95 的意思是：按这个源自己近期最差的表现要求它，而不是按理想值。

三档新鲜度在导播台上的含义：

| 新鲜度 | 判定 | 系统行为 |
| --- | --- | --- |
| `fresh` | 年龄 ≤ 阈值 | 正常轮询，候选照常进入确认流程 |
| `degraded` | 年龄 ≤ 2 × 阈值 | 观察调和窗口放宽到 90 秒，导播台示警 |
| `offline` | 超出两倍阈值，或源停止 | 窗口放宽到 2 分钟，自动播报失去可信输入 |

新鲜度直接连着一条产品语义：`UserMayLead`。只要源不是 `fresh`，系统就承认**用户的电视画面可能领先于我们的数据源**——用户先看到进球是完全正常的。

`ObservationReconcileWindow` 据此放宽观察调和窗口：`offline` 时放到 2 分钟、`degraded` 或 `unknown` 时 90 秒；人工源也按导播配置的预期延迟（fast / normal / conservative）映射成三档窗口。

用户喊"进球了"而系统还没确认时，等多久再回应，答案就在这个窗口里：窗口内保持核验姿态不乱接话，窗口外仍无确认就按观察超时处理（跟进与过期语义在 45 篇的待确认候选对象里）。

### 2.3 人工接管与自动化暂停

导播台对源的操作走 `match_operator_api.go`：

- `GET/POST /api/matches/{id}/sources`——查看状态、启停、切换源（APISports 需要带 fixtureId）；
- `POST /api/matches/{id}/takeover`——人工接管；
- `GET/POST /api/matches/{id}/automation`——查看与设置自动化策略（active / paused，含事件白名单与冷却）。

takeover 的实现值得看一眼：它把活跃源切回 manual 的**同时**，把该比赛的 `AutomationPolicy.Mode` 置为 `paused`。一句话：**人工接管的一瞬间，球球的自动播报一起安静。**

这不是两个独立功能的巧合，是刻意的耦合——导播决定亲自掌管赛况时，最不想要的就是一个还在按旧节奏自动说话的数字人。

主动发言门禁（`conversation/proactive_gate.go`）的第一条判断就是 `Mode != active` 直接拒绝，paused 状态下 critical 事件也一律沉默，场上只剩导播的声音。

导播想恢复自动播报，用 automation 接口把模式改回 `active`——切换与接管都走运营台的幂等写通道（Idempotency-Key），重复点击不会产生双重副作用。

界面上这一切落在 console 的比赛设置页（MatchSettings）：数据源启动面与自动化表单同页，导播看得见当前活跃源、判活状态，也能一口气完成"停源—接管—暂停播报"。

**无 key 纯人工模式**是同一个哲学的起点形态：没配 `APISPORTS_API_KEY` 时，manager 里的 client 为 nil，api-sports 源状态显示 `unconfigured`，此时尝试启动它会得到明确的 "api-sports is not configured" 错误。系统其余一切照常——人工导播、事件确认、语音播报、评测全套可用。

外部源是增强项，不是依赖项。这个定位写进了 44 篇讲过的配置分层：`APISPORTS_API_KEY` 属于可以缺的增强型变量，缺了不拒启动。

### 2.4 verify-datasource：接入前的十分钟体检

`backend/cmd/verify-datasource/main.go` 是一个五十行的校验工具，做的事：加载配置，要求环境里有 `APISPORTS_API_KEY`，然后依次打印——今日比赛列表、实时比赛列表（含比分与进行时间）、每场实时比赛的事件流、以及前几条事件的原始 JSON。

它的价值在"接之前"：把一个 fixtureId 接进正式比赛之前，先人工看一眼这家数据源此刻返回的字段长什么样、事件粒度到什么程度、延迟感如何。工具不写库、不影响运行中的系统，纯粹的只读体检。

### 2.5 来源分级：S1/S2 思想的保留

早期方案设计了 S0 到 S4 五级来源准入，配登记卡与复核流程。真实落地后，五级收敛成一条分级直觉保留下来：

- **S1——静态赛程。** 只用于展示与检索的数据，错误成本是"显示错一场对阵"，不需要确认链路；
- **S2——动态线索。** 比分、进球、红牌这类会被球球当作事实说出口的数据，必须经确认才能公开。

APISports 在我们的分级里就是 S2：它写的每一条都是 `provisional` 候选；人工导播的行为条产生的也是草稿。谁也不直接代表公开事实——公开事实只有一种来源，就是确认。

这个收敛的判断标准是成本：五级准入管理的复杂度，只有在"接入多个来源、来源许可各异"的前提下才值得付。

我们只有一个外部源，且它的输出反正全要走确认，五级里的三级存在意义就没了。

留下 S1/S2 二分，是因为它至今还在指导每一个新字段的去向：这个数据只进赛程展示（S1），还是要进候选队列（S2）？

### 2.6 赛程查询：scope、时区与诚实的 unavailable

赛程是 S1 侧最主要的消费场景。用户问"今天有什么球""明天呢""最近有什么比赛"，链路分四步：

1. **意图分类**（`companion/classify.go`）：关键词命中赛程话题后定 scope——"明天/明日"是 `tomorrow`，"今天/今日/今晚"是 `today`，"现在/当前/正在"是 `current`，其余默认 `nearby`（近期）；
2. **构造请求**（`companion/schedule.go` 的 `BuildScheduleSearchRequest`）：按用户带来的时区算本地零点，today / tomorrow / current 取单日窗口，nearby 取两天窗口——带时区是硬要求，跨时区联赛的"今天"不是同一个今天；
3. **拉取数据**：APISports 客户端按天迭代 `/fixtures?date=` 接口，取回对阵、开球时间与状态；
4. **回答**：按 scope 组织口语化结果。

整条链路还有一个渐进式变体：数据没回来时不硬等，先回一句 ack，随后补上下文与结果。

lookup 有 20 秒过期时间，用户一打断就取消——生命周期管理独立在 `cmd/server/schedule_lookup.go`，用代际号保证"新一轮提问自动作废上一轮未完成的查询"。

这条链路上最重要的一句代码，是能力缺失时的那句诚实回答：

> 数据源客户端只实现了按天查询，没有任意日期范围能力。当注入的 schedule reader 不支持范围接口时，`Search` 直接返回 "schedule date-range search is unavailable"，球球回复固定话术"赛程源这次没接上，我不先乱报。"，trace 记录 `schedule_lookup_unavailable`。

用户问"下周末有什么比赛"，球球不会现编一个答案。

直接查询失败，trace 记 `schedule_unavailable`；渐进式查询解析失败，trace 记 `schedule_lookup_unavailable`——两条路径的 trace 都断言了供应商细节（密钥、凭据字样）绝不漏进回复。

能力边界被如实翻译成"暂不可用"，这是这一域的态度：**来源给不了的数据，宁可说没有，不说一个像样的。**

## 3. 如何验证

**单元层（Go 单测）。** `internal/datasource` 的测试覆盖轮询投递、游标续跑、判活阈值与事件映射（含 match_start→kickoff、比分自动 +1）；`internal/companion` 的赛程测试覆盖 scope 判定、时区换算与 unavailable 回落。

```bash
cd backend && go test ./internal/datasource/... ./internal/companion/...
```

**端到端层（operator-control 源切换接管用例）。** `tests/evals/operator-control.spec.mjs` 里有一条专门的用例："信号源可以切换，并通过人工接管同时暂停自动播报"——

1. `GET /api/matches/{id}/sources`，断言新比赛默认活跃源是 manual、manual 源状态 ready；
2. 切换源、执行 takeover；
3. `GET /api/matches/{id}/automation`，断言策略模式已是 `paused`。

同一份 spec 还锁定了这条输入路径的下游行为：

- 候选进球不改公开比分，确认后只加一次；
- 冲突候选调和，采用候选必须留下更正原因；
- 保留原事实时用户端比分不抖动；
- 比分更正作为独立审计事实发布，且不触发主动话术。

那些属于 47 篇的事实域，用例却与来源用例同文件同套运行——因为"来源写入"与"确认发布"本来就该被一起测试。

**手工层（verify-datasource）。** 换密钥、换环境、或数据源行为可疑时：

```bash
APISPORTS_API_KEY=... go run ./cmd/verify-datasource
```

输出今日与实时比赛、事件流与原始 JSON，人工判断字段与延迟是否还符合预期。

三层合起来的验收标准：

- 无 key 的部署纯人工照常运行；
- 有 key 的部署，源挂掉时导播台能看到状态、球球会安静或放宽等待，而不会播报错误的事实；
- 接管即安静，恢复 active 即恢复播报；
- 数据源给不了的范围查询，得到的是"暂不可用"而不是编造。

## 4. 边界与不做

**不做多供应商竞价。** 没有第二个实时源做交叉对照，没有"两个来源投票出事实"的机制——这个想法被评估过并被明确放弃。

理由有三：多源意味着多份许可与成本，意味着标准的实体映射（同名球队、同一场次的跨源对齐），意味着冲突从例外变日常——而这三样加起来，换来的"自动纠错"能力，我们用"人工确认"这一层已经拿到了，且人工确认的错误成本远低于自动投票。

判活窗口只决定"等多久、信多少"，不触发自动换源。单一来源 + 人工兜底，是这一域最核心的取舍，也是一切设计围绕的锚点。

**不做供应商推送。** 轮询 3 秒是当前全部的实时性——没有 webhook、没有长连接。延迟预算按"用户可能领先"设计（2.2 节），而不是把 3 秒当实时保证向用户承诺。哪天数据源提供推送，正确的做法是加一种投递形态并保留轮询兜底，而不是替换。

**不做自动发布。** 外部源写的永远是 `provisional` 候选，自动播报永远受自动化策略与确认状态双重门禁。进球取消、比分更正、更正原因审计这些兜底机制都在 47 篇——这一域的纪律只有一条：不确认，不公开。

**赛程只覆盖需要的窗口。** 今天、明天、近期、当前，四个 scope 之外不查询。按天拉取的现实成本决定了 scope 上限；"任意日期范围"能力缺失时报 unavailable 是诚实，不是缺陷。扩窗口的前提是数据源给出范围查询能力，且产品真的需要它。

重新评估"单源"这个边界的信号也写在这里：外部源长时间不可用且人工导播无法覆盖全部场次；或出现第二个许可清晰、质量可验证的来源，且它的接入成本被证明低于人工兜底的运营成本。在那之前，加源不进入任何迭代计划。

回头看，这一域的设计哲学和球球这个产品一致：**不确定的时候，宁可安静。** 数据源新鲜，就自动写候选、快速确认、及时播报；数据源迟疑，就放宽窗口、收敛表达、让导播的声音主导；数据源缺席，就纯人工照样开场。系统的每一层都知道自己该退到哪里——这就是"错了怎么办"的完整答案。
