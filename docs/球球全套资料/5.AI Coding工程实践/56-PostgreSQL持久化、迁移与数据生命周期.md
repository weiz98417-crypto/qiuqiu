# PostgreSQL 持久化、迁移与数据生命周期

> **本篇已由《球球课程》同源章节取代。**
> 课程章节按"系统实际怎么工作 + 与旧设计的差异"以 status 锚重写,是本主题的唯一事实源。本页保留原篇的定位说明与阅读指引。

**原篇定位**:0→1 工程执行方案,计划用 PostgreSQL 把可解释的比赛事实、受控会话与用户主动选择的资料,串成保留、删除、撤回、防回写、备份与恢复一条可验证的生命周期,而非事后补上的清理脚本。

其核心判断已按现实吸收:数据库不是"尽可能多记住"的容器,每条记录要能说明为何存在、何时失效、谁能使用、如何删除,以及删除后怎样阻止迟到工作与恢复流程把它重新带回可用状态;但施工细节(六域表、四阶段迁移流程、备份恢复演练)在实现中大幅收敛。

## 该主题讲什么

- **迁移即演化史**:持久化历史写在 `backend/migrations` 的 46 个顺序 SQL 里——001 陪看记忆起步,013 一次建立 user_sessions/fact_revisions/idempotency_records/outbox_messages/privacy_tombstones 五张核心表,022-028 落地账本单调序与冲突调和,031-038 扩展出互动与投递账本。
- **执行与投递**:没有独立 migrate CLI,服务启动时按文件名排序、单事务加 `pg_advisory_xact_lock` 串行执行,任一文件失败整体回滚;事实写入与出站消息靠事务性 outbox 原子落库,由 `RunOutbox`(250ms 轮询、SKIP LOCKED、指数退避)投递。
- **删除与生命周期**:真实删除链路由 privacy 包与墓碑表承担(状态/导出/请求删除/处理/过期清理,`PRIVACY_RETENTION_DAYS` 默认 30 天);旧稿的六个持久化域、R0-R5 保留分层与备份恢复演练属早期设想。
