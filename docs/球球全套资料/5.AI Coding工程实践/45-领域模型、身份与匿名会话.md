# 领域模型、身份与匿名会话

> 文档性质：工程叙事——球球的匿名身份、会话令牌与内部对象边界是怎么定的、怎么落地的、怎么验证的  
> 阅读方式：文中出现的包名、路径、接口与用例全部取自当前仓库，可边读边对照代码

## 1. 问题：陪伴型产品怎么做到"打开即用又可问责"

球球是一款 AI 足球陪看数字人：用户打开页面，一个 Live2D 形象陪他看球、聊球，进球一起喊。这类产品最容易在身份问题上栽跟头，而且是两头栽。

**一头是注册墙。** 陪看的用户往往比赛已经开始了，浏览器里点开一个链接就想马上看球。任何"先注册/先登录"的门槛，都会把"陪伴"变成"办卡"，用户转身就走，产品再聪明也没有出场机会。

**另一头是问责缺失。** 完全无身份的匿名流量，会在这些时刻拿不出答案：

- 用户说"把我的一切删掉"——你说得清"一切"包括哪些吗？删完之后真的一处都不剩吗？
- 球球对用户 A 说了句贴心话，换用户 B 坐下来——你确定 A 的记忆没有串到 B 头上吗？
- 运营或审计要回看"球球为什么对这个人说了这句话"——没有稳定的主体，连追溯的坐标系都没有。

所以我们给自己定的身份目标只有一句话：**打开即用，同时可问责。**

打开即用，指用户第一次访问就自动拥有一个可用的身份，不填任何东西就能进比赛、聊天、调话痨档位。

可问责，指每一条回复、每一次主动发言、每一段记忆都能回答"这是哪个用户的"；用户随时能导出、能删除，删除之后不再被引用。

这两条要求落到领域模型上，是三个分离。它们是这一域真正的地基，后面所有记忆、隐私、审计能力都站在这三个分离上：

- **身份与账号分离。** 用户有一个稳定的匿名标识（客户端生成、本地持有，服务端按设备落库），但没有服务端账号。身份用于隔离与问责，不用于登录与触达。
- **身份与会话分离。** 身份是"你是谁"，会话是"这次访问被允许做什么"。会话令牌可以过期、刷新、吊销，身份本身不受影响。
- **表达与事实分离。** 球球说过什么、用户说过什么、比赛发生了什么，分别记在表达、信号与事实三类对象里，谁也不能替谁作数——这是事实账本（47 篇）和记忆体系（30 篇）能保持干净的前提。

早期方案文档里曾有过一套庞大的身份模型：访客主体、稳定身份、共享显示、恢复保护四种状态，外加 P0 到 P5 六级权限。真实实现把这套纸面架构砍掉了绝大部分。

理由不是偷懒，而是每一级状态都要求配套的恢复流程与文案承诺，在"无账号"的前提下根本无处兑现：没有联系方式就无法做身份恢复，没有敏感资料就不需要共享显示的降级。

留下的部分，这一篇逐一讲清楚。先说身份，再说会话，然后是身份之下挂着的六个内部对象，最后是怎么验证、以及明确不做什么。

## 2. 真实模型

### 2.1 匿名身份：首次访问自动建号，迁移永不换 UUID

身份的起点在客户端。`client/lib/services/preferences_service.dart` 的 `loadOrCreateAnonymousUserId()` 是全链路第一个被调用的身份函数，语义一句话：有就返回，没有就生成。

实现比语义讲究，因为它要同时回答三个问题：存哪里、怎么迁移、什么时候才允许换。

**存哪里：双写。** secure storage 里的值为权威，SharedPreferences 里保留一份兜底副本。secure storage 不可用的设备（老系统、WebView 受限环境）自动退回旧语义，行为不比迁移前差；secure 可用时，每次读取都顺手把兜底副本对齐到权威值。

**怎么迁移：一条带纪律的三步。** 双写策略来自一个真实发生过的问题——匿名标识最初存在 SharedPreferences 里，后来要挪进系统密钥库保护的 secure storage。直接的挪法是"读 secure，没有就生成新的"，但那等于把所有老用户一夜换成新身份：他们的画像、话题、交互账本全部失联。所以真实的迁移逻辑是：

1. 先读 secure storage。读得到就直接用；
2. secure 里没有，再看 SharedPreferences 里有没有历史值。有，就把旧值**原样**迁入 secure storage——函数注释里写死了这条迁移语义：**绝不能因换存储而更换 UUID**；
3. 两处都没有（真正的首次访问），才用 `Random.secure()` 生成新 UUID，双写两处。

**什么时候才允许换：只有显式重置。** `resetAnonymousIdentity()` 把两份存储都清空，下一次读取生成全新 UUID。它是删除能力的入口之一（38 篇），是用户（或演示重置流程）主动做的事，系统自己永远不会触发。

服务端一侧对应两条实现：

- `backend/migrations/026_anonymous_device_identities.sql` 建的匿名设备身份表——026 号迁移只增不改，后续四十多个迁移没有任何一个重写已有身份行；
- `internal/auth` 的 `IssueAnonymous(ctx, deviceID)`：客户端带着设备标识来建会话，服务端把身份落库。

客户端带不上设备标识、而服务端又无法落身份时，接口返回 409（`ErrIdentityUnavailable`）——宁可让这一次访问失败，也不发一个落不了库的令牌。

"迁移永不换 UUID"这条纪律值得反复强调，因为它是匿名产品少数不可逆的红线之一：账号体系里身份丢了可以走找回，匿名身份丢了就是永久失忆。所有围绕这个 UUID 的存储演进——换库、加密、分层——都必须先回答"老值还在吗"，再动手。

### 2.2 会话：POST /api/sessions/anonymous 签发的双令牌

身份建立后，一切 API 访问都凭会话令牌。入口是 `backend/cmd/server/session_api.go` 挂在 `/api/sessions/` 上的三个动作：

| 动作 | 行为 |
| --- | --- |
| `POST /api/sessions/anonymous` | 携带可选 deviceId，签发访问令牌 + 刷新令牌，返回 201 |
| `POST /api/sessions/refresh` | 用刷新令牌换新令牌对，刷新即轮换（旧刷新令牌作废） |
| `POST /api/sessions/revoke` | 吊销访问令牌或刷新令牌，重复吊销不报错（幂等） |

三个响应统一 `Cache-Control: no-store`——令牌永远不进任何缓存；CORS 预检在这一层直接应答，不进业务逻辑。

令牌形态在 `internal/auth/session.go`：

| 属性 | 访问令牌 | 刷新令牌 |
| --- | --- | --- |
| 有效期 | 15 分钟 | 30 天 |
| 形态 | HMAC 签名的紧凑格式（带版本前缀，超长直接拒绝） | 随机字节串 |
| 服务端存储 | 不落库，验签即可 | 只存哈希——库被拖走也拿不到可用令牌 |
| 更换方式 | 到期即弃，用刷新令牌换新 | 轮换（Rotate）：每次刷新换新、旧的一律失效 |

短访问令牌加轮换刷新令牌是这一域的标准答案，我们照做的原因也很直接：访问令牌被盗，损害窗口最多 15 分钟；刷新令牌被盗，轮换机制会把复用暴露出来，损害被限制在单次。

两条硬性约束是"配置错误在启动时爆炸"（44 篇）在这一域的延伸：

- **production 强制 session 模式。** `internal/config` 里，`AUTH_MODE` 未显式配置时，生产环境一律取 `session`（身份绑定在会话令牌上），开发环境才回落 `dual`。这不是可选项，是环境的函数——生产二进制不存在"不绑会话的匿名访问"这个模式。
- **签名密钥至少 32 字符。** `NewManager` 对去空白后不足 32 字符的 `SESSION_SIGNING_KEY` 直接返回错误；生产环境缺这个变量或长度不够，进程拒绝启动。开发环境才允许进程自动生成一把本地密钥——生产绝不代生成，代生成等于人人可用同一把公开密钥签令牌。

把一次典型访问的令牌生命周期串起来：

1. 用户首次打开页面，客户端生成匿名 UUID 并落 secure storage；
2. 客户端 `POST /api/sessions/anonymous`，拿到令牌对，展示层与 WebSocket 都凭访问令牌工作；
3. 15 分钟后访问令牌过期，客户端静默 `refresh`，拿到新令牌对，旧的刷新令牌同时作废；
4. 用户清掉页面数据或触发删除，客户端 `revoke` 并重置身份——下一次打开，一切从第 1 步开始。

### 2.3 内部对象地图：身份之下挂着什么

身份本身是空的——它只是一个稳定的锚点。问责靠的是挂在锚点下面的内部对象。

六个对象，每个一句话，产品语义见"详见"列：

| 对象 | 一句话 | 详见 |
| --- | --- | --- |
| 互动账本（`internal/interaction`） | 追加式 ledger，七类事件——`turn_planned` / `signal` / `delivery` / `fact_revision` / `media_delivery` / `playback_result` / `turn_stale`——是"球球对这个人说过做过什么"的唯一本地事实源 | 41 篇 |
| 画像覆盖层（`internal/memory` portrait） | Memobase 合成与本地 overlay 按 (topic, sub_topic) 确定序合并，overlay 是权威层；用户改与忘写成 edit / tombstone，下回合生效 | 30 篇 |
| 开放话题（`internal/memory` threads） | 未答问题、承诺、情绪时刻、预测进台账，TTL 7 天；过期不等于已答，两种关闭分别写审计，主动发言必须引用某个 thread 或共同时刻 | 30 篇 |
| 待确认候选（`internal/observation`） | 用户喊"进球了"不改事实，只记一条 pending 观察，球球以核验姿态回复；事实确认或撤销后只跟进提出主张的用户，离线重连后补跟 | 41 篇 |
| 更正审计（`internal/matchstate` 事实账本） | 比分更正必须给出原因，correct 动作作为独立审计事实发布，绝不静默覆盖旧事实 | 41、47 篇 |
| 隐私立碑（`internal/privacy`） | 画像删除留下 tombstone 立碑防止复活；`GET /api/me/export` 导出、`DELETE /api/me/data` 起删除 job、过期数据每 6 小时清理、默认保留 30 天 | 38 篇 |

这张表是本篇真正想让读者带走的东西。它背后有三条刻意维持的纪律。

**包边界即数据边界。** `interaction` 不知道 `memory` 的存在，`matchstate` 的事实永远不会被 `memory` 或 `relationship` 改写——不靠运行时隔离，靠 import 方向的纪律加回归锁定（44 篇讲过这条单体纪律在这里的用法）。

**账本永不写比赛事实。** 互动账本记录表达与投递，画像与话题记录陪伴记忆，它们与比赛事实（比分、进球者、时钟）是两个世界。用户可以删光自己的一切记忆而不影响任何一场比赛的公开事实；反过来，事实更正也永远不需要碰任何用户的画像。

**每个对象都能被单独清干净。** 六个对象各有独立的删除与失效路径：画像删 slot 留 tombstone、话题过 TTL 写审计、观察有 deadline 过期不补、隐私删除起 job 可按 jobID 追踪。删除的可问责性不是一句口号，是六个对象各自实现出来的一组接口。

同样要说清楚的是：早期方案文档里的那些概念表——访客主体表、观看会话表、身份主体表——在真实仓库里没有任何对应物，也无须寻找对应物：它们描述的身份分层在"无账号"前提下无处兑现，实现时被整体放弃。

真实的数据字典以 41 篇为准——本篇的六个对象，就是身份域挂账的全部。

## 3. 如何验证

这一域的验证分三层，从界面到用例到隔离回归。

**第一层，运营台身份契约（Playwright）。** `tests/evals/console-identity.spec.mjs` 锁定运营台身份的全套行为：

- 令牌录入一次即持久化，随后概览正常渲染；
- 错误令牌不落库，并保留录入入口；
- 失效令牌在 401 后被清除，回到录入页；
- 机令牌仅显示一次，吊销立即失效；
- auditor 角色只读：运营员页与话题台账的写操作隐藏。

`console-auth.spec.mjs` 补上密码通道：错误密码有提示且不进入管理台、临时密码首登强制改密、改后新密码可再登录、退出即吊销。这些用例同时是身份契约的文档——契约改了而用例没改，评测立刻红。

**第二层，会话机制（Go 单测）。** `internal/auth` 的测试覆盖签发、刷新轮换、访问与刷新吊销、短密钥拒绝；`internal/config` 的测试锁定"production 缺密钥或密钥过短拒启"的硬门。它们都跑在离线评测档里（44 篇四档分层的第一档），零密钥、零外部依赖，每次提交必过。

本地一条命令即可复跑：

```bash
cd backend && go test ./internal/auth/... ./internal/config/...
```

**第三层，用户隔离回归（黄金用例）。** `evals/cases/regression/regression.persisted-user-isolation.json` 是这一域最重要的一条回归，剧情只有两轮：

1. 用户 A 在比赛中先喊"球进了"——球球进入暖性等待，回复核验姿态；
2. 换用户 B 首次喊同样的话——断言 B 拿到**自己的**核验回复（mustMention"还没跟上"），并且**必须不带** A 的暖性话术（mustNotMention"我知道你看到了"）。

身份隔离做得对不对，最终就体现在这种地方：球球不把一个人说过的话、等的期待，记到另一个人头上。

这条用例属于 100 例 Go 黄金套件的 regression 档，与画像一致性、open-thread 恢复等用例同档运行，每次提交都跑。

三层合起来的验收标准可以写成三句话：

- 换一台设备，一切都是新的；
- 同一台设备上，A 的记忆永远不会出现在 B 的回复里；
- 用户删除之后，画像、话题、账本的引用路径全部闭环（删除侧由 38 篇讲述的删除 job 与画像一致性回归共同锁定）。

## 4. 边界与不做

**无注册。** 没有用户名密码、没有手机验证码、没有第三方登录。

这不是"暂缓"，是产品决定：陪看场景里注册墙的流失成本永远高于匿名可承担的问责成本。运营台那边有完整的账号体系，恰好证明这不是能力问题，而是边界选择。

**无账号升级路径。** 匿名身份不会"升级"为正式账号——因为不存在可升级到的目标。

运营台的账号体系（`consoleauth`/`operatorauth`，密码 JWT 与机令牌双通道）服务于导播与审计人员，与用户匿名身份没有任何外键关系，两侧的表、令牌、中间件互不通用。

哪天真要给用户加账号，正确做法是新增一个身份域并设计显式迁移，而不是在匿名 UUID 上打"半账号"补丁。

**共享设备等于同一身份。** 没有设备指纹，没有"检测到不同的人"的推断；一台设备一份 secure storage，同看的朋友共享同一个匿名身份。

这是一条明说的行为约定，不是技术隔离：谁持有这台设备的存储，谁就是这个身份。

由此自然推出两条：不做多人画像能力；删除身份就是删除这台设备上的全部陪伴记忆。

电视投屏、客厅同看这些场景，靠的是这条约定加上"表达内容只锚定公开事实"的表达纪律，而不是靠身份层解决。

**不做跨设备身份同步。** 身份不绑定任何可触达的联系方式，换设备就是新身份。

"迁移永不换 UUID"的边界也在这里：迁移只发生在同一台设备的存储升级路径上，它保护的是老用户不被存储工程伤害，而不是提供设备间的连续性。

想要"换手机还记得我"，得先引入账号——那是另一个产品决策，不是这一域悄悄做的事。

**身份层不做内容判断。** 匿名身份只回答"这是哪个用户"，不回答"该对他说什么"。

话痨档位、安静控制、主动发言门禁全部属于会话编排域（50 篇）；身份域提供主体锚点，不提供行为策略。

这条边界防止身份表随着需求膨胀成万能表——六个对象之外再加任何东西，都应该先回到 41 篇的数据模型里走一遍设计。

重新评估这些边界的信号也写在这里：出现强合规要求的实名或未成年人身份需求；或产品决定引入可触达的账号体系。在那之前，匿名就是完整的方案，不是过渡态。

回头看，这一域真正交付的东西很朴素：一个用户从未感知、却让每一次对话都可归因的身份；一对会过期会吊销、被捅穿也只损失 15 分钟的令牌；和六个各管一段、删除时能被逐个清干净的内部对象。

陪伴可以很轻，问责必须有着落——这就是"打开即用又可问责"的全部含义。
