# Flutter 观赛端与多端降级

> **文档性质**：真实工程叙事。这一篇记录"球球"的观赛端客户端（`client/lib`）是怎样建成的：六个屏幕如何分工、会话控制在哪个模块、Web 和原生在哪里分叉，以及五条已经落地的降级兜底——断线重连、麦克风未授权、TTS 失败、自动播放拦截、Live2D 加载失败。文中所有模块、参数与行为均以仓库现网代码为准，关键路径逐处标注文件。

---

## 1. 问题：同一套代码，要在手机和网页、好网和差网、戴耳机和看字幕之间都成立

观赛端的难点从来不是"做一个 Flutter 应用"，而是三根轴同时拉扯，任何一根都能把体验拉断：

- **端的轴**。同一个仓库既跑 Flutter Web（由后端在 `/` 直接托管 dist），也打包 Android/iOS。浏览器有自动播放策略、标签页休眠、深链能力；移动端有系统运行时权限、应用生命周期、Live2D 依赖的内嵌 WebView。同名能力在两端的行为经常完全不同。
- **网的轴**。一场球 90 分钟以上，WebSocket 一定会断——锁屏、进电梯、切出去回条消息。断线期间比分在别人屏幕上前进，用户不能看到一块冻结的假象，重连后也不能被过期内容刷屏。
- **感官的轴**。用户可能戴着耳机、可能彻底静音、可能在嘈杂环境只看字幕、可能拒绝麦克风权限。角色的声音和形象是"陪看"的魅力所在，但它们必须是可以整个拿掉的层。

我们的核心裁决只有一条：**事实与控制是不可缺失层，声音与形象是可选层**。看比分、读时间线、文字提问、调话痨档、结束离开——这些任务在任何端、任何网络、任何权限状态下都必须成立；而 Live2D、语音播报、连续对话，全部是可以被环境逐个没收的奢侈层。

这句裁决后来变成了一句设计口头禅：**每加一个炫的东西，先回答"它挂了以后用户还剩什么"**。下面会看到，这句口头禅最后落成了五条具体的降级路径和一排把它们锁死的测试。

## 2. 真实结构：client/lib 里有什么

### 2.1 六个屏幕

客户端的页面结构就是六个屏幕加一组组件，按观赛旅程排列：

| 屏幕 | 文件 | 职责 | 失败时的样子 |
| --- | --- | --- | --- |
| 入口 | `screens/match_entry_screen.dart` | 应用起点：建会话、读目录；Web 端处理 `?matchId=` 深链直达比赛 | 目录加载失败给错误文案，不让用户停在白屏 |
| 目录 | `screens/match_catalog_screen.dart` | 列出 scheduled / live / finished 三种状态的比赛，可搜索筛选 | 只露这三种状态，排序按状态秩，不给半成品状态 |
| 大厅 | `screens/match_lobby.dart` | 赛前大厅：对阵、球员名单（首发/替补）、连接标记，进房/重连/设置/离开 | overview 加载失败有错误文案与重连按钮 |
| 比赛 | `screens/match_screen.dart` | 观赛主屏：事实流、对话坞、Live2D 舞台、字幕卡、动作菜单都挂在这里 | 各子系统独立降级（见第 3 节），互不拖垮 |
| 形象 | `screens/portrait_screen.dart` | 球球的立绘与资料页，含"球球懂我"画像入口 | 舞台资源不可用时，静态形象始终存在 |
| 设置 | `screens/settings_screen.dart` | 昵称、主队、话痨程度等偏好 | 保存失败不阻塞观赛 |

入口屏值得单独说一句：Web 端深链 `?matchId=` 可以直达一场比赛，但**退出比赛时会清掉参数**——刷新永远回到目录页，而不是把一场可能已经结束的比赛强行恢复出来。这是我们刻意的选择：恢复一个过期现场的成本和困惑，比多点一次进房高得多。

### 2.2 会话控制中枢与服务层

`services/` 目录里最重要的是 `match_session_controller.dart`——观赛端的**会话控制中枢**。它维护一场比赛的会话状态机：当前阶段、球球的回复文本、表演计划、音频队列、断线补发队列。所有事件——快照到达、时钟推进、比赛事件、语音回执——都以事件分发（dispatch）的方式喂给它，由它算出新状态再广播给界面。比赛主屏本身不持有比赛状态，它只是会话状态的订阅者。

把"这场比赛进行到哪了"收敛在一个模块里，是六个屏幕不至于各自为政的关键，也让"降档/静音/结束"这类横切控制有了唯一落点。

围绕它的服务各管一段：

| 服务 | 文件 | 职责 |
| --- | --- | --- |
| WebSocket 连接 | `services/websocket_service.dart` | 连接管理、25 秒心跳 ping、断线自动重连（≤5 次）、消息收发与客户端上下文注入 |
| 会话控制 | `services/match_session_controller.dart` | 会话状态机、表演计划映射、断线语音补发队列（上限 4 条） |
| 语音活动检测 | `services/vad_service.dart` | 双阈值 VAD（0.015/0.006）、音频分片、输入设备枚举 |
| 偏好持久化 | `services/preferences_service.dart` | 匿名身份存 secure storage，迁移永不换 UUID |
| 表演白名单 | `services/presentation_state.dart` | presentation-map.json 的客户端镜像：表情/动作/风格白名单与别名归一 |
| 浏览器历史 | `services/browser_history.dart`（+ web/stub 分支） | Web 深链与历史记录管理，非 Web 平台是空实现 |
| 目录与概览 | `services/match_catalog_service.dart`、`match_overview_service.dart` | 比赛目录、房间概览的 HTTP 拉取 |
| 会话令牌 | `services/session_service.dart` | 匿名会话的建立与令牌持有 |
| 流式转写 | `services/streaming_transcription.dart` | asr_start / chunk / finish / cancel 的客户端侧协议 |
| 待机三档 | `services/idle_tier_picker.dart` | 按情感向量挑选待机动作（详见第 52 篇） |

组件层同理各司其职：

- `match_dock.dart` 的 `ConversationDock` 是**对话坞**：文字输入、按住说话（onMicDown/onMicUp）、连续对话开关、音频输入设备选择、设置入口。它有一个显式的 `textMode`——文字面板不是隐藏起来的备用功能，而是一等公民；
- `reply_subtitle_card.dart` 负责字幕卡。它不只是 TTS 的附属品，而是 TTS 失败时的正式出口（见 3.3 节）；
- `match_actions_menu.dart` 收纳"少说/别说"这类即时控制；
- `connection_mark.dart` 把连接状态做成一个诚实的标记（见 2.5 节）；
- `live2d_view.dart` 连同 `live2d_bridge_web/stub` 承载舞台；
- `reply_display.dart` 与 `mobile_theme_canvas.dart` 负责回复呈现与移动端主题画布。

### 2.3 一条连接上的消息面

比赛主屏订阅的 WebSocket 消息种类不多，每种都有明确的所有者：

- `match_snapshot` / `match_clock`：比分快照与后台时钟轮播，进概览数据，也进会话控制器；
- `match_event`：确认后的比赛事件，带 `deliveryKey` 供客户端去重——候选（pending）事件不会出现在这条通道上；
- `match_fact_retracted`：事实撤回，已被撤事实触发的回复随之撤下；
- `presentation`：球球的表演计划（表情/动作/语气），经客户端白名单校验后驱动舞台；
- `voice_audio` / `voice_status` / `first_meeting_status`：语音元数据、语音回合状态、开场问候状态；
- `transcript_partial` / `transcript_final` / `transcript_error`：流式转写的三态；
- `interrupt` / `reply_displayed`：打断与展示回执。

上行方向则是 `ping`、`asr_start/chunk/finish/cancel`、`user_speech`、`set_talkativeness`，并且消息会自动带上客户端时区（`withClientContext`，供赛程查询使用）。消息面收敛之后，"哪条消息该改哪个状态"就不再是散落在界面代码里的 if-else，而是一张可以逐条写测试的表。

### 2.4 Web 与原生的分叉点

多端不是靠抽象话术实现的，而是靠五个明确的条件导入分支：

- **音频播放**：`audio_player_web.dart` 与 `audio_player_native.dart`。Web 端要直面浏览器的自动播放策略，所以它的播放器把生命周期拆成五个显式状态：`started / ended / interrupted / blocked / failed`——`blocked` 就是浏览器拦截了首屏自动播放，后面会看到我们怎么用它；
- **浏览器历史**：`browser_history_web.dart` 与 stub。深链只在 Web 上存在，其他平台编译进空实现；
- **时区**：`client_timezone_web.dart` 与 stub。读浏览器时区随消息上行，赛程渐进查询的"今天/明天/现在"窗口按用户本地时区计算；
- **Live2D 桥**：`live2d_bridge_web.dart` 与 stub。原生端走内嵌 WebView 加载模型页，Web 端直接同页加载；
- **录音**：`web_recorder.dart` 与 `recorder_stub.dart`，按平台提供采集实现。

分叉的原则是：**平台差异留在服务内部，不上涌到屏幕层**。六个屏幕对"当前是 Web 还是原生"几乎无感，它们只知道某个能力可能返回失败——而失败永远有文字路径兜着。这不是把头埋进沙子：能力探测发生在用户真的想用某项能力时（点播放、按住说话），而不是应用一打开就索要一圈权限。

### 2.5 连接状态是一个诚实的标记

`connection_mark.dart` 只呈现三种状态，每种都有文字，不靠颜色单独说话：

- **现场**（绿色圆点）：连接正常；
- **连接中**（黄色圆点）：正在重连——此时后台的退避计时器在跑；
- **连接失败**（红色圆点）：五次重连全部失败，等用户手动重试。

每个状态都带 `Semantics` 标签（"比赛已连接 / 比赛正在连接 / 比赛连接失败"）供屏幕阅读器朗读。这个小组件代表了一个态度：连接是个会坏的东西，坏的时候告诉用户，比假装一切正常更有安全感。

## 3. 真实降级：五条已经落地的兜底

### 3.1 断线：重连 ≤5 次、心跳 25 秒、补发语音 4 条

`websocket_service.dart` 的重连策略直接写在常量里：`_maxReconnectAttempts = 5`，退避间隔按 `1, 2, 4, 8` 秒指数增长（封顶 8 秒），重连成功即清零计数。连接期间每 25 秒发一次心跳 `ping`，让服务端的连接看守能及时清理死连接。

两个细节值得展开：

- **半开连接的检测**。TCP 半开（对端已死、本端不知）是移动网络的常态。我们的检测方式是"写失败即重连"：任何一次 send 失败都直接进入可见的重连状态，`_scheduleReconnect` 是幂等的，已有重连计时则忽略。用户会看到连接标记转黄，而不是对着一个假装在线的界面说话；
- **重连对用户可见**。每次重连尝试都会向消息流注入一条 `reconnecting` 事件（带尝试次数），界面与测试都能感知"连接正在自我修复"。

客户端还守着一个"欠账"队列：断线期间球球说过的语音兜底，`match_session_controller.dart` 在重连后排队补发，队列上限 **4 条**（`maxReconnectVoiceFallbacks = 4`），先进先出、淘汰最旧。

这个上限是踩坑换来的。早期没有上限，弱网用户重连后会接连听到四五条积压语音，像快进播放一段错过的广播——球球的陪伴感恰恰毁于这种"补课"。四条、淘汰最旧，意味着用户听到的是最近的心情，而不是一份完整的历史作业。五次重连全部失败后，客户端停止尝试，交还给用户一个红色的"连接失败"标记和手动重试入口，而不是永远假装"正在连接"。

### 3.2 麦克风未授权：文字路径常开

浏览器拒绝麦克风授权、或者系统层没给权限，是高频常态而不是异常。我们的处理原则是"不挽留、不轰炸"：权限失败后语音入口给出说明，**文字输入路径保持常开**——对话坞的文字框、发送、球球的回复，一切照常。用户的一切任务都不因麦克风而中断，也没有任何路径会反复弹权限窗消耗耐心。

这条行为由验收测试专门锁定（`workflows.spec.mjs` 的"麦克风未授权时，用户侧保留可用的文字输入降级路径"一例）。它曾经真的被一次 UI 重构悄悄弄坏过——测试红回来才保住。这也是我们把降级行为写成测试而不是写在注释里的原因：注释会被改掉，测试会喊疼。

### 3.3 TTS 失败：字幕兜底

语音合成失败时，服务端把回合标记为字幕兜底下发（`voice_status` 里的 `tts_fallback` / `text_fallback` 路径），客户端照常展示 `reply_subtitle_card` 的字幕——**听不见的内容一律看得见**。这条规则是单向的：字幕永远不依赖 TTS 成功；语音成功时字幕也在，因为总有人在嘈杂环境、总有人不开声音。

开发环境里还有个刻意的细节：只有设置 `QIUQIU_RUNTIME_TTS=1` 才注入 mock 音频，否则默认纯字幕跑全链路。这让"没声音能不能用"在开发期就每天被验证，而不是等真机出问题才发现字幕路径早就锈了。

### 3.4 自动播放被拦截：首次触碰恢复

浏览器的自动播放策略会拦下首屏语音——用户还没和页面互动过，浏览器不允许出声。我们的处理分两半：

- **如实上报**：`audio_player_web` 把这次拦截上报为 `blocked` 状态，回执进入语音回合的五态入账（started / ended / interrupted / blocked / failed），其中 blocked 记为 skipped 类——账本里不撒谎；
- **首触恢复**：`match_screen` 收到用户首次触碰后恢复播放，`client-voice-runtime.spec.mjs` 专门验证这条 `blocked:autoplay` → 触碰 → 恢复的链路。

诚实记账是关键的一半。如果 blocked 被当成"已播放"上报，运营面看到的送达数据就是假的，"为什么这条语音没人听到"永远查不出答案。现在答案就在数据里：不是服务挂了，是浏览器拦了。

### 3.5 Live2D 加载失败：落回静态待机

Live2D 模型加载是整个客户端最重、最脆的一环：资产可能下载失败、模型页可能脚本出错。失败检测在两端各有入口——原生端 WebView 的 `onModelError` JavaScriptHandler 回调，Web 端的 8 秒就绪超时——但行为归一：置 `_loadFailed`，停止就绪轮询，舞台层不再渲染模型。

失败后的落点是**静态形象**：portrait 一直在那里，观赛与对话完全不受影响；同时给出一个明确的"重新请球球入场"重试按钮。加载中的占位文案是"球球正在入场"，带语义标记（liveRegion）供屏幕阅读器朗读。我们不接受两个反面教材：无限转圈的加载动画（把资源失败伪装成"马上好"），或者整个页面白屏（可选层的失败传染给必需层）。

这五条兜底共同兑现了第 1 节的裁决：网络崩了有重连和补发、麦克风没了有文字、合成挂了有字幕、浏览器拦了有首触、模型挂了有立绘。可选层可以被逐个拿掉，而观赛还在。

## 4. 如何验证

观赛端的验证是分层的：端到端旅程与专项回归各守一段，谁也不替代谁。

**workflows 旅程套件**（`tests/evals/workflows.spec.mjs`，12 例）。这是用户旅程级的主验收，每例都是一条完整的观赛故事，驱动的是真实浏览器里的真实客户端加真实后端：

- 导演主动线、基于记忆回答追问，且全程日志可追溯；
- 用户错误赛况不覆盖比赛事实，并留下核验记录；
- 错误进球者被纠正，玩笑不进事实核验；
- 没有比赛证据时，用户报告的进球保持待确认；
- 没有比赛事件时，指代式赞美不被球球顺着认同；
- 比赛时钟不阻塞客户端状态轮播；赛况与时间提问读后台时钟；
- 零比零时用户说"好球"得到赛场回应且不被当成进球；
- 人工与外部源冲突时，球球暂停确认赛况；
- 导演赛前配置通过页面保存并同步事实 API；
- **麦克风未授权时，文字输入降级路径可用**。

**客户端专项 spec**：

| spec | 例数 | 守住什么 |
| --- | --- | --- |
| `client-vad.spec.mjs` | 3 | 双阈值 VAD 的开口确认与句中宽容 |
| `client-microphone.spec.mjs` | 6 | 麦克风枚举、授权失败、设备回落 |
| `client-voice-runtime.spec.mjs` | 2 | 语音回合完整链路，含自动播放 `blocked:autoplay` 后的首触恢复 |
| `client-delivery-dedupe.spec.mjs` | 1 | deliveryKey 送达去重，重连不重复消费 |

这四个 spec 与 workflows 分工明确：journey 套件证明"故事讲得通"，专项 spec 证明"某个机构在任何边角条件下行为正确"。VAD 的阈值行为没法在 journey 里覆盖——它需要逐帧注入受控音量，那是专项 spec 的活。

五条降级路径与测试的对应关系现在可以列成一张表：

| 降级路径 | 锁定它的测试 |
| --- | --- |
| 重连 ≤5 次 + 语音补发 4 条 | `connection-check.spec.mjs`、`client-delivery-dedupe.spec.mjs` |
| 麦克风未授权文字常开 | `workflows.spec.mjs` 降级例、`client-microphone.spec.mjs` |
| TTS 失败字幕兜底 | `client-voice-runtime.spec.mjs`（纯字幕链路） |
| 自动播放拦截首触恢复 | `client-voice-runtime.spec.mjs`（`blocked:autoplay` 断言） |
| Live2D 加载失败落待机 | `flutter test` 白名单契约 + 静态形象恒在 |

**静态检查与单测**：`flutter analyze` 与 `flutter test` 挂在常规验证路径上；表演白名单另有客户端契约测试，把代码常量、presentation-map.json 与模型资产三方对齐（详见第 52 篇）。

本地复现是标准三步：`flutter pub get`；`flutter run -d chrome --dart-define=QIUQIU_WS_URL=<本地后端>`（或 `-d android`）；`npx playwright test tests/evals/`。spec 与后端共用一套本地编排与测试支撑（假麦克风、测试账号），总览见第 57 篇。

## 5. 边界与不做

- **不做"按场模式卡"**。话痨档位（quiet / normal / active）的调整入口只放在设置页（`settings_screen.dart` 的"话痨程度"分区），不在比赛进行中弹一张模式卡打断观赛。取舍很如实：赛中有比调档更重要的注意力，而档位本身走 `set_talkativeness` 即时持久化并回 ack——真要调，两步就到，改完立刻生效，用户不需要在比赛页里有第二个控制面。这里还有一个刻意的不对称：用户侧能写，console 运营侧只读——档位是用户的主权，运营无权代调（红线写进了 console 契约测试）。
- **刷新不回比赛**。深链退出清参，刷新永远回目录。不做"恢复上次观赛现场"：恢复一个过期现场制造的困惑大于便利，宁可让用户多点一次进房。
- **不做跨用户同看房间**。观赛是"用户 + 球球"的私享陪同，不是多人直播间；实时通道的每条消息都绑定当前会话，不存在围观他人比赛的路径，连接层还有每 IP 连接数与读帧上限兜底。
- **不做视频转播与后台音频**。客户端消费的是事实流与语音回复，不是视频流；页面进后台，语音不续播、麦克风不重开，恢复只恢复状态——移动端来电、标签页失焦得到的都是同一种待遇。
- **横竖屏只重排、不重置**。布局按可用宽度与文字缩放重排，但旋转不重置会话、不重新请求权限、不恢复被用户关掉的声音。

回头看，观赛端的工程答案可以压缩成一段话：六个屏幕按旅程排列，会话状态收敛在一个控制器，平台差异压进五个条件导入分支；然后诚实地承认每一层都会挂，给每层配好它的兜底——重连五次补发四条、文字常开、字幕兜底、首触恢复、落回立绘；最后用 12 条旅程和一排专项 spec 把这些行为锁死。多端降级的本质不是写多少平台判断，而是让"它挂了以后用户还剩什么"这个问题，在每一次代码评审里都有一个测试背书的答案。
