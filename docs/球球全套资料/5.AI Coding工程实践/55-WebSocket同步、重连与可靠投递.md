# WebSocket 同步、重连与可靠投递

> 本文是"球球"AI Coding 工程实践系列的实时链路篇，写给想了解这款产品如何让一场 90 分钟的比赛在断线、重连、重复与撤销中保持状态可信的读者。文中描述的能力均以仓库现网代码为准，实现位置逐处标注；尚未实现的部分，统一归入文末"边界与不做"，不以既有能力的口吻表述。
>
> 核心原则：可靠投递不是"每一条都要送到"，而是"用户看到的每一条都值得看到"。快照先行、revision 保序、deliveryKey 去重、过期不补——我们宁可让用户重连后看到一份新鲜快照，也不把旧消息倒回去重播一遍。

---

## 1. 要解决的问题：一场比赛 90 分钟，连接断了怎么办

观赛是一场长连接的持久战。90 分钟里，手机锁屏、标签页休眠、电梯里断网、代理服务器掐掉空闲连接，任何一件都会打断 WebSocket。连接断了不可怕，可怕的是断线期间发生的一切怎么补回来：

- 进球确认了，用户重连后是收到新鲜快照，还是被旧消息糊一脸？
- 角色一句庆祝话刚排上队，连接断了，重连后要不要重说一遍？
- VAR 取消了进球，断线期间客户端队列里还挂着"进球音频"，重连后播还是不播？
- 用户在弱网下手一抖发了两遍同一句话，角色会不会回答两遍？

我们用四个原则回答这些问题：

1. **快照先行**：重连后的第一件事是拿到当前完整状态，而不是逐条补发历史；
2. **revision 保序**：同一事实的旧版本永远覆盖不了新版本；
3. **deliveryKey 去重**：重复到达的消息最多产生一次用户可见效果；
4. **过期不补**：超过时限的内容宁可丢弃，也不打断下一段比赛。

下面按真实实现展开，服务端在 `backend/internal/ws`（连接网关）与 `backend/cmd/server/watchconnection.go`（/ws/match/ 实时会话引擎），客户端在 `client/lib/services/websocket_service.dart` 与 `match_session_controller.dart`。

## 2. 真实设计

### 2.1 一条连接，三种流

端点是 `WS /ws/match/{id}`，一条连接只服务一场比赛。连接建立后，服务端按固定顺序喂三种消息（`watchconnection.go` 的 identify-and-subscribe 与 pumpMatchEvents 两相）：

**第一流：snapshot 重放（连接建立即发）**

- 先发 `match_snapshot`——公共快照（比分、阶段、关键事件线）；快照剔除了内部 Integrity 调试字段，客户端拿到的就是投影结果；
- 随即补一发 `match_clock`——当前主时钟与版本号。

**第二流：clock 轮播（服务端时钟推进时）**

- 每次时钟推进，服务端推 `match_clock` + 最新 `match_snapshot`；
- 客户端对时钟做版本守卫：新到的时钟版本号更低就直接丢弃，界面时钟绝不倒流。

**第三流：match_event 推送（事实账本变化时）**

- 公开事实推 `match_event`，消息里同时带事件本体、最新快照和 `deliveryKey`；
- 非公开事实（候选、内部状态）只刷快照、不推事件——用户端永远不会看到" pending "的半成品事实；
- 事实被撤销时补发 `match_fact_retracted`，携带事件与事实标识。

消息类型总览（均为代码中真实存在的 wire 类型）：

| 类型 | 方向 | 作用 |
| --- | --- | --- |
| match_snapshot | 服务 → 客户端 | 公共快照，恢复锚点 |
| match_clock | 服务 → 客户端 | 主时钟与版本号 |
| match_event | 服务 → 客户端 | 公开事实 + 快照 + deliveryKey |
| match_fact_retracted | 服务 → 客户端 | 事实撤销通知 |
| presentation | 服务 → 客户端 | 表演计划（表情/动作/保持窗） |
| event (event=qiuqiu_reply) | 服务 → 客户端 | 角色回复：文本、来源、deliveryKey 与表演计划 |
| voice_audio（二进制帧） | 服务 → 客户端 | TTS 音频，携带 traceId 与 deliveryKey |
| interrupt | 双向 | 用户打断；服务端回倾听反应 |
| voice_status | 服务 → 客户端 | 语音链路状态（失败、文字兜底等） |
| pong / ping | 双向 | 应用层心跳应答 |
| user_speech / asr_* | 客户端 → 服务 | 用户轮次与流式转写 |
| voice_playback / reply_displayed | 客户端 → 服务 | 播放与展示回执，驱动送达状态机 |
| session_opened / session_closed | 客户端 → 服务 | 会话绑定与解绑，触发恢复与清理 |
| set_talkativeness | 客户端 → 服务 | 话痨档位即时持久化，服务端回 ack 为真源 |

### 2.2 连接保护：Origin、会话、每 IP 上限与帧限制

握手关是第一道防线（`backend/internal/ws/handler.go` 升级流程 + `backend/internal/config/config.go`）：

- **Origin 校验**：请求 Origin 与请求 Host 同源即放行；跨源则比对允许清单；不可信来源直接 403，拿不到任何比赛数据。生产环境回环地址的宽松规则关闭；
- **会话鉴权**：访问令牌走 `Authorization: Bearer` 头或 `Sec-WebSocket-Protocol: qiuqiu-auth.<base64url>` 子协议携带——查询串里拼 token 的做法被测试明确拒绝。生产环境强制会话令牌并核对作用域；令牌在服务端验签后，连接的身份、比赛订阅都绑定在会话声明上；
- **每 IP ≤ 5 条连接**：超出返回 429。同机多开调试不会把单 IP 变成连接风暴的入口；
- **单帧读上限 1MB**：这个数字是照着最重的合法载荷算的——一段 15 秒 16kHz 单声道语音。更大的帧直接断开，不给协议放大攻击留面；
- **读写超时 60/10 秒**：读超时 60 秒，由协议层 pong 自动续期；每次写出前设 10 秒写死线，写不进去就放弃这条连接。

### 2.3 双向心跳与服务端看守

心跳是双向的，各管一个方向的死活：

- **服务端 → 客户端**：每 30 秒发一个协议层 ping；浏览器和 Flutter 的 WS 栈会自动回 pong，pong 到达即续读超时。这个方向穿过代理时也顺便保活；
- **客户端 → 服务端**：客户端每 25 秒发一条 JSON `ping`，服务端读循环回 `pong`。客户端靠"发得出去"确认这条连接还活着；
- **会话看守**：服务端的连接看守每 30 秒重新校验一次会话声明——令牌过期或被吊销，立即下发 `auth_error` 并关闭连接，不让失效会话继续收发。

### 2.4 客户端重连：≤5 次、指数退避、令牌刷新

`websocket_service.dart` 是客户端连接的全部生命周期：

- **重连上限 5 次**：断线后自动重连，超过 5 次停止并进入 failed 状态——界面上明示"连接失败"，把重试权交还用户，不做无限后台尝试；
- **指数退避**：第 n 次重连等待 2^(n-1) 秒，钳制在 1–8 秒之间，避免弱网下硬碰硬；
- **令牌先刷新**：重连前先走一次令牌刷新回调，拿着新令牌去握手，避免"连接好了才发现令牌过期"的二次断线；
- **代际防串台**：每次连接分配一个代数（generation），旧连接上迟到的回调、迟到的消息一律按代数丢弃——快速断连重连时，旧连接的尾巴不会污染新会话；
- **残坏容错**：旧通道关闭时抛错会被吞掉，重连流程绝不死在半路；
- **未连接不发**：`send()` 在未连接时直接返回 false。用户语音在断线期不假装"已发送"，而是进入客户端补发队列（见 2.6）；
- **状态可见**：connecting / connected / reconnecting（带第几次尝试）/ disconnected / failed 全部作为状态流暴露给界面，用户永远知道现在是哪个状态。

重连不只是恢复传输，还要恢复会话语义。客户端重新绑定会话（`session_opened`）后，服务端在连接上做四件事（`watchconnection.go` 读循环）：

1. 恢复该用户持久化的话痨档位——重连不把说话疏密重置回默认；
2. 重放未送达回复（见 2.6）；
3. 重新排程时限内的观察跟进（第 48 篇）；
4. 若身份与会话声明不匹配，直接 `auth_error` 断开——换人不续用旧连接的授权。

### 2.5 deliveryKey 去重与 revision 保序

去重与保序是同一枚硬币的两面，钥匙是 `deliveryKey = 事件ID:factRevision:factStatus`（`backend/internal/matchstate/store.go`）：

- **重复被吸收**：同一事件、同一版本的重放产生同一个 key，去重后只呈现一次；
- **更正能通过**：确认（confirmed）改调和（reconciled）、revision 递增，都会生成新 key——更正不是重复，必须送达。

三道去重关卡各管一段：

1. **服务端连接级**：每条连接维护一个 512 条的 LRU 已投递集合（`pumpMatchEvents`），事件订阅的重复投递在这里被拦下；
2. **服务端轮次级**：用户每句话带 signalId，服务端 `signalDeduper` 以"用户+比赛+信号"为键去重，TTL 15 分钟、容量 4096 条——客户端重试同一句话，角色只回答一次；
3. **客户端级**：`match_session_controller.dart` 对四类内容（比赛事件、反应、表演、音频）各挂一个 `DeliveryDeduplicator`，重连重放撞上已见过的 key 直接跳过。

**revision 保序**：客户端为每条事实记下已见到的最高 revision，revision 更低的消息直接丢弃——快照、事件、更正无论以什么顺序到达，比分只会向前走。撤回则是单向门：被撤事实的音频从待播队列移除、在播反应被取消（见 2.7）。

用一条时间线看三道关卡如何合流：

```text
T0  进球确认，deliveryKey = evt-12:1:confirmed     ——服务端连接级 LRU 记录，推送客户端
T1  订阅重放又送来 evt-12:1:confirmed              ——服务端 LRU 命中，不再推送
T2  弱网客户端重发请求，evt-12:1:confirmed 再到     ——客户端 Deduplicator 命中，跳过
T3  VAR 通过，evt-12:2:reconciled 到达             ——新 key，放行；revision 2 > 1，应用
T4  一条迟到的 evt-12:1:confirmed 最后抵达         ——客户端 revision 守卫：1 < 2，丢弃
```

用户全程只看到一次"进球"和一次"确认有效"，没有任何重复或回退。

### 2.6 断线语音补发：客户端 4 条 FIFO + 服务端未送达回放

断线期间产生的用户语音与未展示的回复，两边各有一条补偿通道：

**客户端语音补发队列**（`match_session_controller.dart`）：

- 断线期间用户按住说话，语音兜底条目进入 `ReconnectVoiceFallback` 队列；
- 队列上限 **4 条**，满了淘汰最旧——我们补的是"你刚才说的最后几句话"，不是完整录音历史；
- 只在连接恢复后才出队发送，发完一条、确认送达一条，再发下一条；
- **已取消不补**：用户在断线期间松手取消的语音不会进队，取消就是取消。

**服务端未送达回放**：

- 客户端发出 `session_opened` 完成会话绑定后，服务端扫描该用户本场"已生成但未确认展示"的回复，把已解析的逐条以 `event=qiuqiu_reply`（来源标记 recovered_delivery）重放；
- 余额在跟进时限内的观察跟进（第 48 篇）也在同一时刻重新排程；
- 未解析、来源出错的记录只留日志，不重放——回放的是"确定该说的"，不是"所有没说完的"。

### 2.7 已取消不补

实时链路里"收回"比"补上"更常见，三条取消路径都是终局：

- **事实撤销**：`match_fact_retracted` 到达后，客户端把受影响事实（含关联事实）的待播音频逐条移除；如果正在播的反应引用了被撤事实，立即暂停音频、取消表演回返、清掉反应——绝不让庆祝在"这球没算"之后继续响；
- **主动发言过期**：事件触发的主动话术带 TTL（critical 45 秒 / 普通 12 秒），过期即弃，重连回放也不含它们；
- **回放只取已解析**：服务端补发只挑"resolved"状态的记录，取消、过期、来源出错的永不重放。

### 2.8 时钟 409 自愈：服务端主时钟与并发写

比赛时钟的唯一权威在后端（`backend/internal/matchstate/clock.go`），所有客户端只读。导播台推进时钟的 PATCH 请求必须携带版本号（expectedVersion）：

- 版本不匹配（比如两个运营页同时操作）时服务端返回 **409**；
- 导播台前端收到 409 后**自动重读**最新时钟与版本、弹一条提示，随后的操作照常进行——不需要人工刷新页面；
- 比赛事件不会把主时钟拨回去：事件流里带出的时间只能跟随主时钟，不能覆盖它。

## 4. 边界与不做

- **一条连接只属于一场比赛**。没有多房间订阅、没有主题通配符；想看另一场比赛就开另一条连接，经同一套 Origin/会话/每 IP 上限约束；
- **没有续传游标**。重连不恢复"上次读到哪里"——直接发新快照加未送达回放。这是我们权衡后的取舍：观赛场景里游标续传省下的流量，远小于游标失效带来的复杂度；
- **不承诺每条必达**。过期主动话术不补、超时限跟进不补、取消的语音不补。"送达率"不是我们的目标指标，"用户看到的每条都成立"才是；
- **每 IP 上限是单进程内存计数**。当前部署是单 backend 容器，这个实现成立；将来多副本部署需要把计数外移到共享存储，这一点写进边界，不假装它已经分布式；
- **用户端时钟只读**。409 自愈只服务导播台的并发写，用户端不存在写时钟的入口，也就不存在这类冲突；
- **不做传输层实验**。当前只用 WebSocket，没有 WebTransport/QUIC 备份通道；断线降级路径是"快照+文字+用户主动重试"，不是第二条长连接；
- **不做离线消息箱**。离开页面的时间没有为用户保存历史播报；回来看到的是比赛现在，不是错过清单。
