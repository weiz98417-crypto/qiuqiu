# 实时观察与直播延迟协调

> 本文是"球球"AI Coding 工程实践系列的实时观察篇，写给想了解这款产品如何面对"用户可能比数据源先看到进球"的读者。文中描述的能力均以仓库现网代码为准，实现位置逐处标注；尚未实现的部分，统一归入文末"边界与不做"，不以既有能力的口吻表述。
>
> 核心原则：我们把用户的话当作"观察"而不是"事实"。用户先看到的瞬间值得被承认，但不能因此改写比分；数据源先知道的事情也不能因此说错。在延迟不确定的世界里，"知道了但不说错"和"想说时不迟到"是同一条纪律的两面。

---

## 1. 要解决的问题：直播延迟下，怎么不把话说错、不说太迟

同一场比赛，用户和我们的数据源几乎从不同步。

- 用户可能在电视上先看到进球，而我们的外部源要数秒后才轮询到；
- 也可能相反——源先确认，用户的画面还停在上一回合；
- 源还会自我修正：候选进球先挂出来，VAR 之后再撤销；
- 人工导播和外部源可能给出互相矛盾的赛况，需要逐项调和。

这给陪看角色制造了两类随时可能犯的错误：

1. **说错**：用户喊"进了！"，我们把它当成事实写进比分、说出口，结果 VAR 取消进球——比分错了，庆祝也收不回来；
2. **说迟**：源确认了进球，角色的回应在调度队列里排了半分钟才出来，此时用户画面早已走过，一句迟到的"好球"比沉默更尴尬。

我们的解法分两步：

- 先让"用户主张"永远不触碰事实账本，只沉淀为一条**待确认观察**，等公开事实来对账；
- 再给每一条跟进回应设置**时限**——确认后及时跟进，过期就不再补，宁可不说不说错。

再配合"in-band 事实刷新"：一次语音回合里即使赛况恰好变化，也用同一句话重说一遍，而不是追加第二次播报。下面按真实实现展开。

---

## 2. 真实设计

### 2.1 用户主张：只记待确认观察，不改事实

用户的一切赛况主张——报比分、喊进球、指认球员——都先经过确定性判定，再决定"接得住"还是"先记下来"。判定逻辑在 `backend/internal/companion/matchclaim.go`，全部是规则代码，不靠模型临场判断真伪：

**比分主张**（如"现在 2 比 1"）：

- 与公共快照比对：一致返回 confirmed，回答"对，场上现在是主队 2-1 客队。"；
- 不一致返回 contradicted，回答"还没，场上现在是……"；
- 语句里提到客队名、比分前是客队后是主队的，会自动翻转主客顺序再比，避免口径歧义。

**进球主张**（如"法比安进了！"）：

- 从口语里剥出主张的球员/球队："刚刚""好像""这球"这类前导词、"确实""真的"这类坚持副词、"又""也"这类虚词都会被剥掉，剩下的最后一个短语才拿去当人名；"他们""有人"这类泛指不算人名；
- 与最近事件对账：主张球员与实际进球人一致是 confirmed，不一致是 contradicted，对不上是 unverified。

**快照自检**：

- 快照自身事件链对不上（来源冲突、比分迁移不一致、开赛前出现进球）时，一律降级为 unverified——"这会儿赛况有点对不上，我先不报死，等一下再看。"；
- 比赛未开始时的进球主张直接反驳："比赛还没开始，这条不能算。"

**确定度**也顺带记录："好像/似乎/可能/应该/大概/听说/吧"命中任意一个，主张记 uncertain；否则记 asserted。

unverified 的主张会调用观察协调器的 `Record`，落成一条 `pending_sync` 状态的观察。观察记录的字段（`backend/internal/observation/coordinator.go` 的 `PendingObservation`）：

- 身份：`id`、`signalId`（信号去重键）、`traceId`、`userId`、`matchId`；
- 主张：`kind`、`eventType`、`claimedTeam`、`claimedPlayer`、`claimedScore`、`certainty`；
- 生命周期：`status`、`receivedAt`、`followUpDeadline`（跟进时限）、`reconcileUntil`（对账窗口）、`resolvedAt`、`resolutionReason`；
- 对账结果：`candidateFactId`、`resolvedFactId`、`resolvedRevision`。

这里的关键取舍：**Record 的返回值不改任何公开数据**。`matchstate` 事实账本里，候选事实本来就不参与公共比分投影，用户观察更没有写回路径。用户此刻听到的是核验姿态——"我这边还没跟上这粒进球，先等一下看结果。"；比分主张则是"这条赛况我还不能确定，先别急着算。"——而不是附和。

### 2.2 温热保持：重复的主张不重启观察

用户等不到回应往往会再喊一遍"明明进了！"。对系统来说这是同一个主张的重复，不是第二个信源——拿用户的重复当第二条来源去"交叉验证"，等于自己骗自己。

`backend/internal/companion/observation_hold.go` 里的温热保持判定：

- 当前用户在本场已有一条活跃观察（pending_sync / corroborating / conflict），且尚未超出对账窗口；
- 新主张在**语义**上匹配同一内容：按事件类型、主张球员、主张球队、主张比分匹配，而非逐字文本。"球进了"接"明明进了"走同一条保持；主张了不同球员的，才算新主张；
- 命中持久保持时，回复换成固定共情话术：

> "我知道你看到了，我也记下了你这条。我要等慢一点的源确认，一有结果我立刻喊你。"

事实姿态完全没变——协调器里的那条观察原样保留，不刷新计时、不重复落库（协调器对相同 signal 与相同活跃主张天然去重，命中即原样返回既有记录）。用户被听见了，账没有被记两次。新鲜主张则走通用核验姿态（"我这边还没跟上这粒进球……"），两种姿态的切换由关系策略的 cue 控制，不靠生成临场发挥。

### 2.3 观察协调器：状态、时限与上限

协调器是观察的唯一归属地，`backend/internal/observation/coordinator.go` 维护一条观察的完整生命周期：

```text
pending_sync ──候选事实匹配──▶ corroborating ──公开事实──▶ confirmed
     │                            │
     │                    另一个不同的候选事实
     ▼                            ▼
  expired                      conflict ──公开事实/撤销──▶ confirmed / contradicted

confirmed ──事实被撤销──▶ contradicted（更正时限延长到撤销后 45 秒）
进球主张 + 确认的非进球事实（射门/扑救/不进/取消进球）──▶ contradicted
```

各状态的含义与用户可见结果：

| 状态 | 触发 | 用户可见结果 |
| --- | --- | --- |
| pending_sync | 主张刚登记，还没有事实来对账 | 核验姿态："先等一下看结果" |
| corroborating | 有一条候选事实匹配，但还没确认 | 无新发言，继续等 |
| conflict | 出现第二个不同的匹配候选 | 无新发言，等来源收敛 |
| confirmed | 公开事实匹配 | 固定可靠文本跟进（见 2.4） |
| contradicted | 事实被撤销，或确认的非进球事实反驳了进球主张 | "结果出来了，这球没算……" |
| expired | 对账窗口耗尽仍无对账事实 | 不补说，保持沉默 |
| superseded | 同一用户同场活跃观察超过上限 | 最旧一条让位，无用户可见动作 |

状态迁移都由事实事件驱动（`OnFactChanged`），只有候选（provisional）、公开（confirmed）、调和（reconciled）、撤销（revoked）四类事实状态有资格参与对账。匹配不只看身份，还看主张比分与事实比分是否一致——用户主张的比分和实际落定的比分不同，这条观察不会被"确认"。

协调器给每条观察两条时钟：

| 时钟 | 用途 | 档位（按事件类型） |
| --- | --- | --- |
| 跟进时限 followUpDeadline | 确认/反驳后，跟进必须在此窗口内送达，过期不补 | 射门/扑救/黄牌/换人 **10 秒**；一般事件默认 **15 秒**；VAR 结果与取消进球 **45 秒** |
| 对账窗口 reconcileUntil | 窗口内没等到能对账的事实，观察标记 expired | 对应 45 秒 / 60 秒 / 2 分钟 |

两条额外保护：

- 撤销路径：观察被已确认事实反驳时，跟进时限至少延长到撤销后 45 秒，保证"这球没算"这句更正一定来得及说；
- 数量上限：每个用户每场最多 **5 条**活跃观察，超出时最旧的一条被标记 superseded，防止同一用户滚雪球式堆积。

过期由后台清扫兜底：服务端每 **5 秒**跑一次 `Expire`（`backend/cmd/server/main.go` 的 `runObservationExpiry`），把对账窗口耗尽的观察正式标记 expired。expired 的观察不产出任何跟进文本——**过期不补**是协调器的输出语义，不是投递层的偶然失败。

### 2.4 只跟进本人

观察的作用域是"用户 + 比赛 + 信号"三元组，对账产生的跟进（Resolution）只携带原观察主人的用户标识。连接层（`backend/cmd/server/watchconnection.go` 的 `scheduleRecoveredObservations`）按当前连接的用户过滤——张三喊的进球，李四的连接上永远不会冒出"跟上了，确实是法比安进的"。

跟进话术是协调器生成的固定可靠文本：

- 确认：按事件类型取模板——"跟上了，你说的是刚才那脚射门。那一下确实有东西。""跟上了，刚才那次扑救确实漂亮。""跟上了，确实是 X 进的。"（X 取实际进球人或球队）；
- 反驳：统一是"结果出来了，这球没算。刚才那一下是真把人骗到了。"

文本不经过自由生成，杜绝把待确认内容演成确定结论。跟进的 deliveryKey 是"观察 ID:事实 revision:状态"——同一事实的重复广播、同一版本的重放，都会在这里被吸收。投递通过调度器以 critical 优先级排程，TTL 就是"距跟进时限的剩余时间"——时限到了，投递机会自动消失。

### 2.5 离线补跟一次，展示后不重复

跟进的可靠性设计成"至多一次送达"，三个环节各管一段：

- **离线期间对账**：用户断线时事实确认了，跟进会暂存在协调器的待投递表（`PendingResolutions`），带着原时限等待；
- **重连补跟一次**：用户重新打开页面、会话绑定后，连接层重新拉取未过期的待投递跟进，按剩余时限排入调度。补跟仍然受时限约束——离线太久、时限已过的，直接不补；
- **展示即销账**：客户端回执"这条已展示"（`reply_displayed`）后，服务端按 deliveryKey 把这条跟进从待投递表删除（`MarkResolutionDelivered`）。用户刷新、重连、换设备回来，都不会再听到第二遍。

用一条时间线串起来：

```text
20:15:00  用户喊"进了！"            ——记观察，跟进时限 15 秒
20:15:05  用户断线                  ——观察留在协调器里继续对账
20:15:08  源确认进球                ——跟进暂存待投递（时限还剩 7 秒）
20:15:10  用户重连，会话绑定        ——连接层拉到待投递跟进，按剩余时限排程
随后      客户端展示并回执          ——待投递表销账
此后      无论怎么刷新、重连        ——这句话只出现过一次
```

### 2.6 in-band 关键事实刷新：同一句话重说，而不是再播一遍

最微妙的一类延迟发生在语音回合内部：用户开口问"刚才那球怎么样"到回复生成之间，一个关键事实（进球、红牌、点球、VAR、半场/终场等）正好被确认。如果照常播生成好的旧回复，紧接着观察跟进又会播一次同一件事——用户连听两遍。

`backend/cmd/server/main.go` 的 `handleVoiceTurnWithFactRefresh` 这样处理：

1. 生成前记下快照里最新关键事实的 revision 键；
2. 生成后再次检查——键没变或回复为空，照常返回；
3. 键变了，用**同一个用户文本**、带上"事实已刷新"标注重新生成一遍回复，让这句话本身就包含最新赛况；
4. 若这条轮次恰好登记过观察跟进，先抑制它（跟进时限收到当下、待投递删除，`SuppressFollowUp`），并在 trace 里记下 `suppressed_in_band`——回复已经把新事实说了，跟进不再补。

一次语音回合，一次播报，事实是最新的。抑制失败（如协调器暂不可写）时宁可保留原回复并放弃刷新，也不出现"既播旧句又补跟进"的双重播报。

### 2.7 想说时不迟到：主动时限与表达保持窗

"不迟到"靠两条机制兜底：

**主动发言 TTL**：

- 事件触发的主动话术，critical 类 **45 秒**、普通类 **12 秒**过期即弃（关系层决策可按事件覆写时限）；
- 排队超时的评论宁可丢掉，也不在比赛已经走到下一幕时补播；
- 用户正在说话或主动打断时，排程直接取消并回倾听反应。

**表达保持窗**（`client/lib/services/presentation_state.dart`）：

- 每个表演计划带 `holdMs`：服务端可配，默认 **1800ms**，客户端钳制在 0–10000ms；
- 保持窗结束后进入**回返模式**（returnMode）：
  - `decay_to_focus` 回到观赛专注姿态；
  - `decay_to_listening` 回到等待用户开口的倾听姿态——语音回合的回复固定走这条；
  - `decay_to_idle` 交还给待机档位选择器；
- 表情有明确的"说完去哪"，不会僵在庆祝姿势里，也不会用一张兴奋的脸等下一条迟到消息。

## 3. 如何验证

观察协调是本仓库回归最密的一块，分三层：

**端到端**（`tests/evals/observation-coordination.spec.mjs`，3 例）：

- "用户领先现场时，导播确认与撤销只跟进对应用户"——锁定隔离与确认/撤销两条路径；
- "离线期间确认的事实会在重连后跟进且展示后不重复"——锁定补跟一次、展示销账；
- "没有其他在线客户端时也能调和离线用户的观察"——锁定对账不依赖用户在线。

三例合起来覆盖本篇的主张：隔离（只跟进本人）、补跟一次且不重复、离线也能收敛。

**Go 单测**：

- `backend/internal/observation/coordinator_test.go` 与 `conformance_test.go`——内存实现与 Postgres 实现共享同一套纯规则函数（记录去重、5 条上限、状态迁移、时限计算），一致性测试保证两套存储不可能漂移；
- `backend/cmd/server/observation_delivery_test.go` 锁定连接层的跟进排程与用户过滤。

**温热保持回归**：

- `backend/internal/companion/conversation_regression_test.go` 的 persisted-claim 三连——同一主张连说三遍，第一遍进核验姿态、后续遍固定共情话术、观察只记一条；
- `backend/internal/companion/intent_router_test.go` 锁定坚持副词（"确实进了"）不会被误判成球员名导致假反驳。

跑法与仓库一致：Go 侧 `go test ./...`，端到端走 `tests/evals` 的 Playwright 套件。

## 4. 边界与不做

- **剧透保护未实现，属规划**。当前系统不猜测用户的观看进度：没有观看前沿、没有防剧透档位、也没有"用户没看到就不主动说"的逐用户判定。我们跟进的前提是"用户先说了"；公开事实的主动播报跟随导播配置、事件白名单与话痨档位，不做逐用户的延迟个性化。要把它做成可交付能力，需要先回答"如何在不监听设备的前提下获得用户进度"，这是产品与研究问题，不是本篇工程问题；
- **用户观察永远不改事实**。观察不写回事实账本、不参与公共比分、不跨用户共享；重复主张也不算第二信源；观察文本不进入任何公共流；
- **过期即沉默**。跟进时限、对账窗口与主动 TTL 过期后不补播，也没有"稍后摘要"兜底——错过就错过，防止不合时宜的打断；
- **不做逐字匹配**。温热保持按主张语义（类型/球员/球队/比分）匹配，同一件事换种说法仍是同一条观察；不同主张（换了球员、换了比分）则另起新观察，不会被旧的吞掉；
- **不承诺"比直播快"**。我们只承诺不说错：事实确认后的跟进在时限内送达；事实没确认时诚实地说在等；来源冲突时说"对不上"，不挑选看起来更合理的一方。
