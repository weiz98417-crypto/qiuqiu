# 生产运行:现实形态与备份恢复

(原篇名:灰度发布、回滚与生产运行;现按现实形态撰写)

> 本文是"球球"AI Coding 工程实践系列的生产运行篇,写给想了解我们如何回答"这套服务每天真实跑着,坏了怎么办"的读者。文中描述的机制均以仓库现网配置为准(`docker-compose.yml`、`deploy/README.md`、`backend/internal/config/config.go`、`backend/internal/matchstate/postgres.go`),来源逐处标注;尚未建设的能力,统一归入文末"边界与下一步",不以既有能力的口吻表述。
>
> 核心判断:生产运行的可靠性不来自机制的数量,而来自每一项都真的存在、真的被执行。我们的运行形态是刻意的简单——单机、六服务、无灰度、无多环境——把复杂性预算花在两件确定有用的事上:备份可恢复,异常可人工收敛。

## 1. 现实形态:单机 docker compose 六服务

### 1.1 拓扑与自愈

生产就是一台机器上的 `docker compose`,六个服务(`docker-compose.yml`):

| 服务 | 镜像 | 职责 |
| --- | --- | --- |
| backend | 仓库构建(`backend/Dockerfile`) | Go 后端:API、WebSocket、静态托管用户端与控制台 |
| postgres | `pgvector/pgvector:pg16` | 唯一全量事实源:业务表 + 向量扩展 |
| redis | `redis:7-alpine` | 后端缓存与队列 |
| memobase | `ghcr.io/memodb-io/memobase:latest` | 画像合成服务(ADR-0006:永不写比赛事实) |
| memobase-postgres | `postgres:16-alpine` | memobase 专属存储,与主库隔离 |
| memobase-redis | `redis:7-alpine` | memobase 专属队列 |

自愈靠两条内建机制。其一,六个服务全部 `restart: unless-stopped`——进程崩溃、容器退出、宿主机重启,Docker 自动拉起,不需要人守着。其二,数据层三服务带 healthcheck:postgres 用 `pg_isready -U qiuqiu -d qiuqiu`(5 秒间隔、5 秒超时、5 次重试),memobase-postgres 与 memobase-redis 同理;backend 通过 `depends_on: service_healthy` 等 postgres 就绪后才启动,避免对空库抢跑。

backend 一个进程同时托管三个面:`/` 托 Flutter web 用户端,`/console` 托控制台 Vite 产物,WS 走同端口的 `/ws/match/{id}`;dev 专页仅在非 production 暴露。单入口意味着没有独立网关层可坏,也没有跨服务的部署顺序问题——发布就是重建一个镜像。

客户端侧的韧性由 0.2.0.0 的修复补齐:WS 半开连接自愈、断线重连后补一次比赛概览幂等再同步、重连语音回退不遗留队列。运行态的正确性有专门验证——`scripts/evals/docker-restart-e2e.mjs` 起真实容器重启,断言状态不丢、已撤事实不重放。

这里要说清自愈的边界:`restart` 策略解决"进程死了",不解决"数据错了"。容器把一个逻辑坏掉的库自动拉起来,只会更快地把坏状态暴露给用户。所以真正的兜底不在自愈,在第 2 节的备份恢复。

### 1.2 生产约束

production 模式由必需环境变量约束:compose 用 `${VAR:?msg}` 语法声明必需项,`APP_TOKEN`、`SESSION_SIGNING_KEY`、`ALLOWED_ORIGINS`、`POSTGRES_PASSWORD` 等缺失时直接拒绝启动,不存在"带默认密钥先跑起来";`config.go` 在 production 下另校验 `APP_TOKEN`、`SESSION_SIGNING_KEY`、`MIMO_API_KEY`,会话强制 session 模式,签名密钥有最小长度要求。启动即失败优于带病运行——这是单机形态里最便宜也最有效的一道门。

### 1.3 取舍:为什么没有灰度、金丝雀与多环境

如实说:没有。没有 staging / pre-prod / prod 的环境矩阵,没有"5% 用户先见"的灰度或金丝雀发布,生产就是这一台机器。取舍的理由很直接——当前是单人项目阶段,用户量小,部署面就是一台机器;灰度防的是"新版本伤害一部分用户时无法局部收缩",而我们的发布规模还不存在"一部分":每一次发布面对的就是全部用户。在这个规模下,灰度的基础设施成本远大于它防的风险。

替代物是两件已经存在的事:发布前的评测门禁(机制见系列《端到端验收与发布门禁》,release 档必须绿且见真模型),以及本篇第 2、3 节的备份恢复与人工收敛。风险预算的分配是明确的:错误尽量在合入前被评测拦住,漏网的靠回退和人工接管兜住,而不是靠发布拓扑的精巧。

容量问题同样如实:扩容 = 换机器。单机纵向扩容(CPU、内存、磁盘)在当前负载下远未到瓶颈;等单机真的装不下,再讨论横向拆分——那是部署面扩大之后的问题,不是现在的问题。提前建设多机编排,只会让单人项目背上它养不起的运维面。

这个取舍也会过期。触发重估的信号很具体:部署面从一台机器变成多台、用户量突破单人值守能覆盖的范围、或出现"发布伤害部分用户"的真实案例。到那天,灰度才值得重新立项;在那之前,本篇的每一节都以单机为前提写成。

## 2. 备份与恢复

### 2.1 唯一全量事实源

`postgres_data` 卷是唯一全量事实源:画像、交互账本(Interaction Ledger)与全部业务表都在里面(`deploy/README.md` 开篇第一句就是这个定位)。这个定位决定了备份策略的全部重点——只要这个卷可恢复,系统就能从任何故障中重建;反过来,它损坏且无备份,就是不可恢复的灾难。备份的优先级、演练的强度,全部压在这一个卷上。

### 2.2 每日 03:30 定时备份

备份用 `pg_dump` custom 格式(`-Fc`),crontab 每日 03:30 定时执行,命令与完整注释在 `deploy/README.md`:

```bash
30 3 * * * cd /path/to/qiuqiu && docker compose exec -T postgres \
  pg_dump -U qiuqiu -d qiuqiu -Fc > backups/qiuqiu-$(date +\%F).dump
```

选 custom 格式的理由写在运维备忘里:可并行恢复、可压缩。两个执行细节值得记录,都来自真实操作:crontab 里 `%` 必须转义为 `\%`,否则被 cron 当作换行截断,备份文件名悄悄坏掉;`backups/` 目录在宿主机上,应同步到机器之外的存储——备份和数据库放在同一块磁盘上,等于没有备份。

### 2.3 恢复规程

恢复有两条真实路径(`deploy/README.md`):

1. **数据完好、仅回滚数据**:`pg_restore --clean --if-exists` 直接覆盖恢复;
2. **卷损坏需重建**:`compose down` → 删除 `postgres_data` 卷 → 单独起 postgres → 等 healthcheck 通过(`pg_isready`)→ `pg_restore` → 全量 `up`。

大版本恢复不直接在生产上执行。我们的规程是先在隔离环境(临时容器、独立库)恢复同一份 dump,核对两件事再切换:业务表的行数与关键内容是否完整;vector 扩展与含向量列的记忆表是否可用、相似度检索是否正常(migration 001 起 `CREATE EXTENSION vector`,恢复后扩展与数据都要验)。备份没演练过恢复就不算备份——这条用最朴素的方式执行:恢复步骤每次更新,都在隔离环境完整走一遍。

### 2.4 memobase:可重建的库

memobase 的画像缓存库(`memobase_postgres_data`)不参与定时备份,这是刻意的:ADR-0006 规定交互账本是本地唯一事实源,memobase 永不写比赛事实;画像由账本经抽取队列重建,丢失后果可接受,运维备忘明确"不强制定时"。备份优先级跟着数据的可重建性走,不搞一刀切——把备份面铺满每个库,反而会稀释对真正不可重建数据 的注意力。

## 3. 回滚的真实手段

### 3.1 迁移只进不退

数据库迁移是向前滚动的:`runMigrations`(`backend/internal/matchstate/postgres.go`)在事务里逐个执行 `backend/migrations/` 下未应用的 SQL,写入 `schema_migrations` 历史表,已应用的一律跳过,并用 Postgres advisory lock 防并发重入。不存在 down 迁移。

这个纪律的含义是:**代码可以回退到旧版本,但旧版本必须能在新模式的库上运行**。模式只向前走,"回退"永远不意味着回滚 DDL。配套的迁移序号 lint(0.2.0.0 加入)防的是两个迁移撞号导致应用顺序不确定——重复数字前缀直接报错。

### 3.2 模式层的最终回退 = 备份恢复

既然迁移只进不退,错误的迁移无法"滚回去",能做的只有两件事:向前写一个修复迁移;或者,若迁移本身造成不可接受的破坏,用 2.3 的恢复规程把库恢复到迁移前的时间点。这就是备份与迁移纪律咬合的地方:**恢复能力是"只进不退"成立的前提**——没有可信的备份,向前滚动就是不可逆的赌博。

### 3.3 评测门禁:回滚的上游是尽量不回滚

合入前 `eval:pr` 必须绿;发布前 `eval:release` 必须绿且完成真实模型冒烟(机制详见系列《端到端验收与发布门禁》)。"修一个 bug 落一条 regression 用例"的规则让门禁随真实事故变厚——拦在合入前的问题越多,需要动用回滚的次数越少。

### 3.4 运行中收敛:导播台人工接管与干预级别三档

发布之后发现异常,第一手段不是回滚版本,是导播台人工接管——分钟级生效,不重新部署:

- **干预级别三档**:单能力暂停(只停主动行为,其余保留)、接管比赛(整场输出服从人工判断)、路由范围(某类请求整体走保守路径)。一条固定规则:更安静的一档永远不会放开更响一档所限制的能力;
- **数据源层**:外部数据源可随时启停、切换、人工接管,接管同时暂停自动播报;错误事实可撤回,已撤事实触发的主动回复会被 `match_fact_retracted` 移除;
- **全程留痕**:运营写操作按 `Idempotency-Key` 幂等、实名审计,操作轨迹在控制台可查。

一条固定边界:用户侧的静音、结束与纠正永远高于导播台的任何配置——人工接管收敛的是系统,不是用户。

运行中的观察面同在控制台:概览页六格直出活跃比赛、在线会话、话题老化、记忆健康(积压深度 + 降级徽标)、最近主动引用与词汇漏斗;引用审计按 citation 前缀深查 trace,"为什么说话"可逐条回放。异常收敛和异常发现用的是同一个界面,不需要额外的仪表盘。

版本回退本身反而少用:`compose` 重新构建上一个可用构建即可,但因为迁移只进不退,它要求旧代码与当前模式兼容。这正是评测门禁在前、人工接管在先的原因:回滚是最后手段,不是日常工具;日常工具是"先收敛、再调查、再决定"。

## 4. 边界与下一步

如实列出当前没有的:没有独立告警系统,异常发现靠人工使用与控制台概览(活跃比赛、在线会话、记忆积压深度与降级徽标等六格直出);没有对外状态页;值守是单人内部形态——每场真实比赛由项目所有者在导播台值守,例行风险评审与暂停演练尚未制度化。这些不是遗漏,是与部署面匹配的暂缓:单机、单人、受控开放之前,它们的收益还压不过维护成本。

建设节奏已定,一句话:值守、告警与状态页随受控开放一并建设——邀请真实用户进入之前,发现问题的通道必须先于用户存在。在此之前,备份可恢复与异常可人工收敛,是我们押注的两根支柱。
