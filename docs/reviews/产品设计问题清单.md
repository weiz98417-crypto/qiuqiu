## P1 问题

### PD-001：正式控制枚举仍存在同义名称

| 字段 | 内容 |
| --- | --- |
| 等级 | P1 |
| 类型 | 跨文档术语冲突 |
| 位置 | `20-产品设计总览.md:193-204`；`21-信息架构、激活与比赛进入设计.md:473-491`；`24-直播延迟与用户观察协调设计.md:353-364` |
| 设计主张 | 总览规定陪看密度正式枚举为“安静 / 只回应 / 有限提示”，信息保护正式枚举为“严格防剧透 / 事实优先”，并要求文档不得新增同义枚举。 |
| 证据 | 21 使用“安静看球”“只在我问时回应”；24 使用“只回应我”“本场有限提示”“事实优先模式”。 |
| 后果 | 用户文案、接口字段、原型和评测可能把同一选项当成不同能力；“只回应”与“安静”在本套设计中还有不同的行为边界，不能靠读者自行推断。 |
| 是否允许设计领先 | 否；这是设计内部一致性问题。 |
| 建议动作 | 以 20 的枚举为唯一正式名称；自然语言可以作为解释句，但不得作为模式名、接口值或评测标签。补一张“正式名称—解释文案”对照表。 |
| 待确认事项 | “只在我问时回应”“本场有限提示”等是否全部降为解释文案，而不是保留为可选模式名？ |

### PD-002：四维控制的默认向量互相冲突

| 字段 | 内容 |
| --- | --- |
| 等级 | P1 |
| 类型 | 默认值冲突 |
| 位置 | `20-产品设计总览.md:193-202`；`24-直播延迟与用户观察协调设计.md:357-364`；`35-偏好、设置与无障碍设计.md:338-350`；`43-原型验证设计.md:216-230` |
| 设计主张 | 总览给出统一默认向量：安静、严格防剧透、仅文字、低动态。 |
| 证据 | 24 写“默认严格防剧透与只回应我”；35 写动态首轮默认“标准但无高刺激，低动态一键可得”，声音默认仍为“仅文字或点按播放”；43 又把安静、仅文字、低动态作为原型默认。 |
| 后果 | 设计评审、原型测试和后续工程会不知道哪些是规范基线，哪些只是待验证处理组；同一用户在不同入口可能得到不同预期。 |
| 是否允许设计领先 | 否；这是设计决策的作用范围没有分层。 |
| 建议动作 | 保留 20 的四维默认向量作为规范基线；其他文档将不同值明确标为“研究处理组/备选假设”，并写出不改变规范基线的条件。 |
| 待确认事项 | 是否确认首轮规范默认固定为“安静 + 严格防剧透 + 仅文字 + 低动态”？若要保留研究变体，变体只在研究方案中出现。 |

### PD-003：四维控制没有在同一进入节点形成完整选择契约

| 字段 | 内容 |
| --- | --- |
| 等级 | P1 |
| 类型 | 用户任务缺口 |
| 位置 | `20-产品设计总览.md:191-204`；`43-原型验证设计.md:214-249`；`43-原型验证设计.md:510-526` |
| 设计主张 | 四个控制维度彼此独立，用户可以分别调整，且任何收缩都不得被其他维度绕过。 |
| 证据 | 43 的 Step 3“赛前本场设置”只呈现陪看密度、声音方式和动态，没有在该节点呈现信息保护；信息保护在 Step 10 的设置页才出现。 |
| 后果 | 用户在进入比赛时可能已经接受默认的信息保护，却没有在最接近风险发生的入口看到“严格防剧透/事实优先”的选择和后果；原型无法验证四维契约是否被完整理解。 |
| 是否允许设计领先 | 否；这是设计入口和控制模型之间的覆盖缺口。 |
| 建议动作 | 二选一并写清：将信息保护加入 Step 3 的本场设置；或明确它为何属于单独的风险确认节点、何时必须展示、未设置时采用什么默认。两种路径都要回写到 21、24、35、43 的同一流程。 |
| 待确认事项 | 信息保护是否必须在进入比赛前完成知情选择？ |

### PD-004：用户事实状态与领域状态缺少规范化映射

| 字段 | 内容 |
| --- | --- |
| 等级 | P1 |
| 类型 | 状态模型跨层缺口 |
| 位置 | `23-比赛事实与公开比分设计.md:214-238`；`41-领域数据模型设计.md:255-271`；`46-系统架构图集.md:250-267` |
| 设计主张 | 用户应能区分已确认、待确认、冲突、更正和撤销；内部对象还需要记录候选、不可用、归档、取消/延期等生命周期状态。 |
| 证据 | 23 以四类用户卡组织呈现；41、46 又引入候选事实、已归档事实、已取消或延期、已撤销候选、不可用等状态，但没有给出一张规范映射表。 |
| 后果 | 产品、Agent、原型和架构可能对“已撤销候选”“不可用”“已归档”是否可见、如何解释、是否触发更正卡产生不同理解；高影响事实在跨层传递时存在语义丢失风险。 |
| 是否允许设计领先 | 否；这是设计模型之间的合同缺口。 |
| 建议动作 | 在 41 或 20 增加“领域状态 → 用户呈现 → Agent/通知资格 → 终态”映射；明确哪些状态只用于内部生命周期，哪些必须进入用户时间线。 |
| 待确认事项 | “归档”“取消/延期”“不可用”是否需要用户可见卡片，还是仅作为已确认/不可用的解释字段？ |

### PD-005：API 设计正文混入当前实现状态

| 字段 | 内容 |
| --- | --- |
| 等级 | P1 |
| 类型 | 设计边界违规 |
| 位置 | `42-API与实时协议设计.md:3-10` |
| 设计主张 | 这份文档应定义领域接口与实时消息合同，并指导工程开始定义跨端行为。 |
| 证据 | 文档明确写“当前实时通道使用……”并列出现有消息类型，又写“目标合同未完成前，不作为当前客户端接口规范”。 |
| 后果 | 产品设计正文同时承担设计合同、实现盘点和交付状态说明，读者无法判断哪些内容是产品必须遵守的目标，哪些只是阶段性实现事实；也违反本项目“不在产品设计正文出现交付状态和逆向痕迹”的红线。 |
| 是否允许设计领先 | 不适用；问题是材料边界，不是设计领先。 |
| 建议动作 | 设计正文只保留目标协议、状态资格、取消、版本和终态合同；当前消息覆盖与差异迁移到 `docs/reviews/设计—项目事实对齐矩阵.md` 或工程交接材料。 |
| 待确认事项 | 是否确认 42 只保留目标合同，不再在正文描述现有消息覆盖？ |

### PD-007：权利操作的完成语义仍缺少统一用户语言

| 字段 | 内容 |
| --- | --- |
| 等级 | P2 |
| 类型 | 状态与可解释性缺口 |
| 位置 | `38-隐私、记忆删除与数据生命周期设计.md:318-362`；`35-偏好、设置与无障碍设计.md:525-546` |
| 设计主张 | 用户可以查看、导出、修改、暂停、删除和离开，且删除/撤回后后续读取、引用、缓存和重试都应停止。 |
| 证据 | 文档分别描述“请求”“完成状态”“撤回屏障”和“后续不可恢复影响”，但尚未统一定义用户可见的处理中、已完成、失败、部分保留和不可恢复状态词。 |
| 后果 | 原型、客服和评测可能各自使用“已删除”“正在处理”“清空”等不同词，用户无法判断当前权利操作是否真正完成。 |
| 是否允许设计领先 | 是；这是可补强的设计表达，不涉及当前实现覆盖。 |
| 建议动作 | 在 38 增加一组权利操作状态词与用户可见后果，供 35、43、45 复用；保留法律/技术例外的普通语言说明。 |
| 待确认事项 | 首轮是否允许“已请求但尚未完成”作为稳定用户状态？各操作是否需要显示预计完成时间或仅显示状态？ |
