# 产品设计审查标准

> 文档类型：产品设计资料包的独立审查标准  
> 适用范围：`docs/球球全套资料/4.产品设计` 及其公开研究、项目对齐和评测材料  
> 使用方式：先按本标准审查并形成问题清单，经确认后再修改产品设计正文  
> 核心原则：设计可以领先实现；实现尚未覆盖设计，不单独构成设计缺陷

## 1. 审查目的

本标准用于判断产品设计是否清楚、完整、自洽、可验证，并能在后续研究、技术方案和运营治理中保持同一套产品承诺。它不把产品设计当作当前实现说明，也不以代码覆盖率、页面数量或演示效果直接评价设计质量。

审查同时回答四个问题：

1. 用户要完成的任务、获得的价值和承担的边界是否清楚？
2. 不同文档对同一概念、状态、默认值和控制是否表达一致？
3. 高风险场景是否有明确的收缩、退出、替代和求助路径？
4. 设计判断是否有足够的研究、标准或公开资料支持，未确认部分是否被诚实标为假设？

## 2. 审查边界

### 2.1 纳入审查的材料

- `docs/球球全套资料/4.产品设计` 下的产品设计总览、体验、信息、事实、关系、隐私、技术约束、原型和评测文档；
- `docs/球球全套资料/1.市场洞察与战略定位`、`2.用户与价值定义`、`3.验证与商业模式` 中直接支撑产品设计的目标用户、竞争、验证和范围材料；
- `docs/research` 中的公开研究、竞品走查和用户研究记录；
- 独立的项目事实对齐矩阵、问题清单和复审记录。

### 2.2 不纳入产品设计正文的材料

以下内容可以作为独立审查证据，但不得写回 `4.产品设计` 正文：

- 当前代码、接口、测试、部署和运行日志的实现盘点；
- “已实现”“未实现”“当前版本支持”等交付状态；
- 逆向推导、代码图谱、代码依据或内部审查过程；
- 只用于团队内部的缺陷跟踪、责任归属和修复进度。

## 3. 设计状态的区分

审查时必须把下列状态分开，不得把它们混成“正确/错误”二元判断：

| 状态 | 含义 | 是否需要修改设计正文 |
| --- | --- | --- |
| 已确认决策 | 已由产品决策、公开规则或明确研究结论确定的设计约束 | 只有发现矛盾时修改 |
| 待验证假设 | 为研究、原型或试点准备的可证伪方案 | 通常不修改，只补验证方式 |
| 设计领先实现 | 设计明确提出了尚未被项目覆盖的目标体验 | 不因未实现而修改 |
| 项目事实偏差 | 设计文字与已确认的产品事实、公开约束或其他设计决策相冲突 | 需要判断是改设计还是改项目事实记录 |
| 文档缺口 | 用户任务、边界、状态、后果或验收方式没有被说明 | 修改设计正文或补配套材料 |
| 证据不足 | 结论写得过于确定，但缺少公开资料、研究或明确假设 | 降低结论强度或补证据 |

“设计领先实现”只有在它与产品命题、用户权益、技术边界和其他设计决策相冲突时，才升级为设计问题。

## 4. 审查等级

### P0：原则性阻断

会使产品承诺在逻辑上失效，或造成不可接受的用户伤害、身份误导、事实误导、隐私越界、关系操控或不可退出。P0 必须在设计继续流转前处理。

典型情形：

- 把 AI 角色设计成真人、官方裁判、治疗者或现实关系替代；
- 允许待确认、冲突或撤销的事实被表达为确定结论；
- 用户无法静音、停止、结束、删除或撤回关键授权；
- 以关系、内疚、排他或付费压力绕过用户选择；
- 核心任务只能通过声音、颜色、动画或未授权资料完成。

### P1：高优先级设计缺陷

会导致核心任务失败、用户误解、跨文档执行分歧或高风险场景无法评测。P1 必须在进入下一轮原型、研究或产品决策前有明确处理方案。

典型情形：

- 同一设置在不同文档中有不同名称、默认值或作用范围；
- 关键状态没有进入条件、退出条件、用户可见后果或降级路径；
- 需求没有可观察验收结果，或验收不能区分通过与失败；
- 研究假设被写成市场事实、用户偏好或稳定体验结论；
- 高影响能力没有对应的反例、停止条件或人工支持路径。

### P2：可执行性问题

不会立即破坏产品原则，但会增加设计、研发、研究或运营协作成本。P2 应在相关文档下一次更新时处理。

典型情形：

- 术语虽不冲突，但解释重复、层级不清或阅读路径过长；
- 页面、状态或接口示例缺少边界说明；
- 同一决策在多处重复描述却没有唯一锚点；
- 引用标题、链接、访问日期或证据等级不完整。

### P3：表达与治理改进

主要影响阅读效率、维护成本和审查可追溯性，不阻断设计流转。包括格式、元数据、标题、编号和导航一致性问题。

## 5. 七类必审标准

### A. 产品命题与用户价值

必须满足：

- 明确目标用户、使用情境和需要取得的进展；
- 将用户任务与产品价值连接起来，而不是从功能或技术能力倒推价值；
- 明确产品是什么、不是什么，以及首轮不承担哪些责任；
- 对用户的核心承诺能够用日常语言复述；
- 设计范围、目标态和非目标之间不存在互相抵消。

审查证据：产品总纲、用户任务、旅程、市场与价值文档。

### B. 术语、模式与跨文档一致性

必须满足：

- 每个用户可见枚举只有一个正式名称；
- 同一名称在不同文档中的行为、默认值和作用范围一致；
- 独立控制维度不得被重新合并成未定义的总模式；
- 普通形容词与正式设置名称有清楚区别；
- 文档标题、导航、编号和相互引用可互相解析。

审查重点：模式、状态、权限、记忆、主动性、媒介、动态、事实资格和关系阶段。

### C. 旅程、交互与状态完整性

每个核心任务至少应说明：

- 触发情境和用户目标；
- 用户可采取的动作；
- 系统可见的结果和状态变化；
- 等待、错误、冲突、撤销、重试和中断行为；
- 用户如何暂停、改变主意、返回、结束或求助；
- 声音、文字、视觉和辅助输入之间的等价路径。

不存在“只有正常路径才有设计”的核心能力。高影响状态必须有明确的失败和退出路径。

### D. AI 身份、关系边界与内容安全

必须满足：

- 用户能理解这是 AI 服务，不是真人、官方或专业支持者；
- 角色表达服务于用户任务，不索取照顾、忠诚、排他或持续互动；
- 事实、观点、推测、情绪表达和角色表演有明确分层；
- 高风险请求有中性拒绝、替代帮助、支持入口和暂停条件；
- 未成年人、脆弱状态、危机表达和敏感资料有适用边界；
- 互动量、停留时长、好感或转化不能抵消安全失败。

### E. 数据、隐私与用户权利

每类资料必须说明：

- 内容和来源；
- 使用目的和作用范围；
- 是否本场临时、跨场保存或用于研究；
- 用户如何查看、修改、暂停、删除、导出和拒绝；
- 删除或撤回后，后续读取、引用、缓存、重试和触达如何停止；
- 权利操作是否会被关系、付费或基础任务门槛阻挡。

不得把“角色会记住你”作为对资料范围、用途和生命周期的替代说明。

### F. 技术约束、媒介等价与降级

产品设计可以规定技术边界，但不能把技术名词当作产品价值。必须审查：

- 核心任务是否能在文字、静音、低动态、弱网和辅助输入下完成；
- 用户动作是否优先于生成、播放、缓存、重试和自动恢复；
- 事实资格是否先于声音、字幕、角色和动效表达；
- 外部供应商失败时是否有不扩大权限的回退路径；
- 技术选型变化是否会改变用户任务、控制或风险边界。

### G. 评测、指标与决策治理

每项高影响产品要求至少应有：

- 用户任务；
- 可观察结果；
- 正常场景、高风险反例和控制/降级场景；
- 阻断条件；
- 研究或评测方法；
- 通过、收缩、暂停和复审规则；
- 对应的产品决策或决策编号。

指标必须区分价值指标、理解指标、控制指标和风险指标。互动量、时长、好感和转化不得单独作为放行依据。

### H. 生产版本能力拓展

生产版本设计可以扩大自动事实发布、提醒、可管理长期连续性、受控工具、外部动作和语音/舞台主体验，但审查必须逐项核对：用户价值、触发事件、授权范围、事实资格、Agent/工具责任、外部副作用、失败/撤回/退出、评测门和回滚条件。生产拓展不得被写成当前交付状态，也不得通过扩展章节绕过单 Agent、关系边界、隐私权利或多媒介等价要求。

## 6. 证据与对标标准

### 6.1 证据等级

| 等级 | 证据 | 可支持的结论 |
| --- | --- | --- |
| A | 法规、标准、官方文档、官方产品页面 | 规范要求或公开声明 |
| B | 可复现的产品走查、截图、录屏和操作记录 | 特定条件下的实际路径 |
| C | 访谈、可用性测试、日记研究和受控任务 | 目标用户的理解、行为和负担信号 |
| D | 团队判断、评论线索和待研究问题 | 研究假设与实验方向 |

不得用 A 级公开营销文案证明用户体验，也不得用单次 B 级走查证明长期价值或市场规模。

### 6.2 对标范围

质量审查至少应覆盖以下公开基线：

- 服务设计和用户研究：GOV.UK Service Manual；
- 旅程、信息架构和对话可用性：Nielsen Norman Group；
- 多媒介、状态可感知和减少动态：W3C WCAG 2.2；
- 生成式 AI 风险、治理和持续评测：NIST AI RMF / GenAI Profile；
- 实时语音会话、打断、重连和降级：具体、可访问的实时语音官方文档；
- 同类产品体验：体育比分/资讯产品、陪伴型 AI、语音助手和相关替代品。

对标的目的不是复制功能，而是比较同一用户任务下的默认行为、控制路径、事实表达、退出成本、资料权利和风险边界。

## 7. 问题记录格式

每条问题必须包含：

| 字段 | 要求 |
| --- | --- |
| 编号 | 稳定、可引用，不因排序变化而改变 |
| 等级 | P0、P1、P2 或 P3 |
| 类型 | 矛盾、歧义、缺口、证据不足、治理或对齐问题 |
| 位置 | 文件与章节/行号 |
| 设计主张 | 用原文准确描述，不代替文档发明意图 |
| 证据 | 标准、研究、项目事实或跨文档对照 |
| 问题说明 | 说明用户、产品或协作后果 |
| 是否允许设计领先 | 明确回答“是/否/待确认” |
| 建议动作 | 保持、补充、改写、拆分、研究或另建审查材料 |
| 待确认事项 | 需要产品负责人决定的最小问题 |

没有明确设计主张和证据的内容，只能记录为“待调查”，不能直接判定为缺陷。

## 8. 审查流程

### 阶段一：建立基线

1. 固定文档清单、版本、审查日期和审查范围；
2. 读取产品命题、用户任务、统一术语、PR 矩阵和决策记录；
3. 建立正式枚举、状态和默认值清单。

### 阶段二：内容审查

1. 按 A–G 七类标准逐篇检查；
2. 提取关键设计主张、开放假设、用户后果和验收条件；
3. 做跨文档术语、默认值、作用范围和链接一致性检查；
4. 记录问题，不在本阶段修改正文。

### 阶段三：事实与对标审查

1. 将设计主张放入独立的项目事实对齐矩阵；
2. 使用代码、接口、测试和运行材料验证项目事实；
3. 对体育产品和陪伴型 AI 做同一任务卡下的公开资料与可复现走查；
4. 将设计领先、项目缺口、证据不足和真正冲突分开分类。

### 阶段四：问题确认

1. 按 P0–P3 排序；
2. 先确认是否为真实问题，再确认是否需要修改设计；
3. 对设计领先项明确保留，不因实现缺口降级；
4. 对需要产品取舍的问题形成决策记录。

### 阶段五：定向修改与复审

1. 只修改已确认的问题；
2. 修改后重新检查受影响文档、术语、PR、决策和链接；
3. 更新审查记录，不把项目实现状态写入产品设计正文；
4. 只有在 P0 清零、P1 有明确处理、关键 PR 全部可回指时，才可称为本轮审查通过。

## 9. 通过条件

一轮产品设计审查满足以下条件，才可标记为“通过本轮审查”：

- 不存在未处理的 P0；
- 每个 P1 都有明确的修改、研究、决策或保持理由；
- 正式术语、枚举、默认值和作用范围无跨文档冲突；
- 每个核心 PR 都有用户任务、可观察验收结果、反例和阻断条件；
- 高风险能力都有退出、降级、求助和暂停路径；
- 设计领先实现的项目事实已在独立矩阵中标明，不污染设计正文；
- 竞品和公开标准的证据等级清楚，假设没有被写成事实；
- 文档元数据、导航、引用和链接达到可维护状态；
- 修改后的问题清单、决策记录和审查日期可追溯。

“通过本轮审查”不等于产品已经实现、已经上线、已经被用户证明有效或已经完成法律意见审查。

## 10. 建议的配套材料

- `docs/reviews/产品设计问题清单.md`：记录本标准发现、待确认和处理结果；

- `docs/reviews/产品设计质量对标审查.md`：记录本标准与外部方法论、标准和同类产品的比较；
- `docs/research/竞品体验走查与对标报告.md`：保存体育产品、陪伴型 AI 和语音产品的可复现研究证据。

以上材料是审查与研究资产，不替代 `4.产品设计` 中的产品设计正文。
